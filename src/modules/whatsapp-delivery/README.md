# `whatsapp_delivery`

Generic WhatsApp delivery capability (Issue #963, [ADR-0133](../../../docs/adr/0133-generic-delivery-capability-whatsapp-promotion.md) phase 1).

This module **delivers** WhatsApp messages that another module decided to send — booking reminders, hr_payroll notices, a downstream commerce adapter. It has no opinion about what deserves a message and ships no business wording except a neutral `system.notice` template. It is WhatsApp-specific on purpose: `WhatsappDeliveryPort` is **not** a multi-channel facade (that would be notification orchestration, which ADR-0133 section 7 does not admit).

## "No second outbox", stated precisely

ADR-0074 already made `push_delivery` a second outbox, so the issue's constraint cannot be read literally. What this module does, and what ADR-0133 section 3 binds:

- It is a **channel queue table** (`awcms_whatsapp_messages`), the repo's third after `awcms_email_messages` and `awcms_push_messages`. It does **not** join `awcms_domain_events` (a provider call inside the claim transaction would violate ADR-0006) and it does **not** extend the e-mail table (a mixed-shape table with two dispatchers contending).
- It reuses the **lease mechanism**, not a new one: claim with `FOR UPDATE SKIP LOCKED`, `next_attempt_at` doubles as the lease expiry, send **outside** any transaction, finalise per row.
- **One queue per channel per deployment, never one per domain.** Booking, hr_payroll, commerce and every later consumer enqueue into this single queue through the port. A consumer never adds its own WhatsApp table, dispatcher or provider call. What the rule refuses is a **second WhatsApp queue**.

## The port

`_shared/ports/whatsapp-delivery-port.ts`, adapter `whatsappDeliveryPortAdapter` in `application/whatsapp-enqueue.ts`:

- `enqueue(tx, input)` is **one INSERT in the caller's transaction** (so a rolled-back booking sends no reminder). There is no `send`: the provider is called only by the dispatcher, outside any transaction. The caller never learns the provider's answer synchronously.
- Refusals and suppressions are **returned**, never thrown: `refused` (`CONSENT_REQUIRED`, `CONSENT_SCOPE_REQUIRED`, `BUSINESS_SCOPE_UNRESOLVED`, `TEMPLATE_UNKNOWN`, `DISABLED`, `RATE_LIMITED`, plus `RECIPIENT_INVALID`, `RECIPIENT_UNRESOLVED`, `EXPIRY_REQUIRED`) and `suppressed` (`hard_failure`, `opt_out`). The idempotency key is required and unique per tenant; a replay answers `duplicate`.
- `getStatusByCorrelation` reads state back by the caller's own record id (masked recipient, never the number); `cancelByCorrelation` cancels still-waiting messages and is a no-op once sent.
- The port performs **no access check and writes no audit row**: the consumer authorises and audits its own business action.

Consumers register templates with `registerWhatsappTemplate` (module-prefixed keys, e.g. `booking.reminder`). A template has **exactly one purpose** and a variable allow-list; a variable that is not on the list is **dropped** by the renderer, which is what keeps a payroll notice free of salary data.

## Purpose classes and consent

| Purpose         | Consent                                                           | Suppression honoured                  |
| --------------- | ----------------------------------------------------------------- | ------------------------------------- |
| `transactional` | none                                                              | every reason                          |
| `security`      | none; mandatory `expiresAt`; never blocked by a marketing opt-out | hard failure only                     |
| `marketing`     | explicit, per recipient, recorded with its source                 | every reason, and a withdrawn consent |

**Consent is independent of segment membership.** The decision (`domain/whatsapp-eligibility.ts`) takes the suppression row and the consent row and nothing else; being in a segment, list or campaign audience never implies consent. It runs at enqueue **and again at dispatch**, so a withdrawal lands in minutes even for a row claimed a moment earlier. Withdrawing a consent, or suppressing a number, cancels the recipient's waiting messages in the same transaction.

A `security` message that passes `expires_at` is `expired`, **not retried late**. A row that carries a secret (an OTP) has its body and variables cleared when it reaches any terminal state, and the secret never reaches an attempt row, an audit row, a log line or an event.

## The phone number

E.164-normalised or **refused, never guessed** (a national `08…` number is read only when `WHATSAPP_DEFAULT_COUNTRY_CODE` is set). Stored raw in **one column** (`awcms_whatsapp_messages.recipient`) because no adapter can deliver to a hash; `recipient_hash` (keyed HMAC, see below) drives consent, suppression, rate limits; `recipient_masked` is what every list, log line, audit row and event carries. Consent and suppression tables store only the hash and the masked form.

## Providers

The **deployment sender** (`senderAccountId = null`) is chosen per **deployment** from the environment, never per request (a request-supplied token would let one tenant's admin make the deployment speak as someone else). Never in the database, logs or error text. A **tenant-owned sender** is a different path: see [Sender routing](#sender-routing-issue-1141) below.

- `WHATSAPP_PROVIDER=log` — records "would have sent", calls nothing.
- `fonnte` (`WHATSAPP_FONNTE_TOKEN`) — free text over Fonnte's HTTP API.
- `meta` (`WHATSAPP_META_ACCESS_TOKEN`, `WHATSAPP_META_PHONE_NUMBER_ID`) — WhatsApp Cloud API **template** messages. A template with no approved `providerTemplate` fails terminally; it never falls back to free text.

A missing or unknown provider does not crash the dispatcher and does not silently become `log`: it resolves to a provider that fails every send **non-retryably**, and `config:validate` rejects `WHATSAPP_ENABLED=true` without one. Every call goes through `ssrfSafeFetch` under a total timeout; only the **adapter** feeds the circuit breaker, so a per-message rejection (bad number, bad template) never trips it. A provider that reports a number cannot receive WhatsApp makes the dispatcher record a `hard_failure` suppression.

## Behaviour when off

Without `WHATSAPP_ENABLED=true`, `enqueue` answers `refused: DISABLED` and writes nothing, and `bun run whatsapp:dispatch` claims not a single row. `bun run whatsapp:queue:purge` runs **regardless** (for every tenant): a deployment that turned WhatsApp off still has rows from when it was on.

## Retention: `delegated`

The purge first expires stale non-terminal rows (clearing an OTP), then deletes only terminal ones. Its DELETEs name the terminal statuses (`sent`, `failed`, `cancelled`, `expired`) and uses `updated_at` as the cursor, so a message waiting out a provider outage — or a reminder scheduled days ahead — is never deleted. Attempts go before messages (FK order). Consents and suppressions are never purged: they are privacy decisions, and deleting a suppression would resume sending to someone who asked to stop.

## Admin surface

`/admin/whatsapp` (navigation entry gated on `whatsapp_delivery.messages.read`): delivery status, recent messages with cancel, recent attempts, the consent store, the suppression list and the registered templates. Each panel is gated on its own permission. The ten permissions are seeded by `sql/179`; the two sender-routing permissions (`senders.read`, `sender_policy.configure`, API only, no screen yet) by `sql/323`.

## Security notes and known limits (audit of PR #975)

- **The recipient hash is keyed.** `HMAC-SHA256(key, tenantId 0x00 "whatsapp:recipient" 0x00 e164)` under the secret ring `WHATSAPP_RECIPIENT_HASH_KEYS` (`keyId:base64` pairs, the first writes, all are read, the key id is stored in the value as `k1:<hex>`; shape of ADR-0137 section 2). A hash salted only with the tenant id is invertible in about a millisecond (the number space is small and the mask leaks the last four digits), and consent and suppression rows hold no plaintext, so this could never have been migrated later. With no usable ring enqueue, consent and suppression **refuse** and the dispatcher claims nothing (fail closed); `config:validate` requires the ring when `WHATSAPP_ENABLED=true`. **A key id can never be retired while any consent or suppression row, or a restorable backup, still carries it**: those rows cannot be re-hashed. Rotation is "prepend a new key"; there is deliberately no re-hash job.
- **One owner per row.** The claim lease is sized to the whole batch (`limit` times the provider timeout), the lease is renewed and verified immediately before each row, and finalisation matches the exact lease value this pass wrote, so a lease that expires mid-batch is skipped rather than sent twice. A re-claim of an expired `sending` row counts as an attempt, a row past the retry cap is failed, and a throw while processing a row fails that row only. Residual: at-least-once to the provider remains (a crash after the provider accepted and before finalise can resend).
- **Opting out is protected.** Re-granting consent over a withdrawn row is refused unless the request says `reinstateWithdrawn`, carries an `evidenceRef`, is not `source: "import"`, and the caller holds the high-risk `consents.restore` instead of `consents.create`. The withdrawal stays in `withdrawal_history`, and the reinstatement is audited at warning severity and emitted as an event.
- **Expiry never depends on the dispatcher.** `whatsapp:queue:purge` marks any non-terminal row past `expires_at` as `expired` and clears an OTP, for every tenant, regardless of the flag, the breaker and the tenant's state.
- **Provider text is redacted before it is stored.** A secret-bearing row keeps no provider detail (`Provider reported <code>.`); any other row has the exact values of its own body and variables removed. The Fonnte adapter has no structured "invalid recipient" signal, so it never creates a hard-failure suppression from free text; Meta's numeric codes keep that verdict.
- **Rate limits.** `security` messages have their own per-recipient bucket (`WHATSAPP_RATE_SECURITY_PER_RECIPIENT_PER_HOUR`, default 5), so notices cannot exhaust it and an OTP flood cannot target one number. The counts are racy under concurrency by design.
- **Idempotent replay ignores the payload.** A second `enqueue` with the same `(tenant, idempotencyKey)` returns `duplicate` whatever its template, variables or recipient; a caller that reuses a key for a different message loses it silently. Keys must be derived from the caller's own record id.
- **Opt-out versus an in-flight message.** A withdrawal cancels `queued` and `retry_wait` rows and the dispatcher re-checks consent before every send, but a row already `sending` is in a provider call and cannot be recalled; that window is bounded by the provider timeout.
- **Erasure is not implemented.** The `subjectData` descriptors declare `anonymize` for the four tables, but no executor path has been exercised for them yet; a data-subject erasure of a WhatsApp recipient is an open item (and clearing `recipient_hash` removes a suppression, so it must not run on suppressed numbers without a decision).

## Sender routing (Issue #1141)

[ADR-0148](../../../docs/adr/0148-omnichannel-foundation-is-five-gated-capabilities-with-fail-closed-per-account-capability.md) section 4. A tenant can own several WhatsApp senders (a Meta Cloud API phone number per brand, later StarSender devices) in [`channel_accounts`](../channel-accounts/README.md), and a message can be sent through one of them. **One queue, one dispatcher, no dual write**: the sender is a **key on the existing queue**, not a second one.

### What changed on the port, and who is affected

`WhatsappDeliveryPort` goes from `1.0.0` to **`1.1.0`, additively** (`capability-contract-versions.ts`, `awcms-family-compatibility.yaml`):

| Added (all optional) | Meaning                                                                                                    |
| -------------------- | ---------------------------------------------------------------------------------------------------------- |
| `senderAccountId`    | The tenant-owned account that should send. Never a token, a phone number id or a device id.                |
| `inReplyToMessageId` | Thread affinity: this message continues an earlier message to the same recipient and **keeps its sender**. |
| `businessScope`      | `{ type, id }`: the brand or unit; the key of the default-sender policy.                                   |
| refusals             | `SENDER_UNAVAILABLE`, `SENDER_AFFINITY_CONFLICT`, `REPLY_TARGET_UNKNOWN`.                                  |

**Compatibility (stated, and tested).** No existing field, signature or refusal changed. A call that sets none of the new fields, for a tenant with no sender policy, is queued with `senderAccountId = null` (the **deployment sender**) and takes the same path, the same provider, the same credential and the same event payload as in `1.0.0`. So `booking`, and the commerce adapter behind `awcms-one`'s per-tenant `legacy`/`upstream` mode router (downstream ADR-0047; [ADR-0133](../../../docs/adr/0133-generic-delivery-capability-whatsapp-promotion.md) section 6), compile and behave **unchanged**. A tenant in `legacy` mode never reaches this port, so sender routing does not apply to it until its cutover (a tenant is in exactly one mode, so there is still no second queue and no dual write); `awcms-one` adopts the new inputs after a subtree sync as a merge commit, and the StarSender default of a derived product is a **configuration of the policy**, applied per tenant, never a code change. A consumer that switches exhaustively over the refusal reasons (none in this repository does: booking maps an unknown reason to a coarse code) must add the three members before it passes a sender. A consumer that accepts a sender id from a **user** must authorise that choice itself: the port enforces tenant authority, it performs no access check (the consumer authorises its own business action, ADR-0011).

### Which sender a message gets

In this order, once, at enqueue, **snapshotted on the row and immutable** (`sender_account_id`, `sender_selection`, `sender_policy_version`, the business scope; the database refuses an UPDATE of any of them, for every role):

1. the thread's sender, when `inReplyToMessageId` names an earlier message to the same recipient (a different explicit sender is `SENDER_AFFINITY_CONFLICT`, an unknown, foreign or other-recipient target is `REPLY_TARGET_UNKNOWN`);
2. else the explicit `senderAccountId`;
3. else the **default of the business scope** (`awcms_whatsapp_sender_policies`), else the tenant-wide default;
4. else the deployment sender (`null`).

The default is a **prospective policy with a configuration version**: `PUT /api/v1/whatsapp/sender-policy` (high-risk, `whatsapp_delivery.sender_policy.configure`, `Idempotency-Key`, audited at `warning`) changes what **later** messages get; a message already queued keeps the sender and the version it was given. `defaultSenderAccountId: null` is an explicit decision to use the deployment sender for a scope. There is **no provider default in code**: a derived product that wants StarSender (or Meta) as its default configures the policy.

### A sender that cannot send never sends through another

A sender is usable only when `channel_accounts` says so **right now**: an account of **this tenant** (another tenant's id and an unknown id are one answer), a WhatsApp sending identity, `connected`, its connection grant active, and the capability (`dm`, `reply`, or `broadcast` for marketing) granted with evidence against the current matrix (`ChannelAccountPort`). Otherwise:

| Moment   | Sender state                                                                                                                        | Result                                                                                                        |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| enqueue  | not usable for any reason, or the provider has no adapter on this deployment (StarSender unless `WHATSAPP_STARSENDER_ENABLED=true`) | `refused: SENDER_UNAVAILABLE`, nothing queued, **never** another sender, number or provider                   |
| dispatch | unknown, revoked, disabled, connection not active, capability withdrawn, no adapter                                                 | terminal `failed` with `sender_unavailable`; the provider is never called                                     |
| dispatch | degraded, pending, expired grant or token awaiting refresh, no key ring, control plane off                                          | the lane is **held**: rows stay waiting, nothing is claimed, the retry budget is not spent                    |
| dispatch | the provider rejects the sender's credential (`unauthorized`)                                                                       | that row and the rest of the lane are **held** with backoff (counted, bounded), **no further call** this pass |

There is no rotation to another number to evade a provider limit, a quality rating or a failure (ADR-0148 I4, I5); an explicit reroute is a **new** enqueue.

### Adapter and secret: from the tenant's record, never from the request

The Meta adapter is built **per lane, per pass** from the sender's own record (`external_id` is the `phone_number_id`) and its own credential, decrypted **in memory** for the claimed row's tenant by `ChannelSenderCredentialPort` (the application key ring, AES-256-GCM, associated data binding purpose, tenant and row). The port input type has no field a token could ride on, and the policy endpoint rejects a body that smuggles one. The sender-resolution adapter (`channel-account-port-adapter.ts`, used on the enqueue path) **never imports the secret store**; only `scripts/whatsapp-dispatch.ts` composes the credential adapter, which is why `CHANNEL_SECRETS_ENCRYPTION_KEYS` is granted to `whatsapp:dispatch` alone among the jobs that reach this module. A revoked sender is therefore effective on the **next claim**, and inside a pass already in flight within at most `WHATSAPP_SENDER_REVALIDATE_EVERY_ROWS` rows (default 10; Issue #1231 L1): the verdict and the built provider (the decrypted token in memory) are dropped and resolved afresh every N rows of a lane, so a sender revoked mid-pass fails closed from the next re-check (terminal or held, per the policy above) and the stale credential is never used again. **The window that remains:** the rows sent between two re-checks (at most N, each bounded by the send timeout) and the one row in flight when the revocation lands, which cannot be recalled. `1` re-checks before every row at the cost of one account read and one secret read per row.

### Per-sender health, quota, throttle, breaker, fair claiming

- **Lanes and fair claiming.** A pass serves each sender that has due rows as its own lane, oldest-waiting first, at most `limit / lanes` rows per lane, so a stalled or throttled number cannot starve the others. A sender **already at its cap** is reported as `quota_reached` but takes neither a fair share nor one of the 64 discovery slots from the healthy lanes (Issue #1231 L5); the trade-off is that a sender that is revoked **and** at its cap has its queued rows failed only once its window frees, not at once (it sends nothing meanwhile).
- **Breaker.** One circuit breaker per sender (`whatsapp-delivery:sender:<account id>`); the deployment sender keeps `whatsapp-delivery`. One failing number does not stop another.
- **Quota and throttle.** `WHATSAPP_SENDER_RATE_PER_HOUR` (default 1000) and `WHATSAPP_SENDER_RATE_PER_DAY` (default 10000), counted from what the sender really **sent** plus what is in flight. A reached cap makes the lane wait; the rows are never rerouted. The allowance is computed **and claimed in one transaction under a per-sender advisory lock** (`pg_advisory_xact_lock`, keyed on tenant and sender; never held across a send), so overlapping passes or workers cannot each claim up to their share against the same allowance (Issue #1231 M2). The per-sender breaker stays **in-process**: with several workers each keeps its own. These are deployment-wide ceilings, not per-sender settings.
- **Diagnostics.** `GET /api/v1/whatsapp/senders` (`whatsapp_delivery.senders.read`): per sender, availability (a coarse reason code), the queue, the quota and whether it is throttled. No credential, secret reference, phone number or device id is ever projected; the messages list gains `senderAccountId` and `senderSelection`. The `awcms.whatsapp.message.*` events gain `senderAccountId` (absent for the deployment sender, so that payload is unchanged); "accepted" by the provider is never "delivered".

### Consent and suppression: the recipient, not the sender

Consent, suppression, expiry, the purpose classes, the idempotency key and the recipient rate limits are keyed by the **recipient** (and checked at enqueue and again at dispatch), never by the sender: changing the sender does not change who consented, and an opt-out or a suppressed address stops every sender of the tenant. Marketing through a sender needs the `broadcast` capability (restricted for an unofficial provider, so it needs contract evidence there).

### Marketing consent is per brand (Issue #1231 M4, owner decision 2026-11-11: option (c))

The decision, applied as written: the consent **stays keyed by tenant and recipient** (`awcms_whatsapp_consents_recipient_unique` is unchanged), but every opt-in **records the business scope (brand) it was collected for**, and a marketing message of brand B is refused unless an opt-in for brand B exists. Withdrawals and suppressions stay **tenant-wide**. Transactional and security messages are unchanged.

| What                            | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Recording an opt-in             | `POST /api/v1/whatsapp/consents` takes an optional `businessScope`. A brand is **appended** to the row's `business_scopes` (`sql/354`; a repeat re-stamps that brand) with its own `source` and `grantedAt`; none sets `unscopedGranted` (an opt-in for the tenant itself). A brand grant never rewrites the row-level `source`/`grantedAt` (those describe the first recording or the latest unscoped grant) and never removes another brand.                                                                                    |
| Which brand a message is        | The business scope **the caller declares** (`businessScope`, or the thread's for a reply), snapshotted on the row. For MARKETING it must resolve to a real scope of the tenant, else `refused: BUSINESS_SCOPE_UNRESOLVED`. It is **bound to the sending number only when the sender is itself scoped** (a scoped sender may send only for its own scope). With a tenant-wide sender or the deployment sender nothing ties the declared brand to the number: brand X's opt-in authorises a tenant-wide number sending for brand X. |
| Marketing of brand B            | Eligible only when the granted row lists **exactly** `(type, id)` B. No hierarchy, no "any brand". Otherwise `refused: CONSENT_SCOPE_REQUIRED` at enqueue (nothing queued) and a terminal `cancelled` with `consent_scope_required` at dispatch. Never downgraded, never re-scoped.                                                                                                                                                                                                                                               |
| Marketing that names no brand   | Eligible only with an unscoped (or legacy) opt-in. A brand opt-in never covers it.                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Withdrawal (opt-out)            | **Tenant-wide**: one withdrawal ends every brand and the unscoped opt-in in the same statement and cancels every waiting marketing row. No per-brand withdrawal exists (narrowing an opt-out is the unsafe direction). The ended brands are kept in the audit record.                                                                                                                                                                                                                                                             |
| Reinstatement                   | Covers **only** the brand (or the unscoped opt-in) the reinstating request names: the withdrawal ended every earlier brand, so none is resurrected. Still `consents.restore` + `evidenceRef`, never `import`.                                                                                                                                                                                                                                                                                                                     |
| Suppression                     | Tenant-wide, unchanged: it stops every brand whatever the opt-ins say.                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Where it is enforced            | At **enqueue** and again **immediately before each send** (the same pure rule, `decideEligibility`). A database CHECK (`sql/354`) refuses a withdrawn row that still covers a brand or the unscoped opt-in, for every role and code path.                                                                                                                                                                                                                                                                                         |
| Who may record a brand's opt-in | The caller must hold that scope through the access chokepoint (the business-scope confinement of `channel_accounts`, as for the sender policy: a scope the caller does not hold, including an unknown one, is `403`), and it must resolve in this tenant (`422 SCOPE_UNRESOLVED`). A caller confined to brands cannot record the unscoped opt-in. Only `office` resolves today (`tenant_admin`'s hierarchy, ADR-0060), so in practice a brand is an office.                                                                       |

| Reading consents | `GET /consents` and the grant response list only the brands the **caller holds** (each scope decided once per request through the chokepoint); with the channel module unavailable, none. The masked number and status are unchanged. |
| Withdrawing | `consents.withdraw` only, **not** scope-confined (owner decision: an opt-out is tenant-wide and can only stop messages), so a caller confined to brand A may record the opt-out of someone who also opted in for brand B. The permission decision is written to `awcms_abac_decision_logs` like every route guard. |
| Races | A grant that loses to a concurrent withdrawal answers `409 CONSENT_WITHDRAWN` (the grant UPDATE is guarded by `status = 'granted'`), never the CHECK as a 500; a withdrawal behind a grant still ends every brand, including the one just granted. |

**Rows recorded before `sql/354` (legacy).** They carry no brand, and **none is backfilled**: nobody knows which brand a historical opt-in was collected for, and inventing one would manufacture consent. `unscoped_granted` is `NULL` on them, read exactly like an unscoped opt-in: they keep authorising marketing that **names no brand** (today's behaviour of a single-brand tenant) and authorise **no brand-scoped marketing** until an opt-in for that brand is recorded (`POST /consents` with `businessScope`, which keeps the legacy marker). This is stricter than the alternative considered, "treat a legacy row as tenant-wide while the tenant has at most one business scope with an active sender": that rule depends on another module's live sender configuration, so adding a sender or a policy later would silently change what an old consent authorises, and "one brand today" does not show which brand the person agreed to. The cost, stated: a tenant that already sends **brand-scoped** marketing with legacy consents is refused (`CONSENT_SCOPE_REQUIRED`, loud, nothing sent) until the brand's opt-ins are recorded.

**Not a database guard, on purpose:** a trigger refusing a marketing row without matching consent. The recipient hash is keyed by a ring outside the database, so a consent recorded under an older ring key has a different hash; a trigger could only match the active key, would refuse lawful sends after a rotation, and one that tolerated the miss would guard nothing. The application re-reads consent under every ring key at enqueue and at dispatch. The window that remains is the one of every opt-out: a row already `sending` cannot be recalled.

### Limits of this change (open, stated)

- **Hardening from the independent security audit (`sql/324`, `sql/328`).** The worker's view of `awcms_channel_secrets` is bounded by a RESTRICTIVE policy twice over: to the three purposes a send resolves (`provider_access_token`, `api_token`, `device_key`; `sql/324`) AND, since `sql/328` (Issue #1233 H1), to rows a `whatsapp_cloud` or `starsender` **account** or a `whatsapp_cloud` **connection** actually references. A compromised worker can therefore no longer read refresh-token, bot-token, webhook-secret, PKCE or authorisation-code ciphertext, **nor the Facebook, Instagram, Threads, TikTok, YouTube, LinkedIn or Mailketing tokens** that share those purposes. `security:readiness` fails if the policy is dropped or stops naming the provider test. **Residual risk, stated plainly (ADR-0148 section 5):** the worker still reads, and with the job's key ring can decrypt, the WhatsApp sender credential of **any** tenant, because it chooses the tenant context. AES-GCM associated data stops re-labelling and is not a mitigation against a compromised worker; **the in-process decrypt counter bounds nothing** (it is telemetry inside the same process, which a compromised process can skip or reset, and `scripts/whatsapp-dispatch.ts` only prints it). What holds: the column-only read-only grant, the provider-aware row policy, the key ring being outside the database and its backups and granted to this job alone, and fast revocation. The per-sender cap applies to a `broadcast`-only or `reply`-only sender too. A child number resolves its **parent's** connection and borrows the parent's credential only from a `connected` container of the right provider and kind; an expired grant is a **hold**, a revoked grant or a disabled parent is terminal. A sender policy cannot be deleted, and its audit row records the previous default and version.
- **Audit residuals closed by Issue #1233 (`sql/328` and code).** (M1) `PUT /sender-policy` and `GET /senders` apply the per-account assignments and business-scope confinement of `channel_accounts` (the routes' access loader `infrastructure/channel-account-access-loader.ts`): a caller confined to a brand cannot set another brand's or the tenant-wide default, cannot bind a sender they cannot see (a refusal is the same `422 SENDER_UNAVAILABLE` as an unknown id; binding needs at least the `operator` assignment), and `GET` returns only the senders and policies they may see (a confined caller gets neither the tenant-wide deployment lane nor the tenant-wide policy); default-deny if the channel module cannot be loaded. (L1) A provider `401` or a malformed `WHATSAPP_META_API_VERSION` **holds** rows (retry with backoff, each attempt counted against `WHATSAPP_SEND_MAX_RETRIES`, then a terminal `failed`) instead of failing them on the spot; a revoked, disconnected, unapproved or wrong-tenant sender stays terminal; nothing falls back to another sender or provider. (L2) The policy for a message's scope and the tenant-wide row are read directly, not filtered out of a 500-row window, so a scope's own row (including an explicit `NULL` deployment sender) can never be lost to the tenant-wide default. (L3) A marketing message always needs `broadcast`, even when linked to an earlier message: affinity pins the sender, it never relaxes the capability.
- **Known residual risks and follow-ups:** (Issue #1231 closed the cap race (M2), the mid-pass revocation window (L1, bounded, see above), lane fairness under stuck lanes (L5), the route-ordering wording (L4: `prepare` runs first, so a missing `Idempotency-Key`, an oversized body or malformed JSON is answered `400`/`413` to any bearer-holding caller before the permission check; only the field-level schema validation follows authorization) and the database guards (L6, `sql/329`: the message insert guard also requires a WhatsApp number shape, and a policy default must be `connected` and of that shape; capability, which needs the provider matrix evidence, stays an application check).) A read narrower than "any tenant's WhatsApp credential" would need a definer function keyed by a leased message; it is not built (it would not bind a worker that can claim rows itself). Finding M4 is decided (owner, 2026-11-11, option (c)) and implemented: see [Marketing consent is per brand](#marketing-consent-is-per-brand-issue-1231-m4-owner-decision-2026-11-11-option-c).
- **`whatsapp_cloud` always has an adapter; `starsender` only behind its flag.** With `WHATSAPP_STARSENDER_ENABLED` off (the default) a StarSender sender is refused at enqueue and fails closed at dispatch; the adapter and its gates are [StarSender (Issue #1142)](#starsender-issue-1142).
- **Applied decision (M4, Issue #1231): marketing consent records its brand.** Owner decision of 2026-11-11, option (c), implemented by `sql/354` and the enqueue and dispatch checks: see [Marketing consent is per brand](#marketing-consent-is-per-brand-issue-1231-m4-owner-decision-2026-11-11-option-c). Not done in this change: the `/admin/whatsapp` consent form records an **unscoped** opt-in only (a brand's opt-in is recorded through the API), and its server-rendered table does not show brands at all. **Not bound: the brand of a marketing TEMPLATE.** A template carries a purpose but no business scope, so nothing stops a caller from declaring brand X for a message whose content is brand Y's; binding a scope to template metadata would change the template registry for every consumer and is left as a follow-up. A deleted or deactivated office is refused at enqueue but a row already queued for it is not re-resolved at dispatch.
- **No per-purpose sender override** in the policy (the pack lists it as optional) and **no per-sender cap override** (the caps are deployment-wide).
- **Per-sender breaker and health are in-process**, like the deployment breaker: they reset when the dispatcher process restarts; the quota is counted from the queue and survives restarts. No health row is written by the dispatcher.
- **No admin screen** for senders or the policy (the connection manager is #1154); the API is complete.
- **Per-person account assignment** is applied by the two sender ROUTES (Issue #1233 M1), not by `ChannelAccountPort` itself, which answers "may this account send" for the dispatcher too; any other consumer that lets a user pick a sender must apply the same check.
- **A race window of one transaction:** an account revoked between the enqueue check and the INSERT is caught by the database guard, which raises inside the caller's transaction (loud, fail closed); a revocation after the INSERT is caught at dispatch.

## StarSender (Issue #1142)

An **optional, unofficial** adapter for tenant-owned StarSender devices, under the **same** queue and dispatcher (no second queue, no commerce-owned fork). [ADR-0148](../../../docs/adr/0148-omnichannel-foundation-is-five-gated-capabilities-with-fail-closed-per-account-capability.md) section 7 sets the posture, and the points where this implementation goes beyond it (operator-attested device state, held lanes, unknown outcomes) are the **Proposed** [ADR-0158](../../../docs/adr/0158-starsender-adapter-conditions-that-differ-from-adr-0148-operator-attested-device-state-held-lanes-and-an-unapproved-acknowledgement-text.md), which needs the owner's decision. The code is off by default and fail closed, so it is safe to merge before that decision; the operations runbook is [`starsender-adapter-runbook.md`](../../../docs/awcms/starsender-adapter-runbook.md).

**What it is not:** a Meta-authorised interface. StarSender is an unofficial gateway; nothing here claims Meta approval, ban-free sending or reliable delivery status. A `success` answer is **"accepted by StarSender"**: the row becomes `sent`, with **no provider message id** (the documentation shows none), and nothing downstream ever reports delivered or read.

### The gates (each independent, each fail closed)

1. `WHATSAPP_STARSENDER_ENABLED=true`, **off by default** (`isStarsenderAdapterEnabled`, `_shared/unofficial-provider-flags.ts`). Off: enqueue is `refused: SENDER_UNAVAILABLE`, a claimed row is terminal `failed`, the provider is never called.
2. A **risk acknowledgement** of the current text (acknowledging and attesting need a fresh step-up from a person who has an MFA factor, conditional like the credential route), per operator, stored in `channel_accounts` (`awcms_channel_provider_risk_acknowledgements`, `sql/340`): provider, person, time, text version and the SHA-256 of the exact words, revocable by stamp, never edited or deleted. **The shipped text is a draft with no approval**, so none can be recorded until the business owner approves it in a reviewed change (a human step, ADR-0148 condition 4).
3. A device can be `connected` only with an active acknowledgement (a database trigger, `sql/340`), and only through `POST .../attest-device`: **operator-attested, not verified**, because StarSender documents no status call.
4. The send decision (`ChannelAccountPort`) and the credential decryption (`ChannelSenderCredentialPort`) both re-check the acknowledgement on every call and answer `RISK_ACKNOWLEDGEMENT_REQUIRED` (terminal); the credential port also checks the adapter flag BEFORE it reads any secret (`PROVIDER_ADAPTER_DISABLED`, terminal), so a device key is never decrypted while the adapter is off. A device is bound to the acknowledgement it was attested under: revoking THAT one degrades it even while the tenant holds another, and revoking the tenant's last one degrades every device of the provider (concurrent revocations are serialised, so two of them cannot leave a connected device with no active acknowledgement). Replacing a device key moves the device back to `pending` and it must be attested again.
5. The `dm` capability needs evidence; marketing (`broadcast`) is `restricted` for StarSender and needs contract evidence.

### The adapter (`domain/starsender-contract.ts`, `infrastructure/starsender-provider.ts`)

- **Endpoint:** `POST https://api.starsender.online/api/send`, a constant (never read from a record, a request or the environment), `Authorization: <device key>`, `{messageType: "text", to, body}`. **Redirects are refused** (`maxRedirects: 0`), so the device key header is never forwarded to another host.
- **Per device:** built per lane, per pass, from the device's own record and its own decrypted key; its own circuit breaker (`whatsapp-delivery:sender:<id>`); one failing device never opens another's.
- **Bounded timeout** from the shared outbound seam (`WHATSAPP_SEND_TIMEOUT_MS`).
- **HTTP 200 is not success.** The body's boolean `success` decides; `success:false` is a semantic failure; a body that is not JSON, not an object or without a boolean `success` is `malformed_response`, **never accepted**.
- **Retry classification** (a coarse `failureCode`, a FIXED sentence per code; provider text, the key, the number and the body are never copied into an error, a row, a log or an event): `network_error` (DNS: it never left, retryable), `rate_limited` (429 or a limit message, retryable), `device_disconnected` (retryable, and it **holds the device's lane**: one call, no more, bounded by `WHATSAPP_SEND_MAX_RETRIES`), `unauthorized` (401/403, lane held), `rejected` (terminal), `malformed_response` (terminal), `endpoint_refused` and `unexpected_redirect` (terminal), and **`outcome_unknown`** (a timeout, a reset or **ANY 5xx**: the request may have been processed, a failing gateway may already have forwarded the message, so it is **not retried**: StarSender documents no idempotency key and a retry could message the person twice; it still counts against the device's breaker). A free-text match never produces a recipient-level suppression.
- **`healthCheck`** reports the breaker only: StarSender documents no side-effect-free status call, and a send would message someone.

### Inbound and status: none, on purpose

StarSender's public documentation describes a webhook but **no authentication of the request**. There is **no StarSender webhook route**, no signature scheme is invented, and no status or contact is ingested (ADR-0148 I9; the matrix keeps `inbound` `unverified`). The adapter runs in **status-unknown mode**; any compensating mechanism needs its own ADR addendum and evidence.

### API (`channel_accounts`, OpenAPI `openapi/modules/channel-accounts.openapi.yaml`)

`GET/POST /api/v1/channel-accounts/risk-acknowledgements`, `POST .../risk-acknowledgements/{id}/revoke` (high-risk) and `POST .../accounts/{id}/attest-device`: see the [`channel_accounts` README](../channel-accounts/README.md).

### Not verified, stated plainly

The request and response fields are taken from one public documentation page (read 3 November 2026) and **have not been verified against the live API**: only the success body is documented, every failure fixture is an assumption (`tests/fixtures/starsender/contract-fixtures.ts`). The runbook lists what to confirm with a test device before production. The acknowledgement text is not approved by anyone.

## Meta Cloud API multi-WABA senders (Issue #1143)

[ADR-0148](../../../docs/adr/0148-omnichannel-foundation-is-five-gated-capabilities-with-fail-closed-per-account-capability.md) section 4 and I9, and the conditions of the issue's owner comment. A tenant can run **several Meta numbers on several WABAs**, each a `channel_accounts` row of kind `waba_phone_number` whose parent is its `waba` container (`external_id` = the WABA id). **One queue, one dispatcher**: nothing here is a second queue, and nothing is sent from the webhook path.

**Not verifiable from the pages above, so fail closed:** whether a `FLAGGED` template is still safe to send (it is refused until Meta reports it approved again); the expiry of an `ACCOUNT_RESTRICTION` (held until an operator clears it); and the exact field override list for per-number callback URLs (each number gets its own token; an event that names another WABA or number on that token is dropped, never applied). Whether `entry.id` is always the WABA id for partner events is inconsistent in Meta's own examples, so a partner event whose `entry.id` is not the bound WABA is dropped.

### Binding: the verified sender identity is on the row

- A Meta number is usable only with a **live `waba` container of the same provider** (`ChannelAccountPort` 1.2.0, `CONTAINER_BINDING_INVALID`, terminal). An API-token number with no parent is refused: it has no verifiable WABA.
- At enqueue the database guard (`sql/365`) **fills and checks** `sender_external_id` (the `phone_number_id`) and `sender_container_external_id` (the WABA id) from the records, and makes both immutable. A request can never supply them (the port input has no such field).
- At dispatch the live record is compared with the snapshot: a number moved to another WABA (or any identity drift) is terminal `sender_unavailable` (`SENDER_BINDING_CHANGED`), never sent from the new binding. The provider call uses that number's own `phone_number_id` and its own token, as since #1141.
- **Legacy rows** queued before `sql/365` have NULL snapshots and are bound by the current record, which must still have a valid WABA.

### Templates are approved per WABA; free text only inside the window

`awcms_whatsapp_meta_templates` records Meta's status of a template (name, language, category) on one WABA. Approvals and restrictions are keyed by the **WABA id** (Meta's id), not by the container's record id, so deleting and re-registering a container neither loses an approval nor lifts a restriction (security review L-3). For a **tenant-owned Meta number** (not the deployment sender, not StarSender):

| Message                                   | Rule                                                                                                                                                         | Refusal (enqueue) / failure (dispatch)              |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| registration with a `providerTemplate`    | a row on **that number's** WABA, status `APPROVED` or `REINSTATED`, category = purpose (marketing MARKETING, transactional UTILITY, security AUTHENTICATION) | `TEMPLATE_NOT_APPROVED` / `template_not_approved`   |
| registration without a `providerTemplate` | a free-text service message, only while the recipient's **24-hour window with that number** is open (opened by a verified inbound message)                   | `OUTSIDE_SERVICE_WINDOW` / `outside_service_window` |
| marketing without a `providerTemplate`    | never: marketing content is an approved MARKETING template (an opt-in is necessary, not sufficient)                                                          | `TEMPLATE_NOT_APPROVED`                             |

Checked at enqueue and **again immediately before the send** (a webhook may have paused the template, a window may have closed). Never free text instead of a template, never another number. Marketing consent (per brand, #1231 M4) is unchanged and still required.

Approvals are written two ways: `PUT /api/v1/whatsapp/meta-templates` (operator, `meta_templates.configure`, `Idempotency-Key`, `warning` audit; `APPROVED`/`REINSTATED` need an `evidenceRef`, a database CHECK enforces it), because Meta sends a status webhook only when a status **changes**; and a signed `message_template_status_update` webhook of a number of that WABA. Order is Meta's `entry.time`, clamped to the moment the verified webhook arrived (a future one would otherwise win against every genuine later event and freeze the state; one past the Date range is unreadable; #1267 audit M3): an older event never overrides a newer one, and on a tie the not-sendable status wins. **A caller confined to business scopes** does not see the approvals and signals of a **tenant-wide** WABA (`GET`), cannot record or clear them (`PUT` is the same `422 CONTAINER_NOT_FOUND`, `clear-restriction` the same `404` as an unknown id), and cannot create a webhook subscription for one of its numbers (the same `404`): tenant-wide state is not theirs (#1267 audit M2).

### The webhook: tenant and account come from the token, never the payload

`channel_accounts` mints a per-number **opaque callback token** (`POST /api/v1/channel-accounts/accounts/{id}/webhook-subscription`, conditional step-up, `Idempotency-Key`, `warning` audit). The Meta app secret is stored write-only (purpose `webhook_signing_secret`); the token is shown **once** and only its SHA-256 is stored. Creating a new subscription revokes the old one and erases its secret (rotation); so do **disconnecting and deleting** the number (security review M-3). The operator configures `https://<host>/api/v1/whatsapp/webhooks/meta/<token>` as the number's callback URL override at Meta, with the same token as verify token.

**Who may create one (security review M-1).** Whoever holds a subscription's app secret can feed WABA-LEVEL state (template approvals, a restriction that stops every sibling number, 24-hour windows). So creating or rotating one needs `channel_accounts.webhooks.configure` **and** `whatsapp_delivery.meta_templates.configure` **and** `whatsapp_delivery.meta_signals.configure`, the `owner` assignment on the number **and on its WABA container**. Every WABA-level change a webhook makes (a template status, a restriction set or lifted, a closed window opened) is **audited** (`whatsapp_meta_webhook.*`, ids and fixed codes only, no person, the subscription and number named). **The app secret is not verified with Meta** (it is the operator's statement of which secret signs this number's webhooks; a wrong one only makes every delivery refuse), which is why the permissions above, and not the secret, bound what a subscription can do.

`GET`/`POST /api/v1/whatsapp/webhooks/meta/{token}` is public by design (listed in `SESSION_FREE_BODY_ENDPOINTS` with its reason) and does, in order: `404` when `WHATSAPP_ENABLED` is off; two buckets **before any database work**: one keyed by the **address alone** that counts requests whose callback token has not matched (a verified one is refunded, and so is a refusal that comes after the token matched: a wrong or stale app secret, a revoked subscription, a broken binding is charged to that tenant's own denial bucket instead, so one misconfigured tenant cannot make Meta's address `429` every other tenant's genuine deliveries; #1267 audit M1), so a caller cannot dodge it by choosing tenant uuids in forged tokens (security review M-2: 300 random tenants from one address now meet `429` after 120), and one per (tenant of the token, address) so one tenant's genuine volume never spends another's (`429`; Meta retries, so a status or an inbound message is **delayed, never dropped**); the capped body (128 KiB) as **raw bytes**, over which the HMAC is computed before anything is decoded (review L-5; a signed body that is not UTF-8 JSON is accepted as malformed and applied nowhere); then, in the token's tenant transaction, verification by `ChannelWebhookVerifierPort` (token hash and HMAC compared in constant time; every refusal one `401`, counted against a smaller denial bucket); the **body hash dedupe** (`awcms_whatsapp_webhook_receipts`, 8 days); and the actions, read only **within the binding**:

- `messages.statuses[]` reconcile only a row of **the bound sender** with that provider message id, and, when Meta names the recipient, only if it hashes to the row's recipient. Forward-only (`sent` < `delivered` < `read`; `failed` only before delivery): a repeat or a late status changes nothing and emits nothing. A move emits `awcms.whatsapp.message.provider_status_changed`. The queue status stays `sent`: provider-accepted is never "delivered", and "delivered" is a separate fact.
- `messages.messages[]` open the 24-hour window of (that number, the sender's keyed hash). **No content is read or stored**, and nothing is sent in reply.
- `message_template_status_update` updates the bound WABA's template rows; `phone_number_quality_update` records its messaging-limit tier; `account_update` restricts or clears the bound WABA (below).
- An entry of another WABA, or a `messages` change of another phone number id, is **dropped and counted**, never applied to "whichever row matches".

### Monitoring, rate limits, restrictions

- **Restriction.** `DISABLED_UPDATE` (ban or scheduled ban, or an unknown ban state), `ACCOUNT_RESTRICTION`, `ACCOUNT_DELETED`, `ACCOUNT_OFFBOARDED`, `PARTNER_APP_UNINSTALLED` restrict the WABA: its numbers are refused at enqueue (`SENDER_UNAVAILABLE`) and **held** at dispatch (`SENDER_RESTRICTED`, counted against the retry budget, then terminal). `REINSTATE` and `ACCOUNT_RECONNECTED` lift only the restriction they reverse, and only when strictly newer. Anything else is cleared by an operator (`POST /api/v1/whatsapp/meta-signals/{id}/clear-restriction`, `meta_signals.configure`, `warning` audit) after checking at Meta. Another WABA of the tenant is unaffected; nothing reroutes.
- **Rate limits.** A `rate_limited` answer from Meta (`429`, codes 4, 80007, 130429, 131056) retries that row with backoff and holds the **rest of that sender's lane** for 60 seconds, uncounted; other senders continue. The per-sender hourly and daily caps of #1141 still apply. Rate-limit history is read from the queue itself (`failure_code`), so no new worker write exists.
- **Credential expiry and permission changes.** A `401`/code 190 still holds the lane with bounded retries (#1233 L1); a revoked grant or disconnected account is terminal (#1141).
- `GET /api/v1/whatsapp/meta-templates` returns the approvals and each WABA's signals (restriction, messaging-limit tier) for the WABAs the caller may see, at most 500 of each, with `itemsTruncated`/`signalsTruncated` saying when there were more (review L-6).

### Backward compatibility (the single-sender deployment)

The deployment sender (`WHATSAPP_PROVIDER=meta`, `WHATSAPP_META_ACCESS_TOKEN`, `WHATSAPP_META_PHONE_NUMBER_ID`) is **unchanged**: same path, same templates-only adapter, same failures (Meta itself rejects an unapproved template). It has no WABA record, so none of the per-WABA rules apply to it, it cannot receive webhooks (there is no subscription to bind them to), and its rows carry no snapshot. Moving a deployment to tenant-owned numbers is a **configuration** step: register the WABA and its numbers, record their template approvals, create each number's webhook subscription, then point the sender policy at them (prospective). No row changes sender after enqueue.

### Security notes

- The webhook signing secret is decrypted by the **application** role in the request. The worker's `awcms_channel_secrets` policy (`sql/328`) is **unchanged** and still excludes `webhook_signing_secret`; `sql/365` grants the worker only `SELECT` on approvals and signals and `SELECT, DELETE` on windows and receipts (purge), pinned in `security:readiness`.
- The callback token is in the URL path. This repository logs no request paths, but a reverse proxy or CDN in front of it might: configure them not to log `/api/v1/whatsapp/webhooks/`. A leaked token alone is not enough: every body must also carry a valid HMAC under the app secret.
- `whatsapp:queue:purge` removes windows two days after they closed and receipts after eight days (legal-hold gated descriptors). The worker's `DELETE` on those two tables is itself limited by RESTRICTIVE policies to exactly those ages (review L-2), pinned by their exact expressions in `security:readiness`: a compromised worker cannot delete a fresh receipt (re-opening replay) or an open window.
- The verified identity snapshot (`sender_external_id`, `sender_container_external_id`) is immutable for the owner, the application and the worker role alike (review L-1, tested per role).

### Audit follow-ups (Issue #1298, the Low findings of the #1267 audit)

- **L1, an operator clear moves the event clock.** `clearMetaRestriction` now sets `restriction_event_at` strictly past both the event that set the restriction and the moment of the clear, so the same (or any older) `ACCOUNT_RESTRICTION` arriving later, in another body or through another subscription, no longer re-restricts the WABA. Only an event Meta stamps after the clear can. (Meta stamps whole seconds: an event in the same second as the clear counts as older. Accepted: the operator can see and clear again.)
- **L2, replay.** `replay_window_seconds` (`sql/318`, written as 300) is **deliberately not read** for Meta: `X-Hub-Signature-256` is an HMAC of the body alone, so there is no signed timestamp to bound; the column stays for providers that sign one, and `sql/393` records that on the column. The replay controls of this path are: (1) the body-hash receipt is looked up **per tenant**, not per subscription, so rotating a number's token (new subscription, same app secret) does not reopen a captured body; (2) WABA-level changes (template status, messaging limit, restriction) need a **stated `entry.time` within seven days** (`META_ENTRY_MAX_AGE_MS`, strictly below the eight-day receipt retention), so a body whose receipt was purged cannot apply, and a body stripped of its time is refused instead of defaulting to "now"; (3) the forward-only and ordering rules that already bound statuses, templates and restrictions. A genuine first delivery delayed more than seven days by Meta is dropped (counted as `ignored`); a later status or event repairs the state.
- **L3, the dispatcher's write access is narrowed to columns and values** (`sql/392`). `awcms_worker` loses table-level `UPDATE` on `awcms_whatsapp_messages` and holds it on exactly the eleven columns its call sites write (`WORKER_COLUMN_GRANTS`; `provider_status*`, recipient, template, purpose, sender and `contains_secret` are not among them). A `BEFORE UPDATE` trigger that binds **only** `awcms_worker` allows exactly the transitions the code makes (claim, retry, sent, failed, cancelled, expired), freezes a terminal message, lets `body`/`variables` only be cleared on a secret message, ties the provider acceptance writes to `sending -> sent`, and refuses a lower retry count. The trigger body is pinned exactly by `security:readiness` (`WHATSAPP_META_AUDIT_TRIGGERS`), and the tests log in as the real worker role.
- **L4, the database clock** (`sql/393`). A `BEFORE INSERT` trigger stamps `awcms_whatsapp_webhook_receipts.received_at := now()` for every role; `awcms_app` loses `UPDATE` and `DELETE` on receipts and `DELETE` on service windows (the purge is the worker's, under its restrictive floors). `last_inbound_at` is the provider's own time, not our stamp, so it keeps the application's value but a trigger caps it at `now()` for every role. Readiness pins the three trigger bodies and the narrowed app privileges (`RETIRED_TENANT_TABLE_PRIVILEGES`).
- **L5, the enablement preflight.** `bun run whatsapp:meta:preflight` (read-only, as `awcms_worker`) lists, before the Meta path is switched on, the numbers with no live WABA parent and the queued rows that would fail terminally (no sendable approval of the right category on the number's WABA, or free text outside the 24-hour window), OTP rows counted apart. It applies the dispatcher's own `decideMetaSend`. Runbook: [`docs/awcms/whatsapp-meta-enable-runbook.md`](../../../docs/awcms/whatsapp-meta-enable-runbook.md). A mechanical approval backfill is **not** provided: an approval is Meta's fact and needs evidence, and inventing one would authorise a send Meta will refuse.
- **L6, the per-(tenant, address) attempt bucket is refunded for a verified, new delivery.** A tenant with real volume from Meta's address is no longer answered `429` by its own success. A refusal, a malformed body and a verified duplicate (a replay or a provider retry, which still costs a transaction) keep the charge, and a request that never verified can never earn a refund.

### Audit follow-up of the L1-L6 change (Issue #1298, independent audit: PASS with three Lows, all fixed)

- **LOW-1, the worker's INSERT and DELETE on the queue** (`sql/394`). `sql/392` bounded only the worker's `UPDATE`; as `awcms_worker` an `INSERT` could still create a forged `sent`/`read` row or an unvetted `queued` one, and a `DELETE` could erase fresh evidence. A `BEFORE INSERT` trigger that binds only `awcms_worker` now requires a fresh `queued` row (no provider name/id/`sent_at`, no provider status, rank 0, no failure text, `retry_count = 0`: exactly what the booking reminder job's enqueue through the port writes). A RESTRICTIVE `FOR DELETE TO awcms_worker` policy allows only a terminal row last touched more than seven days ago (the purge default is 30; a configured retention below 7 days is clamped by the floor). The floor does not rest on a column the worker can write: a terminal row is frozen against the worker by the `sql/392` guard. `security:readiness` pins the trigger body exactly (`WHATSAPP_META_AUDIT_TRIGGERS[3]`), the policy expression exactly (`WORKER_PURGE_POLICIES`) and the delete floor by the rolled-back behavioural probe (`probeWorkerPurgeDeleteFloors`, now also seeding a fresh sent, an old queued and an aged failed message).
- **LOW-2, the preflight uses the dispatcher's own binding rule.** The preflight no longer re-derives "has a live WABA parent" with a look-alike JOIN: for each connected Meta number it asks the sender port (`resolveWhatsappSender`, capability `dm`, the lane verdict the dispatcher takes) and classifies the answer with the dispatcher's `classifySenderUnavailable`. A revoked or disabled parent, a parent whose business scope does not contain the number's (`CONTAINER_BINDING_INVALID`) or a missing capability is a `number_unusable` **terminal** finding; a degraded or pending one is reported as a **hold** (rows wait; they are not counted as blocked). The "number without a WABA parent" finding is kept. The preflight needs the channel-accounts control plane enabled in its environment, like the dispatcher: with it off every number reads as a hold (`CHANNEL_ACCOUNTS_DISABLED`), which is what the dispatcher does.
- **LOW-3, the receipt dedupe is atomic.** `recordWebhookReceipt` takes `pg_advisory_xact_lock(hashtextextended(tenant, body hash))` before its `NOT EXISTS`, so the same signed body arriving at two subscriptions of one tenant at once is applied once (the second waits for the first to commit, then sees its receipt). A unique `(tenant_id, payload_sha256)` index was **not** chosen: the table is purged on an 8-day clock, existing data would need de-duplication first, and the lock achieves the same without a constraint the replay-window arithmetic does not need.

## Realtime sender progress (Issue #1171, ADR-0154)

One sender's delivery progress, live, as Server-Sent Events from the existing Bun process: `GET /api/v1/whatsapp/senders/{id}/progress/stream`, with the REST snapshot and polling fallback `GET /api/v1/whatsapp/senders/{id}/progress`, under the separately grantable permission `whatsapp_delivery.progress.read` (`sql/360`, which also adds the keyset index `(tenant_id, sender_account_id, updated_at, id)`). Implementation: `application/whatsapp-sender-progress.ts` (the topic) over `_shared/progress-sse-route.ts` (the factory).

- **A projection, never a send path.** Frames are read from `awcms_whatsapp_messages`; nothing in the stream enqueues, sends or changes a status (ADR-0148 I10). "Sent" means the provider accepted the message, as everywhere else in this module.
- **Same visibility as `GET /senders`.** The sender must be a `channel_accounts` account the caller may see (assignment, business scope); an unknown, another tenant's and a hidden account are one `404`. Re-decided on every 5 s tick together with the permission: a role, an assignment or a brand removed mid-stream ends the stream with `authorization-revoked` and an audit row `realtime_stream.revoked`.
- **Rows, not only the account (security audit M-1).** A tenant-wide sender carries messages of every brand. A caller confined to business scopes sees through it only the messages whose OWN business scope they hold (decided per tick through the chokepoint, descendants included): counts, change list, recent list and cursor alike, in the snapshot and the stream. An unscoped message is invisible to a confined caller; a cursor naming a row they may not see gets `snapshot-required`. An unconfined caller sees every row.
- **Bounded cost (audit M-2).** Counts cover messages CREATED in the last 7 days (`countWindowDays`), served by `awcms_whatsapp_messages_sender_window_idx`; each read is one statement (`tests/integration/whatsapp-sender-progress-query-budget.integration.test.ts`). Ticks run on their own small `realtime_stream` work class, and the connection slot is taken before any topic query, so a `429` costs one guard chain.
- **Redacted.** Counts per status, and per changed message only its id, status and time. Never the number (raw, masked or hashed), the body, the variables, the template, the provider response or an error text.
- **Cursor.** `wsp1.<account>.<updated_at µs>.<message id>`, computed by PostgreSQL; `Last-Event-ID` resumes; a foreign, malformed or purged cursor, or more than 50 changes at once, gives `snapshot-required`.
- **Screen.** The progress panel on `/admin/channel-accounts/{id}` renders the counts server-side, has a manual refresh, polls when the stream is unavailable, states the connection as text and announces politely at a bounded rate.
- **Open decision (fail-closed for now):** the deployment sender (`sender_account_id` NULL) has no stream: it has no account id to resolve visibility against. **Deploy note:** `sql/360` builds two indexes without `CONCURRENTLY` (the runner wraps each migration in a transaction), which holds writes to `awcms_whatsapp_messages` until they finish; run it in a quiet window on a large queue. **Pre-existing, out of scope here:** `POST /whatsapp/messages/{id}/cancel` does not apply business-scope confinement; tracked separately. Operations: [realtime progress streams](../../../docs/awcms/realtime-progress-streams.md).
