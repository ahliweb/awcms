# `social_publishing`

Account-scoped social publishing (Issue #1145, [ADR-0157](../../../docs/adr/0157-social-publishing-is-an-account-scoped-publication-intent-and-per-account-job-module.md), [ADR-0148](../../../docs/adr/0148-omnichannel-foundation-is-five-gated-capabilities-with-fail-closed-per-account-capability.md) capability C3; design in [`docs/awcms/social-publishing.md`](../../../docs/awcms/social-publishing.md)) behind the `SocialPublishingPort` that `blog_content` already calls when an article is published.

Status: `experimental`, **off by default** (`SOCIAL_PUBLISHING_ENABLED`), no navigation entry until the admin screen lands. **One connector ships, Facebook Pages (Issue #1146), behind its own switch `SOCIAL_PUBLISHING_FACEBOOK_ENABLED` (default off)**; the other connectors are #1147 to #1151, each with its own provider approval. A provider with no adapter (or whose switch is off) is refused at enqueue and fails a job at dispatch.

## What it owns

| Table                              | Holds                                                                                                                                                                                                              |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `awcms_social_publishing_settings` | Two tenant switches: `auto_publish_enabled` (default `false`) and `approval_required` (default `true`)                                                                                                             |
| `awcms_social_publish_rules`       | Which `channel_account`s an article event publishes to (unique per trigger and account; disabled, never deleted)                                                                                                   |
| `awcms_social_publications`        | One publication with an IMMUTABLE content snapshot (title, caption, link, media snapshot, content hash), its approval and cancel lifecycle, `not_before`                                                           |
| `awcms_social_publish_jobs`        | One job per (publication, account): provider and variant snapshot, status (`needs_reconciliation` when the outcome is unknown), attempts, holds, the provider's post id and URL. **No token, no secret reference** |
| `awcms_social_publish_attempts`    | Append-only ledger: an outcome, a fixed code, a fixed phrase                                                                                                                                                       |

It reads the account model only through the `channel_account` port (`ChannelPublisherPort`, `ChannelPublisherCredentialPort`, `ChannelPublisherHealthPort`, capability version 1.3.0) and verifies media through `MediaLibraryPort`. It owns no account, credential, media or article content.

## Flow

1. **Enqueue** (`application/publication-enqueue.ts`), in the caller's transaction, plain writes only. Per account, in order: may the account publish now (revoked, disabled, degraded, no granted `publish` capability with evidence: refused), does the provider have an adapter, can its capability map carry the content. A refusal is a returned code, never a downgrade, and every account refused leaves nothing recorded.
2. **Approve / schedule** (routes). Nothing is claimable before approval; a creator cannot approve their own manual publication; `not_before` defers.
3. **Dispatch** (`bun run social-publishing:dispatch`): claim with a lease and a per-account advisory lock (fair share and daily cap), re-resolve the account, ask the credential port for the credential in a transaction that closes before the call (the real port only behind the connector switch; otherwise the one that refuses every request), call the adapter with an `ssrfSafeFetch` client and a per-account breaker, finalise with a compare-and-set.

## Invariants and where each is enforced

| Invariant                                                     | Enforced by                                                                                                                                              |
| ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tenant first                                                  | RLS `ENABLE` + `FORCE` with `USING` and `WITH CHECK` on all five tables, composite `(tenant_id, id)` foreign keys, RBAC/ABAC default-deny on every route |
| A job holds no credential                                     | No column can (`tests/integration/social-publishing.integration.test.ts` asserts it on `information_schema`); the dispatcher resolves it per call        |
| Content is a snapshot                                         | Trigger `awcms_social_publications_snapshot_guard`; the job never re-reads the article                                                                   |
| `published` is terminal; partial failure never replays        | Trigger `awcms_social_publish_jobs_guard`; retry and cancel act on unsent jobs only                                                                      |
| Idempotent per (article, trigger, account)                    | Unique indexes and `buildSocialPublishIdempotencyKey`                                                                                                    |
| Unsupported content is refused, not downgraded                | `checkAdapterSupport`; the adapter map is a ceiling, never a grant                                                                                       |
| No network inside a transaction; SSRF-safe                    | Three-phase dispatcher; adapters get `request.http` (`ssrfSafeFetch`) and no raw `fetch`                                                                 |
| A revoked account stops its jobs; nothing is rerouted         | `resolvePublisher` at enqueue and at claim; terminal vs hold in `classifyAccountReason`                                                                  |
| The article's publish transaction never fails because of this | `onArticlePublished` runs in a savepoint and answers `{ jobsCreated: 0 }`                                                                                |

| `POST publications/{id}/schedule`             | `publications.schedule`                    |

Every mutation requires `Idempotency-Key` and refuses a machine credential; every route answers `503 SOCIAL_PUBLISHING_DISABLED` unless the deployment enables the module. Using an account additionally needs the per-account access of `channel_accounts` (assignment rule and business scope).

## Facebook Pages connector (Issue #1146)

`infrastructure/facebook-pages-adapter.ts`. Off by default behind `SOCIAL_PUBLISHING_FACEBOOK_ENABLED` (it needs `SOCIAL_PUBLISHING_ENABLED` too); while it is off the registry has no Facebook adapter and the dispatcher is composed with `noPublishCredentialPort`, so nothing decrypts a social token. The registry answers it from `builtInAdapter`, which reads the switch on every call, so the enqueue path and the dispatcher agree without a composition root registering it.

**Verified against the official documentation on 2026-11-11** (developers.facebook.com; re-verify before enabling, Meta versions the Graph API):

The permissions need **Meta App Review**: a business step, not code. Nothing here claims an approval; each account still needs a `granted` `publish` capability with evidence (an `app_review_reference`).

| Decision                                                                                                                                                                                     | Why                                                                                                                                                                                       |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Variants `text` and `image` only; JPEG and PNG up to 4 MB                                                                                                                                    | The matrix has one `publish` cell; video needs `publish_video` and a resumable upload. A WebP or a larger image is REFUSED at enqueue, never converted                                    |
| The token travels as `Authorization: Bearer`, never in the URL or the body; the page id must be numeric                                                                                      | The URL and body are what a proxy or a log may keep; the page id becomes a path segment                                                                                                   |
| `supportsIdempotencyKey: false`                                                                                                                                                              | The Graph API documents no idempotency key for these edges: every unknown outcome is `needs_reconciliation`                                                                               |
| `externalPostIdPattern` `^[0-9]{1,32}_[0-9]{1,32}$`, `postUrlHosts` `www.facebook.com`                                                                                                       | L6: the id is the `{page}_{post}` shape both edges answer; the photo edge's PHOTO id is never stored                                                                                      |
| 190/102/reauth subcodes and 10/200-299 are `needs_reauth`                                                                                                                                    | A person must re-authorise or re-grant; the dispatcher fails the job `NEEDS_REAUTH` AND degrades the account (`reportPublishCredentialRejected`), so its other jobs are HELD              |
| 4, 17, 32, 341, 613, 80001 are `rate_limited`, waiting what the usage header asks (bounded to a day)                                                                                         | Throttling never fails a job                                                                                                                                                              |
| `code` 2 is `retryable` ONLY on a 503 that flags `is_transient: true`; any other `code` 2, a 5xx without a Graph envelope, `code` 1, a lost answer and a 2xx without a post id are `unknown` | The guide tells a client to retry code 2 but never says the post was not created (the #1271 audit, L4); `is_transient` is not on the guide, so it can only narrow a retry, never widen it |
| 506 (duplicate post) is `unknown`                                                                                                                                                            | It may be OUR earlier post whose answer was lost: reconcile, never retry                                                                                                                  |
| 368 (policy block), 100, 324 and other 4xx are `rejected`                                                                                                                                    | Never retried automatically                                                                                                                                                               |
| The media URL is re-checked (https, named host, type, size) before Facebook is told to fetch it                                                                                              | The adapter never fetches it itself; SSRF on Meta's side is out of our reach, so only a public https URL is handed over                                                                   |

**Engagement is NOT in this slice.** Reply, comments, DM and inbound are `candidate` cells of the matrix, but ADR-0157 section 8 keeps comment ingestion, reply and DM out of `social_publishing`, and the inbound boundary (#1144) decides the store before any content event is accepted (Issue #1146 comment of 2026-11-10). They are follow-ups: a signed webhook (ADR-0150, `X-Hub-Signature-256`) in `SESSION_FREE_BODY_ENDPOINTS` with a per-IP pre-verification limit, and reply/comment calls through the same credential path. `appsecret_proof` (required when the Meta app enables "Require App Secret") needs the app secret in the job and is not sent; leave that app setting off until it is added.

## Composition roots

`POST /api/v1/blog/posts/{id}/publish` and `scripts/blog-scheduled-publish.ts` choose the port through `resolveSocialPublishingPort`: the real adapter only when `SOCIAL_PUBLISHING_ENABLED` is on, otherwise `blog_content`'s no-op, so a deployment that configures nothing is unchanged. `scripts/social-publishing-dispatch.ts` runs ONLY as `awcms_social_dispatch` (`SOCIAL_PUBLISHING_DATABASE_URL`, no fallback; it refuses to start with a shared login in its environment or when the server says it is another role), holds `CHANNEL_SECRETS_ENCRYPTION_KEYS` as a dedicated-role job (the runner withholds `DATABASE_URL`, `WORKER_DATABASE_URL` and `SETUP_DATABASE_URL`), and composes the publish method of the credential adapter only when `SOCIAL_PUBLISHING_FACEBOOK_ENABLED` is on.

## Known limits

- One provider adapter (Facebook Pages, publish only), no admin screen, no caption templates (see the remaining limitations in `docs/awcms/social-publishing.md`).
- **Retention (Issue #1145 admission, `sql/357`).** `bun run social-publishing:retention:purge` (daily, as `awcms_worker`) deletes a whole publication (attempts, jobs, publication) only when every job is terminal and it is older than the window: **default 730 days, bounded 365 to 3650, a proposed default the owner may change** (`domain/social-publishing-lifecycle.ts`). A waiting or `needs_reconciliation` job and a `pending_approval` publication are never removed; a legal hold on any of the three descriptors stops it. The window is measured from `terminal_at`, a stamp only database triggers write (never `updated_at`, which the app and the worker can write). Restrictive row policies refuse the worker a DELETE of anything younger than 365 days or not terminal, but that floor is **per row**: keeping a publication whole, and honouring a legal hold, are enforced by the purge (the application), not by the database.
- The crash window between "the provider accepted the post" and "the job was finalised" is closed automatically only as far as the provider honours the passed idempotency key. A `publishing` job whose lease expired is `needs_reconciliation` (`LEASE_EXPIRED_UNKNOWN`) for any other provider and is never re-sent by the dispatcher.
- **The credential path (audit finding H1, activated by Issue #1146).** The `awcms_worker` role still cannot read a social token (`sql/328` is unchanged). The dispatch job runs as the **separate DB role** of `sql/358`, widened by `sql/373` to exactly the columns the dispatcher touches (the queue, the tenant list, the enablement flag, audit and outbox inserts, a degrade-only account update), each write bounded by a RESTRICTIVE policy (no re-queue of a failed or unknown job, no cancel, only `connected` -> `degraded` of a live social account, only a `failing` health row, only this module's audit rows and its two events), pinned exactly and probed (positive controls included) by `security:readiness`. The role as of `sql/358`: `awcms_social_dispatch`, column-only reads of the four channel tables, no table privilege, and a restrictive policy that admits only the access token of a social connection (`active`/`expired`) used directly by a `connected`/`degraded` account with a `granted` `publish` capability (M2); an account borrowing a parent's credential is refused as `CREDENTIAL_UNAVAILABLE` (L10). The secret policy is keyed on the CONNECTION, so `resolvePublishCredential` also requires THE requested account's own granted `publish` capability before any secret is read (`CAPABILITY_DENIED`), and two further policies hide every account and connection that is not one of the six social providers. `security:readiness` pins all three to their exact expressions and runs a rolled-back probe that must see exactly one secret. It still ships `NOLOGIN`: a deployment activates LOGIN and points `SOCIAL_PUBLISHING_DATABASE_URL` at it. `whatsapp:dispatch` is unaffected.
- **Open decision (recorded, fail-closed):** the connector switch stays OFF until (1) the human security review of the credential path and its role (ADR-0157 section 6), and (2) Meta App Review for the account's permissions (a business step). The third condition, residual **L8**, is closed (below).
- **L8 closed (`sql/386`): the source is re-checked immediately before every provider call.** In the pre-send transaction, before the credential is decrypted, the dispatcher asks `blog_content` (`ArticlePublicationStatusPort`, capability `article_publication_status`) whether the source article is still published publicly, and `media_library` (`MediaPublicationRecheckPort`, `media_library` 1.1.0) whether the media object is still available and still cleared. A job whose article was unpublished, archived, made private, deleted or passed its `unpublish_at` fails `SOURCE_RETRACTED`; a media object missing, soft-deleted (taken down) or no longer `verified`/`attached` fails `MEDIA_UNAVAILABLE`; rights no longer `verified` or an unknown copyright status fails `MEDIA_RIGHTS_REVOKED` (`fair_use` stays accepted). Terminal: never sent, never retried by the dispatcher, the breaker is not charged, and the audit row carries ids and the code only. A check that cannot be answered is `SOURCE_CHECK_UNAVAILABLE` (retried, never sent). The answers come from two SECURITY DEFINER functions owned by the NOLOGIN, memberless role `awcms_social_source_check` (column reads only); `awcms_social_dispatch` holds EXECUTE and gains no read of `awcms_blog_posts` or `awcms_news_media_objects` (its only new grant is `source_kind`, `source_id`, `media_object_id` of its own publications). `security:readiness` pins both functions and both roles' column matrices exactly and probes every verdict in a rolled-back transaction. What it does not do: an operator's `jobs.retry` of such a job is allowed (the next pass re-checks and refuses again), and a media object replaced in place (same id, new bytes) is not detected (the registry does not do that today).
- **Fixes from the #1271 audit (security review of this PR):** M1, the role has no grant on `awcms_domain_event_deliveries` (no consumer subscribes to the two job events; a delivery INSERT bound only by its own `event_type` let a role deliver another module's event to any consumer) and reads back only its own events; L1, a trigger (`awcms_social_publish_jobs_dedupe_flag_guard`) lets this role change `dedupe_key_supported` only while claiming a job, so it cannot mark an in-flight job dedupe-capable and re-queue it; L2, the start-up check requires `session_user` AND `current_user` to be the role; L3, `security:readiness` reports a dedicated-role probe that could not run as a warning; L4, Graph code 2 is `unknown` unless a 503 flags `is_transient`; L5, `reportPublishCredentialRejected` answers `recorded` only when it moved the account. The same M1 pattern on the Telegram dispatcher role is fixed by `sql/374`.
- **Residual risk once the switch is on** (ADR-0157 section 6, stated, not removed): a compromised `social-publishing:dispatch` can read and decrypt the publishing access tokens of every tenant, and can mark a live social account `degraded`.
- An unknown outcome (a timeout, a throw after the request was sent) is retried automatically only for an adapter that declares `supportsIdempotencyKey`; otherwise the job is `needs_reconciliation` and waits for an operator (`POST jobs/{id}/retry` with `confirmPossiblyPublished`, or cancel). The adapter HTTP client follows no redirects and is cancelled by the call's signal.
- **L6 closed:** every adapter declares an anchored `externalPostIdPattern` and its `postUrlHosts` (the registry refuses one that does not); a post id that does not match, or the identifier alphabet of `sql/359`, makes the outcome UNKNOWN (`INVALID_POST_ID`) and is never stored; a top-level `|` does not count as anchored; a URL on an undeclared host is dropped, and a kept URL loses its query and fragment.
- Audit residuals recorded, not fixed here (full text in ADR-0157 section 6): **L4** reads are not scoped per account or business scope (a `publications.read` holder sees unpublished captions and other brands' `accountId`s); **L9** `prepare` runs before `authorize`, the repository-wide route pattern, so an unauthorised caller can tell a 400 or 422 from a 403; **M-1/L-7** a connector declares `supportsIdempotencyKey` truthfully and answers `unknown`, not `retryable`, after any request that may have been processed.
