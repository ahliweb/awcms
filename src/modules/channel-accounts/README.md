# `channel_accounts`

The **account and credential control plane** of the omnichannel foundation (Issue #1140, [ADR-0148](../../../docs/adr/0148-omnichannel-foundation-is-five-gated-capabilities-with-fail-closed-per-account-capability.md) capability C1; design pack [`docs/awcms/omnichannel-foundation.md`](../../../docs/awcms/omnichannel-foundation.md); field encryption [ADR-0137](../../../docs/adr/0137-payout-account-encryption-at-rest-and-keyed-hashing.md)).

It holds a tenant's **connected external accounts** (a WhatsApp WABA phone number or StarSender device, a Facebook Page, an Instagram or Threads profile, a YouTube channel, a Telegram bot, a Mailketing ESP login and its sender identities), the **provider connections** behind them (OAuth 2.0 grants, API tokens, bot tokens, device keys), **per-account capability evidence**, **secret references**, webhook subscription metadata, health, and who may operate each account.

**It sends nothing and calls no provider.** There is no queue, no dispatcher and no provider HTTP call here. Provider adapters, the OAuth token exchange and publishing (#1145) are later issues; sender routing in `whatsapp_delivery` (#1141) has landed. The operator screen is `/admin/channel-accounts` (#1154, see below) that conform to this account model. A website's social links are not connected accounts.

Status: `active` and **off by default** (`CHANNEL_ACCOUNTS_ENABLED`; the screen then says it is switched off).

## Admin screen (#1154, ADR-0148 UP-08)

`/admin/channel-accounts` (list: filter, search, sort, keyset pager over at most 200 loaded accounts; provider connections; the provider matrix with why a provider has no Connect action) and `/admin/channel-accounts/{id}` (status, health and "last synced", provider authorisation, nine capability rows with their evidence state, unsupported ones shown disabled). Actions on the detail: replace credential (write-only password field, MFA and step-up, no "show"), disconnect and revoke authorisation (typed confirmation, queue impact for a sender) and make default WhatsApp sender. Every mutation goes through the existing API with an `Idempotency-Key`. Reads reuse the routes' own visibility rules (assignment gate, business scope). Claims `accounts.read`, `accounts.revoke`, `credentials.manage` and the two `whatsapp_delivery` sender keys.

**Not on the screen (recorded remainder of #1154):** the connect wizard (no provider connector exists, so `POST connections/oauth/start` answers `PROVIDER_ADAPTER_UNAVAILABLE` and a Connect button would mislead), registering or enabling an account (`accounts.create`), recording a capability grant (`capabilities.configure`), assigning operators (`assignments.assign`), and per-account health/capability summaries in the list (they would be an N+1; they are on the detail). A holder of `credentials.manage` who has not enrolled MFA sees no credential form and no explanation.

## The provider matrix (a code mirror)

`domain/provider-matrix.ts` is the code mirror of section 3 of the readiness pack (v1). `tests/channel-accounts-provider-matrix.test.ts` parses the documentation table and fails if any cell differs. A cell is `candidate`, `restricted` (usable only with `contract_reference` or `written_authorization` evidence), `not_offered`, `unverified`, `not_applicable` or `barred`. `GET /api/v1/channel-accounts/providers` serves it.

Nine rows are **phase-gated** (Issue #1152, pack §3.1): X, LINE Official Account, Pinterest and Google Business Profile (P3), Discord, Bluesky, Mastodon, Snapchat and Reddit (P4). They record what each provider's official documentation was read to say on 11 November 2026; they carry a `phase`, are not registrable, declare no account kind or authentication mode, and `cellGrantability` refuses every one of their cells (`PROVIDER_UNVERIFIED`) whatever the cell reads. The API returns the `phase` and the screen shows them as phase-gated, never with a Connect action. A provider leaves its phase only through its own admission ADR. Adding them changed no existing cell, so `PROVIDER_MATRIX_VERSION` stays 1.

`AccessAction` is a closed vocabulary shared by every module, so the pack's working names map onto it: connect to `create`, disconnect to `revoke`, `capabilities.grant` to `capabilities.configure`, `assignments.manage` to `assignments.assign`. The pack's `channel_accounts.senders.use` is **still not seeded**: the port performs no access check (the consumer authorises its own business action, ADR-0011), so nothing could enforce it. The `whatsapp_delivery` sender permissions (`senders.read`, `sender_policy.configure`) are seeded by `sql/323` with their routes (#1141).

Every mutation except the OAuth start and callback requires `Idempotency-Key` (a keyed-HMAC request hash; the response is stored redacted). Every route refuses a machine credential (`403 INTERACTIVE_SESSION_REQUIRED`) and answers `503 CHANNEL_ACCOUNTS_DISABLED` unless the deployment enables the module.

## Per-account access

Three layers, all default-deny: the tenant-wide permission; the **assignment** gate (by the account's explicit `access_mode`, below: an `assigned` account is visible and operable only to its assignees at the required kind, plus holders of `assignments.assign`); and **business-scope ABAC** (an account bound to a scope requires the caller to hold it, re-evaluated through the same chokepoint, so a deny policy and the decision log both apply). Connection break-glass belongs to the holder of the connection's scope and to the tenant administrator (`assignments.assign` as decided by the chokepoint, not derived from holding a scope; ADR-0148 amendment, #1215).

## OAuth

`POST oauth/start` creates a single-use `state` (256 random bits, stored only as a SHA-256, bound to tenant **and** person, 10 minutes) and, where the adapter offers PKCE, an S256 challenge whose verifier is held as ciphertext. The redirect URI is the deployment's fixed callback and is **never an input**. It needs a registered `ChannelOAuthAdapter` (`application/oauth-adapter-registry.ts`, one pure function that builds the authorisation URL); none is registered by this issue, so it answers `422 PROVIDER_ADAPTER_UNAVAILABLE`.

`GET oauth/callback` is authorised like any call (it carries the session). It verifies the `state` (exists, unexpired, unconsumed, this tenant, this person, this redirect URI; **every** failure is `400 STATE_INVALID`), consumes it by compare-and-swap, and leaves a **durable hand-off**: a `pending` connection holding the authorisation code as ciphertext. It does not exchange the code, because that is provider I/O and must not run inside a request transaction (ADR-0148 I10). The connector's job finishes the grant with `activateConnectionGrant` (or `failConnectionGrant`).

Refresh is guarded by a **lease** (`acquireRefreshLease`, a compare-and-set on the connection row: of N racers one wins), `completeRefresh` accepts only the holder's lease version, and `failRefresh` backs off exponentially (bounded) or, on a permanent failure, expires the grant and degrades its accounts. A revoked grant is terminal (trigger-enforced), clears and deletes its credentials, and revokes its accounts.

## Secrets

`SecretStorePort` (`application/secret-store.ts`) has one adapter, the application key ring: `CHANNEL_SECRETS_ENCRYPTION_KEYS` (`keyId:base64` pairs, the first key writes, all read, 32 bytes each, no default, no plaintext fallback, outside the database and its backups). A KMS or vault adapter can replace it without changing a caller. The only method that returns plaintext, `resolve`, is for connectors and dispatchers of later issues; `tests/channel-accounts-secret-handling.test.ts` holds that no route imports it. Each resolution is counted per tenant and purpose (`snapshotSecretDecryptCounts`) for the dispatcher's alerting. A restore without the ring fails closed.

**Rotation:** prepend a key, deploy, run `bun run channel-accounts:secrets:rekey` (idempotent, resumable, batched, race-safe; runs as `awcms_app`), verify nothing is left under the old key id, and only then remove it. The job exits 1 without a ring, 2 when a tenant did not finish, 3 when rows cannot be decrypted.

## Provider risk acknowledgements and device attestation (Issue #1142)

[ADR-0148](../../../docs/adr/0148-omnichannel-foundation-is-five-gated-capabilities-with-fail-closed-per-account-capability.md) section 7: StarSender is an **unofficial** WhatsApp gateway, so its use needs a recorded **acknowledgement of the risk** by an accountable person. Table `awcms_channel_provider_risk_acknowledgements` (`sql/340`, RLS `FORCE`): provider, person, time, **text version and the SHA-256 of the exact words shown**, revoked by a stamp. It is append-only apart from that stamp (trigger), never deleted, never purged by age, and one **active** row per person, provider and version makes a double submit a no-op.

- **The text is a human decision, so it ships unapproved.** `domain/risk-acknowledgements.ts` carries the StarSender wording (English and Indonesian) with `approval: null`: until the business owner approves it in a reviewed change, `POST` answers `409 RISK_TEXT_NOT_APPROVED`, nothing can be acknowledged and no device can be connected. A new `textVersion` invalidates every earlier acknowledgement.
- **A person acknowledges for themselves.** The body names the provider and the text version shown and has no field to name anyone else; a stale version is `409 RISK_TEXT_VERSION_STALE`. A machine credential is refused.
- **The database is the net under the application.** A `starsender` account cannot be inserted as, or moved to, `connected` while the tenant has no active acknowledgement (`awcms_channel_accounts_risk_ack_guard`). The application additionally checks the **current approved version** in `ChannelAccountPort` (before the account status, so a revocation is terminal rather than a hold) and again in `ChannelSenderCredentialPort` before decrypting a device key.
- **Revocation** stamps the row; revoking the tenant's **last** active acknowledgement degrades its `connected` devices of that provider in the same transaction (`RISK_ACK_REVOKED`), and a degraded device cannot come back without a new acknowledgement.
- **A device is bound to the acknowledgement it was attested under** (`attested_acknowledgement_id`, `sql/340`): revoking THAT acknowledgement degrades it even while the tenant holds another, and revoking the tenant's last one degrades every device of the provider. "Is this the last one?" is a question about a set, so a revocation first locks every active acknowledgement of (tenant, provider) `FOR UPDATE` in id order, and an attestation reads the one it relies on `FOR SHARE` before it locks the account: two concurrent revocations, or an attestation racing a revocation, can no longer leave a `connected` device with no active acknowledgement (proved with interleaved transactions in `tests/integration/starsender-adapter.integration.test.ts`).
- **Replacing a device key demotes the device** (`PUT .../credential` on an unofficial-provider account that is `connected` or `degraded` moves it to `pending`, `CREDENTIAL_REPLACED`, in the same transaction): the attested state is a claim about that key.
- **Acknowledging and attesting need a fresh step-up from a person who has an MFA factor** (conditional, the same rule as the credential route, ADR-0141); a person with no factor is not locked out and no enrolment is imposed.
- **Attestation, not verification.** Account health is reported by connectors and never asserted by a person, with ONE recorded exception: StarSender documents no side-effect-free status call, so `POST accounts/{id}/attest-device` lets an operator who holds their **own** active acknowledgement attest that a device is paired (stored credential, `pending` or `degraded` account, `WHATSAPP_STARSENDER_ENABLED=true`). Health reads `OPERATOR_ATTESTED`; the response says `basis: operator_attested`. If StarSender evidences a status call a connector replaces it.
- The worker (`awcms_worker`) holds column-only `SELECT` on `(id, tenant_id, provider, text_version, revoked_at)` and nothing else of this table.

## Meta WABA binding and signed webhooks (Issue #1143)

- **A Meta number belongs to a WABA.** `ChannelAccountPort.resolveWhatsappSender` (capability `channel_account` 1.4.0) answers `CONTAINER_BINDING_INVALID` (terminal) for a `whatsapp_cloud` `waba_phone_number` whose parent is not a live `waba` container of the same provider, whatever its auth mode, and returns the container's account id and WABA id with a usable sender. A degraded, pending, revoked or disabled container answers its own status reason.
- **`POST /accounts/{id}/webhook-subscription`** (`webhooks.configure`, high-risk: the `owner` assignment on the number AND on its WABA container, `whatsapp_delivery.meta_templates.configure` AND `whatsapp_delivery.meta_signals.configure` too, because the subscription can feed that WABA-level state (security review M-1), conditional step-up, `Idempotency-Key`, `warning` audit with no secret, token or external id; the app secret is not verified with Meta): stores the Meta app secret write-only (purpose `webhook_signing_secret`) and mints an opaque callback token `wcb1.<tenant>.<subscription>.<256 random bits>` that is shown ONCE (`revealed: true`; a replay answers without it). Only its SHA-256 is stored in `awcms_channel_webhook_subscriptions.callback_token_hash`. A new subscription revokes the number's earlier ones and erases their secrets.
- **`ChannelWebhookVerifierPort`** (`application/webhook-subscription-directory.ts`) is what `whatsapp_delivery`'s public webhook asks, in the tenant transaction the token names: token hash (constant time, against a dummy when no row matches), an `active` `hmac_signature` subscription, a live Meta number with a live WABA, and `X-Hub-Signature-256` over the exact bytes (constant time). The app secret is decrypted by the APPLICATION role only; the worker policy of `sql/328` still hides every `webhook_signing_secret` from `awcms_worker`.
- `disconnect` and `delete` revoke the account's subscriptions AND hard-delete their signing-secret ciphertext, like rotation (security review M-3).
- Not done: a screen for the subscription (`webhooks.configure` is in `NOT_YET_SCREENED`).

## Retention and data-subject answers

Each table answers both questions in the same change. `subjectData` descriptors are in `module.ts` (stamp-only tables are `severed_with_subject_row`; assignments are exportable and hard-deleted on erasure; the health table is a reasoned `NO_SUBJECT_DATA`). Retention is a reasoned `BOUNDED_BY_DESIGN` entry per table: every table is bounded by authorship, a unique key, or the bounded sweep `sweepExpiredOAuthStates` that runs on the write path of an OAuth start (it deletes expired unreferenced states with their verifier ciphertext and fails abandoned hand-offs). A delegated lifecycle descriptor was rejected because it would have needed an `awcms_worker` read grant on a control-plane table. Since #1141 the one worker that decrypts a sender's credential (`whatsapp:dispatch`) holds **column-only, read-only** `SELECT` on exactly the columns sender resolution needs (`sql/322`): no display name, actor stamp, refresh-token, OAuth-state, authorisation-code or webhook column, and no write of any kind; no other worker role holds any privilege on these tables.

## Known limits

- No provider adapter, token exchange, refresh call, health check or webhook receiver exists yet; `recordAccountHealth` and `activateConnectionGrant` are the entry points those issues call.
- No domain events (`channel.account.*`) are published: there is no consumer, and the contracts outline leaves them to the issues that need them.
- **`ChannelAccountPort` and `ChannelSenderCredentialPort` are exported since #1141** (`_shared/ports/channel-account-port.ts`, capability `channel_account` 1.0.0; first consumer `whatsapp_delivery`). `application/channel-account-port-adapter.ts` answers "may this account send now?" through the same `evaluateCapability` and returns metadata only (it never imports the secret store); `application/channel-sender-credential-adapter.ts` is the one place a sender's credential is decrypted, composed only by the dispatcher's composition root. Both are fail-closed and tenant-scoped (another tenant's account and an unknown id are one answer, `ACCOUNT_NOT_FOUND`).
- The key ring must contain a different key from every other module's ring (`config:validate` checks the Telegram, push and WhatsApp recipient-hash rings).

## Binding scope rule (#1215)

An account lends its connection's token to everyone who can act on the account, so **the account's business scope must be contained in its connection's scope, with no administrator exception**:

| connection \ account | tenant-wide | scope A | scope B |
| -------------------- | ----------- | ------- | ------- |
| tenant-wide          | allowed     | allowed | allowed |
| scope A              | refused     | allowed | refused |

"Contained" is **exact `(type, id)` equality** for a scoped connection; the business-scope hierarchy (ADR-0060) is not consulted (most restrictive, fail-closed reading; see open questions). A refusal answers like an unknown connection (`422 CONNECTION_NOT_FOUND`). The check runs before every authority check, so the tenant administrator is bound by it too. Authority comes after containment: a connection with no account yet is bound only by its creator or by break-glass (the same authority as revoking it); one with accounts needs `owner` authority over all of them, which only the tenant administrator skips. The `account.create` audit row carries the internal `connectionId` (a UUID).

`canSeeAllAccounts` (the administrator bypass) requires `assignments.assign` through a **tenant-wide grant** (`scope_type = 'tenant'`) as well as the chokepoint's allow: ADR-0080 keeps a scoped grant's keys tenant-level at the chokepoint, so without this a grant confined to one office would act as the administrator of all of them. The grant writer only writes `tenant` today; this is the **binding requirement for the PR that adds a scoped-grant writer** (`holdsTenantWidePermissionKey`, pinned by `tests/integration/channel-accounts-api.integration.test.ts`, LOW-1).

A caller is **scope-confined** (`callerIsScopeConfined`) while they hold an active, non-tenant business-scope assignment that has not ended, **including one that has not started yet** (Issue #1171, fail-closed). Every reader of that answer shows or allows less when it is `true`. The assignment's `effective_from` is stamped by the database clock in microseconds and was compared with the request's millisecond `new Date()`, so a request made within a millisecond of the grant (or on a host whose clock lags the database) treated a just-confined caller as tenant-wide and showed them every brand's rows of a tenant-wide sender. Which scopes actually COVER rows is still decided at the chokepoint, which honours `effective_from`: until a pending confinement starts the caller sees the rows of no brand, not of every brand.

Connection break-glass asks the tenant-level question first (one memoised decision per request); only a caller who is not the administrator pays per-scope decisions, and only for the distinct scopes asked about, not per connection.

`APP_URL` is required when the module is enabled and is the only source of the OAuth callback origin: `resolveChannelOAuthRedirectUri` returns `null` (start answers `PROVIDER_ADAPTER_UNAVAILABLE`, callback `STATE_INVALID`) instead of falling back to a built-in host, and `config:validate` refuses to boot the deployment (#1215 L7).

## Access mode and the last owner (#1215 M-c, owner decision of 11 November 2026)

Visibility used to be inferred from the **absence** of rows (no assignee meant open to the whole tenant), so removing the last assignee, or erasing the person who was it, silently opened a sender identity. It is now a column, `awcms_channel_accounts.access_mode` (`sql/398`), and the default is the closed one:

| `access_mode`        | Who sees and operates the account                                                                                                  |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `assigned` (default) | its assignees (at the kind the action needs) and the holders of `assignments.assign`; with no assignee at all: administrators only |
| `tenant_wide`        | the permission alone decides (the old "no assignee" behaviour), chosen on purpose and audited                                      |

- A new account is `assigned` and its **creator becomes its first owner** (`createAccount`), so registering an account does not hand it to administrators only. Every row that existed when `sql/398` ran became `assigned` (fail-closed; the module ships off).
- `PUT /accounts/{id}/access-mode` (`assignments.assign`, `Idempotency-Key`) switches the mode; the audit row (`channel_accounts.account.access_mode_set`, `warning`) is written only when it changes. Switching to `assigned` needs an owner to exist (`422 OWNER_REQUIRED`).
- **The last owner of an `assigned` account cannot be removed or demoted** through the API (`409 LAST_OWNER`). The writers take the account row lock first, so two concurrent removals of two owners cannot each see the other remain. The database is the second wall (`sql/398` refuses an unowned switch to `assigned`; `sql/399` refuses demoting the last owner and an assignment's re-pointing).
- **Erasure must always complete**, so deleting the last owner is NOT refused in the database: `sql/399` instead leaves one `warning` audit row, `channel_accounts.account.owner_orphaned`, carrying the account id only (never the person). The account stays fail-closed: it is reachable only by its remaining assignees (the viewers and operators that are left) and the tenant administrators, who can name a new owner. (The two owner-counting guards SHARE-lock the owner rows, so an erasure racing a demotion or a mode switch waits for it and always leaves this trace when it orphans an `assigned` account.)
- `awcms_channel_accounts.business_scope_*` is now immutable for every role (`sql/398`, the same identity guard as the account's identity).
- Every other module that asks "may this caller use this account?" (`whatsapp_delivery`, `email`, `social_publishing`, `telegram_engagement`) goes through `isAccountVisibleTo`, so they inherit the rule; none re-implements it. `omnichannel_inbox` does **not**: it sends nothing, so it only applies the business-scope rule, and a holder of the inbox permission within the same scope still sees the conversations of an `assigned` account. Making conversations follow assignment would be a separate owner decision.

## Residual items and open questions (#1215, owner decisions)

Not done here; each needs an owner design decision and, for most, a migration:

- **External-id squatting** (M4 of the first review): a `pending` row already holds the global `(provider, external_id)` claim. Needs verified claims or claim expiry, i.e. a platform-scoped job. Deliberately NOT built: the options are written up on #1215 for the owner to choose.
- **N2** (OAuth state sweep runs only on the next start), **N3** (`LIMIT 200` lists without a cursor), and L5/L6 as described in the issue (small inconsistencies, the documented cross-tenant oracle).
- **Hierarchy containment**: should a child scope (an office under a region) be allowed to bind a parent scope's connection? Exact equality was chosen; relaxing it is an owner decision.
- `sql/318` carries a stale comment (N10) that cannot be edited in an applied migration; the accurate statement is this README and ADR-0148.
