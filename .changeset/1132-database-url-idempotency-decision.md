Decide the last two over-wide job secret grants (Issue #1132, rows 5-6). `DATABASE_URL`, the `awcms_app` login, is now withheld by `ops/run-job.sh` from every job that never opens the app connection whenever the app container has a non-blank `WORKER_DATABASE_URL` (the worker client falls back to `DATABASE_URL` only when that is blank, so a host without a worker role behaves as before). Which targets keep it is derived by `appConnectionTargets()` in `scripts/jobs-env-allowlist.ts` from each target's import closure (a call to the app or setup client, the name spelled out, or anything the tracer cannot follow) and written into a generated block of `run-job.sh` that `jobs:env-allowlist:check` holds current; no scheduled job keeps it, the one-off scripts that run as `awcms_app` on purpose (`telegram:chat:rekey`, `blog:legacy:*`, the backfills) do. `IDEMPOTENCY_HMAC_SECRET` stays global by a recorded decision: the only request-hashing code reachable from a scheduled job is booking's `BookingPort` adapter, which the module registry imports and a consumer's job is meant to call, so a file-level trace cannot separate callers from loaders; a missing key is loud (production throws), and `tests/jobs-env-scoped-reach.test.ts` now pins the fact the decision rests on and the accepted residual risk is written in `GLOBAL_SECRETS` and `deploy-coolify(.id).md`. `jobs:env-allowlist:check` and `:generate` join `OPERATOR_ONLY_TARGETS` (tooling), because they now trace every target.

**Operator action:** replace `ops/run-job.sh` on the host with the one from this release (the env files are unchanged); the image-drift check refuses to run jobs until the host copy matches the image. After that, jobs on a host with `WORKER_DATABASE_URL` set run without `DATABASE_URL` in their container and the job log says `DATABASE_URL withheld from <job>`. A job that unexpectedly needed the app login would fail loudly at connect time (`DATABASE_URL is required`), never silently, and the derivation errs toward keeping the login.
