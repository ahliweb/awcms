security(hr_payroll): mutation results are masked, and the payroll catalog check runs daily (Issue #1095, owner decision K3; the residuals 1 to 7 stay "narrowed"). BREAKING (MAJOR per the SemVer policy of `docs/awcms/09_roadmap_repository_commit.md`: an incompatible change to the public API contract): `POST /api/v1/hr-commission/accruals` and `POST /api/v1/hr-commission/accruals/{id}/approve|release|pay|void`, and the in-process `CommissionAccrualPort`, no longer return the accrual. They return a masked receipt (status edge, rule key and version, currency, `sourceType`, `calculation`, `occurredOn`, timestamps, `masked: true`; OpenAPI `HrCommissionAccrualMutationReceipt`, `additionalProperties: false`) and never the amount, the beneficiary, the source reference or the payment reference, which are readable only through the audited `GET /accruals[/{id}]`. The body stored for the Idempotency-Key is the same receipt, and a replay of a body stored before this change is projected onto the receipt keys, so an old full body never leaves the database again. A replay of `POST /accruals` is no longer a read of anyone's earnings and no longer writes a read audit. A client that read `amount`, `employmentId`, `sourceRef`, `rate` or `paymentReference` from one of those responses must read them from `GET /accruals/{id}`. Capability `commission_accrual` is 2.0.0 (the port record lost `amount` and `employmentId`; nothing in this repository consumes the port). The `auditExemptImporters` exemption for the four mutation routes and the adapter is removed; `sensitive-reads:check` now fails when a write-path importer stops calling its mask (`maskedResultImporters`), and `voidCommissionBySource` is a guarded write-path function. New job `payroll:catalog-boundary:job` (daily 03:17, `hr_commission` registry) reads the catalog of the deployed database as the new least-privilege role `awcms_catalog_boundary_audit` (`sql/420`, `NOLOGIN` and `NOINHERIT` until the operator grants LOGIN; CONNECT and catalog views only, no table privilege), a dedicated-role job like `social-publishing:dispatch`: login only through `PAYROLL_CATALOG_AUDIT_DATABASE_URL` (job-scoped, no fallback, the runner withholds the shared URLs; set in the app service's environment, which is where the runner copies from). Every outcome is a structured repo-logger line: one `error` line per finding, exit 1; a split-role deployment without `PAYROLL_EXPECTED_OWNERS` is named; not activated (URL unset) logs `SKIPPED (not activated)` and exits 0; a URL that is set but wrong is refused (exit 1). `security:readiness` pins the role (critical: no table or column privilege, no EXECUTE on any SECURITY DEFINER function, NOINHERIT, no membership, owns nothing) and warns while it is not activated. Runbook: `docs/awcms/payroll-catalog-boundary-job.md`.
