feat(identity-access): passkey groundwork — principal-owned recovery codes and a recorded step-up method (Issue #1405, ADR-0168 slice S2). No passkey endpoint, screen or flag is added; this changes only what the later slices stand on.

- **A1, `sql/442`:** recovery codes belong to the principal, not to the TOTP factor that was enrolled when they were issued. `factor_id` and its `ON DELETE CASCADE` are dropped; a code is spendable while the principal has an active factor of any type; the set is replaced on first-factor enrolment and on regenerate and deleted only when no factor is left (self-service disable, administrative reset). The migration first deletes every code that could not be spent before it ran (codes of a pending or disabled factor, or of a factor belonging to another principal) and keeps every other code untouched, `used_at` included, so no dead code comes back and no valid one is lost. `identity:principal-access:check` no longer accepts `factor_id =` as a key.
- **A2, `sql/443`:** `awcms_sessions` and `awcms_session_handoff_codes` gain `stepped_up_method` (`totp`, `recovery_code`, `passkey`; NULL exactly for `aal1`, enforced by a CHECK) and `stepped_up_passkey_id`. Every issuer writes the method of the credential that actually matched: the login challenge (TOTP or recovery code), enrolment completion (TOTP), handoff redemption (snapshotted when the code was minted) and `POST /auth/mfa/step-up`, where a refresh replaces the previous method. `createSessionWithAssurance` now takes a `SessionAssuranceGrant`, so an `aal2` session cannot be minted without its proof. Live `aal2` rows are backfilled `recovery_code`, the weakest method consistent with the evidence, behind the `NO FORCE` toggle so the backfill reaches every tenant.
- **Fail closed until the credential table exists:** `stepped_up_passkey_id` has no FK yet, so `awcms_sessions_passkey_step_up_unavailable` (and its handoff twin) refuse any passkey step-up; the slice that creates `awcms_principal_passkeys` adds the FK and drops the constraint in one migration.
- **Q7:** `awcms_sessions.origin_auth` admits `passkey`. Nothing produces it (passwordless login is not in the first release), and it is listed in `NON_SWITCHABLE_ORIGIN_AUTH` until the A4 target-tenant check exists.

Behaviour visible today: none for TOTP users beyond the internal method stamp; recovery codes keep working exactly as before for every principal with an active factor.
