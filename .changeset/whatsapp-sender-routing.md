feat(whatsapp_delivery): sender-aware routing on the one WhatsApp queue (Issue #1141, ADR-0148 section 4). A message can now be sent through a tenant-owned `channel_accounts` sender (a WhatsApp Cloud API phone number of the tenant) instead of the single deployment sender. **Nothing changes for a deployment or tenant that configures no sender**: `senderAccountId = null` IS the deployment sender, and it takes the same path, the same provider, the same credential and the same event payload as before.

`WhatsappDeliveryPort` is versioned `1.0.0` to `1.1.0` additively (capability `whatsapp_delivery` is now registered in `capability-contract-versions.ts` and `awcms-family-compatibility.yaml`): three OPTIONAL `enqueue` inputs (`senderAccountId`, `inReplyToMessageId` for thread affinity, `businessScope`) and three new refusal reasons (`SENDER_UNAVAILABLE`, `SENDER_AFFINITY_CONFLICT`, `REPLY_TARGET_UNKNOWN`). Existing consumers (`booking`, and the commerce adapter behind `awcms-one`'s `legacy`/`upstream` mode router, ADR-0047) compile and behave unchanged; the only thing a consumer that switches exhaustively over the refusal reasons must do is add the three members before it passes a sender.

**Sender selection** (pure, snapshotted on the row, never rotated): the explicit sender, else the thread's sender (reply), else the prospective default of the message's business scope, else the deployment sender. The default is a per-scope policy with a configuration version (`awcms_whatsapp_sender_policies`, `PUT /api/v1/whatsapp/sender-policy`, high-risk: `whatsapp_delivery.sender_policy.configure`, `Idempotency-Key`, audited at `warning`); a change affects later messages only. There is no provider default in code. A sender that is unknown, another tenant's, revoked, disabled, disconnected, unapproved or without an adapter is `refused: SENDER_UNAVAILABLE` at enqueue and a terminal `sender_unavailable` failure at dispatch, never another sender, number or provider; a sender that is only degraded or pending, or whose key ring is missing, is held (rows wait, retry budget untouched). The adapter and the credential come from the tenant's own sender record, never from the request: no input carries a token, a phone number id or a device id, and the policy body rejects any such key.

**Schema (`sql/322`, `sql/323`)**: `awcms_whatsapp_messages` gains `sender_account_id` (nullable, immutable, composite tenant FK to `awcms_channel_accounts`), `sender_selection`, `sender_policy_version` and the business scope pair, with an immutability trigger and a live-sender insert guard; one new tenant-scoped table (`FORCE` RLS) and two permissions (`senders.read`, `sender_policy.configure`). No second queue and no dual write.

**Dispatcher**: per-sender lanes with fair claiming, a per-sender circuit breaker, hourly and daily caps counted from what the sender really sent (`WHATSAPP_SENDER_RATE_PER_HOUR`, `WHATSAPP_SENDER_RATE_PER_DAY`, both new, defaults 1000 and 10000) and per-sender diagnostics (`GET /api/v1/whatsapp/senders`). Consent, suppression and the recipient rate limits stay keyed by the recipient, never the sender. `whatsapp:dispatch` now decrypts a tenant-owned sender's credential in memory, per lane, for the claimed row's tenant: it is granted `CHANNEL_SECRETS_ENCRYPTION_KEYS` (job-scoped, regenerate `ops/awcms-jobs.env-*`) and column-only read grants on four `channel_accounts` tables in `sql/322` (the residual risk ADR-0148 section 5 accepts). A deployment that runs the dispatcher through `ops/run-job.sh` must redeploy the regenerated env files together; one that does not use tenant-owned senders needs no key ring.

The channel module is off by default (`CHANNEL_ACCOUNTS_ENABLED`) and a StarSender sender cannot be used until its adapter (Issue #1142) lands; both fail closed.
