Close the host/image drift gap in per-job secret scoping (Issue #1131, part L5). The `jobs` stage of `Dockerfile.production` now ships `ops/run-job.sh`, `ops/awcms-jobs.env-global` and `ops/awcms-jobs.env-scoped` at `/home/bun/app/ops/` (variable names and `<job> <VAR>` grants only, never values, so no secret enters the image). Before it starts any job container, `ops/run-job.sh` compares the SHA-256 of its own host copies (itself and both env files, honouring `AWCMS_JOBS_ENV_GLOBAL` / `AWCMS_JOBS_ENV_SCOPED`) with the image's through one `docker run --rm --network none --entrypoint sha256sum`, and refuses with exit 1 on any difference, an unreadable host file, or an image that lacks the files. Previously a newer `:latest` image could read a scoped secret in a job the host's older scoped file did not grant, and the job ran without it and reported success. There is no bypass switch; the `# awcms-jobs-env-fingerprint:` pair check is unchanged and still runs afterwards. `tests/jobs-image-ops-files.test.ts` covers the Dockerfile copy, the names-only property and the runner against a stub `docker`.

**Operator action:** this is a one-time bootstrap and then once per release that changes `run-job.sh` or either env file. Pull the new jobs image, then install its copies next to `run-job.sh` on the host (write each to a temporary file and `mv` it into place) with `docker run --rm --entrypoint cat <image> /home/bun/app/ops/<file>` for `awcms-jobs.env-global`, `awcms-jobs.env-scoped` and `run-job.sh`, as spelled out in `docs/awcms/deploy-coolify.md`. Do it before the new image becomes the one cron pulls: until the host files match, every job refuses to run (fail closed). A rollback pin of `AWCMS_JOBS_IMAGE` needs the host files of that image too. A legacy local build from `$AWCMS_JOBS_CONTEXT` is refused unless its context was built from this release's `Dockerfile.production`.
