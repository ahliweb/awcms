fix(auth): `/login` now has the pre-session enrolment step (Issue #1425). When a tenant's MFA policy requires a second factor and a user with a correct password has none yet, `POST /api/v1/auth/login` answers `401 MFA_ENROLLMENT_REQUIRED` with an enrolment grant, and the page showed the generic failure, so the person was locked out without an administrator. The page now calls `enroll/start` with the grant in `X-AWCMS-MFA-Enrollment-Token`, shows the secret as a locally encoded QR (the same renderer `/admin/account` uses, made addressable through an optional `targets` argument) plus the manual key, confirms with a 6-digit code through `enroll/verify`, shows the recovery codes once, and continues to `/admin` on the `aal2` session that call mints. The grant lives only in script memory (never storage, URL or DOM) and the QR and key are wiped when the step ends or the page is left. Anti-oracle: after the password step the page distinguishes only `success`, `MFA_REQUIRED` and `MFA_ENROLLMENT_REQUIRED`; a refused start or an exhausted attempt budget returns to the password step with one generic sentence. Seven new msgids in the `login` context (en/id). The QR encoder is a separate chunk loaded by dynamic `import()` only when enrolment starts, so a normal sign-in does not download it (a failed chunk load returns to the password step); `APP_BUDGET_BYTES` rises 388,085 -> 392,355 (measured 392,215 B, a total over all files).
