Add the `channel_accounts` module, the account and credential control plane of the omnichannel foundation (Issue #1140, ADR-0148 capability C1). A tenant now has a registry of connected external accounts (WhatsApp WABA phone numbers and StarSender devices, Pages, profiles, channels, bots, Mailketing ESP logins and their sender identities), unique per live `(provider, external id)` across tenants, with a brand expressed as a business scope. Provider connections cover OAuth 2.0 (single-use state bound to tenant and person, S256 PKCE where the connector offers it, a fixed server-side redirect URI, a verified callback that leaves a durable hand-off, a refresh lease with bounded backoff, terminal revocation; a connection carries the business scope it was started for, and that scope is the authority to bind accounts to it or revoke it) and API-token, bot-token and device-key connections. Capability is fail-closed per account and evaluated against a code mirror of the provider matrix v1 that a test holds equal to `docs/awcms/omnichannel-foundation.md`. Credentials are stored only as AES-256-GCM ciphertext references through a `SecretStorePort` (ring `CHANNEL_SECRETS_ENCRYPTION_KEYS`), written through a write-only, MFA-gated, step-up, idempotent, warning-audited endpoint, and never returned, logged or audited. Migrations `sql/318` to `sql/320` add eight tenant tables with FORCE RLS, six permissions and integrity triggers. `bun run channel-accounts:secrets:rekey` re-encrypts after a key rotation. The module is `experimental`, sends nothing, has no screen (Issue #1154) and is off unless `CHANNEL_ACCOUNTS_ENABLED=true`.

**Operator action:** none for existing deployments (inert). To enable it, set `CHANNEL_ACCOUNTS_ENABLED=true` and a `CHANNEL_SECRETS_ENCRYPTION_KEYS` ring that shares no key with another ring, enable MFA enrolment (the credential permission requires it), enable the module per tenant, and run `bun run identity-access:permissions:backfill` for tenants created earlier.
