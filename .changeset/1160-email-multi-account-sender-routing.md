feat(email): tenant-scoped multi-Mailketing accounts and verified sender routing on the single email queue (Issue #1160, ADR-0151 section 2). **Nothing changes for a deployment that does not set `EMAIL_SENDER_ROUTING_ENABLED=true`**: the single-account env path (`EMAIL_MAILKETING_API_TOKEN`, `EMAIL_FROM_ADDRESS`) keeps working byte for byte, a named sender is refused (`409 SENDER_ROUTING_DISABLED`) and no tenant-sender row is ever claimed.

**Model.** A Mailketing account is a `channel_accounts` `mailketing`/`esp_account` whose API token is an envelope-encrypted `channel_secrets` row; each verified from-address is a child `mailketing`/`sender_identity` that borrows its parent's token only while the parent is `connected`. No second queue, no per-account dispatcher, no token in settings JSON or the browser.

**Enqueue.** `awcms_email_messages` gains an immutable, nullable `sender_account_id` plus a snapshot of the verified address, display name, selection (`deployment`/`explicit`/`policy`), policy version, business scope and `purpose` (`transactional`/`security`; `sql/346`). `NULL` is the deployment sender. A trigger refuses, for every role, a sender that is not a connected Mailketing sender identity of the row's own tenant, a snapshot address that is not the account's, a scope mismatch, a tenant sender on security mail, and any later change of the snapshot. `POST /api/v1/email/announcements` takes optional `senderAccountId`/`businessScope` (needs the new `email.senders.use`); the prospective default per business scope is `PUT /api/v1/email/sender-policy` (`email.sender_policy.configure`, high-risk, idempotent, audited at warning; never deleted); `GET /api/v1/email/senders` (`email.senders.read`) shows availability, queue and quota, never a credential. Security mail always uses the deployment sender.

**Dispatch.** The deployment lane is unchanged. Each tenant sender is its own lane: re-resolved every pass for the row's tenant, held when its verification or its account's credit is stale, unknown or below `EMAIL_MAILKETING_CREDIT_FLOOR`, claimed under a per-sender hourly cap (`EMAIL_SENDER_RATE_PER_HOUR`, advisory lock), sent through Mailketing v2 with that account's token decrypted in memory and that account's own circuit breaker, from the row's snapshotted address. Holds are bounded (`SENDER_HOLD_BUDGET_EXCEEDED`); revoked, disabled or foreign senders fail (`SENDER_UNAVAILABLE`). No automatic rotation across senders or accounts. `sql/348` lets `awcms_worker` see a Mailketing token only as the own credential of a live `esp_account` and grants it six read-only health columns.

**Verification.** New hourly job `bun run email:senders:verify` reads `GET /api/v2/credits` and `GET /api/v2/senders` per account and records health: a sender becomes `connected` only when the provider lists it as verified. The response shapes of these two endpoints are **not verified against the live API**; the parsers are fail-closed. This repository does not create or verify domains at Mailketing (the documented API offers no such call).

`channel_account` capability goes `1.1.0` to `1.2.0` (additive email ports). New `AccessAction` `use`.

Operator action: run `bun run db:migrate` (`sql/346`-`sql/348`, forward-only) and `bun run identity-access:permissions:backfill` for existing tenants; schedule `email:senders:verify` hourly before turning routing on; redeploy the regenerated `ops/awcms-jobs.env-*` files (the key ring `CHANNEL_SECRETS_ENCRYPTION_KEYS` is now also granted to `email:dispatch` and `email:senders:verify`). The admin screens are #1162.

**Security review fixes (PR #1259 audit).** A child account (a Mailketing sender, a WABA number) is registered under a parent only by a caller who may operate the parent and only inside the parent's business scope; a parent lends its token only to a child whose scope it contains, at every lend; the `sql/346` guard refuses a sender borrowing from a non-containing account. `security:readiness` now pins the worker secret policy by its exact normalised expression and probes it behaviourally (seeded negatives, rolled back, as `awcms_worker`), and pins the email sender guard and policy no-delete triggers. The worker sees a Mailketing token only for a CONNECTED account. A policy-chosen tenant sender also needs `email.senders.use` and the channel-account access rules. Rows of a tenant sender waiting behind routing switched off, an open account breaker or a reached hourly cap fail after the hold budget. `GET /senders` entries that contradict each other are recorded as unknown; a verification is discarded when the account's token changed while it ran. A Mailketing sender identity never holds or uses a token of its own.
