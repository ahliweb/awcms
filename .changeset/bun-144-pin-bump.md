chore(bun): the pinned Bun version moves 1.4.3 → 1.4.4 (#1172) across every place that pins it — `package.json`'s `packageManager` and `@types/bun` (`^1.4.4`), the current-pin `setup-bun` steps in `ci.yml` (`quality`, integration, E2E), `changesets.yml` and `release.yml`, `Dockerfile.production`'s base image (`oven/bun:1.4.4`, index digest `sha256:1d22548f177f4ff38e0c15baa3c2c46c6c2060ba2d1bc573bb4720b407548f1d`), `deploy/cron/awcms.crontab`'s job runner image, `scripts/ci-local.ts` `CI_BUN_CURRENT` (+ `tests/ci-local-parity.test.ts`), and `awcms-family-compatibility.yaml` — plus the EN/ID docs that name the current pin (family-compatibility, ci-local, implementation blueprint, ADR-0032). `bun.lock` is regenerated through Bun 1.4.4. The `engines.bun >=1.3.0` floor and the CI `minimum-supported` cell deliberately stay at 1.3.0 (a separate ADR-0032 support-contract decision). The `apt-get upgrade` step in `Dockerfile.production` is kept; the 1.4.4 image was inspected and already ships perl-base 5.40.1-6+deb13u1 (the #833 CVE fix), so the three CVEs are not present in it.

Bun 1.4.4 behaviour change found by the DB-backed integration suite: a raw transaction-control statement (`BEGIN;`/`COMMIT;`) sent through `unsafe()` on a POOLED client now throws `ERR_POSTGRES_UNSAFE_TRANSACTION` ("Only use sql.begin, sql.reserved or max: 1"). The one place that did so — `tests/integration/access-policy-equivalence.integration.test.ts`, which re-runs `sql/103` (the file carries its own `BEGIN`/`COMMIT`) — now runs it on a reserved connection (`sql.reserve()`). No production code path sent raw `BEGIN` through a pooled client.
