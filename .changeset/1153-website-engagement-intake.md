Add the `website_engagement` module: tenant-scoped website lead and contact capture and inbound website interaction events, INTAKE ONLY (Issue #1153, ADR-0155). One public, unauthenticated-by-design `POST /api/v1/website-engagement/submissions` authenticated by an opaque per-source token (a keyed hash at rest, shown once, rotatable, revocable; the tenant is opened from the token and a body or query tenant id is never believed) and by the verified Origin host against the domains registered for that source, so three websites and two domains under one tenant each accept exactly their own hosts. Rate-limited per address and per source (the per-source ceiling is spent only after the token is proven), an optional Turnstile challenge verified against the request's own Origin host that fails closed where required and is recorded per submission, a closed versioned field set (no HTML, no upload, no URL fetch, no inferred identity, no IP/fingerprint/cookie stored), idempotent on `(source, eventId)` with one uniform refusal before proof. Contact details are one AES-256-GCM envelope with keyed hashes and masked projections; consent provenance is explicit (separate, never-implied marketing purpose against the exact consent copy version shown). The outward contract is the outbox events `awcms.website_engagement.submission.received` and `...withdrawn` (AsyncAPI), carrying an opaque reference; a CRM adapter reads details through an audited reveal endpoint under its own permission. Admin API for sources, masked submissions, reveal and the controller's withdrawal; retention declared through data_lifecycle (default 180 days); migrations 325-327; new env `WEBSITE_ENGAGEMENT_KEYS` (and optional rate-limit variables). The embeddable widget was assessed and not built; the admin screen is deferred (the module is `experimental` with no navigation entry). New permissions need the owner or an administrator to grant them to a role before they can be used.
