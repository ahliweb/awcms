security(readiness): new `critical` check "No view or materialized view bypasses RLS on a FORCE-RLS table" (Issue #1347, follow-up of #1279). Every earlier check read `relkind IN ('r', 'p')`, so a view was invisible: a view runs with its owner's privileges and policies unless it is `security_invoker`, so a definer view over a FORCE-RLS table is read under the owner's policies (with no row level security at all for a superuser or BYPASSRLS owner) by whoever holds SELECT on it. The check follows dependencies transitively through nested views and fails every such definer view whatever its owner and whether or not it is granted; a materialized view (no RLS, no `security_invoker`) over a FORCE-RLS table fails as soon as a restricted role can SELECT it; and grants on relkind v/m now enter a fail-closed view grant matrix (`REVIEWED_VIEW_GRANTS`, empty today: the repository defines no view), covering every role that is neither superuser nor BYPASSRLS, and `PUBLIC`; an entry for a view that no longer exists is reported as stale. Note `ALTER DEFAULT PRIVILEGES` (sql/021) hands `awcms_app` DML on any new view, so a future view needs a `REVOKE` or a reviewed entry. No schema, API or event change; the clean schema passes. The scan covers every non-system schema and every role that is neither superuser nor BYPASSRLS (not only `awcms_*`), counts privileges reached through role membership, PUBLIC or column-level grants, and treats a restricted owner of a materialized view as a reader.
