feat(whatsapp_delivery): optional StarSender per-device adapter, off by default, behind a per-operator risk acknowledgement (Issue #1142, ADR-0148 section 4 and 7). **Nothing changes for a deployment that does not set `WHATSAPP_STARSENDER_ENABLED=true`**: the adapter does not exist, a StarSender sender is still refused at enqueue and fails closed at dispatch, and the generic backend has no provider default.

StarSender is an **unofficial** WhatsApp gateway. Nothing here claims Meta authorisation, ban-free sending or reliable delivery status: a `success` answer is "accepted by StarSender", the row becomes `sent` with no provider message id, and nothing reports delivered or read. There is no automatic fallback and no device rotation: a failed, disconnected or unapproved device never sends through another device, number or provider.

**Adapter** (under the existing queue and dispatcher, no second queue): `POST https://api.starsender.online/api/send` as a constant, the device key as `Authorization`, redirects refused so the key is never forwarded, a bounded timeout, a per-device circuit breaker and lane, fixed error sentences keyed by a coarse code (provider text, the key and the number are never stored). HTTP 200 is not success: the body's boolean `success` decides and an unknown shape is `malformed_response`, never accepted. A timeout, a reset or **any 5xx** is `outcome_unknown` and is **not retried** (a failing gateway may already have forwarded the message and StarSender documents no idempotency key); only DNS failure, HTTP 429, a reported rate limit and a disconnected device are retried, and `device_disconnected` and `unauthorized` hold the device's own lane.

**Risk acknowledgement** (new `awcms_channel_provider_risk_acknowledgements`, `sql/340`; permissions `risk_acknowledgements.read`, `.create` and a high-risk `.revoke`, `sql/341`): provider, person, time, text version and the SHA-256 of the exact words, revocable by a stamp, append-only by trigger, never deleted. A StarSender device cannot be `connected` without an active one (database trigger), the send decision and the credential decryption re-check the current approved version (`RISK_ACKNOWLEDGEMENT_REQUIRED`, terminal; the credential port also checks the adapter flag before it reads any secret, `PROVIDER_ADAPTER_DISABLED`). A device is bound to the acknowledgement it was attested under, so revoking THAT one degrades it, and revoking the tenant's last one degrades them all; revocations are serialised (every active acknowledgement of the provider is locked first) so concurrent ones cannot leave a connected device with no active acknowledgement. Replacing a device key moves the device back to `pending` (`CREDENTIAL_REPLACED`). Acknowledging and attesting need a fresh step-up from a person who has an MFA factor (conditional, like the credential route). The database stamps the acknowledgement and revocation times. `POST /api/v1/channel-accounts/accounts/{id}/attest-device` is the one operator-attested `connected` (StarSender documents no status call), recorded as `OPERATOR_ATTESTED`. `ChannelAccountPort` goes `1.0.0` to `1.1.0`, additively (two new terminal refusal reasons).

**The acknowledgement text ships as an UNAPPROVED DRAFT** (`approval: null`): until the business owner approves the wording in a reviewed change nothing can be acknowledged and no device can be connected. That human step is not performed here.

**Governance:** the points where this goes beyond the Accepted ADR-0148 (operator-attested device state as a recorded exception to "health is reported, never asserted by a person", a provider-reported disconnect holding the lane instead of failing terminally, unknown outcomes not retried) are recorded in the **Proposed** ADR-0158 and need the owner's decision; ADR-0148 itself is unchanged. The code is off by default and fail closed, so it is safe to merge before that decision.

**No webhook, on purpose:** StarSender's documentation describes one with no authentication of the request, so no route exists, no signature scheme is invented and no status or contact is ingested (status-unknown mode, ADR-0148 I9); any compensating mechanism needs its own ADR addendum.

**Not verified against the live API:** only the success body is documented; the failure fixtures are assumptions. See `docs/awcms/starsender-adapter-runbook.md` section 6.

Operator action: run `bun run db:migrate` (applies `sql/340` and `sql/341`, forward-only) and `bun run identity-access:permissions:backfill` for tenants that already exist. `WHATSAPP_STARSENDER_ENABLED` is new and optional (off); the job env allowlist gained that one name (`ops/awcms-jobs.env-global`): redeploy the regenerated `ops/awcms-jobs.env-*` files if you deploy them.
