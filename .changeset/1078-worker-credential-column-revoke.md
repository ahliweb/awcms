security(identity_access): `awcms_worker` can no longer read credential columns (#1078, found by the security review of #1044). `sql/022` gave the worker a table-level `SELECT` on `awcms_identities`, which silently included `password_hash`; since RLS trusts `app.current_tenant_id`, anyone able to run SQL as the worker could read every tenant's password hashes. `sql/304` revokes it and re-grants only the six columns the worker jobs read (`id, tenant_id, profile_id, status, login_identifier, created_at`: recipient resolution for `workflow:escalations:dispatch`, the identity cursor stream of `reporting:projections:refresh`). The same audit narrowed the token-bearing tables the worker only purges (`awcms_password_reset_tokens`, `awcms_invitations`, `awcms_delegated_access_grants`, `awcms_omes_enrollments`, `awcms_newsletter_subscribers`, `awcms_comments_reply_subscriptions`) to `id, tenant_id, created_at`, and `awcms_tenant_domains` / `awcms_telegram_link_codes` / `awcms_telegram_bindings` to every column except their token or PIN hash. `security:readiness` gains a `critical` check, "Worker roles cannot read credential columns", that fails if any worker role can SELECT a column in the central `CREDENTIAL_COLUMNS` list (`has_column_privilege`, table-level or column-level) or if a credential-looking column is unclassified; `WORKER_ROLE_GRANTS` / `WORKER_COLUMN_GRANTS` are updated to match. Two documented exceptions stay readable (`awcms_push_subscriptions.auth_secret`, `awcms_omes_repository_progress_config.secret_ref`). No application behaviour change.
