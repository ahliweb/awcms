Split the `website_engagement` key ring in two (Issue #1262, ADR-0137 section 3): `WEBSITE_ENGAGEMENT_ENCRYPTION_KEYS` encrypts submission contact details and `WEBSITE_ENGAGEMENT_HASH_KEYS` keys every source-token and identifier hash. The two rings must share no key with each other or with any other ring or single-key secret of the deployment; this is refused at runtime (every route answers 503) and by `bun run config:validate`. **Operator action required for the experimental module:** the single ring `WEBSITE_ENGAGEMENT_KEYS` is retired and, if still set, makes the module refuse rather than being used for either role. Existing deployments follow the transition runbook in the module README: keep the old key as a non-first (decrypt-only) encryption key and as a verify-only `WEBSITE_ENGAGEMENT_LEGACY_HASH_KEYS` entry, so existing source tokens and stored contact details keep resolving; a token verified under a legacy key is re-hashed under the new hash key on its first accepted submission (compare-and-swap, never undoing a concurrent rotation), and `bun run security:readiness` now counts live source tokens and stored contact ciphertexts per key id so the operator knows when the legacy key can be dropped. No re-encryption job: a submission stays append-only evidence and old rows leave through retention or withdrawal. No migration, no API or event change.
