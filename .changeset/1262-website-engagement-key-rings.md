Split the `website_engagement` key ring in two (Issue #1262, ADR-0137 section 3): `WEBSITE_ENGAGEMENT_ENCRYPTION_KEYS` encrypts submission contact details and `WEBSITE_ENGAGEMENT_HASH_KEYS` keys every source-token and identifier hash. The two rings must share no key with each other (refused at runtime, where every route that hashes or decrypts answers 503 with a generic "key configuration was refused" and logs a fixed cause code, and by `bun run config:validate`), and no key with another module's ring or single-key secret (refused by `config:validate`). A key id may never be reused for new material: the configuration rules refuse the visible cases and `bun run security:readiness` decrypts one sample ciphertext per encryption key id and recomputes one sample identifier hash per hash key id, failing when the configured material no longer opens the stored rows. **Operator action required for the experimental module:** the single ring `WEBSITE_ENGAGEMENT_KEYS` is retired and, if still set, makes those routes refuse rather than being used for either role. Existing deployments follow the transition runbook in the module README: keep the old key as a non-first (decrypt-only) encryption key and as a verify-only `WEBSITE_ENGAGEMENT_LEGACY_HASH_KEYS` entry, so existing source tokens and stored contact details keep resolving; a token matched under any key other than the active hash key (a legacy key, or an older key after an ordinary hash-ring rotation) is re-hashed under the active key on its next accepted submission (compare-and-swap, never undoing a concurrent rotation), and `security:readiness` counts live source tokens and stored contact ciphertexts per key id so the operator knows when the legacy key can be dropped. No re-encryption job: a submission stays append-only evidence and old rows leave through retention or withdrawal. No migration and no event change; the OpenAPI 503 description now names the refusal causes.
