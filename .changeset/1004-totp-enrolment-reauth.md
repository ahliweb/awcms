security(identity_access): TOTP enrolment can no longer be started by a session alone (#1004, audit F-3 of #977, ADR-0141 section 7). `POST /api/v1/auth/mfa/totp/enroll/start` from a session now needs `currentPassword` (`400 PASSWORD_REQUIRED` / `INVALID_CREDENTIALS`), or an SSO session minted within 5 minutes (`403 REAUTHENTICATION_REQUIRED` when stale), verified by the login rule (principal credential, else identity hash), counted toward the principal lockout, rate limited per session and per source, and the SSO exemption holds only when the person works in no other tenant (`sql/261`); the login-forced enrolment-grant path is unchanged and an account with an active factor still gets `409 MFA_ALREADY_ACTIVE`. `enroll/verify` is now rate limited, bound to the session or grant that started the enrolment, expires after 10 minutes and destroys the pending secret after 5 wrong codes (`sql/260`). Activating a factor now writes a `critical` `mfa_enrolled` audit event and, like disabling one, emails the account owner a `system.security_notice` through the existing auth-notification port (needs the default email templates seeded). The account screen asks for the password before setup. A stolen session can no longer enrol the thief's authenticator; someone who knows the password still can, but no longer silently. An enrolment grant minted by a tenant switch (or with no recorded origin) now re-authenticates like a session; only a grant minted by a login that verified the password keeps the exemption (`sql/262`). The wrong-code cap is race-safe (the pending row is locked and the cap is checked before a code is evaluated), and an unlinked identity fails closed for the SSO exemption.
