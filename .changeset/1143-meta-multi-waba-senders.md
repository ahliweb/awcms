feat(whatsapp_delivery): Meta Cloud API multi-WABA, multi-number sender binding with signed per-number webhooks (Issue #1143, ADR-0148 section 4 and I9). One queue and one dispatcher, unchanged; nothing is sent from the webhook path.

**Binding.** A tenant-owned Meta number (`whatsapp_cloud` `waba_phone_number`) is usable only under a live `waba` container of the same provider (`ChannelAccountPort` 1.2.0, `CONTAINER_BINDING_INVALID`, terminal). The database guard (`sql/365`) fills and checks the verified identity on the queue row at INSERT (`sender_external_id` = phone_number_id, `sender_container_external_id` = WABA id) and makes it immutable; the dispatcher refuses to send a row whose live binding differs (`SENDER_BINDING_CHANGED`, terminal). **Behaviour change for existing tenants:** a Meta number registered without a WABA parent is now refused (it was usable through its own API token); register it under its WABA.

**Meta rules, for tenant-owned Meta senders only** (not the deployment sender, not StarSender), re-verified against Meta's documentation on 11 November 2026: a template must be `APPROVED`/`REINSTATED` on THAT number's WABA in the category its purpose requires (`TEMPLATE_NOT_APPROVED`); a registration without a provider template may go only as a free-text service message inside the recipient's 24-hour window with THAT number (`OUTSIDE_SERVICE_WINDOW`); marketing is never free text. Checked at enqueue and again before each send. `WhatsappDeliveryPort` 1.3.0, additive. New `awcms_whatsapp_meta_templates` (operator records with evidence via `PUT /api/v1/whatsapp/meta-templates`, kept current by signed status webhooks).

**Webhooks.** `POST /api/v1/channel-accounts/accounts/{id}/webhook-subscription` (`channel_accounts.webhooks.configure`, high-risk) stores the Meta app secret write-only and shows an opaque per-number callback token once; `GET`/`POST /api/v1/whatsapp/webhooks/meta/{token}` (public, in `SESSION_FREE_BODY_ENDPOINTS`) resolves tenant and account from the token, verifies `X-Hub-Signature-256` in constant time, dedupes bodies (`awcms_whatsapp_webhook_receipts`), reconciles statuses only against the bound sender's rows forward-only (new event `awcms.whatsapp.message.provider_status_changed`), opens 24-hour windows from inbound messages without storing content (`awcms_whatsapp_service_windows`), and records WABA restrictions and messaging-limit tiers (`awcms_whatsapp_meta_sender_signals`). A per-(tenant, address) bucket answers `429` before any database work; nothing is dropped. A restricted WABA's numbers are refused at enqueue and held at dispatch; a Meta rate-limit answer holds that sender's lane for 60 s. Never a fallback to another number or provider.

**Permissions** (`sql/366`): `channel_accounts.webhooks.configure`, `whatsapp_delivery.meta_templates.read`/`.configure`, `whatsapp_delivery.meta_signals.configure`. The worker gains only `SELECT` on approvals and signals and `SELECT, DELETE` on windows and receipts (purged by `whatsapp:queue:purge`); its `awcms_channel_secrets` policy is unchanged. The legacy single-sender deployment (`WHATSAPP_META_*`) is unchanged.

**Security review fixes (before merge).** Creating a webhook subscription also needs `whatsapp_delivery.meta_templates.configure` and `.meta_signals.configure` and the owner assignment on the WABA container (M-1); every WABA-level change a webhook makes is audited (`whatsapp_meta_webhook.*`); the app secret is documented as not verified with Meta. A per-address bucket of unverified webhook requests answers `429` before any database work whatever tenant a forged token names (M-2). Disconnecting or deleting a number erases its webhook app-secret ciphertext (M-3). The worker's `DELETE` on windows and receipts is limited by RESTRICTIVE policies to the purge's retention, pinned exactly in `security:readiness` (L-2). Approvals and restrictions are keyed by the WABA id, so re-registering a container does not reset them (L-3). The HMAC is computed over the raw request bytes (L-5). The template/signal list says when it is truncated (L-6).

**Independent audit fixes (before merge).** The per-address webhook bucket is charged only while the callback token has not matched: once it matches, a refusal (a wrong or stale app secret, a revoked subscription) is refunded there and charged to that tenant's own denial bucket, so one misconfigured tenant no longer makes Meta's address `429` every other tenant's genuine deliveries; forged tokens still spend the address bucket (M1). A caller confined to business scopes neither sees nor changes the template approvals and restriction signals of a tenant-wide WABA, nor creates a webhook subscription for one of its numbers; each refusal is the same answer as an unknown id (M2). A webhook's `entry.time` is clamped to its arrival, so a future one can no longer freeze template or restriction state, and a timestamp past the Date range is unreadable instead of a `503` retried for a week (M3).

**Human steps not performed here:** a Meta app, business verification and WABA ownership for a test tenant. No admin screen yet for the new endpoints.
