Close three Medium audit findings of the channel-accounts control plane before `CHANNEL_ACCOUNTS_ENABLED` is ever turned on (Issue #1215, follow-up of #1140; the module is off by default and has no consumer yet). M1: connection break-glass (revoke and list visibility) no longer depends on whether the caller holds a business-scope assignment; it is the holder of the connection's scope or the tenant administrator (`assignments.assign` decided by the access chokepoint), so an owner who is given one scope keeps authority over every other connection. M2: binding a new account to a scoped connection now needs `owner` authority over the accounts already bound to it, so a colleague of the same scope can no longer borrow the connection's token; only the tenant administrator skips that check. M3: scope decisions are made per scope without a resource id and share a per-request authorization read cache, so one `GET /connections` writes a bounded number of `awcms_abac_decision_logs` rows whatever the number of connections. L2 (partial): for an `oauth2` account, a connection of another provider now answers the same `422 CONNECTION_NOT_FOUND` as an unknown one; a connection id sent with a non-`oauth2` shape is still answered by shape first. OpenAPI, the API reference and ADR-0148 (EN and ID) record the corrected break-glass rule. Not changed: the assignment model (M-c), external-id squatting and any migration.
