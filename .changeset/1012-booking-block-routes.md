feat(booking): block create/release routes, and the follow-ups N1 to N4 of the #940 review (#1012, ADR-0131, ADR-0135). `booking` gains `POST /api/v1/booking/blocks`, `POST /blocks/{id}/release`, `GET /blocks` (keyset; filters `resourceId`, `unitId`, `status`) and `GET /blocks/{id}`, gated by the already-seeded `booking.blocks.create` / `.release` / `.read` (default deny, neutral `404 BLOCK_NOT_FOUND` for an unknown or another tenant's id, RLS). Both mutations take the shared `Idempotency-Key` through the same per-key-locked `runIdempotent` as the reservation routes (N2): a client that retries after the commit receives the stored `201` for its own block and never `409 BLOCK_CONFLICT` naming it; five parallel requests with one key make one block; a refusal is never stored. A conflicting reservation (number, status, dates; never a customer reference) is named in `error.details.conflicts` only to a caller who also holds `booking.reservations.read`, checked through the access chokepoint; creating a block never cancels anything. Audited `warning` / `info` with ids, dates and the closed reason code; no domain event in v1 (blocks are configuration of what is for sale and nothing consumes them; an event can be added later under the AsyncAPI rules). N1: a resource-wide block now also covers units added later (`sql/240`: an AFTER INSERT trigger on `awcms_booking_resource_units` inserts the block row of the new unit for every active resource-wide block, after locking the resource row `FOR NO KEY UPDATE`; `readBlockUnits` takes the same row `FOR SHARE`, so a unit insert and a block placement serialise and no unit is left uncovered in either order; both orders and a race are tested with the interleaving proven through `pg_stat_activity`). N3: the lazy reclaim before a block expires only the elapsed holds on the covered unit(s), and its audit text and attributes say so. N4: a block and its allocation rows carry one release instant (`sql/241`, the trigger copies the block's `released_at`). OpenAPI, the bundle, the API reference and docs (booking.md EN/ID, module README EN/ID) are updated. Existing tenants need nothing new (the permissions were seeded by `sql/181`); units added before this release to a resource with an active resource-wide block stay reported by the reconciliation (`block_missing_allocation`).
