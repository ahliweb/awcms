feat(realtime): cross-instance wake-up hint for the progress streams over PostgreSQL LISTEN/NOTIFY, with no new service (Issue #1171, ADR-0154 section 2 and 7). `sql/418` adds `awcms_realtime_wake_hint()` and row triggers on `awcms_whatsapp_messages` and `awcms_inbox_conversations` that `pg_notify('awcms_realtime', {"t": tenant id, "k": topic})` at commit; the payload is only a tenant id and a topic name (no row id, no personal data). Each process holds ONE `LISTEN` connection (not per client), started on the first stream open, which refuses a SUPERUSER or BYPASSRLS login, reconnects with jittered exponential backoff and, once back, wakes every stream so each reads from the cursor it already holds. A hint only shortens the wait before a stream's next tick: every tick still re-authorizes and reads durable state, tenant filtering and authorization stay on the server, a lost or forged hint costs latency only, and wakes are throttled to one per tenant and topic per 250 ms. New env `REALTIME_WAKE_HINT_ENABLED` (default `true`; not attempted under `DATABASE_PGBOUNCER=true`) and three metrics (`realtime_wake_hints_total`, `realtime_wake_listener_up`, `realtime_wake_listener_events_total`). Tested with two independent listener connections as two instances (delivery across instances, the join race, tenant isolation, payload content, rollback, privileged-login refusal, kill and reconnect with exactly one backend). No API or event contract changes.
