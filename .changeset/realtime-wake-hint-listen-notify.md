feat(realtime): cross-instance wake-up hint for the progress streams over PostgreSQL LISTEN/NOTIFY, with no new service, OFF by default (Issue #1171, ADR-0154 section 2 and 7). `sql/418` adds `awcms_realtime_wake_hint()` and row triggers on `awcms_whatsapp_messages` (INSERT and status change only; a lease renewal does not notify) and `awcms_inbox_conversations` that `pg_notify('awcms_realtime', {"t": tenant id, "k": topic})` at commit; the payload is only a tenant id and a topic name. The writer switch is a database setting read in each trigger's `WHEN` clause: `ALTER DATABASE <db> SET awcms.realtime_wake = 'on'` (new sessions, `RESET` to switch off, no deploy), default OFF, and the process switch `REALTIME_WAKE_HINT_ENABLED` also defaults to `false`: a NOTIFY commit was measured at about 2000 to 3000 commits/s against 5400 to 13000 without (one shared machine, re-measure in the target environment). Each process holds ONE `LISTEN` connection, started on the first stream open, which refuses a SUPERUSER or BYPASSRLS login, reconnects with jittered exponential backoff, wakes every stream afterwards so each reads from its cursor, and probes its own liveness with a periodic self-NOTIFY so a half-open socket is rebuilt. A hint only shortens the wait before a stream's next tick: every tick still re-authorizes and reads durable state, a lost or forged hint costs latency only, wakes are throttled to one per tenant and topic per 250 ms and released over a random window (20 ms per extra stream, cap 2 s) so a herd cannot fill the `realtime_stream` work class, and a hint-triggered tick the database refuses falls back to the timer instead of ending the stream. With the hint on, a stream may tick up to 4 times a second instead of every 5 s (more load, not less; documented with its ceiling). New optional `REALTIME_LISTEN_DATABASE_URL` (direct listener connection for PgBouncer deployments; secret, web only), four metrics (`realtime_wake_hints_total`, `realtime_wake_listener_up`, `realtime_wake_listener_events_total`, `realtime_wake_queue_usage`) and an alert note: a full NOTIFY queue fails writers' commits. No API or event contract changes.
