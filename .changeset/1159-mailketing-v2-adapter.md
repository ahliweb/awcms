Add an optional, version-gated Mailketing REST API v2 adapter behind the existing `EmailProvider` port and `email:dispatch` outbox (Issue #1159, ADR-0151 stages 0-1). v1 stays the default: with `EMAIL_MAILKETING_API_VERSION` unset (or `v1`) nothing changes, including direct email and OTP delivery. `v2` sends `POST /api/v2/send` as JSON with the token in an `Authorization: Bearer` header only, to a fixed allow-listed host (`https://api.mailketing.co.id`, no arbitrary base URL, no redirects followed, bounded timeout and response size). Outcomes are classified: 200 `success:true` is accepted-by-provider (not delivered), 200 `success:false` is a refusal, 401/403/422 terminal, 402 held without spending a retry, 429 honours `Retry-After`, 5xx/timeout/network/invalid JSON retryable; results never carry the token, provider body text or recipient. `email:provider:health` probes `GET /api/v2/credits` (read-only). The dispatcher now marks a message re-claimed from an expired lease as uncertain (a crash after provider acceptance may duplicate), counted as `uncertain=` in the `email:dispatch` summary. New `config:validate` rules fail closed on an unknown version or a non-allow-listed v2 base URL. No migration, no OpenAPI/AsyncAPI change.

Fail-safe behaviour (audit follow-up): a configuration error (missing token, unknown version, bad base URL or token charset, including the pre-existing v1 missing-token case) now DEFERS claimed messages (kept `queued`, no attempt row, no retry spent, loud `email.dispatch.misconfigured` log, `misconfigured=N` summary and a non-zero `email:dispatch` exit) instead of marking them `failed`; a 200 without a boolean `success` is terminal and uncertain (never retried, so no duplicate copies); refusals and 4xx count toward the existing 5-consecutive breaker so a wrong field name cannot silently fail the whole queue; an egress-policy denial is retryable; a 402 hold is bounded to 1 hour (`CREDIT_HOLD_BUDGET_EXCEEDED`); the uncertain note is written for every outcome of a re-claimed row. New optional `EMAIL_MAILKETING_V2_VERIFIED` acknowledgement flag: until set, `config:validate`, `email:dispatch`, `email:provider:health` and each dispatch pass warn "Mailketing v2 contract UNVERIFIED" — production v2 is NOT approved until the live stage-2 check is done.

The v2 request-field names and every provider status were built from the documented contract WITHOUT network access: live-API verification has NOT been done (ADR-0151 stage 2 must do it before any production use).

**Operator action:** none for existing deployments (inert; v1 remains the default). To trial v2: set `EMAIL_MAILKETING_API_VERSION=v2` (the existing `EMAIL_MAILKETING_API_TOKEN` is reused; leave `EMAIL_MAILKETING_API_BASE_URL` unset or exactly `https://api.mailketing.co.id`), run `bun run config:validate` and `bun run email:provider:health`, and install the updated `ops/awcms-jobs.env-global` (it gains `EMAIL_MAILKETING_API_VERSION` and `EMAIL_MAILKETING_V2_VERIFIED`) next to `run-job.sh` so the jobs runner passes the variable. Roll back by unsetting the variable (or `v1`) and restarting; queued messages are unaffected because the outbox is version-agnostic.
