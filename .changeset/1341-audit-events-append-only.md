security(logging): `awcms_audit_events` is now append-only for the runtime role (Issue #1341, `sql/408`). The docs and the header of `sql/224` already described it that way, but `sql/019` had granted `awcms_app` SELECT, INSERT, UPDATE and DELETE on every table and nothing revoked them on this one, so a compromised web process could rewrite or erase the audit trail; `security:readiness` even required all four verbs. The migration revokes UPDATE, DELETE and TRUNCATE from `awcms_app`, and `security:readiness` now pins the table to exactly SELECT + INSERT in both directions, and also fails on TRUNCATE, TRIGGER, REFERENCES or any column-level INSERT/UPDATE/REFERENCES grant on it (which the four-verb check could not see). The retention purge (`bun run logs:audit:purge`) runs as `awcms_worker`, which keeps its DELETE, so nothing about retention changes.

Operator action: if `DATABASE_URL` is the `awcms_app` login, point `WORKER_DATABASE_URL` at the `awcms_worker` login BEFORE or together with `bun run db:migrate`. With `WORKER_DATABASE_URL` empty the unattended jobs fall back to `DATABASE_URL`, so `logs:audit:purge` would fail with `permission denied` and audit rows would stop being purged; a new readiness check ("Worker jobs are reachable when the web connection is the narrowed app role") now fails in exactly that configuration. Then run `bun run db:migrate`. A deployment that has not activated the dedicated `awcms_app` login still connects as the schema owner, which this migration does not narrow. Other log and event tables are not changed here.
