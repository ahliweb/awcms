security(access): the remaining append-only ledgers are now append-only for the runtime role (Issue #1346, `sql/409`, following #1341/`sql/408`). The ABAC decision log, the access-policy event history, the business-scope assignment event history and the domain-event outbox were documented as append-only, but `sql/019` had granted `awcms_app` SELECT, INSERT, UPDATE and DELETE on every table and nothing revoked them, so a compromised web process could rewrite the record of which decisions and grants were made, or the event stream consumers replay from. The migration revokes UPDATE, DELETE and TRUNCATE from `awcms_app` on all four, and `security:readiness` pins each to exactly SELECT + INSERT in both directions. Every table was audited by call site first: no `awcms_app` UPDATE or DELETE path exists; decision-log retention is the one legitimate DELETE and runs as `awcms_worker`, which keeps it; the outbox dispatcher updates `awcms_domain_event_deliveries`, not the event table, so no table was excluded. Database-level `TEMP` stays deliberately unchecked by readiness.

Operator action: if `DATABASE_URL` is the `awcms_app` login, point `WORKER_DATABASE_URL` at the `awcms_worker` login BEFORE or together with `bun run db:migrate`, otherwise the decision-log retention purge falls back to `awcms_app` and fails with `permission denied` (the existing readiness check "Worker jobs are reachable when the web connection is the narrowed app role" reports exactly that). A deployment that has not activated the dedicated `awcms_app` login still connects as the schema owner, which this migration does not narrow.
