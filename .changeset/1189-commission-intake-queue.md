`hr_commission` commission intake queue and an `awcms_app` posting job for event-driven consumers (Issue #1189, ADR-0147, resolving #1138). A consumer that runs in `domain-events:dispatch` as `awcms_worker`, such as the commerce `order.paid` attributor of a derived repository, can now report a sale without any privilege on the accrual ledger: it submits through the new neutral port `commission_intake` 1.0.0 (`submitAccrual`, `submitVoid`; same request shapes and validators as `CommissionAccrualPort`; outcomes `queued`, `duplicate`, `input_invalid`, `actor_required`, `disabled`), which is one `INSERT ... ON CONFLICT DO NOTHING` into the new `awcms_hr_commission_intents`. The worker holds `INSERT` on that table and nothing else on it, and nothing on any payroll-family relation; `PAYROLL_ALLOWED_GRANTEES`, the empty `PAYROLL_WORKER_EXECUTE_ALLOWLIST`, `PAYROLL_CATALOG_EXEMPTIONS` and `commission_accrual` 1.1.0 do not change.

- New job `hr-commission:intents:post` (every minute, runs as `awcms_app` and is the only scheduled job that keeps `DATABASE_URL`): claims due rows per tenant with `FOR UPDATE SKIP LOCKED` and a lease, posts each through the existing `accrueCommission` / `voidCommissionBySource` in a tenant transaction with the stored actor (the ledger write and the settlement commit together), and settles it `posted`, `refused` (a business refusal, terminal) or, after eight transient failures with a back-off, `failed`. A void that arrives before its accrual waits for it; `period_closed` is routed to a human. Settled rows are purged after 30 days, `refused` and `failed` rows after 90 (clamped to 7..90 at run time).
- Exactly once: the unique key `(tenant_id, kind, source_type, source_ref, source_line, employment_id, request_digest)`, the ledger's own digest, makes a redelivery `duplicate`; the same identity with a different request surfaces as `source_conflict`; a replay after a crash is the ledger's `replayed`.
- The worker's claim about who acted is never trusted: the poster stamps the ledger and the audit with the tenant's intake system actor (`intakeActorTenantUserId`, an active tenant user, required to switch intake on), and posts a void only for an accrual this intake itself created (otherwise it waits up to 24 hours, then is refused as `no_intake_origin`).
- Default-deny per tenant: the switch `commission_intake_enabled` (`GET`/`PUT /api/v1/hr-commission/intake/settings`, new high-risk `hr_commission.intake.configure`, idempotency-keyed, audited at `warning`) is off until set. New read-only `GET /api/v1/hr-commission/intake/exceptions` (new `hr_commission.intake.read`, which opens no accrual): refused and failed requests with an outcome code and masked ids, plus the queue counts and the age of the oldest live row. No amount reaches an audit row, a log or a response.
- Migrations `sql/316` (tables, RLS `FORCE`, guard triggers, grants, the count-only lifecycle function) and `sql/317` (the two permissions); OpenAPI, the data-lifecycle and subject-data descriptors, the worker grant matrix and the module README and `hr-payroll.md` in English and Indonesian are updated. Operator action: run `bun run db:migrate`, replace `ops/run-job.sh` and `ops/awcms-jobs.crontab`, EXISTING tenants do not receive the two new permissions (`hr_commission.intake.read` and `.configure`) automatically: run `bun run identity-access:permissions:backfill` (dry-run by default, `--tenant <code>`) and grant them to the roles that should have them; only then switch intake on per tenant, naming the intake system actor. No admin screen yet. The downstream adapter (`ahliweb/awcms-one#391`) is not part of this repository.
