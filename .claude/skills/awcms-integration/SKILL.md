# AWCMS — Backend & Integration Hardening

Sources of truth: **`docs/awcms/16_backend_data_access_integration.md`** (transactional outbox, transaction wrapper, idempotency), **`docs/awcms/05_openapi_asyncapi_detail.md`** (API/event contracts), and **`docs/awcms/10_template_kode_coding_standard.md`** (guardrails). This skill is about **improvement**: raising reliability and resilience, not merely creating an endpoint (that is `awcms-new-endpoint`).

## Integration principles (non-negotiable)

- **External providers are optional** (ADR-0006): R2/WA/email/AI/tax **must not** become a dependency of a critical operational flow, and **must not** be called inside a DB transaction. Provider down → the action still enters the queue rather than failing. The shared worker runner (`src/lib/jobs/job-runner.ts`, Issue #697) — used to orchestrate `scripts/*.ts` (locking, batching, exit codes, telemetry) — is designed to be CONSISTENT with this rule: it does not encourage a pattern that puts a provider call inside the same DB transaction; a job handler that calls a provider is still required to do so outside `withTenant`'s transaction block, exactly like the outbox dispatcher pattern below.
- **Secrets come only from the environment** (doc 18); a flag enabled without its credentials → fail to start (fail-fast).

## Resilience checklist

- [ ] **Transactional outbox** — external side effects (sending WA/email, uploading an object, publishing an event) are written to an outbox table **inside** the business transaction, and a separate dispatcher sends them outside that transaction (at-least-once). Not a direct inline call. Real examples already exist; follow this pattern: `awcms_object_sync_queue` + `dispatchObjectSyncQueue` (`src/modules/sync-storage/application/object-dispatch.ts`, Issue #436) — three phases: CLAIM (short transaction, `FOR UPDATE SKIP LOCKED`, transient status `sending` acting as a lease) → UPLOAD (outside any transaction) → FINALIZE (a second short transaction). `awcms_sync_outbox` (local events between nodes) has no live dispatcher yet. Email (epic #492, Issues #493–#495) is a second real instance of this pattern, with a variation: `awcms_email_messages` (`sql/014`) + `dispatchEmailQueue` (`src/modules/email/application/email-dispatch.ts`) — CLAIM (reusing `next_attempt_at` as the lease, same as the object queue) → SEND (render from `template_key`/`variables`, then call `EmailProvider.send`, outside any transaction) → FINALIZE (retry_wait/sent/failed + record `email_delivery_attempts`). Real callers have existed since Issues #496/#497 (epic #492 complete): password reset (`POST /auth/password/forgot`) and bulk announcements (`POST /email/announcements[/preview]`, two-tier ABAC) both enqueue into `email_messages` before `bun run email:dispatch` claims them. (`social_publishing`, Issue #643, is a third instance with the same shape **in awcms-mini** — the module does not exist here — a candidate to BUILD via an admission ADR (ADR-0055 §1) — so do not go looking for `src/modules/social-publishing` in this repo; see the `awcms-social-publishing` skill, which is READ-ONLY.) **The generic MULTI-consumer counterpart** (Issue #742, epic `platform-evolution` #738): `domain_event_runtime` — one event can fan out to many registered consumers (rather than one dispatcher / one provider as in the three examples above), with explicit ordering per aggregate/order-key. Its two built-in reference consumers are same-process/DB-only (not external providers), so claim + execute + finalize is deliberately ONE transaction rather than a 3-phase CLAIM/CALL/FINALIZE — see `src/modules/domain-event-runtime/README.md` §Execution model for when the 3-phase pattern remains mandatory (future out-of-transaction/broker-backed consumers).
- [ ] **Timeout + retry + backoff** — every outbound call has an explicit timeout (`withTimeout`, `src/lib/integration/timeout.ts`, Issue #436 — reuse it, do not rebuild it); retry with bounded exponential backoff (the `evaluateObjectRetry` pattern, max attempts); never retry indefinitely.
- [ ] **Circuit breaker** — a dependency failing repeatedly is opened temporarily so it does not drag the system down. `src/lib/database/circuit-breaker.ts` has had a **per-provider registry** since Issue #436: `getProviderCircuitBreaker(providerKey)` for external providers (reuse it, do not build a separate circuit breaker) — distinct from the database singleton that has existed from the start. While a breaker is open, rows needing that provider are not claimed at all on that pass (they stay `pending`); rows that do not need the provider still run.
- [ ] **Idempotency at the integration boundary** — the dispatcher is safe to repeat (dedup by natural key / `Idempotency-Key` / a batch ledger such as `sync_push_batches`); a double send does not double the effect. For object uploads the upload key (`objectKey`) is itself a natural dedup key (a PUT to the same S3/R2 key is an overwrite, not a duplicate) — a separate ledger is not always needed.
- [ ] **Dead-letter / failure status** — an item that exhausts its retries is marked `failed` with `last_error` rather than disappearing silently; there is an admin manual-retry path (e.g. `/sync/object-queue/{id}/retry`).
- [ ] **Verify inbound webhooks** — HMAC signature + anti-replay (timestamp skew) for provider callbacks, following the `awcms-sync-hmac` pattern. Do not trust an unsigned payload.
- [ ] **SSRF-safe** — provider URLs come from trusted configuration (env), never from user input; validate the host where needed. Real example: `object-storage-uploader.ts` (Issue #436) — the R2 endpoint always comes from `process.env.R2_ACCOUNT_ID`, never from the request.
- [ ] **Contracts in sync** — a new or changed endpoint → update OpenAPI; a new or changed event → update AsyncAPI; `module.ts` publishes/subscribes stays accurate. `bun run api:spec:check` green. Internal dispatchers/CLIs (not HTTP endpoints) do **not** need an OpenAPI update.
- [ ] **Versioning & compatibility** — a breaking change to a path or schema needs a new version or an additive change; do not break older clients (the additive-cookie pattern in `/auth/login`).
- [ ] **Observability** — a correlation ID is set automatically in `meta.correlationId` for `/api/*` endpoints since Issue #447 (no manual wiring needed, see `awcms-observability`); structured JSON logs (honour `LOG_LEVEL`); high-risk actions are audited; secrets/PII are redacted before logging; the `setLogSink`/`setAuditExportHook` extension points are available to deployments/external consumers that need to forward to an external SIEM (`awcms-observability`).
- [ ] **Graceful degradation** — with the provider or flag off, operational endpoints keep working (POS does not stop); messages/objects stay queued.
- [ ] **Rate limiting / anti-abuse** — bound public and expensive endpoints. `src/lib/security/rate-limit.ts` (Issue #437) provides a generic fixed-window counter keyed by source + context, now at **two tiers** (ADR-0066): `checkSharedRateLimit` shares state **across instances via Redis** — used by the auth surface (18 route files), and required for anything that needs cross-replica consistency; `checkRateLimit` is in-process per instance for everything else. **Reuse these, do not build a separate limiter.**

## Verification

- Test with the provider off: the action still lands in the outbox/queue, with no operational error.
- Test retries: force a failure → the item backs off → attempts exhausted → `failed` + `last_error`, and a manual retry returns it to `pending`.
- Test dispatcher idempotency: re-send a batch → the effect does not double.
- `bun run check` green; OpenAPI/AsyncAPI in sync; the correlation ID appears in logs across hops.
