# AWCMS — New / Changed Domain Event

Follow `docs/awcms/05_openapi_asyncapi_detail.md`.

## Two DIFFERENT shapes — do not mix them up

There are **two** different shapes in this event system, used in different layers.
Both MUST be documented/followed, but do not mix one with the other.

### 1. Wire envelope (the AsyncAPI contract, what goes out to external consumers)

The single source of truth: `asyncapi/awcms-domain-events.asyncapi.yaml`'s
`components.schemas.DomainEventEnvelope` — `additionalProperties: false`,
so a field outside this list is **rejected**, not ignored:

```ts
type DomainEventEnvelope<TPayload> = {
  event_id: string; // uuid
  event_type: string; // pattern "^[a-z0-9]+(\.[a-z0-9_]+)+$", e.g. "awcms.blog-content.post.published"
  occurred_at: string; // ISO date-time
  producer: { service: "awcms"; module: string }; // module = the publisher's ModuleDescriptor.key
  tenant_id?: string | null;
  correlation_id?: string | null;
  payload: TPayload; // additionalProperties: true
};
```

There is no `event_version`/`node_id`/`aggregate_type`/`aggregate_id`/`actor`/
`causation_id`/`metadata` in this envelope — if you need a payload version,
encode it in `event_type`/inside the `payload` itself, not as a separate
envelope field (the schema is deliberately minimal & closed).

### 2. DB-level append input (internal, `domain-event-runtime`'s outbox)

`AppendDomainEventInput` (`domain-event-runtime/application/append-domain-event.ts:18-38`)
is the shape other modules' code ACTUALLY calls to write an outbox
row — **different from the wire envelope above**, flat, and it has NO `eventId`
(the DB creates it via `RETURNING id`, it is not generated by the caller):

```ts
type AppendDomainEventInput = {
  eventType: string;
  eventVersion: string;
  aggregateType: string;
  aggregateId: string;
  aggregateVersion?: number;
  orderKey?: string; // default deriveOrderKey(aggregateType, aggregateId)
  correlationId?: string | null;
  causationId?: string | null;
  producerModule: string; // the publisher's ModuleDescriptor.key, always explicit
  schemaRef?: string | null; // a documentation pointer to the AsyncAPI channel, not validated here
  actorTenantUserId?: string | null;
  actorProfileId?: string | null;
  payload: Record<string, unknown>;
  occurredAt?: Date; // default now()
};
```

`appendDomainEvent` stores this row in `awcms_domain_events` +
delivery rows in the same transaction as the source state change;
the separate dispatch process that reads the outbox is what assembles shape #1
(the wire envelope) to send to consumers — do not assume the two shapes are
identical when reading/writing code in either layer.

## Rules

1. Event name `namespace.aggregate.action` (lowercase, dots).
2. Bump `eventVersion`/`schemaVersion` when the payload changes incompatibly.
3. **The payload must not** carry raw PII/tax identity (mask it first — `awcms-sensitive-data`).
4. Publish **after** the transaction commits (or through the outbox), not as a replacement for audit.
5. Hybrid nodes: the event goes into `awcms_sync_outbox` for sync (`awcms-sync-hmac`).
6. **Update AsyncAPI** (`asyncapi/`) for a new event & payload; run `api:spec:check`.

## Core events (real channel examples — not a complete list)

`asyncapi/awcms-domain-events.asyncapi.yaml` is the single
source of truth — the channel count grows with every new module, DO NOT
hardcode the number in this skill (it drifts on every audit); run
`grep -c "^  awcms\." asyncapi/awcms-domain-events.asyncapi.yaml`
for the live count, and `grep -n "^  awcms\." ...` for the full
list. Representative cross-module examples that REALLY exist in there:

- `awcms.blog-content.post.published` (`blog_content`)
- `awcms.social-publishing.job.published` (`social_publishing`)
- `awcms.email.message.sent` (`email`)
- `awcms.sync.push.requested` (the `sync-storage` baseline envelope)
- `awcms.database.pool.saturated` (backpressure/pooling, doc 16)

Do not invent retail/POS domain channel names (e.g. `sales.*`/
`warehouse.*`/`tax.*`/`crm.*`) as examples — those modules do not exist
in this base repo, they were moved to an example derived application (e.g. AWPOS);
see `docs/awcms/06_github_issues_detail.md` §"Backlog change
history" and the `awcms-legacy-migration` skill. New events follow
the `namespace.aggregate.action` pattern above, with `namespace` = the `module_key`
of the real module publishing it.

## Verification

```bash
bun run api:spec:check
```

Register `publishes`/`subscribes` in the relevant module's `module.ts` and update the event table in doc 05 when adding a core event.
