# AWCMS — UI Screen / Component

Follow **`docs/awcms/14_ui_ux_design_system.md`** (tokens, components, layout, screens) and **`docs/awcms/15_frontend_architecture_integration.md`** (SSR/islands, API client, offline).

## Screen implementation checklist

1. **Tokens first** — use the doc 14 CSS variables (`--color-*`, `--sp-*`, `--fs-*`, including `--color-primary-strong`/`--color-success-strong`/`--color-danger-strong` for white text on solid colours, Issue #434 — all measured ≥4.5:1, do not use the plain variants for that); do not hardcode colours/sizes. Theme via `data-theme` with no flash.
2. **There is no component library yet — use the real markup patterns already in practice** — this repo does **not** have `src/components/ui` (no `Button`/`FormField`/`DataGrid`/`DataTable`/`Pagination`/`FilterBar`/`ActionBanner`/`StatusBadge`/`ConfirmDialog`; verify it yourself with `find src/components -type d`) — do not assume or refer to these components. The real admin screens (`src/pages/admin/offices.astro`, `roles.astro`, `users.astro`, etc.) use hand-rolled markup + consistent CSS classes: `<p class="state-notice" role="status|alert">` for access-denied/temporarily-failed states (differentiate the message per case, not with a separate component — do not invent another ad-hoc `.permission-denied` block); `<p class="admin-create-error" role="alert" hidden>` for per-form/per-action errors toggled via JS; `<div class="data-table-scroll"><table class="data-table">…</table></div>` (with `<td class="data-table-empty">` for the empty state) for lists/tables — there is **no** pagination/filter UI wired into any admin screen today (the API is already keyset-cursor, but the admin pages render the whole result as-is); `<span class="status-badge">` for lifecycle status. For confirming destructive actions, the code that EXISTS TODAY calls `window.confirm(...)` directly (see `roles.astro`/`offices.astro`) — there is no custom dialog; follow the existing pattern for new destructive actions, do not silently introduce a new dialog component without an explicit design decision. Real admin screens to copy from: `src/pages/admin/offices.astro` and `src/pages/admin/roles.astro`.
3. **State pattern is mandatory** — loading (skeleton), empty (+CTA), error (`<p class="state-notice" role="status|alert">` — differentiate "access denied" from "temporary failure, try again", with a safe i18n'd message derived from the doc 05 error code), success/submitting.
4. **Islands only where needed** — pages are SSR; interactivity only inside islands (POS, forms, chat). Initial data via SSR, mutations via the API client.
5. **Client-side form/mutation** — use `lockElement`/`sendJson`/`postJson` (`src/lib/ui/admin-form-client.ts`; the ONLY exports that exist — verify with `grep -n "^export" src/lib/ui/admin-form-client.ts` — do not assume `showBanner`/`submitJson`/`reloadAfterDelay`, none of the three exist) for mutation forms/buttons on admin pages. `lockElement` prevents double-submit (disables the button + busy label for the duration of the request, restoring it including on failure); `sendJson`/`postJson` return a narrow `{ ok, errorCode }` that never throws. **Importing from this module is mandatory, not merely DRY**: this repo's CSP is `default-src 'self'` without `'unsafe-inline'` (`astro.config.mjs`/security-headers middleware) — Astro hoists an import-free `<script>` into inline (blocked by CSP), whereas a script that imports from `admin-form-client.ts` is bundled into an external `/_astro/*.js` file that `'self'` permits; without this import, admin page scripts can "silently die" because CSP blocks them with no obvious error. Do not duplicate this implementation per page, and do not use raw `fetch`.
6. **Role-aware navigation** — filter the menu from the permissions in `GET /auth/me`; the backend still validates (hiding in the UI is not a control).
7. **i18n** — see the `awcms-i18n` skill (gettext `.po` catalogues, locale resolution via middleware, locale-aware formatters, `LanguageSwitcher.astro`) — static UI strings **always** go through `t("namespace.key")`, never hardcoded, including small components (theme toggle, skip-link, etc. — Issue #434 found that `ThemeToggle.astro` escaped the initial extraction because the i18n PR never touched it).
8. **A11y (WCAG 2.1 AA)** — contrast ≥4.5:1, visible focus, explicit labels, dialogs trap focus + Esc, touch targets ≥44px (mobile), status not conveyed by colour alone. Keyboard skip-link in the admin layout (`AdminLayout.astro`, Issue #434). Responsive admin sidebar (Issue #693): below `--bp-md` it becomes an off-canvas drawer with an `aria-expanded`/`aria-controls` toggle, a closing scrim, `Esc` closes it + returns focus to the toggle, focus moves into the drawer when it opens, and the rest of the page is made `inert` while the drawer is open — do not build a new drawer/dialog without an equivalent pattern (see the `<script>` comments in `AdminLayout.astro`).
9. **Masking** — sensitive data is displayed through `MaskedText`; do not cache raw PII in IndexedDB.
10. **POS specifics** — F1–F10 keyboard map (doc 14), optimistic cart with rollback, offline outbox + `SyncIndicator` (doc 15).
11. **Wide tables** — wrap them in a scroll container (`overflow-x: auto`), do not let a table force the whole page to scroll horizontally (Issue #434) — the real pattern: `<div class="data-table-scroll"><table class="data-table">` as used by `offices.astro`/`roles.astro`/`users.astro`.
12. **Capability-gated controls (Issue #693)** — NEVER render an interactive control (dropdown, button) that visually implies an action/capability and then `disabled` it on the client as the only guard (a real example: `TenantBadge.astro` replaced `TenantSwitcher.astro`, which used to do exactly that). If the capability genuinely does not exist for anyone today, do not render the control shape at all — render a static badge/text. If the capability CAN exist for some users, the computed data (option lists, permissions) must come from the server based on real authorization, not from a client flag/state; and the action's target endpoint must still reject requests from unauthorized users even when the UI "happens" not to be hidden (defense in depth — the backend is the real enforcer).

13. **Auth/login screens (doc 14 §Auth screen)** — `src/pages/login.astro` is the canonical public auth card pattern: brand header (`.auth-mark` + `.auth-wordmark`) + title/subtitle, adaptive tenant field (single-tenant readout "Signing in to <name>" / `<select>` / manual, read SSR from the root table `awcms_tenants`, bounded by `TENANT_PICKER_LIMIT`), a show/hide password toggle wired inside the bundled script (not an inline `onclick` — CSP), a styled `<select>` with a CSS caret (not a `data:` URI), and a `transform`-only card entrance (`@keyframes auth-card-rise` — not `.fade-in-up`, which starts from `opacity:0`; see doc 14 §Motion, avoid axe contrast flags on primary text). Preserve the DOM contract (`#login-form`/`#tenant-id`/`#login-identifier`/`#password`/`#login-submit`/`#login-error`) when touching it.
14. **Public auth pages besides login** — since Wave 2 there are three more: `forgot-password.astro`, `reset-password.astro`, `register.astro`. Their styling is **no longer scoped inside `login.astro`**: the `.auth-*` classes live in `src/styles/auth.css`, which all four `import`. Adding a new auth page means importing that stylesheet, not copying a `<style>` block — and adding new classes there, not to the page. The tenant picker is shared through `loadTenantPickerModel()` (`tenant-admin/application/tenant-picker-directory.ts`), so do not query `awcms_tenants` yourself. Each page has its own DOM contract pinned by a contract test — check the file before renaming an id. One rule that is easy to break: these pages face anonymous visitors, so the **post-submit message must be identical** for the "succeeded" and "did not qualify" cases — the endpoints are deliberately designed so they cannot be used as an oracle, and a UI that distinguishes the two destroys that guarantee.

## Wireframes & inventory

The layout shells (admin/POS/portal) and the route→persona→API table are in doc 14 §Screen inventory — obey its routes and its main components.

## Verification

- Rendering the 4 states (loading/empty/error/ready) can be demonstrated.
- Keyboard-only pass for POS; axe/contrast pass for AA.
- No hardcoded strings; no literal colours; no raw `fetch`.
- Offline: open the POS screen with no network → still operational, the queue is visible.
- New/migrated admin screens: layout verified at 320px, tablet, desktop, 200% zoom, and keyboard-only (Issue #693); the automated accessibility smoke test (`@axe-core/playwright`, see `tests/e2e/admin-a11y-smoke.e2e.ts`) finds no critical/serious violations.
