# AWCMS — UI Screen / Component

Follow **`docs/awcms/14_ui_ux_design_system.md`** (tokens, components, layout, screens) and **`docs/awcms/15_frontend_architecture_integration.md`** (SSR/islands, API client, offline).

## Screen implementation checklist

1. **Tokens first, and one hue has THREE roles** — use the doc 14 CSS variables (`--color-*`, `--sp-*`, `--fs-*`); never hardcode colours/sizes. Theme via `data-theme` with no flash. Picking the wrong one of the three families is the most-repeated UI defect in this repo (Issue #434, PR #720, twice more in ADR-0120):
   - `--color-X` — text/icon/border **on `--color-surface`** (a link, the outlined `.btn-danger`).
   - `--color-X-strong` — solid fill **under white text** (`.btn-primary`, the avatar disc).
   - `--color-X-on-soft` — text **on `--color-X-soft`** (status badges, the active sidebar link).

   Lines split the same way: `--color-border-strong` for anything that identifies an operable control (input/select/textarea boundary — WCAG 1.4.11 wants 3:1), `--color-border` for decorative separators only. **Adding a new foreground/background pairing to CSS means adding a line to `PAIRS` in `scripts/design-token-contrast-check.ts`** — `bun run design:token-contrast:check` is in `bun run check` and is the only thing that has ever stopped this defect.

2. **The SHELL owns the page title — do not render your own `<h1>`** (ADR-0120). `AdminLayout.astro` renders the breadcrumb, `<h1>`, description and a `page-actions` slot. Pass `title` (required), `description` or the `page-description` slot (use the slot when the description contains a link or `<code>`), and `breadcrumb` only if the derived middle crumb is wrong. There is no `<header class="page-header">` anywhere any more — 45 screens had one, every one of them printing its name twice. Put the screen's primary button in `page-actions`, not in the body.
3. **There is no component library yet — use the real markup patterns already in practice** — this repo does **not** have `src/components/ui` (no `Button`/`FormField`/`DataGrid`/`DataTable`/`Pagination`/`FilterBar`/`ActionBanner`/`StatusBadge`/`ConfirmDialog`; verify it yourself with `find src/components -type d`) — do not assume or refer to these components. The real admin screens (`src/pages/admin/offices.astro`, `roles.astro`, `users.astro`, etc.) use hand-rolled markup + consistent CSS classes: `<p class="state-notice" role="status|alert">` for access-denied/temporarily-failed states (differentiate the message per case, not with a separate component — do not invent another ad-hoc `.permission-denied` block); `<p class="admin-create-error" role="alert" hidden>` for per-form/per-action errors toggled via JS; `<div class="data-table-scroll"><table class="data-table">…</table></div>` (with `<td class="data-table-empty">` for the empty state) for lists/tables — there is **no** pagination/filter UI wired into any admin screen today (the API is already keyset-cursor, but the admin pages render the whole result as-is); `<span class="status-badge">` for lifecycle status. For confirming destructive actions, the code that EXISTS TODAY calls `window.confirm(...)` directly (see `roles.astro`/`offices.astro`) — there is no custom dialog; follow the existing pattern for new destructive actions, do not silently introduce a new dialog component without an explicit design decision. Real admin screens to copy from: `src/pages/admin/offices.astro` and `src/pages/admin/roles.astro`.
4. **State pattern is mandatory** — loading (skeleton), empty (+CTA), error (`<p class="state-notice" role="status|alert">` — differentiate "access denied" from "temporary failure, try again", with a safe i18n'd message derived from the doc 05 error code), success/submitting.
5. **Islands only where needed** — pages are SSR; interactivity only inside islands (POS, forms, chat). Initial data via SSR, mutations via the API client.
6. **Client-side form/mutation** — go through `src/lib/ui/admin-form-client.ts`. **Read its exports before writing against it** (`grep -n "^export" src/lib/ui/admin-form-client.ts`): the wiring is `onSubmit`/`onSubmitAll`/`onAction`/`mutateAndReload`, the request is `sendJson`/`sendJsonRequest`/`sendJsonForData`, the feedback is `lockElement` + `messageBox`, and the field readers are `field`/`inputValue`/`blankToNull`/`checkboxChecked`/`integerValue`/`localDateTimeToInstant`. An earlier revision of this skill told you to use `postJson`, which **was deleted on 22 August 2026** (PROJECT_STATE D12 — it had zero callers and a docblock claiming otherwise), and warned you off `showBanner`/`submitJson`, which never existed. That is why the instruction is "grep the exports", not "use these names". `lockElement` prevents double-submit (disables the button + busy label for the duration of the request, restoring it including on failure); `sendJson` returns a narrow `{ ok, errorCode }` that never throws. **Importing from this module is mandatory, not merely DRY**: this repo's CSP is `default-src 'self'` without `'unsafe-inline'` (`astro.config.mjs`/security-headers middleware) — Astro hoists an import-free `<script>` into inline (blocked by CSP), whereas a script that imports from `admin-form-client.ts` is bundled into an external `/_astro/*.js` file that `'self'` permits; without this import, admin page scripts can "silently die" because CSP blocks them with no obvious error. Do not duplicate this implementation per page, and do not use raw `fetch`.
7. **Role-aware navigation** — filter the menu from the permissions in `GET /auth/me`; the backend still validates (hiding in the UI is not a control).
8. **i18n** — see the `awcms-i18n` skill (gettext `.po` catalogues, locale resolution via middleware, locale-aware formatters, `LanguageSwitcher.astro`) — static UI strings **always** go through `t("The English sentence")` — the msgid **is** the English text, there are no `namespace.key` identifiers — never hardcoded, including small components (theme toggle, skip-link, etc. — Issue #434 found that `ThemeToggle.astro` escaped the initial extraction because the i18n PR never touched it).
9. **A11y (WCAG 2.1 AA)** — text ≥4.5:1 (1.4.3) **and control boundaries ≥3:1 (1.4.11)**, visible focus, explicit labels, status not conveyed by colour alone, keyboard skip-link (`AdminLayout.astro`, Issue #434). Target size: ≥44px on the mobile portal and on touch-first controls; admin form controls are deliberately **38px** since ADR-0120 (WCAG 2.2 AA asks 24px, this is pointer-first, and 44px inputs beside 36px buttons made every filter bar look mis-set) — do not "fix" that back to 44 in isolation.

   **Modals: use a native `<dialog>` + `showModal()`.** It supplies the focus trap, `Esc`, page inertness, the backdrop and focus restore with no script — see `src/lib/ui/admin-command-palette.ts`. The admin **sidebar drawer** is the exception and is **CSS-only** (a hidden checkbox `#admin-nav-toggle` + two `<label>`s; the closed drawer is `visibility: hidden` so its links leave the tab order). It therefore has **no `Esc`-to-close and no focus trap**, which is an accepted trade for a nav drawer and is **not** a licence to build an input-taking modal the same way. An earlier revision of this skill described a JS drawer with `aria-expanded`, `inert` and a hand-written focus trap, and pointed at `<script>` comments in `AdminLayout.astro` — that script does not exist.

10. **Masking** — sensitive data is displayed through `MaskedText`; do not cache raw PII in IndexedDB.
11. **POS specifics** — F1–F10 keyboard map (doc 14), optimistic cart with rollback, offline outbox + `SyncIndicator` (doc 15).
12. **Wide tables** — wrap them in a scroll container (`overflow-x: auto`), do not let a table force the whole page to scroll horizontally (Issue #434) — the real pattern: `<div class="data-table-scroll"><table class="data-table">` as used by `offices.astro`/`roles.astro`/`users.astro`.
13. **Capability-gated controls (Issue #693)** — NEVER render an interactive control (dropdown, button) that visually implies an action/capability and then `disabled` it on the client as the only guard (a real example: `TenantBadge.astro` replaced `TenantSwitcher.astro`, which used to do exactly that). If the capability genuinely does not exist for anyone today, do not render the control shape at all — render a static badge/text. If the capability CAN exist for some users, the computed data (option lists, permissions) must come from the server based on real authorization, not from a client flag/state; and the action's target endpoint must still reject requests from unauthorized users even when the UI "happens" not to be hidden (defense in depth — the backend is the real enforcer).

14. **Auth/login screens (doc 14 §Auth screen)** — `src/pages/login.astro` is the canonical public auth card pattern: brand header (`.auth-mark` + `.auth-wordmark`) + title/subtitle, adaptive tenant field (single-tenant readout "Signing in to <name>" / `<select>` / manual, read SSR from the root table `awcms_tenants`, bounded by `TENANT_PICKER_LIMIT`), a show/hide password toggle wired inside the bundled script (not an inline `onclick` — CSP), a styled `<select>` with a CSS caret (not a `data:` URI), and a `transform`-only card entrance (`@keyframes auth-card-rise` — not `.fade-in-up`, which starts from `opacity:0`; see doc 14 §Motion, avoid axe contrast flags on primary text). Preserve the DOM contract (`#login-form`/`#tenant-id`/`#login-identifier`/`#password`/`#login-submit`/`#login-error`) when touching it.
15. **Public auth pages besides login** — there are four more: `forgot-password.astro`, `reset-password.astro`, `register.astro`, `accept-invitation.astro`. Their styling is **not** scoped inside `login.astro`: the `.auth-*` classes live in `src/styles/auth.css`, which all five `import`. Since ADR-0120 all five are a **split panel** — `<main class="auth">` is a two-column grid at ≥900px holding `AuthBrandPanel.astro` beside an `.auth-form-panel`. A new auth page renders `<AuthBrandPanel />` too. That panel is `aria-hidden="true"` and repeats nothing the form half does not already say; below 900px it is not rendered at all. Its gradient uses **literal colours on purpose** — it is a brand surface, and a `--color-*` token would flip it with `data-theme`. Adding a new auth page means importing that stylesheet, not copying a `<style>` block — and adding new classes there, not to the page. The tenant picker is shared through `loadTenantPickerModel()` (`tenant-admin/application/tenant-picker-directory.ts`), so do not query `awcms_tenants` yourself. Each page has its own DOM contract pinned by a contract test — check the file before renaming an id. One rule that is easy to break: these pages face anonymous visitors, so the **post-submit message must be identical** for the "succeeded" and "did not qualify" cases — the endpoints are deliberately designed so they cannot be used as an oracle, and a UI that distinguishes the two destroys that guarantee.

## Verification

- Rendering the 4 states (loading/empty/error/ready) can be demonstrated.
- `bun run design:token-contrast:check` passes — and if the screen introduced a new foreground/background pairing, that pairing has a line in `PAIRS`. The gate cannot measure a combination nobody registered.
- Keyboard-only pass for POS; axe/contrast pass for AA **in a real browser**. Dev mode is not good enough: Vite serves CSS as a `<script type="module">`, which this CSP blocks, so a dev-server screenshot is an unstyled page. Build and run `dist/standalone-entry.mjs`.
- No hardcoded strings; no literal colours; no raw `fetch`; **no inline `style=` attribute** — `default-src 'self'` has no `'unsafe-inline'`, so a `style="…"` is dropped by the browser with nothing in the build to warn you.
- The screen renders **no `<h1>` of its own** and no `page-header` block.
- Offline: open the POS screen with no network → still operational, the queue is visible.
- New/migrated admin screens: layout verified at 320px, tablet, desktop, 200% zoom, and keyboard-only (Issue #693); the automated accessibility smoke test (`@axe-core/playwright`, see `tests/e2e/admin-a11y-smoke.e2e.ts`) finds no critical/serious violations.
