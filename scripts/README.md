# AWCMS Scripts

The repo's tooling/ops scripts, run through Bun (`bun scripts/<x>.ts` or the
`bun run <name>` target in `package.json`).

## Inventory

The table below is **generated from `package.json`** by
`bun run scripts:inventory:generate`, and `bun run scripts:inventory:check`
(in the `check` chain) fails if it is stale.

The reason is not tidiness. The previous hand-written version listed 12 of 52
scripts as active, and its companion table called fifteen pieces of tooling
"not yet ported" when all of them had already landed — some of them already in
the `bun run check` chain (`api:docs:check`, `modules:compose:check`,
`db:work-class:check`, and every per-module worker). **Negative** claims are
the dangerous kind: "X does not exist yet" gets more wrong over time and never
fails on its own, unlike a positive claim that breaks the moment the code
changes. The reader would conclude `db:work-class:check` still needs building,
and then build a duplicate of it.

## What is not in `check`, and why

The `check` chain must be safe to run on any local checkout without a database,
without a server, and without PR context. What sits outside the chain is there because it
violates one of those conditions:

| Target                                                                  | Why it is outside `check`                                                                                     |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `security:readiness`                                                    | Needs a migrated database — it checks RLS `FORCE`, a non-superuser app role, worker/setup grants              |
| `config:validate`                                                       | Needs a real environment (`process.env`, or `--file <path>`). Run it before deploying                         |
| `db:migrate`, `db:pool:health`, `redis:health`, `email:provider:health` | Needs a running database/Redis/provider                                                                       |
| Every scheduled worker                                                  | Needs a database, and is run by cron/systemd — see `ModuleDescriptor.jobs` + `GET /api/v1/modules/{key}/jobs` |
| `changesets:policy:check`                                               | PR-diff shaped (`origin/main...HEAD`); run by `.github/workflows/changesets.yml`                              |
| `release:verify`                                                        | Only meaningful on a `vX.Y.Z`-tagged commit; run by the `validate` job in `.github/workflows/release.yml`     |
| `*:generate`                                                            | The write half of a `*:check`. The one gating CI is its `:check`                                              |

The authoritative order of the `check` chain lives in `package.json` itself — deliberately not
duplicated here so it cannot drift.

## Job schedules

Not listed here. The source of truth is `ModuleDescriptor.jobs` (per module,
carrying `purpose`, `recommendedSchedule`, `environmentNotes`,
`safeInOfflineLan`), served through `GET /api/v1/modules/{moduleKey}/jobs` and
gated by `bun run modules:jobs:check`. See
[`docs/awcms/deployment-profiles.md`](../docs/awcms/deployment-profiles.md)
§Job registry.

## Deferred (not present in this repo yet)

The following reference scripts have not been ported because they depend on architecture that has
not been built. `scripts:inventory:check` **fails** if any of the names
below turns out to be registered in `package.json` — that is exactly how the previous
table rotted.

These names may be mentioned as **targets** in `docs/awcms/` and
`.claude/skills/` (documents adapted from the reference repo), but they must not
appear as `bun run <target>` in **current-state** files: `README*.md`,
`AGENTS.md`, `CONTRIBUTING.md`, `docs/ARCHITECTURE.md`, `docs/PROJECT_STATE.md`,
this file, module READMEs under `src/**`, and **code comments** in `src/`/`scripts/`.
`check:docs` gates that. That source coverage was added after finding
six comments in `src/modules/module-management/` telling the reader to
run the `modules:sync` target — a command that never existed in this repo
(the real mechanism is `POST /api/v1/modules/sync`) — while `bun run check`
stayed green because its old gate only read five root markdown files.

| Reference target                                | Missing prerequisite                                                 |
| ----------------------------------------------- | -------------------------------------------------------------------- |
| `config:docs:check`                             | Three-way reconciliation `.env.example` ↔ doc 18 ↔ `validate-env.ts` |
| `i18n:extract` / `:pot:check` / `:parity:check` | i18n setup (`.po`/`.pot`) + UI                                       |
| `database:capacity:check`                       | Cross-instance capacity validation (preflight)                       |
| `production:preflight`, `resilience:dr-drill`   | Aggregates the gates above + a running server                        |
| `performance:*`                                 | A load harness + a production-sized environment                      |

See the sprint map in
[`docs/awcms/11_implementation_blueprint.md`](../docs/awcms/11_implementation_blueprint.md)
and the related skills in [`.claude/skills/`](../.claude/skills/README.md).
