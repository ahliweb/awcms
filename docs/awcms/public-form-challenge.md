# Public-form challenge (captcha) seam

Implementation reference for Issue #1353 (owner decision K9, 22 November 2026). Module contract `4.8.0`. **No migration.** Cloudflare Turnstile ([ADR-0029](../adr/0029-deployment-profile-aware-turnstile-bot-protection.md), `turnstile-bot-protection.md`) is the first provider behind it, and its former per-route call sites now go through this seam, so there is **one** path.

## 1. What it is

A pre-session form (login, forgot/reset password, register, invitation accept, platform setup, or a module's own public form) opts into a human-presence challenge with one call:

```ts
const refused = await enforcePublicFormCaptcha(request, "my_form", body, {
  clientIp
});
if (refused) return refused;
```

No edit to a shared file. `src/lib/security/public-form-challenge.ts` owns the seam; a module contributes a provider from its own descriptor (`ModuleDescriptor.publicFormChallengeProviders`, ADR-0164's model: the seam reads the module list through the extension-point source that `src/middleware.ts` installs). The platform ships exactly one provider, Turnstile, declared by `identity-access`. It ships no widget and no puzzle of its own.

**The rate limit of each route stays the primary control.** It runs before the seam and is not relaxed by it.

## 2. Contract, in the order it is enforced

| Property                 | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Off by default           | No declared provider switched on by its own `isEnabled(env)` means the call returns `null`; a deployment that sets nothing behaves exactly as before. Turnstile is on only with the full-online profile gate and `TURNSTILE_ENABLED=true`. A process that installed **no extension-point source** cannot tell which providers exist, so the seam **refuses** (fail-closed, ADR-0164); the web entry installs it, and tests get it from the `bunfig.toml` preload. |
| One provider             | More than one enabled provider is a configuration error and the request is **refused**, with the refusal text of the provider that triggered it (the same words as an ordinary refusal, so wording is no configuration oracle). A provider whose `isEnabled` throws is refused too, never assumed off.                                                                                                                                                            |
| Fail-closed              | A missing token, a refusing verifier, a verifier that **throws**, one that does not answer in 10 s, and a result that is not exactly `{ ok: true }` all refuse the request. The verifier's error text is never logged or returned.                                                                                                                                                                                                                                |
| Single use               | A presented token is burned (hashed, bounded to 10 000 entries, 15 minutes, per process) **before** the verifier is asked, so a replay is refused even when requests race, and a refused attempt cannot be retried with the same token. The provider's own `verify` is the source of truth across processes; this is defence in depth.                                                                                                                            |
| Bound to form and tenant | `verify` receives the form name and the tenant (`x-awcms-tenant-id`, or the `tenantId` option, or `null` for a tenant-less form) and must refuse a token issued for another. Turnstile binds the form (its `action`) and the hostname; it has no tenant concept, so its tenant binding is the deployment's host.                                                                                                                                                  |
| No oracle                | Everything except "nothing presented" is one response: wrong form, wrong tenant, replay, expired, verifier error and timeout are indistinguishable. "Nothing presented" is `CHALLENGE_REQUIRED` so a client knows to render its widget.                                                                                                                                                                                                                           |
| Bounded input            | A field over 4 096 characters is refused without reaching the verifier; a non-string field counts as absent.                                                                                                                                                                                                                                                                                                                                                      |

## 3. Provider contract

`ModulePublicFormChallengeProvider` (`src/modules/_shared/public-form-challenge-contract.ts`): `key`, `isEnabled(env)`, `issue(formName, tenantId) -> challenge`, `verify({ token, challengeId, challengeAnswer, formName, tenantId, remoteIp, env }) -> { ok: true } | { ok: false, reason }`, and optionally `legacyTokenField` and `refusal` (code and message of an already published contract; Turnstile keeps `TURNSTILE_REQUIRED` / `TURNSTILE_INVALID` and the `turnstileToken` field). A self-hosted arithmetic challenge and a third-party provider are both valid implementations; `issuePublicFormChallenge(formName, tenantId)` is the server entry point for an endpoint that hands a client its challenge (the platform ships no such endpoint, because no provider of its own needs one).

A provider whose verifier reads a **web-only secret** (Turnstile's `TURNSTILE_SECRET_KEY`) must keep its descriptor LIGHT: `listModules()` is imported by dozens of jobs, so importing the file that reads the secret would put it in their import closure (`tests/jobs-env-scoped-reach.test.ts`, part c, fails, and the secret would have to be copied into every job container). Its `verify`/`issue` therefore resolve the implementation from a verifier slot (`_shared/public-form-challenge-verifier-slot.ts`) that `src/lib/security/public-form-challenge-bindings.ts` fills; the seam imports that file, so every process that enforces a challenge has it bound, and no job does. Nothing bound means `verify` throws, which the seam refuses. A provider with no web-only secret just implements `verify` in its descriptor.

`bun run extension-points:check` validates the declarations (unique snake_case keys, the three functions present, well-formed refusal codes, no `solveForTests` in a descriptor) and refuses any file outside a short allow-list that **imports** `enforceTurnstileIfRequired` or `verifyTurnstileToken` from `turnstile.ts` (an alias, a namespace import, a re-export, a dynamic `import()` or `require()` is caught too): such an importer is a second path that skips the burn, the deadline and the uniform refusal. The allow-list is the module itself, the web-only binding, and `website-engagement`'s submission intake, which verifies Turnstile per SOURCE (its own action and the source's allowed hostnames), a different shape from a pre-session form; the reason is recorded next to the entry.

## 4. Client

Field contract: `challengeId`, `challengeAnswer`, `challengeToken`. `src/lib/ui/public-form-challenge-client.ts` reads them from the submitted form (`readChallengeFields`, which also reads Turnstile's `cf-turnstile-response` as `challengeToken`) so a page spreads them into its JSON body, and `focusChallengeOnRefusal` hands focus back to the element marked `data-challenge-widget` when the response code is a challenge refusal. With no widget on the page the helper returns `{}`, so the body is exactly what it was. A page script must **import** the helper: Astro inlines a script without an import and this app's CSP blocks inline scripts.

**The widget is provider-driven (module contract 4.9.0).** A provider declares its client widget in its descriptor (`widget`: optional external `scriptSrc`, the `cspOrigins` it needs, a `containerClass`, and `attributes({ formName, challenge })` returning `data-*` attributes built from what `issue` returned; Turnstile: the public site key and the form name as `action`). A page renders `<PublicFormChallengeWidget formName={PUBLIC_FORM_NAMES.x} />` (`src/components/PublicFormChallengeWidget.astro`), which calls `resolvePublicFormChallengeWidget` for the **enabled** provider and renders nothing when none is on, when the provider declares no widget, or on any error (the server still refuses a request with no token, so a missing widget never fails open). The loader is an external `<script src>`, never inline; provider output is untrusted at this boundary, so only `data-*` attributes with bounded string values survive. The middleware opens the declared `cspOrigins` in `script-src`/`frame-src` for the enabled provider only (`challengeWidgetOrigins` of `buildSecurityHeaders`; only plain `https://host[:port]` origins are admitted, a malformed entry is dropped, and a gate fails a malformed declaration). Login, register, forgot, reset and accept-invitation use the component and `readChallengeFields` / `focusChallengeOnRefusal`; none sends the legacy `turnstileToken` any more, and `/accept-invitation` now carries the widget (before, the accept API required a token the page could not produce when Turnstile was on).

**The legacy `turnstileToken` field is still ACCEPTED by the server** (no page sends it). It is a published wire field: ADR-0029 and the OpenAPI bodies document it, and the frozen pre-migration snapshot check (`tests/openapi-bundle.test.ts`, `isAdditiveSuperset`) fails if it is removed from `/auth/login` or `/setup/initialize`. Removing it is a contract change that needs its own deprecation window and ADR note; it is not done here.

## 5. Integration harness

A module declares the public forms it owns and their API routes in its own descriptor (`publicFormChallengeForms: [{ formName, routes }]`, module contract 4.9.0; `[param]` segments allowed). `resolvePublicFormForRoute(pathname)` reads those declarations, so the harness keeps **no** route-to-form table and a module's new protected route needs no harness edit (the former shared `PUBLIC_FORM_ROUTE_FORMS` is gone). `extension-points:check` closes the loop in both directions: a declared route must be a real route file, a route file that calls `enforcePublicFormCaptcha` must be declared, and that file must name the declared form.

`invoke()` in `tests/integration/harness.ts` adds a **solved** challenge to the JSON body of a declared public form when a provider is on and has a solver registered with `registerPublicFormChallengeTestSolver` (a test-only registration inside the seam; it refuses outside `NODE_ENV=test`, and `extension-points:check` rejects a call from `src/` or `scripts/`, so a solver cannot ride along in a production descriptor), so a suite needs no per-route edit. `challenge: false` opts out (to test a refusal); fields already in the body are never overwritten. With no provider on, which is the default, nothing changes.

## 6. Open points

- The single-use burn is per process. A provider without its own single-use guarantee is replayable across processes; the contract requires the guarantee at the provider.
- `newsletter` (`POST /api/v1/newsletter/subscribe`) and `comments` (`POST /api/v1/comments`) now call the seam once each, after their per-IP limiter and before any database work. **Trade-off to decide before enabling Turnstile on a deployment that serves tenant sites:** Turnstile pins ONE hostname (`TURNSTILE_EXPECTED_HOSTNAME`), and these two routes are called from tenant public sites on other hostnames (and by `awcms-astro`), so with Turnstile on a request from another host is refused until the form carries the widget and a per-tenant or multi-host binding exists. With the seam off (default) nothing changes. Their OpenAPI operations document the `challenge*` fields and the `TURNSTILE_REQUIRED`/`TURNSTILE_INVALID` 400. The per-tenant or multi-host binding and the `awcms-astro` widget wiring are not built; do them before enabling Turnstile on a multi-host deployment. They are bound by form name only (`tenantId: null`) because the tenant is resolved from the host inside the transaction.
- The website-engagement source intake keeps its own per-SOURCE verification (Issue #1477 owns it).
- A shared, database-backed single-use burn ledger is deferred (follow-up issue #1524). Turnstile's own `siteverify` is single-use at Cloudflare, which is the cross-process guarantee today; the per-process burn only closes the replay window inside one process. With several web replicas a replayed token can reach `siteverify` once per replica, and Cloudflare still refuses the second; a provider WITHOUT its own single-use guarantee is replayable across replicas until the ledger exists.
- `forgot` and `reset` still share the form name `password_reset` (so one Turnstile token action serves both pages); splitting them changes a published Turnstile `action` and is not done here.
