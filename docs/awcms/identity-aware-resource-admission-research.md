# Identity-aware resource admission — research and ADR proposal

- Version: 0.2.0
- Date: 2026-11-28
- Status: PROPOSED research, pre-Gate 9. Not an accepted ADR, not an implemented feature, not production evidence.
- Related issue: #1541
- Evidence snapshot: `main` at commit `f19aa0a8b8e0` (2026-11-28), static reading only.
- Document changeset: references re-checked at takeover, unverifiable statements removed or marked, Indonesian mirror added; all design items stay `proposed`.

## 1. Problem and evidence

Network identity is a useful anonymous admission signal, not a principal. NAT, CGNAT and a shared backend-for-frontend egress may group unrelated users; valid credentials must not remove infrastructure bounds. RFC 6269 documents address sharing; RFC 6585 defines the 429 response without prescribing how a client is identified. OWASP API4:2023 and NIST SP 800-228 cover resource consumption and API protection.

A public video motivated the question: <https://www.youtube.com/watch?v=MopxiEARThI>. Its transcript was unavailable and it was not verified; it is a trigger for the research, not evidence, and no conclusion is attributed to it. The design below is independent: no external code, assets, dependency or license admission.

Verified by static reading of the default branch at takeover (not executed, no deployed configuration seen):

- `src/lib/security/rate-limit.ts` (blob `5d5c07690d673d3164440290428956bd0e06c13d`): a fixed-window limiter with a shared Redis path and an in-process fallback; the local window is anchored on the first hit, the shared window on `floor(now / window)`, so the two anchors differ today. The documented posture for a configured-but-unreachable Redis is described in the file header and in [ADR-0066](../adr/0066-shared-rate-limiting-and-full-auth-surface-coverage.md).
- `src/lib/security/auth-rate-limit.ts`: a per-source ceiling checked together with the per-tenant ceiling on the auth routes.
- [ADR-0172](../adr/0172-more-than-one-application-process-per-node-is-supervised-inside-the-image-behind-an-opt-in-count-and-is-gated-on-the-state-that-assumes-one-process.md) and issues #1503 and #1508 cover the effective instance count (replicas times processes). Issue #1540 covers counter lifecycle and refund atomicity as a potential, static, not reproduced finding. Issue #1385 is closed and was contract work, not a behavior change.
- Not verified at takeover: the earlier claims about the session-introspection source ceiling and about worker polling (a pre-auth claimed pair plus a source backstop and signature verification). They are removed from the baseline until someone inspects them.

Before any implementation, inventory all rate-limit and refund call sites, tests, migrations, OpenAPI and telemetry at the then-current branch HEAD.

## 2. Proposed decisions and alternatives

- Reuse the existing shared limiter, proxy configuration, identity and access, work-class admission, audit, PostgreSQL and Redis; no new service by default. Keep one-process offline/LAN supported; multi-process admission is subject to ADR-0172. Do not change accepted ADRs without review.
- Pre-auth: cheap edge, source and global limits, a body cap, concurrency and target-identifier attempt signals (HMAC, bounded TTL and cardinality; not proof of identity); preserve uniform account and tenant error and timing behavior. Retain the source ceiling even for verified actors, but tune the shared-network ceiling separately. Use a trusted proxy hop count only with an authenticated, isolated origin and a validated proxy path; canonicalize the IP and reject malformed forwarded values.
- Post-auth: verified tenant and actor from the existing authorization context (session, credential, worker signature), operation from the server route registry; independent actor, tenant, global and cost quotas. Never use a caller-supplied ID or token string as an authoritative bucket. Avoid long-lived per-token keys; a stable account prevents session-rotation bypass. Rate limiting never grants RBAC/ABAC or bypasses FORCE RLS.
- A fixed window is O(1) and cheap but admits a burst of up to 2L near a boundary; keep the contract until an approved migration. A sliding counter is approximate; an exact sliding log needs O(n) state. A token bucket with burst B, refill r and cost c admits only if tokens >= c and bounds admitted cost over an interval t by B + r·t under ideal serialized state. Weighted token units must be measured and capped; concurrency is separate (active work, not arrival rate). Adaptive policy is deferred until stable telemetry and overload tests exist.
- Per-bucket atomic decision plus TTL, bounded eviction and cardinality, and monotonic or authoritative time. Distinguish attempts charged even on rejection from work reservations; avoid naive compensation; make reservation and refund idempotent within the original window (absent or expired means no-op). A timeout may mean the work ran: do not blindly retry a debit. Cross-slot Redis operations cannot promise all-key atomicity: choose conservative sequential attempt charging, same-slot co-location after explicit review, or a persistent transaction for a hard multi-scope budget. Redis failover loss and clock skew need explicit error bounds; no exact global guarantee is claimed.
- Financial or paid-agent limits are durable business controls: a PostgreSQL transaction conditionally reserves all parent budgets before dispatch; unique idempotency key; settle the actual cost and release only a known unused reservation; an ambiguous external effect stays pending or unknown and is reconciled, never treated as zero. Concurrency leases carry a TTL with fencing at the execution authority; a stale lease cannot perform a new effect. A rate-limit token is not a monetary balance.
- Cloudflare edge limiting is optional, coarse and advisory (per-location, eventually consistent counts); the origin must still enforce policy. No added dependency and no assumption of a global hard edge budget.

## 3. Proposed policy contract (design, not schema)

Policy ID and version, owner, route or operation, pre/post-auth stage, trusted scope resolver, independent bucket dimensions, algorithm, positive integral cost and capacity, window or refill, max active work, store authority, retention, error and overshoot semantics, failure mode, exception expiry, metrics and tests. The default policy for an unclassified new endpoint must be reviewed; invalid configuration is rejected in CI. Key serialization is length-bounded and unambiguous, namespaced by deployment and version, with purpose-specific HMAC for sensitive identifiers and key rotation with overlap and expiry; no raw bearer token, OTP, email or IP in logs. Telemetry labels are restricted to policy, route, outcome and reason class; tenant and actor identifiers appear only in protected audit where necessary. Audit is not a per-request amplification channel.

Decisions: ALLOW, THROTTLED, DEPENDENCY_UNAVAILABLE; carry retry-after seconds where meaningful, with reason and policy version kept internal; the public envelope follows existing contracts and never leaks another tenant's capacity. 429 when a quota is exceeded, 503 when a required authority is unavailable; no-store; Retry-After as defined by the HTTP specifications (RFC 6585 and RFC 9110); the IETF RateLimit header fields stay optional pending a final RFC or ADR. Clients bound retry with jitter and idempotency and never blindly retry a mutation or an ambiguous spend.

| Work class           | Controls                                                         | Store failure proposal                                                              |
| -------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Public static/cache  | edge + bounded local capacity                                    | degraded read; no auth bypass                                                       |
| Login/registration   | source/global + account/authenticator + admission                | preserve PostgreSQL account defense; bounded local emergency mode only after review |
| Search/export/upload | actor+tenant+cost, size/time/active limits                       | degrade or refuse expensive work                                                    |
| OTP/provider calls   | target+tenant+global + hard provider budget                      | reject if required quota unavailable                                                |
| Checkout/payout      | actor/tenant throttles + separate transactional ledger           | reject unsafe mutation, preserve durable webhook ingress/idempotency                |
| Worker/agent         | verified worker+tenant+run + host admission and budget authority | pause new paid work, recover known work, no duplicate runtime                       |

## 5. Measurement and rollout (proposed)

Hypotheses: verified actor quotas reduce shared-egress collateral throttling; independent tenant limits reduce noisy-neighbor starvation; an atomic lifecycle bounds stale state. Compare a baseline against a candidate with a reproducible seed, the same build and configuration, single-process and distributed real Redis and PostgreSQL, cache warm and cold, legitimate bursts and synthetic abusive load. Record offered versus accepted rate, legitimate false positives (rejected eligible / eligible), per-scope overshoot (admitted cost minus declared bound, floor zero), per-tenant demand-normalized acceptance, p50/p95/p99, memory, TTL and key count, CPU, pool wait, error/429/503 counts, timeouts and recovery. Use repeated runs and report distributions and uncertainty, hardware, dataset, SHA and policy version; no invented thresholds, and tolerances are agreed before testing.

Hard ledger invariant: no committed reservation exceeds the authorized budget under concurrency (subject to explicit provider billing uncertainty); no financial reliance on edge or Redis. Rollback means returning the policy version to the prior approved configuration with a compatibility and TTL drain; never weaken authentication and never edit applied migrations.

Implementation would also need security review, the repository's required checks at that time, a changeset where behavior changes, English and Indonesian documentation, the contract gate and the relevant RLS tests. Security-scan requirements follow the repository's CI policy at implementation time. Upstream release comes before consumer subtree sync; UAT happens in the consuming repository. Gate 9 comes first, then atomic issues and pull requests; Gate 15 and approval are needed before production. This document claims no gate status.
