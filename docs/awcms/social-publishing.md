# Social publishing (`social_publishing`)

> **Status:** implemented foundation and **one connector, Facebook Pages (Issue [#1146](https://github.com/ahliweb/awcms/issues/1146)), off by default** behind `SOCIAL_PUBLISHING_FACEBOOK_ENABLED`; the connector's API versions, permissions and error mapping are in the module README (`src/modules/social-publishing/README.md`, section "Facebook Pages connector"). Migration `sql/373` activates the dispatcher's own role for the whole job. Issue [#1145](https://github.com/ahliweb/awcms/issues/1145), [ADR-0157](../adr/0157-social-publishing-is-an-account-scoped-publication-intent-and-per-account-job-module.md) (**Proposed**), capability C3 of [ADR-0148](../adr/0148-omnichannel-foundation-is-five-gated-capabilities-with-fail-closed-per-account-capability.md) and [`omnichannel-foundation.md`](omnichannel-foundation.md) section 2.3. Migrations `sql/330` to `sql/331`. The module is `experimental` and off by default.

## 1. What it is

The module that turns "an article was published" (or "an operator wants this said") into **one publication** with an immutable content snapshot and **one job per target `channel_account`**, and delivers each job through a provider adapter, outside any transaction, safely retried and never replayed.

It is a plug-in host. It ships the interface, the registry, the queue, the dispatcher, the approval and schedule rules and the API. It ships **no provider adapter** and makes no provider call: the connectors for Facebook, Instagram, Threads, TikTok, YouTube and LinkedIn are separate issues (#1146 to #1151), each of which also needs its provider app approval or audit evidence (a business step, not a code step). Until one registers, enabling the module publishes nothing.

## 2. Data

| Table                              | Key facts                                                                                                                                                                                                                                                                                                                 |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `awcms_social_publishing_settings` | One row per tenant. `auto_publish_enabled` default `false`; `approval_required` default `true`                                                                                                                                                                                                                            |
| `awcms_social_publish_rules`       | `(tenant, trigger, account)` unique. `enabled`. A pointer to an account, not a grant. At most 200 per tenant                                                                                                                                                                                                              |
| `awcms_social_publications`        | The intent. `source_kind` (`article`, `manual`), `source_id`, trigger, `state`, the immutable snapshot (`title`, `caption`, `link_url`, `media_snapshot`, `content_hash`), `not_before`, approval and cancel stamps. Unique per (article, trigger)                                                                        |
| `awcms_social_publish_jobs`        | One per (publication, account). `provider`, `account_kind`, `variant`, `idempotency_key` (unique per tenant), `status`, `attempt_count`, `max_attempts`, `hold_count`, `next_attempt_at` (also the claim lease), the provider's post id and URL, a coded failure and a fixed phrase. **No token and no secret reference** |
| `awcms_social_publish_attempts`    | Append-only ledger, unique per (job, attempt number): outcome, fixed code, fixed phrase                                                                                                                                                                                                                                   |

The aggregate status of a publication (`pending_approval`, `queued`, `in_progress`, `partially_published`, `published`, `failed`, `cancelled`, `refused`) is **derived** from its jobs when read.

State machines:

```text
publication.state:  pending_approval -> ready -> cancelled        refused (terminal, zero jobs)
                    pending_approval -> cancelled
job.status:         queued -> publishing -> published (terminal)
                                         -> retry_wait -> publishing ...
                                         -> failed -> queued (manual retry only)
                    queued | retry_wait -> cancelled (terminal)
```

A database trigger enforces: the snapshot and identity never change; `published` and `cancelled` jobs never change; a failed job can only go back to `queued`; the attempt counter never decreases; a job is created only for a live publication and a `connected` account of its own tenant.

## 3. The flow

1. **Article event.** `blog_content` calls `SocialPublishingPort.onArticlePublished` inside its publish transaction. With the deployment flag off, the tenant switch off, or no rule for the trigger, it answers `{ jobsCreated: 0 }` and does nothing. Otherwise it builds the snapshot (excerpt or title as caption, `https://{APP_URL origin}/blog/{tenantCode}/{slug}` as the link, the featured image resolved through `MediaLibraryPort`), then enqueues for every enabled rule account. It runs in a savepoint: any failure rolls back only this module's writes and the article still publishes.
2. **Manual publication.** `POST /api/v1/social-publishing/publications` takes a title, a caption, an optional link, an optional media object and the account ids. The caller must be able to use every account.
3. **Enqueue rules, per account, in order.** The account may publish now (`channel_accounts` port: connected, active connection, `publish` capability granted with evidence under the current matrix); the provider has an adapter; the adapter's capability map can carry the content (variant, caption length including the link, image type and size). Any failure is a returned code for that account. Accounts are evaluated before anything is written, so a request in which every account is refused records nothing.
4. **Approval and schedule.** With approval required the publication waits; the dispatcher claims nothing until `approve`. A manual publication cannot be approved by its creator. `not_before` defers dispatch; `schedule` moves it while nothing has been dispatched.
5. **Dispatch.** `bun run social-publishing:dispatch`, three phases: claim (lease, per-account advisory lock, fair share and daily cap, account re-check), send (the credential comes from a credential port, the real one only behind the connector switch, otherwise one that refuses every request; the adapter is called with an `ssrfSafeFetch` client that follows no redirects, a timeout that cancels the request and a per-account circuit breaker), finalise (compare-and-set on the claimed attempt, ledger, event, audit).

## 4. Failure behaviour

| Situation                                                           | Result                                                                                                                                                                                                                                                                                          |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Account revoked, disabled, capability withdrawn, connection revoked | Job `failed` (`ACCOUNT_*`), provider never called, nothing rerouted                                                                                                                                                                                                                             |
| Account degraded, pending, grant expired, secret store unavailable  | Job held (`queued`, `hold_count + 1`, no attempt consumed); `HOLD_EXHAUSTED` after 12 holds                                                                                                                                                                                                     |
| Provider definitely did not accept (the adapter says `retryable`)   | `retry_wait` with exponential backoff (capped at 4 hours); `RETRIES_EXHAUSTED` when spent                                                                                                                                                                                                       |
| Timeout, an adapter that threw, or an adapter's own `unknown`       | **The post may exist.** A provider that dedupes on the idempotency key (`supportsIdempotencyKey`): `retry_wait`, same key, one post. Any other: `needs_reconciliation`, never retried by the dispatcher; an operator checks the account and retries with `confirmPossiblyPublished`, or cancels |
| Rate limited                                                        | Same, and the provider's `retryAfterSeconds` can only lengthen the wait                                                                                                                                                                                                                         |
| Credentials no longer accepted                                      | `failed` `NEEDS_REAUTH`; never retried by backoff                                                                                                                                                                                                                                               |
| Provider rejected the content                                       | `failed` with a fixed code; never retried by backoff                                                                                                                                                                                                                                            |
| Another job of the same publication failed                          | No effect on a published sibling; a manual retry moves only the failed job                                                                                                                                                                                                                      |
| Worker crashed mid-send                                             | The lease expires: a lost answer. A provider that dedupes gets the same key again as a new attempt; any other provider's job becomes `needs_reconciliation` (`LEASE_EXPIRED_UNKNOWN`) and is never re-sent by the dispatcher (the database refuses the re-claim too)                            |
| Breaker open for an account                                         | Its jobs are not claimed; other accounts are unaffected                                                                                                                                                                                                                                         |
| Source article no longer published publicly (ADR-0157 L8)           | Re-checked just before the call: `failed` `SOURCE_RETRACTED` (unpublished, archived, private, deleted, past `unpublish_at`); no credential decrypted, provider never called, never retried by the dispatcher                                                                                    |
| Media object taken down, or its rights withdrawn (ADR-0157 L8)      | Same: `failed` `MEDIA_UNAVAILABLE` (missing, soft-deleted, not `verified`/`attached`) or `MEDIA_RIGHTS_REVOKED` (rights not `verified`, copyright unknown; `fair_use` stays accepted)                                                                                                           |
| The re-check itself cannot be answered (a database error)           | Never "may send": `retry_wait` `SOURCE_CHECK_UNAVAILABLE` within the retry budget, nothing sent                                                                                                                                                                                                 |

## 5. Security notes

- A job never carries a credential, and **only the dispatch job, as its own role, can read one** (audit finding H1, Issue #1146): it is composed with the real `ChannelPublisherCredentialPort` (capability `channel_account` 1.3.0) only behind `SOCIAL_PUBLISHING_FACEBOOK_ENABLED`, and with a port that refuses every request (`noPublishCredentialPort`) otherwise. A credential the provider refuses degrades the account through `ChannelPublisherHealthPort` (new in 1.3.0), so its other jobs are held. A dispatcher without an adapter fails closed (`PROVIDER_ADAPTER_UNAVAILABLE`) before any credential is asked for.
- **Why the worker role was not widened.** A first revision added a migration letting `awcms_worker` read social access tokens. The independent audit showed that `whatsapp:dispatch` shares that role and key ring, so a compromised WhatsApp worker could have decrypted every tenant's social tokens from the day the migration ran, with no adapter even present. It was withdrawn: `sql/328` is untouched.
- **The separate DB role exists (`sql/358`, admission condition of Issue #1145).** `awcms_social_dispatch` holds no table-level privilege anywhere, only a column-only read of `awcms_channel_accounts`, `awcms_channel_account_capabilities`, `awcms_channel_provider_connections` and `awcms_channel_secrets(id, tenant_id, purpose, ciphertext)`, and a RESTRICTIVE row policy (`awcms_channel_secrets_social_dispatch_publish`) that admits only a `provider_access_token` referenced as the `access_secret_id` of a facebook, instagram, threads, tiktok, youtube or linkedin connection whose grant is `active` or `expired`, used directly (`connection_id`) by an account of the same provider that is not deleted, is `connected` or `degraded`, and holds a `granted` `publish` capability (audit **M2**). A revocation or a withdrawn capability leaves the role's view in the same statement. An account that would borrow a parent's credential is not admitted: the credential adapter finds no row and answers `CREDENTIAL_UNAVAILABLE` (audit **L10**; none of the six providers has a container kind today). `awcms_worker` and its `sql/328` policy are unchanged, so `whatsapp:dispatch` still cannot see a social token.
- **The role runs the whole dispatch job (Issue #1146, `sql/373`).** It still ships `NOLOGIN`; a deployment activates LOGIN and points `SOCIAL_PUBLISHING_DATABASE_URL` (job-scoped, never global) at it. `social-publishing:dispatch` is a "dedicated-role job" (`dedicatedRoleTargets` in `scripts/jobs-env-allowlist.ts`): it holds `CHANNEL_SECRETS_ENCRYPTION_KEYS` and that login only, the runner withholds `DATABASE_URL`, `WORKER_DATABASE_URL` and `SETUP_DATABASE_URL`, and the job refuses to start when one is present or when `current_user` is not `awcms_social_dispatch` (or is superuser or `BYPASSRLS`). `sql/373` grants exactly the columns the dispatcher touches (queue, tenant list, enablement flag, audit and outbox inserts, a degrade-only account update and a `failing` health row) and bounds every write with a RESTRICTIVE policy: a failed or `needs_reconciliation` job cannot be re-queued and no job cancelled by this role, an account only goes `connected` to `degraded` (never back, so a refused token never re-enters its view), audit rows and events only of this module. The real `resolvePublishCredential` is composed only behind `SOCIAL_PUBLISHING_FACEBOOK_ENABLED` (default off), after the human security review of the credential path. `security:readiness` pins the role (no table privilege, exact column grants, not superuser, not `BYPASSRLS`) pins every one of its row policies to its EXACT canonical expression, and runs a probe in a rolled-back transaction that seeds an unreferenced token, a WhatsApp token behind a publish-granted account, a denied capability, a revoked account and a refresh token, assumes the role, and requires that exactly the one legitimate secret is visible. Two further restrictive policies hide every account and connection that is not one of the six social providers (L-6 of the #1261 audit). The secret policy is keyed on the CONNECTION, so `resolvePublishCredential` also requires THE requested account's own granted `publish` capability before any secret is read (`CAPABILITY_DENIED`; L-5). Residual risk once activated (ADR-0157 section 6): a compromised `social-publishing:dispatch` can decrypt the publishing-capable access tokens of every tenant.
- Adapters get `request.http` (`ssrfSafeFetch`) and no raw `fetch`; the credential is in memory for one call and is never logged, stored, evented, audited or placed in an error, and a thrown adapter error's message is never kept. A failure code is a closed vocabulary each adapter declares (`errorCodes`); a code outside it is recorded as the generic code for its outcome, so a provider string or the credential cannot reach a row through a "code".
- Per-account access: creating a publication, a rule, and acting on a publication or job require the caller to be able to use every targeted account (assignment rule and business scope of `channel_accounts`); anything else is a uniform `422 ACCOUNT_NOT_USABLE` or `404`. Reads are gated by the permission only.
- Every mutation is idempotent (`Idempotency-Key`), audited with ids, codes and counts (never a caption, a title or a URL) and refuses a machine credential. Events carry ids, enums and counts.

## 6. Permissions

`publications.read`, `publications.publish`, `publications.schedule`, `publications.approve`, `publications.cancel`, `jobs.retry`, `rules.read`, `rules.configure`, `settings.configure` (module `social_publishing`, seeded by `sql/331`). All are on the `NOT_YET_SCREENED` ledger until the screen lands. A tenant created before this migration needs `bun run identity-access:permissions:backfill`.

## 7. Configuration

`SOCIAL_PUBLISHING_ENABLED` (off by default). It needs `CHANNEL_ACCOUNTS_ENABLED=true` and `SOCIAL_PUBLISHING_DATABASE_URL` as a login distinct from the app and worker ones (`config:validate` refuses the combination otherwise), and `CHANNEL_SECRETS_ENCRYPTION_KEYS` for the dispatcher. `SOCIAL_PUBLISHING_FACEBOOK_ENABLED` (off by default, needs the module switch) registers the Facebook Pages connector and composes the credential path. `APP_URL` must be `https` for an article event to carry a link; otherwise the event is recorded as a refused publication (`LINK_INVALID`).

## 9. Remaining limitations

- **One provider adapter, Facebook Pages, publish only** (#1146, off by default); #1147 to #1151 remain. The provider app approvals (Meta App Review for Facebook) are business steps outside this repository. Facebook reply, comments, DM and inbound are follow-ups (ADR-0157 section 8, the inbound boundary #1144). **The Facebook switch stays off until** the human security review of the credential path and the Meta App Review are done (residual L8, the third condition, is closed by `sql/386`, below).
- **No admin screen.** Admin SYSTEM screens are built here ([ADR-0051](../adr/0051-admin-screens-consolidated-in-awcms.md)); the screen contract is UP-08 to UP-16 in [`omnichannel-ui-ux-screen-contracts.md`](omnichannel-ui-ux-screen-contracts.md).
- **Retention of publication evidence (Issue #1145, `sql/357`).** Publications, jobs and attempts have real `data_lifecycle` descriptors (`social_publishing.publications`, `.jobs`, `.attempts`), executed by the delegated adopter `bun run social-publishing:retention:purge` (daily). The unit is a whole publication: it is deleted (attempts, then jobs, then the publication, in one transaction) only when it is `ready`, `cancelled` or `refused`, and it and every job are terminal (`published`, `failed`, `cancelled`) and older than the window. A waiting job, a `needs_reconciliation` job and a `pending_approval` publication are never removed. A legal hold on any of the three keys stops the purge for the tenant. **Default 730 days, bounded 365 to 3650: a proposed default the owner may change** (`domain/social-publishing-lifecycle.ts`); the database floor refuses `awcms_worker` a DELETE of anything younger than 365 days or not terminal whatever the code asks, so lowering the minimum also needs a migration. `awcms_app` still cannot delete any of the three. The window and the floor are measured from `terminal_at`, a stamp written only by database triggers from the database clock (when a job enters a terminal status, when a publication leaves `pending_approval`), never from `updated_at`, which the app and the worker can write (M-2 of the #1261 audit). The database floor is **per row** (L-3): keeping a publication whole is the purge's job, and a legal hold is enforced by the purge, not by the floor (L-4), as for every other module. Rows that existed before `sql/357` have no `terminal_at` and are never deleted by the floor.
- **No caption templates**, no per-provider formatting beyond refusing content that exceeds a length, type or size ceiling, no video, short or story variants (the vocabulary is closed and reserved).
- The crash window between "the provider accepted the post" and "the job was finalised" is closed automatically only where the provider honours the passed idempotency key; elsewhere the job waits for an operator.
- Reads (list and detail) are gated by the permission, not by per-account access (residual L4 below).
- Per-process circuit breakers: each dispatcher process has its own state.
- **Audit residuals recorded, not fixed in this slice** (decisions of 3 November 2026). Full text in [ADR-0157](../adr/0157-social-publishing-is-an-account-scoped-publication-intent-and-per-account-job-module.md) section 6:
  - **L4:** reads are gated by `publications.read` and `rules.read` only, not by per-account access or business scope; a holder sees unpublished captions, titles, links and other brands' `accountId`s. Filter by `channel_accounts` access before a multi-brand tenant uses the module.
  - **L6 (closed by Issue #1145's admission change):** every adapter declares an anchored `externalPostIdPattern` and its `postUrlHosts`, and the registry refuses one that does not. A `published` answer whose id does not match (or the identifier alphabet `sql/359` enforces in the database: `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`) is recorded as UNKNOWN (`INVALID_POST_ID`, so `needs_reconciliation` for a provider without a dedupe key) and the id is not stored; a URL on an undeclared host is dropped (stored as NULL), and a kept URL loses its query and fragment; a pattern with a top-level `|` is not anchored. A connector still chooses its pattern and hosts truthfully.
  - **L8 (closed, `sql/386`):** the snapshot still decides what is sent, and the source is re-checked immediately before every provider call, in the pre-send transaction and before the credential is decrypted: the article through `blog_content`'s `ArticlePublicationStatusPort` (capability `article_publication_status` 1.0.0), the media object through `media_library`'s `MediaPublicationRecheckPort` (`media_library` 1.1.0). A failure (`SOURCE_RETRACTED`, `MEDIA_UNAVAILABLE`, `MEDIA_RIGHTS_REVOKED`) is terminal, never sent and never retried by the dispatcher, audited with ids and the code only. The adapters call two SECURITY DEFINER functions owned by the NOLOGIN, memberless role `awcms_social_source_check` (column reads only, `search_path = public, pg_temp`, tenant argument bound to the transaction tenant); `awcms_social_dispatch` holds EXECUTE and no read of the posts or the media registry. `security:readiness` pins both functions (body, owner, `search_path`, volatility, EXECUTE list) and both roles' column matrices exactly, and probes every verdict in a rolled-back transaction. Not covered: an operator's `jobs.retry` of such a job is allowed (the next pass refuses it again), a media object replaced in place under the same id is not detected, and a withdrawal in the seconds between the check and the provider call is still sent once (the pre-send transaction closes before the call; ADR-0157 L8 (b)).
  - **L9:** `prepare` runs before `authorize` (the repository-wide route pattern), so an unauthorised caller can distinguish a 400 or 422 from a 403. Accepted as the repository pattern.
  - **M2, L10:** met by the row policy of the separate DB role `awcms_social_dispatch` (`sql/358`, section 5); the role is activated by the first connector.
  - **M-1, L-7:** a connector declares `supportsIdempotencyKey` truthfully and answers `unknown`, not `retryable`, after any request that may have been processed; an expired lease for a provider without a dedupe key is never re-sent.
- A tenant's module-off switch is honoured by enqueue and dispatch, and by every route through the access guard, but a publication already `published` stays published (nothing recalls a post).
- **ADR-0157 is Accepted (2026-11-11).** A security review of the credential path and its separate DB role is still needed before any connector leaves the flag.
