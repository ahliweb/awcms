# PII inventory and retention proposal for the legacy ledger tables

> **This is a proposal, not a legal-compliance claim.** Nothing here changes the ledger, a descriptor, the gate, a migration, any code, or any data. The periods below are proposals with a written basis; the owner approves retention per module group in a later step (the group table in section 6 is the approval unit). Where a period needs a business or legal call it says `needs owner decision` and lists the options instead of guessing.

Issue: [#1501](https://github.com/ahliweb/awcms/issues/1501), sub-issue (1) of epic [#1397](https://github.com/ahliweb/awcms/issues/1397). Owner decision K19.16 (24 Nov 2026) made it ready. Rules it builds on: [`data-lifecycle.md`](data-lifecycle.md) section "Legacy tables without a descriptor: review order".

## 2. Conventions

- **PII verdict.** `yes`: a column holds personal data itself (name, login identifier, contact detail, IP address or a hash of one, an IdP subject), or the row records something ABOUT a person identified by an id (an access grant, an assignment, a delegation). `no`: no such column; at most actor stamps (`created_by`, `deleted_by`, `requested_by`), which resolve to nobody once the identity is anonymised (the `severed_with_subject_row` answer in the subject-data registry). `unknown`: a free-form `jsonb` or text column whose content depends on what callers write; listed separately in section 5 with the question that decides it.
- **Tier.** T1 direct personal data or network identifiers; T2 row about a person by id; U unknown; T3 actor stamps only; T4 no person column.
- **Volume.** H grows with requests, sign-ins or events; M grows with users, content or admin actions; L bounded by tenants or authored configuration. These are judgements from how the code writes the table, not measurements; no database was read.
- **Rank.** PII verdict first (T1, T2, unknown, then no/T3, no/T4), then sensitivity, then volume, then name.
- **Disposition.** `descriptor`: an age-based retention descriptor; `bounded`: a `BOUNDED_BY_DESIGN` candidate (the table does not grow with traffic); `owner`: needs the owner's decision before either.
- Free-text `reason` and `note` fields written by authorised staff about an action (workflow, access, tenant status, moderation) can name a person. They were NOT classified one by one as unknown, because that would mark most of the schema; the owner may reclassify them.
- Secrets (password hashes, token hashes, client secrets) are listed only where they sit beside personal data; protecting a secret is a confidentiality question, not a retention one.

## 4. Retention bases

Each proposed period cites a basis code. The periods are proposals; the figures quoted come from code or documents of this repository, with the file and line.

| Code | Basis                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AUD  | Access-control and authorisation history. Aligned with the audit-event default of 730 days (`AUDIT_EVENT_DEFAULT_RETENTION_DAYS`, `src/modules/logging/application/audit-purge.ts:54`) and inside the 365-1825 day audit_security band in `data-lifecycle.md`. Option for the owner: 1825 days.                                                                                                                                                                               |
| CAT  | Catalogue or reference data synced from code or a public dataset. Rebuilt on the next sync or import, holds no traffic, so there is nothing to age out.                                                                                                                                                                                                                                                                                                                       |
| CFG  | Configuration authored by an administrator, one row per tenant or per authored item, never accumulated by traffic. It lives as long as the tenant. Candidate for a `BOUNDED_BY_DESIGN` entry (the existing entries use exactly this argument).                                                                                                                                                                                                                                |
| CMT  | Comments. The existing job `comments:retention` already anonymises comment authors after 365 days (`COMMENTS_DEFAULT_ANONYMIZE_DAYS`, `scripts/comments-retention.ts:33`) and keeps the append-only moderation history by design (same file, lines 5-10). Reports of abuse follow the same 365 days.                                                                                                                                                                          |
| CNT  | Authored content. Live rows are the product and are not aged out. Soft-deleted rows exist to allow restore; 180 days is proposed as the restore window (options: 90 or 365). No statute known to this document requires keeping deleted CMS drafts; this is a product call the owner may change.                                                                                                                                                                              |
| DER  | Derived and rebuildable (projections, search index). The source of truth is elsewhere; rows are removed with the source row, and bounded per projection or stream.                                                                                                                                                                                                                                                                                                            |
| ENT  | Entity table of a person or tenant. Its lifecycle is the account's lifecycle, not an age: it is anonymised or removed through the subject-data erasure path (ADR-0094), not by an age-based purge. How long an INACTIVE account may be kept is a business and legal call, so it is marked needs owner decision with options 2 years, 5 years, or until the person requests erasure.                                                                                           |
| EVT  | Event log. The floor is the longest of: the delivery retention (120 days, `DELIVERY_DEFAULT_RETENTION_DAYS`, `src/modules/domain-event-runtime/application/delivery-retention-purge.ts:46`) and, once `SYNC_REPLICABLE_EVENT_TYPES` is non-empty, the longest time an offline node may stay away (`/sync/pull` reads this table, ADR-0077). Because `payload` may carry personal data the proposal is the short end: 180 days. Needs owner decision between 120, 180 and 365. |
| HLD  | Compliance bookkeeping of the lifecycle engine itself. A hold record is evidence that a retention rule was suspended; deleting it by age could erase that evidence, so the period is an owner decision.                                                                                                                                                                                                                                                                       |
| OPS  | Operational run history and telemetry. 90 to 180 days, the same band the repo already uses for comparable tables (webhook delivery 90, deliveries 120, `data_lifecycle_runs` 180 in `data-lifecycle.md`).                                                                                                                                                                                                                                                                     |
| REV  | Revision history of content. It grows with every save, so it is the highest-volume content table; the cap (by count or by age) is a product call. Needs owner decision, options: keep the last 50, or 730 days.                                                                                                                                                                                                                                                               |
| SEC  | Single-use security artifact with a lifetime of minutes and no evidentiary role: the audit trail records the sign-in, not the artifact. Proposed 7 days after expiry or consumption; 7 is the lowest floor the repo's descriptors use (`retentionMinDays: 7`).                                                                                                                                                                                                                |
| SES  | Credential or session records. 90 days after expiry or revocation, enough to investigate an account takeover that is reported late, while the audit trail (730 days) keeps the sign-in evidence. Options: 30 or 180 days.                                                                                                                                                                                                                                                     |
| SUP  | Suppression list. Deleting an entry re-enables sending to an address that opted out or complained, so removal is not age-based for those reasons. Hard bounces can age out (365 days) because mail providers re-evaluate addresses. The opt-out rule is a legal call, hence needs owner decision.                                                                                                                                                                             |
| SYN  | Offline sync. Retention must outlast the longest time an offline node can be away and the time needed to resolve a conflict; both are operating decisions (ADR-0077, `docs/awcms/08_offline_online_sync_design.md`). 90 days for processed batches and inbox, 365 days for resolved conflicts.                                                                                                                                                                                |
| VIS  | Visitor analytics. These are the defaults of the job that already exists, `analytics:purge` (`src/modules/visitor-analytics/domain/visitor-analytics-settings.ts:69-71`): raw IP and login snapshot 30 days, session rows 90 days, rollups 730 days. Proposing them as the descriptor makes the existing behaviour visible, not new.                                                                                                                                          |
| WF   | Workflow records. A workflow approves business actions, possibly financial ones, whose own retention can be years (the KUP-related note in `data-lifecycle.md`). The period therefore follows the governed resource and is an owner decision. Options: 1825 days after completion, 3650 days after completion, or follow the governed resource.                                                                                                                               |
