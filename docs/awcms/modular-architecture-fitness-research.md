## 2. Hypothesis and scope (#1543)

Separate the graph edge kinds: lifecycle order, actual static source import (value, type, re-export, alias), runtime wiring and capability, data read, write and reference, and event publish and consume. Cycles in lifecycle order must fail; source cycles require explicit review under the existing policy. Bidirectional event interaction or an optional capability need not imply a cyclic boot order; never flatten the graphs blindly.

Audit resolver behavior at a pinned HEAD: TypeScript relative imports, path aliases and barrels, Astro script and frontmatter, dynamic literal imports, unresolved or non-literal imports, scripts and composition roots. Inventory all scopes and the existing detection; mark unresolved edges and do not claim a complete graph. Candidate: extend the existing deterministic test or helper only if a gap is reproduced; use strongly connected components to report actual source cycles and compare them with the declared graph and the exceptions. The knowledge graph (Graphify, see closed issue #805) is advisory only; no new parser or dependency without license and ADR review. Keep runtime boundaries and valid optional modules.

Exception record: edge kind, source and target, rationale and ADR or issue, owner, risk and control, evidence, review trigger or expiry; no permissive blanket allow-list. Do not remove a bootstrap or auth exception without preserving its invariants.

## 3. Related data and transaction evidence (separate issues #1544 and #1545)

One canonical writer, not one database per module. Audit literal and dynamic SQL, views, triggers and functions, SQL roles and grants, security definer and search_path, FORCE RLS, worker operations and approved descriptor-based paths. The PostgreSQL catalog alone cannot resolve all dependencies in SQL bodies. Classify foreign keys as intra-aggregate or intra-module, tenant or canonical identity, cross-module approved invariant, extraction candidate, and cascade; preserve necessary constraints. Use tenant-safe composite references where the domain requires; foreign key and unique checks bypass RLS, so avoid existence leaks and verify uniform authorized errors. An approved reporting projection or read path may be allowed. Test tenant A and B with the same logical ID, unauthorized function or cascade, orphan record and rollback, plus legitimate positive paths. Do not delete constraints merely to avoid coupling.

A local typed port invocation may share a transaction for invariants; remote calls cannot assume local atomicity. Keep the existing domain-event runtime, durable outbox and consumer registry. Verify transaction-to-outbox atomicity, duplicate delivery and effect, versioned schema, per-aggregate order where required, retry, backoff and quarantine, replay, unknown provider outcome and reconciliation. No blanket exactly-once promise. Protect tenant, actor and worker scope; logs and traces carry no sensitive payload. Resource admission limits (#1541) stay separate from module authorization. No new broker and no HTTP-for-local rewrite.

Data changes follow expand, backfill, reconcile, contract; applied migrations are immutable; one canonical writer is maintained.

## 4. Extraction evidence (ADR-0013 section 7)

ALL six conditions require measured evidence: a materially different CPU, IO or concurrency profile; a different security, process or network boundary; a business-required independent release cadence; a clearly different on-call owner; separable data ownership with a stable API and event contract; and a business-continuity need for failure isolation. Prerequisites: historical backfill, shadow read, explicit cutover, rollback, no dual write, and observability before the authority switch. A score cannot compensate for a missing condition. Compare the modular monolith, a worker split and a selective service with the same workload, seed, build and hardware over repeated runs. Observe throughput, p95 and p99, error rate and queue age, resource cost, recovery, RPO and RTO, and on-call burden. A new ADR and Gate 9 are needed before implementation; no service extraction is proposed here.
