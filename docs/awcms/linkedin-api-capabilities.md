## 1. Verdict in one paragraph

LinkedIn offers **organisation-Page publishing** through the **Community Management API**, a **vetted** product (not self-serve) available only to **registered legal organisations for commercial use cases** [S3][S4]. It needs an approved developer app with a **Development tier** first and, for real volume, a **Standard tier** after a screencast review [S3][S4]. Posting needs OAuth scope `w_organization_social` and the authorising member must hold a Page role such as ADMINISTRATOR [S1]. Member data (commenters, reactors) is **display-only, cached for hours not months, and barred from CRM, ads, sales, recruiting and export** [S12][S13]. The platform model for many tenants under one operator app is the one the terms describe (LMA sections 1.2 and 1.5), see section 10 (decision K15). That bar is already enforced here by matrix row `linkedin_member` (all cells denied, leads `barred`, [ADR-0148](../adr/0148-omnichannel-foundation-is-five-gated-capabilities-with-fail-closed-per-account-capability.md) I7). **Build/no-build gate for the adapter: no-build today** (section 11).

The Posts API and Comments API pages name **different scope strings** for what looks like the same capability (`w_organization_social` versus `w_organization_social_feed`). Which scope a given app actually receives is shown in the Developer Portal Auth tab [S6]. See open item U3.

Roles of a member in a Page are read through the `organizationAcls` endpoint; "access to a Company Page cannot be granted or updated through the API", only in LinkedIn's UI [S5].

## 3. OAuth 2.0 (3-legged) flow, token lifetimes and storage

| Step | Detail                                                                                                                                                                                                                                                                                          | Source    |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| 1    | Register an **HTTPS**, absolute **redirect URL** in the app's Auth tab. Query parameters are ignored; a `#` is not allowed. Keep the client secret server-side and never in a URL                                                                                                               | [S6]      |
| 2    | Send the member's browser to `GET https://www.linkedin.com/oauth/v2/authorization` with `response_type=code`, `client_id`, `redirect_uri`, `scope` (space-delimited) and a hard-to-guess `state` (the page marks `state` optional but says to verify it against CSRF; this repo always uses it) | [S6]      |
| 3    | LinkedIn redirects back with `code` and `state`. The **authorization code lives 30 minutes** and must be used immediately. The consent is all-or-nothing: the member cannot pick individual scopes. Declined consent returns `error=user_cancelled_login` or `user_cancelled_authorize`         | [S6]      |
| 4    | `POST https://www.linkedin.com/oauth/v2/accessToken` as `application/x-www-form-urlencoded` with `grant_type=authorization_code`, `code`, `client_id`, `client_secret`, `redirect_uri`                                                                                                          | [S6]      |
| 5    | Calls to `https://api.linkedin.com/rest/...` carry `Authorization: Bearer`, `Linkedin-Version: YYYYMM` and `X-Restli-Protocol-Version: 2.0.0`                                                                                                                                                   | [S1][S14] |

**Token lifetimes.**

- Access tokens: "all access tokens are issued with a 60-day lifespan" (`expires_in` 5184000 s in the sample) [S6]. Tokens are ~500 characters; plan for at least 1000 [S6].
- Refresh tokens: **not available to every app**. "Programmatic refresh tokens are available for a limited set of partners" [S6], and the dedicated page says LinkedIn supports them "for all approved Marketing Developer Platform (MDP) partners" [S7]. Where enabled the refresh token is valid for **one year (365 days) by default** and its lifetime is **not extended** when it is used: day 59 refresh leaves 306 days [S7]. When it expires "the member must reauthorize" [S7]. LinkedIn "reserves the right to revoke Refresh Tokens or Access Tokens at any time" and the integrator must fall back to the normal OAuth flow [S7].
- Without programmatic refresh the documented way to get a new access token is to run the authorization again; the consent screen is skipped only if the member is still logged in to LinkedIn and the current token has not expired [S6].
- Requesting a **different scope** than previously granted **invalidates all previous access tokens** for that member and app [S6].
- Whether this repo's app will receive refresh tokens (the Community Management tier does not state it either way on the pages read): **not documented / not found**. See U4.

**Mapping to the `channel-accounts` vault** (no code change implied):

- The tokens are stored as encrypted `awcms_channel_secrets` rows, never in `.env` and never in `channel_accounts`/`social_publish_jobs`. The purposes that already exist are `provider_access_token`, `provider_refresh_token`, `oauth_pkce_verifier` and `oauth_authorization_code`; no new purpose is needed (`src/modules/channel-accounts/domain/channel-accounts-constants.ts`).
- The app-level `client_id` and `client_secret` are an **application** credential, not per-tenant account material. Per decision K15 (section 10) there is **one platform app** whose client secret lives in the platform secret store with a rotation runbook; it is never added to `.env`, never per tenant, and never shipped with the template.
- The account kind is `organization_page` (matrix row `linkedin`, auth mode `oauth2`). The provider-stable `externalId` for an account is the organisation id (the `urn:li:organization:{id}` URN) [S1].
- A social job that decrypts the credential runs under a dedicated DB role, not `awcms_app` and not the shared worker (the pattern of `awcms_social_dispatch`, ADR-0157 section 6). The refresh-token rotation write must be a restricted write by that role.
- On expiry or revocation the adapter returns `needs_reauth` and the account moves to a re-authorise state; it is never retried by backoff.
- Disconnecting an account deletes the ciphertext of its secrets (brief rule, audit lesson 8).

**Create call:** `POST /rest/posts`, success is **HTTP 201** and the new id is in the **`x-restli-id` response header** as `urn:li:share:{digits}` or `urn:li:ugcPost:{digits}` [S1]. Read back with `GET /rest/posts/{encoded urn}`; the public URL structure given is `https://www.linkedin.com/feed/update/urn:li:ugcPost:<id>/` [S1].

**Scheduling.** The Posts API accepts only `lifecycleState: PUBLISHED` on creation; `DRAFT`, `PUBLISH_REQUESTED` and `PUBLISH_FAILED` are states that can be **returned** [S1][S2]. **No scheduled-publish field is documented** on the pages read. Scheduling is therefore **not a provider capability to rely on**: `social_publishing` already schedules by holding the job until `not_before` and calling the provider at that time (ADR-0157), which needs nothing from LinkedIn.

**Idempotency.** **No idempotency-key header or field is documented** for post creation on the pages read [S1]. Treat the provider as not de-duplicating (see section 8, `supportsIdempotencyKey = false`). The same page says a 409 `CONFLICT` means "a write conflict occurred. Retry the request" [S1], which is not a guarantee against a duplicate.

## 5. Rate limits

- Limits are a **maximum number of calls per 24 hours**, resetting at **midnight UTC**, at two levels: per **application** and per **member** (per member token, per app) [S11].
- A limited request gets **HTTP 429**; "standard rate limits are not published in documentation". They are read per endpoint in the Developer Portal app **Analytics** tab, which lists an endpoint only after at least one call that UTC day [S11].
- The only published numbers are the **Development tier** defaults in the Community Management FAQ: per app raised **from 100 to 500** and per member **from 10 to 100** requests [S3]. The unit is not restated there; read it with [S11] as per day. The **Standard tier** numbers are **not documented / not found**.
- Developer admins get an email at **75%** of the application-level quota, delayed about 1 to 2 hours; there is no alert for member-level breaches [S11].
- Implication: a Development-tier app is limited to roughly 100 calls per member per day in total (image upload initialise, upload, post, read-back each count); a tenant with many Pages under one admin member could exhaust that. The adapter must map `429` to `rate_limited` and must not retry before the next UTC midnight when no `Retry-After` is given (U7).

### 6.3 Implications for `data_lifecycle` and the rest of AWCMS

These are design consequences, not implemented behaviour. They apply only if a LinkedIn engagement connector is ever built; publishing alone stores none of the member data above.

1. **What the publish adapter stores is within the allowances.** `social_publish_jobs` keeps the provider post id and URL (IDs and URNs: no duration limit) and a failure code, and **no token and no secret reference** (social-publishing section 2). The organisation's own post content is the tenant's own content snapshot, not LinkedIn-retrieved data.
2. **Ingesting LinkedIn comments or reactions would create rows with a hard TTL.** A descriptor for any such table must declare a purge of **48 hours** for member content and **24 hours** for member profile fields, and the table must not be joinable to contacts, leads or CRM entities. Because a retention floor must not depend on a column the restricted role can write (audit lesson 5), the clock must be a DB-set timestamp.
3. **Subject-data and erasure.** LinkedIn requires immediate deletion on the member's request and when the member closes the account (ToU section 4.4, [S16]). A person-level erasure path must reach any cached LinkedIn member row; the short TTLs make this mostly moot but the descriptor must still be registered (`data-lifecycle:registry:check`, `subject-data:coverage:check`).
4. **No mirroring of the Page feed into AWCMS public pages.** The "no social feed" rule [S13] forbids showing LinkedIn company updates on the tenant website. This blocks, for example, an "embed our LinkedIn posts" widget in `blog_content` or an index of LinkedIn posts in `site_search`. Publishing **to** LinkedIn from an AWCMS article is not affected.
5. **CRM isolation is already coded.** Matrix row `linkedin_member` has every cell `not_applicable` or `barred`, `leads` is `barred`, and `evaluateCapability` is the single decider (`provider-matrix.ts`; ADR-0148 I7). The negative test "CRM lead enrichment from LinkedIn member data is denied" remains an acceptance item of #1140 and of any LinkedIn adapter.
6. **Termination duty.** If LinkedIn suspends or terminates the app, stored LinkedIn-derived data must be deleted (ToU section 4.5 [S16]; LMA section 4.2 [S17]). A kill switch that disables the connector should also be able to purge LinkedIn-derived rows for all tenants.
7. **Reporting data** (page analytics) may be kept up to one year [S12]; if analytics ever land in `reporting` projections they need a one-year descriptor and no member-level columns.
