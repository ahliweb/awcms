# Omnichannel foundation — readiness pack (v1, 24 October 2026)

**Design only.** This pack accompanies [ADR-0148](../adr/0148-omnichannel-foundation-is-five-gated-capabilities-with-fail-closed-per-account-capability.md) (Issue #1139). It contains the logical data dictionary, the provider capability matrix, the multi-sender semantics, the threat model, the compliance reading, the contracts outline, the rollout plan and the test matrix. **Nothing here is implemented**: there is no `channel_accounts` module, no table, no route, no sender key on the WhatsApp queue and no social connector. Status words in this document are about design, never about code. Where the current code is described it is described as it is on `main`, and the documents that remain authoritative for it are the module READMEs.

Sources of the provider facts are the official documents linked from Issue #1139 and its children, as of 24 October 2026. Provider APIs, tiers and terms change; the matrix is **versioned**, every cell that is not verified is treated as denied, and any row is re-verified against the then-current official documentation by the issue that implements it.

### 2.3 Social publishing (C3, Issue #1145)

Publishing jobs reference a `channel_account` and a capability row, never a token. A job snapshots the content (the article's text and a verified media reference) at enqueue, is idempotent per `(article, trigger, account)`, goes through an approval state when the tenant requires one, and is dispatched outside any transaction. Replacing the `blog_content` no-op adapter is behind a flag, default off.

### 2.4 Inbound events and contact linkage (C4, Issue #1144 decides the rest)

The event envelope is: `tenant_id`, `channel_account_id`, `provider_event_id`, `provider_conversation_id`, sender and recipient (platform-scoped ids), `privacy_class`, `occurred_at`, authenticated provenance, `correlation_id`. Idempotency key is `(channel_account_id, provider_event_id)`.

`contact_link_evidence` (only when a platform contact is linked to a CRM person): the two ids, the **method** from a closed list (`first_party_form` where the customer typed the identifier, `reply_to_addressed_message`), provenance, who and when, and revocation. No probabilistic, cross-platform or enrichment-based method exists in the list.

### 2.5 Consent

No new global consent table. Consent stays where it is per channel (`whatsapp_delivery` consent and suppression, `email` suppression and newsletter, Telegram binding) and gains the **scope** it must be keyed by: tenant, channel, purpose, and business scope where the tenant has several brands. The CRM-side consent bridge is downstream (#458).

**Design and adoption decisions only.** Nothing here adds a connector, a permission or a promise. Every row below is a **candidate for admission**, not a feature; capability stays fail-closed per account (ADR-0148 I2) and a cell that is not `candidate` is denied. **Partner versus first-party.** The default is a **first-party connector** on the common account and capability interface (ADR-0148 §1 C1): the tenant's token is held by AWCMS under I3 and never by an intermediary. A partner or aggregator is admitted only by its own ADR that shows the provider requires one or that the first-party route is not available, and that the intermediary's terms, data location and token custody meet I3, I7 and I12. No row above meets that bar today.

#### What is reusable and what is connector-specific

- **Reusable (the interface):** the `channel_accounts` identity, grant and health model; the capability row with evidence; the `SocialPublishingPort` request and result shape; consent per channel, scope and purpose; the outbox and dispatcher; the audit and redaction rules.
- **Connector-specific (never abstracted away):** the account identity type (user, bot, location, instance account); the consent a platform requires (for example a user starting a bot, a friend relationship, a service window); quota and cost accounting; media rules; webhook verification scheme; deletion and caching duties; the application review itself.
- **Prohibited, restating ADR-0148 I5 and I6:** presenting a post on one network as a message on another; degrading an unsupported action to a different one; using cookies, scraped sessions or browser automation to bypass an access approval; using a personal account where an organization or bot account is required. An unsupported action is refused and the UI shows it disabled with the reason.

## 4. Multi-sender semantics (detail of ADR-0148 §4)

1. **Selection.** Explicit `senderAccountId`, else the business scope's `default_sender_account_id`, else the deployment sender. Resolution happens at enqueue and is snapshotted. If an explicit sender is given and it is not usable, the call is `refused: SENDER_UNAVAILABLE`; it does not fall to the default.
2. **Authority.** The adapter and the credential are resolved from the sender record in the authenticated tenant. A request-supplied token, phone number id or device id is never read.
3. **Affinity.** A reply to an inbound message uses the account that received it. The provider's service window is per sender and recipient; sending a reply from another number is a different conversation and is not offered.
4. **Failure.** `disabled`, `revoked`, `disconnected`, `unapproved`, `wrong tenant` or an open per-sender breaker keeps the row waiting (breaker) or fails it terminally (revoked, wrong tenant) with a sanitised reason. No other sender, number or provider is tried. Rotating numbers to evade a quality rating or a spam limit is prohibited by design.
5. **Quotas and health.** Per-sender hourly and daily caps (configurable), a tenant cap on top, throttling to the provider's documented limits, and a health state the dispatcher reads before claiming.
6. **Consent and suppression** are checked against the recipient and the **business scope**, not the sender: changing the sender does not change who consented.
7. **Unofficial provider.** StarSender: feature flag off by default; per-operator risk acknowledgement; no claim of Meta authorisation; "accepted" is never "delivered"; status and contacts only through an authenticated path or not at all.
8. **Default per product.** A derived product may select StarSender as its default sender (owner decision, 24 October 2026) by configuring the policy, never by a code default; the other provider remains independently selectable.

## 6. Secret handling (detail of ADR-0148 §5)

- Storage is `channel_secret` rows encrypted with `src/lib/security/field-encryption.ts` (AES-256-GCM, `v2:<keyId>:<iv>:<tag>:<ciphertext>`, associated data = purpose, tenant, row, first key encrypts and all decrypt, fail-closed key handling). The ring comes from a **dedicated environment variable** for this module, `secret: true` in the config validator, outside the database and its backups. No key is needed at boot unless the module is enabled.
- Write and rotate go through one audited, high-risk, separately grantable permission with a conditional step-up (never an unconditional one, ADR-0141 §4). Reading a secret is never an API operation. A "replace token" call overwrites; there is no "show token".
- **Rotation** is "prepend a new key, run the re-encrypt job, retire the old key when no row and no restorable backup needs it". Unlike the keyed recipient hash, ciphertext can be re-encrypted.
- **Revocation** is effective on the next claim: the dispatcher re-reads account status and capability before each send, and a revoked connection clears its secret reference.
- **Telemetry:** a decrypt counter per tenant and per dispatch run, alert on an unusual rate; a startup and `security:readiness` check that the ring is present, long enough and not a placeholder.
- **Restore:** a restore without the ring must fail closed (no send, masked reads work), rehearsed in the restore drill alongside the payroll rings.
- `SecretStorePort` is the seam: the first adapter is the application ring; a KMS or vault adapter can replace it without changing callers or the stored reference.

## 10. Rollout, migration and compatibility

1. **Additive and inert.** All migrations are new files. With no account configured every deployment behaves as today, including `WHATSAPP_PROVIDER` and the single deployment credential (the `null` sender).
2. **Order.** #1140 (accounts, secrets, security review), then #1141 (sender key), then #1142 and #1143 (adapters), #1154 (admin screens) alongside; #1145 (publishing engine) after #1140, then connectors.
3. **Downstream.** `awcms-one` keeps its per-tenant `legacy`/`upstream` mode router (ADR-0047). A sender-aware port is a versioned additive change; commerce adopts it after a subtree sync as a merge commit. The StarSender default for a derived product is a configuration of the policy, applied per tenant, never a code change.
4. **No rewrite of applied migrations; no dual write; no second WhatsApp queue** during or after the change.
5. **Rollback** is forward-only: disable the provider flag or the module, keep the tables inert; the `null` sender path is always available.

## 13. Implementation reconciliation: Issue #1140 (`channel_accounts`)

Sections 1 to 12 stay the design baseline. What Issue #1140 built, and where it differs from the working names above (module [`src/modules/channel-accounts/`](../../src/modules/channel-accounts/README.md), `sql/318` to `sql/320`, [`openapi/modules/channel-accounts.openapi.yaml`](../../openapi/modules/channel-accounts.openapi.yaml)):

- **Eight tables, not seven.** The seven plus `awcms_channel_oauth_states` (the single-use `state` nonce and PKCE verifier reference of a flow in flight). The webhook-subscription table is metadata only: no route reads it yet.
- **Health is one row per account** (upsert). The bounded history is not stored: an unbounded append log would need its own purge before any consumer exists.
- **Permission names.** `AccessAction` is a closed vocabulary, so `.connect`, `.disconnect`, `.capabilities.grant` and `.assignments.manage` became `accounts.create`, `accounts.revoke`, `capabilities.configure` and `assignments.assign`; `accounts.read` and `credentials.manage` are unchanged. `senders.use` and the `whatsapp_delivery.*` sender permissions are **not** seeded: nothing enforces them until #1141.
- **Key ring and rotation (section 6).** `CHANNEL_SECRETS_ENCRYPTION_KEYS` (`config:validate` checks it shares no key with the Telegram or push ring) and `bun run channel-accounts:secrets:rekey` (manual, runs as `awcms_app`). The decrypt counter is `snapshotSecretDecryptCounts()`. The flag `CHANNEL_ACCOUNTS_ENABLED` is built, default off; every route answers `503 CHANNEL_ACCOUNTS_DISABLED` after authorization.
- **Verified callback (T1) is a verified hand-off.** The callback consumes the state and stores the authorisation code as ciphertext on a `pending` connection. The token exchange is provider I/O (I10) and belongs to the first connector's job (`activateConnectionGrant`).
- **Not built:** `ChannelAccountPort` and the `channel.account.*` events (no consumer exists; `resolveCapability` is the function the port will wrap, first consumer #1141).
- **Retention.** Each table answers the retention question in the same change through the gate-accepted forms: `subjectData` descriptors (a reasoned `NO_SUBJECT_DATA` for the health table) and a reasoned `BOUNDED_BY_DESIGN` entry per table. A delegated `data_lifecycle` descriptor for `oauth_states` was rejected: it needs a worker read grant on a control-plane table.
- **The matrix code mirror** is `src/modules/channel-accounts/domain/provider-matrix.ts`, held equal to section 3 above by `tests/channel-accounts-provider-matrix.test.ts`, cell by cell.
