# Dependency governance — freshness audit and atomic upgrades

> **What this is.** The rules for keeping libraries, the Bun runtime and the
> pinned container images current, secure and compatible **without ever taking
> an unreviewed version change into production**, plus the two artefacts that
> support them: `bun run deps:freshness` (a read-only report) and the held-back
> register (`scripts/dependency-held-back.ts`). Issue #1173.
>
> **What this is not.** It is not a mass upgrade and it does not upgrade
> anything. Every version change is its own reviewed pull request.

## Principles

1. **Report is not upgrade.** The weekly job reads registries and prints drift.
   It never edits `package.json`, `bun.lock`, a workflow or a Dockerfile, and it
   opens no pull request. A scheduled job that changed the lock would be the
   silent mass update this policy exists to prevent.
2. **One upgrade, one pull request.** A PR moves one dependency (or one tightly
   coupled set, such as `astro` + `@astrojs/node`, or every place the Bun pin
   lives). The point is rollback and blame: when something breaks, one revert
   undoes one change.
3. **`bun.lock` is generated by Bun, never edited by hand.** Preview with
   `bun update <name> --dry-run`, apply with `bun update <name>`. `bun update
--latest` crosses semver ranges and is run **only when the upgrade has been
   approved** in the issue or ADR.
4. **UNKNOWN is not a pass.** A check that could not run (registry unreachable,
   rate-limited, output in a shape we do not parse) is reported as `UNKNOWN`,
   never as "no drift". This is the same fail-closed rule
   `deps:audit:check` documents for itself.
5. **Pinned means deterministic.** Production versions are pinned: the Bun
   version in `packageManager`, the `setup-bun` steps and the images
   (`oven/bun:<x.y.z>`, with the index digest recorded beside it in
   `Dockerfile.production`); `bun install --frozen-lockfile` everywhere. There
   is no floating `latest` anywhere in the path to production.

## What is audited, by what

| Surface                                                                                             | Covered by                                                                                                                      | Cadence                         |
| --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |

| Advisories, incl. transitive                                                                        | `bun run deps:audit:check` (blocks `high`/`critical`, in every `bun run check`) and the `bun audit` section of `deps:freshness` | every PR; weekly                |
| Bun runtime pin vs npm latest                                                                       | `deps:freshness`                                                                                                                | weekly                          |
| Base images (`Dockerfile.production`, cron runner and backup images in `deploy/cron/awcms.crontab`) | `deps:freshness` — newest same-shape tag on Docker Hub, and whether the digest recorded in the Dockerfile still matches the tag | weekly                          |
| GitHub Actions (pinned by SHA)                                                                      | Dependabot `github-actions`                                                                                                     | weekly (Mon 09:30 Asia/Jakarta) |
| npm dependencies, PR proposals                                                                      | Dependabot `bun` (limit 5 open PRs)                                                                                             | weekly (Mon 09:00 Asia/Jakarta) |
| Static analysis                                                                                     | CodeQL (required check)                                                                                                         | every PR                        |
| Licenses and SBOM of the dependency tree                                                            | `bun run deps:license:check` (in every `bun run check`; writes a CycloneDX SBOM with `--out-sbom`)                              | every PR; weekly                |
| Provider API changelogs                                                                             | `bun run deps:provider-changelog:check` (in every `bun run check`) against `scripts/provider-api-register.ts`                   | every PR; weekly                |
| SBOM of the release image                                                                           | `release.yml` (`anchore/sbom-action`)                                                                                           | per release                     |
| Held-back versions                                                                                  | `scripts/dependency-held-back.ts` + `tests/dependency-held-back.test.ts`                                                        | continuous (test)               |

Not covered yet, and said so rather than implied: the OMES Control Center API
types (tracked with that work). Provider API changelogs for WhatsApp, Telegram,
Meta Graph, Mailketing and Google FCM are covered by the provider register below;
an upgrade PR still reads the changelog of a provider-facing SDK by hand.

**Not ours.** The OMES / Hermes Python and operating-system runtime on the host
is not owned by AWCMS. It is audited in the host repository, separately.
`awcms-astro` has its own dependency set and its own audit.

## Cadence and severity

| Class                                                    | Handling                                                                                                                                                                                                 |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Security fix (`high`/`critical` advisory)                | Urgent, out of cycle. Usually an `overrides` entry for a transitive package, never `bun update <name>` (it would add the package as a direct dependency) — see `scripts/dependency-audit-exceptions.ts`. |
| Patch / minor of a direct dependency                     | One atomic PR per dependency (or coupled set), picked up from the weekly report.                                                                                                                         |
| Major version, or a change of a runtime support contract | Only after an ADR and a compatibility matrix. Not taken from a report; the report only says it exists.                                                                                                   |
| Bun runtime                                              | Its own PR, following the pin-bump playbook below.                                                                                                                                                       |
| Base image                                               | Bumped with the Bun pin when it is the Bun image; any other image is its own PR with the Dockerfile/crontab change and a `docker run` check.                                                             |

## The gates every upgrade PR must pass

1. `bun run check` — the whole chain, including `deps:audit:check`,
   `family:conformance:check`, typecheck, the test suite and the build. CI's
   `quality` job runs the same command and is authoritative.
2. The DB-backed integration tests and the Playwright smoke (axe accessibility
   scan) in CI — a library that changes behaviour at runtime shows up there,
   not in the unit tests (Bun 1.4.4 refusing a raw `BEGIN` through a pooled
   client was found by the integration suite).
3. The client asset budget (`bun run build:asset-budget:check`) after a build
   when the upgrade touches Astro, an integration or anything that ships to the
   browser.
4. `bun.lock` regenerated by Bun in the same PR; a diff that touches only the
   upgraded package and its own dependency edges. A lock diff that moves
   unrelated packages is a reason to stop and split.
5. A changeset (`"awcms": patch` for a dependency bump with no behaviour change).
6. New or newly-transitive packages only from a trusted publisher; provenance
   attestation where npm publishes one; license compatible with the repository;
   `engines` and `peerDependencies` satisfied; no new install scripts without
   `trustedDependencies` review. Provider-facing SDKs: read the changelog for
   API and webhook-signature changes before merging.
7. Never bypass a failing test, never `--force`, never loosen a gate to land an
   upgrade. A red upgrade is split or held — and a hold goes in the register.

### Bun pin bump (playbook)

The Bun version is pinned in several places that must move together; #1102
(1.4.2 -> 1.4.3) and #1176 (1.4.3 -> 1.4.4) are the precedents. In one PR:
`package.json` `packageManager` and `@types/bun`; the current-pin `setup-bun`
steps in `ci.yml`, `changesets.yml`, `release.yml` and
`dependency-freshness.yml`; `Dockerfile.production` (image tag, plus the index
digest in its comment); the cron runner image in `deploy/cron/awcms.crontab`;
`scripts/ci-local.ts` `CI_BUN_CURRENT` and its parity test;
`awcms-family-compatibility.yaml`; the docs that name the pin (family
compatibility, ci-local, implementation blueprint, ADR-0032); `bun.lock`
regenerated through the new Bun. The `engines.bun` floor and the
`minimum-supported` CI cell do **not** move with the pin — that is an ADR-0032
support-contract decision, recorded in the held-back register. Dependabot is not
used for the Bun image: a Dockerfile-only bump would leave the other pins behind.

## Rollback

- **Code and lock:** revert the upgrade PR. The revert restores `package.json` and
  `bun.lock` together; CI re-verifies with `bun install --frozen-lockfile`.
  Because each PR holds one upgrade, the revert removes exactly that change.
- **Bun runtime / base image:** revert the pin PR. For an already-deployed image,
  redeploy the previous `oven/bun:<x.y.z>` tag; tags are pinned, never
  `latest`, and the previous index digest is in the Dockerfile's history.
- **Never** restore a lock by hand-editing it, and never `git checkout` a single
  file out of an upgrade PR — `package.json` and `bun.lock` are one unit.
- If a revert is needed because an upgrade turned out unsafe, add a held-back
  entry in the same PR so the next report does not propose it again unreviewed.

## Using the report

```bash
bun run deps:freshness                          # markdown report on stdout
bun run deps:freshness --json                   # the manifest, machine readable
bun run deps:freshness --out-json m.json --out-md r.md
bun run deps:freshness --strict                 # exit 1 unless it is a clean all-clear
```

It prints, for each surface above, installed vs in-range update vs latest with
the drift class (patch / minor / major), the advisory summary, the Bun pin vs npm,
each pinned image vs the newest same-shape tag and digest, and the held-back
register. **Nothing in it is written back to the repository.**

Exit code: drift alone never fails (some exists nearly every week, and an
always-red report is not opened). With `--strict` it exits 1 on any `UNKNOWN`
section, an unhandled `high`/`critical` advisory, an expired or stale held-back
entry, or a recorded image digest that no longer matches its tag.

The scheduled workflow `.github/workflows/dependency-freshness.yml` runs it every
Monday 02:00 UTC (09:00 Asia/Jakarta) and on `workflow_dispatch`, with
`contents: read` only. The report goes to the run summary and the JSON manifest
is uploaded as an artifact (90 days) — that is the auditable weekly manifest. A
red run means "look at this report", not that something was changed.

### Turning a report into work

- Pick **one** row. Open an issue (or use the existing one) that names the
  package, the installed and target versions and the source (`bun outdated` on
  the report's date), and do the upgrade in its own PR with the gates above.
- A row that is deliberately not taken goes in the **held-back register**, not in
  a comment.
- `bun outdated` reports the in-range update separately from latest: a package
  with an in-range update (`astro 7.4.0 -> 7.4.2`) can be taken without touching
  `package.json`; one whose latest is outside the range is a range change and, for
  a major, an ADR.

## Licenses and SBOM

`bun run deps:license:check` reads `bun.lock` (parsed by the script, Bun-only),
reads each package's license from the installed `node_modules/<pkg>/package.json`,
and fails when a license is outside `ALLOWED_LICENSES` in
`scripts/dependency-license-policy.ts`. `--out-sbom <file>` writes a CycloneDX 1.6
SBOM of the same tree (purl, SHA-512 from the lock's integrity, license, and the
dependency edges resolved with the lock's nesting).

- **Expressions are evaluated, not matched as text.** `A OR B` passes when either
  side is allowed, `A AND B` needs both, `X WITH Y` is one license that must be
  listed as written, and an expression it cannot parse is refused.
- **An exception is a reasoned, expiring entry** in `LICENSE_EXCEPTIONS`: package
  (or `family-*`), the license it declares, why it is acceptable, owner, review
  date. It admits that package at that license only: a package that changes
  license is a violation again. An exception that matches nothing is stale and
  fails; one past its review date fails, and so does one whose date is not a
  real `YYYY-MM-DD` within 400 days (a `"never"` would otherwise never expire).
- **No copyleft is allowed globally.** `MPL-2.0` and `LGPL` packages are each a
  dated exception, so a new one stops the gate instead of passing on a list
  written for another package. What redistribution means is recorded in the
  policy file: `Dockerfile.production` copies the `--production` `node_modules`
  into the runtime image, so runtime-reachable packages (`lightningcss`, reached
  through `astro` -> `vite`, and the `sharp` libvips binaries) ARE shipped, each
  with its own license file and unmodified; the test-only `axe-core` packages are
  not. Modifying or bundling any of them needs an ADR before a new date.
- **Unreadable is not clean.** A package whose license cannot be read (not on
  disk, no field) is reported `UNKNOWN` and fails; run `bun install` first.
  Optional packages that a plain install does not put on disk (platform
  binaries, wasm fallbacks) are counted and listed as not installed here: their
  license is marked unverified in the SBOM, not invented.
- **Reuse in a downstream workspace.** The gate assumes no layout of this
  repository: `--root <dir>` points at the workspace root that holds `bun.lock`,
  `package.json` and `node_modules`, and `--policy <file>` swaps in the
  workspace's own `ALLOWED_LICENSES` / `LICENSE_EXCEPTIONS`. The embedding
  workspace keeps its own policy file; it does not edit this one
  (ahliweb/awcms-one#471 is the consumer this was shaped for).

## Provider API changelogs

`scripts/provider-api-register.ts` records, per provider surface the code talks
to (Meta Graph for Facebook Pages, Meta WhatsApp Cloud, Fonnte, StarSender,
Telegram Bot API, Mailketing, Google FCM HTTP v1, Cloudflare API, Cloudflare
Turnstile, the GitHub REST API, and TikTok as `planned`), the version or surface in
use, the changelog URL, the owner, and the date a maintainer last read that
changelog. `bun run deps:provider-changelog:check` enforces:

1. **Register -> code.** Each `pins` literal must appear **exactly once** in its
   file, so a literal repeated (or quoted in a comment) cannot let one copy be
   bumped unnoticed; pin a single exported constant. Change a version in code
   without the register and the gate fails. The pin sees the code default, not a
   deployment's environment override (for example `WHATSAPP_META_API_VERSION`):
   ask what is deployed at review time.
2. **Code -> register.** Every non-test source file that names a provider host
   must be listed by an active entry. A new connector nobody registered fails.
   That rule can only see hosts already in `PROVIDER_HOSTS`, so
   `tests/provider-changelog-check.test.ts` also extracts every `https://` host
   in non-test source and requires it to be a provider host or listed in that
   test's `NOT_A_PROVIDER` map with a reason: a new outbound integration cannot
   slip in without someone choosing.
   A `planned` entry owns no file; its host appearing in source fails until the
   entry is flipped to `active` with a first review.
3. **The clock.** `lastReview` (or `recordedOn` while it is `null`) plus
   `maxAgeDays` is the deadline; past it the gate is red. Within 14 days it is a
   warning and the weekly workflow files an issue. `--skip-age` runs rules 1 and 2
   only. The clock has no other lever: `recordedOn` and `lastReview` may not be in
   the future and `maxAgeDays` is capped at 180. Entries carry different
   intervals (90 to 150 days) so they do not all fall due on one day and turn
   every open PR red together; that the age check is part of `bun run check` at
   all is a deliberate trade-off, and its warning arrives through the weekly
   issue, which fails the job (not silently) if it cannot be filed.

`lastReview` is set by a person who read the changelog, never by a script and
never carried forward to turn the gate green; `null` means "recorded from the
code, not yet reviewed" and the report says so. The gate does not fetch the
changelog URLs: a PR check must not depend on a third party being up. For a
downstream workspace: `--register <file>` (exporting `PROVIDER_REGISTER` and
`PROVIDER_HOSTS`), `--src <dir>` and `--root <dir>`.

## Issues from the weekly run

The `file-issues` job of the scheduled workflow runs `bun run deps:issues:sync`
over the freshness manifest and the findings of the two gates above. It is the
only write the workflow has (`issues: write`, on that job alone).

- **One open issue per finding.** Every finding has a stable key (never a day
  count or a digest); its fingerprint is a hidden marker in the issue body. A run
  lists the open issues labelled `dependency-finding` and files only findings
  without an open marker.
- **Closing is not hiding.** A closed issue whose finding is still true is filed
  again on the next run.
- **No spam.** At most 10 per run (`--max-create`); the rest are deferred, and
  filed on later runs. It never edits, comments on or closes an issue. If the
  open-issue listing fails or may be truncated, nothing is filed. The workflow
  step runs under `shell: bash` (`-eo pipefail`) so that failure, or a failed
  create, turns the job red instead of vanishing behind `| tee`.
- **Third-party text is not trusted.** The marker is only honoured as the first
  line of a body, and finding text (a dependency's `license` field, an advisory
  title) has comment delimiters defanged and `@` neutralised outside code spans
  before it goes into a public issue.
- Dry run by default (`bun run deps:issues:sync --findings f.json --freshness m.json`);
  `--create` writes. A manual `workflow_dispatch` files issues only with the
  `create_issues` input.

## The held-back register

`scripts/dependency-held-back.ts` lists versions we knowingly stay on:

| Field         | Meaning                                                                                                    |
| ------------- | ---------------------------------------------------------------------------------------------------------- |
| `packageName` | As the registry names it; `bun` stands for the Bun runtime.                                                |
| `heldVersion` | The version or floor we stay on.                                                                           |
| `reason`      | What was found that makes the newer version unsafe now — not "risk".                                       |
| `owner`       | Who decided and who re-justifies it.                                                                       |
| `reviewDate`  | ISO date. After it, `tests/dependency-held-back.test.ts` fails until the entry is re-justified or removed. |

Entries also go **stale**: when the held version is no longer behind the registry,
`deps:freshness --strict` reports it so it can be removed instead of lingering as
something no longer true. Drift nobody has evaluated yet does not belong here (it is
the backlog), and an advisory that cannot be fixed goes in
`scripts/dependency-audit-exceptions.ts`.
