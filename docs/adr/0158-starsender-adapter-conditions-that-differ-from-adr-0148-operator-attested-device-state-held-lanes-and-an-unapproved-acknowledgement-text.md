# ADR-0158 — StarSender adapter: the conditions that differ from ADR-0148 (operator-attested device state, held lanes, unknown outcomes, an unapproved acknowledgement text)

- **Status:** Proposed
- **Date:** 2026-11-03
- **Decision maker:** ahliweb (owner). **Not decided.** This ADR records what the implementation of Issue #1142 had to do differently from, or beyond, what the Accepted [ADR-0148](0148-omnichannel-foundation-is-five-gated-capabilities-with-fail-closed-per-account-capability.md) says, so that the owner can accept, change or reject each point. An agent cannot change an owner decision inside a pull request, and ADR-0148 is therefore **unchanged**.
- **Extends (when accepted):** [ADR-0148](0148-omnichannel-foundation-is-five-gated-capabilities-with-fail-closed-per-account-capability.md) section 4 (multi-sender semantics, "a provider's `success` is accepted, never delivered"), section 7 (unofficial-provider rules) and invariant I9 (verified inbound or deferred).
- **Related:** Issue #1142 (the adapter), PR #1241, [ADR-0133](0133-generic-delivery-capability-whatsapp-promotion.md) (one queue, at-least-once), [ADR-0141](0141-permissions-may-require-an-enrolled-mfa-factor.md) (the conditional step-up rule), `docs/awcms/starsender-adapter-runbook.md`.

## Safe to merge before this is accepted

The code that depends on this ADR is **off by default and fail closed**: `WHATSAPP_STARSENDER_ENABLED` is unset by default, and the shipped acknowledgement text carries `approval: null`, so **no acknowledgement can be recorded, no StarSender device can be `connected`, and nothing can be sent** until the owner approves the text in a reviewed change. Merging the pull request therefore changes no deployment's behaviour. Accepting this ADR (or changing it) is what makes the adapter usable; the text approval is a separate, human step this ADR cannot perform.

## Context

ADR-0148 admitted StarSender as the single recorded exception to "official interfaces only" (I6) and set conditions (section 4, section 7, I9, and the Issue #1142 comment "Design gate lifted"): the adapter is off by default, needs a per-operator risk acknowledgement stored with provider, user, time and text version and revocable, a device may be `connected` only after that, a `success` is "accepted" never "delivered", there is no fallback or rotation, and status and contact ingestion needs a verified path or a fail-closed status mode. It also says "the default in a derived product is activated only after those gates, **a verified device state** and receiver consent", and (section 4) that a sender that is "disabled, revoked, **disconnected**, unapproved or from another tenant" makes a claimed row terminal `failed`.

Implementing it against StarSender's public documentation (one page, read 3 November 2026) met facts the ADR did not decide:

- StarSender documents **no side-effect-free device-status call**. The only evidenced endpoint is the send, which messages a person.
- StarSender documents a webhook with **no authentication of the request** (no signature, secret header or challenge).
- StarSender documents **no idempotency key** and no error responses.
- A device can be unpaired by the vendor or the phone at any time, which is a transient, tenant-fixable condition, not the end of the account.

## What differs from ADR-0148, and what is proposed

| #   | ADR-0148 says                                                                                                                                           | This ADR proposes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Derived-product default only after "a **verified** device state". `channel_accounts` health is **reported by a connector, never asserted by a person**. | A StarSender device is `connected` only by `POST /accounts/{id}/attest-device`: **operator-attested, not verified**, recorded as health `OPERATOR_ATTESTED`. This is a **recorded exception** to "health is reported, never asserted by a person", for this provider only, because there is nothing a connector could verify with. It needs the attester's OWN active acknowledgement of the current text, a conditional step-up, and a stored credential. If StarSender evidences a status call a connector replaces it and the exception ends.          |
| 2   | Inbound/status: "a verified webhook **or** a fail-closed status mode"; Issue #1142 adds "an ADR addendum decides any compensating mechanism".           | The **fail-closed status mode is chosen**: no StarSender webhook route, no invented signature scheme, no status or contact ingested; a message is `sent` (accepted) and stays that. **No compensating mechanism is proposed** (a polling endpoint, if StarSender documents one, needs its own decision and evidence).                                                                                                                                                                                                                                     |
| 3   | A sender that is "disconnected" makes a claimed row terminal `failed` (section 4).                                                                      | A **provider-reported** device disconnect (`device_disconnected`) **holds that device's lane** (one call, no more) and retries with backoff bounded by `WHATSAPP_SEND_MAX_RETRIES`, then terminal. A **control-plane** `revoked`, `disabled`, unacknowledged or flag-off sender stays terminal, exactly as ADR-0148 says. The difference is the cause: a phone that needs re-pairing is the tenant's to fix, and failing every queued message at once would discard messages the tenant wants sent. Nothing is ever rerouted.                             |
| 4   | The acknowledgement is "stored" per operator (section 4, 7). The pack names `whatsapp_delivery.risk.acknowledge`.                                       | It is owned by `channel_accounts` (`awcms_channel_provider_risk_acknowledgements`, `sql/340`) because it gates `connected`, a control-plane state; the permission is `channel_accounts.risk_acknowledgements.create` (`AccessAction` is a closed vocabulary), with `.read` and a high-risk `.revoke`. The record keeps the SHA-256 of the exact words shown, is append-only apart from a revocation stamp, never deleted, with database-stamped times. A device is bound to the acknowledgement it was attested under, and revoking THAT one degrades it. |
| 5   | The queue is at-least-once (ADR-0133); retry classification is the adapter's.                                                                           | **A timeout, a reset or ANY 5xx is an unknown outcome and is NOT retried** (`outcome_unknown`), because StarSender documents no idempotency key and a retry could message the recipient twice. Only DNS failure, HTTP 429, a reported rate limit and a disconnected device are retried. This is stricter than the other adapters.                                                                                                                                                                                                                         |
| 6   | A device key is a credential in `channel_secrets` (section 5).                                                                                          | Replacing a device key moves an unofficial-provider device back to `pending` (`CREDENTIAL_REPLACED`) in the same transaction and needs a fresh attestation: the attested state is a claim about THAT key's pairing.                                                                                                                                                                                                                                                                                                                                       |
| 7   | Condition (4) of the issue: the acknowledgement text must be approved by the business owner (human step).                                               | Unchanged and **not performed**: the text ships as a draft with `approval: null` and the endpoints answer `409 RISK_TEXT_NOT_APPROVED`. A new `textVersion` invalidates every earlier acknowledgement.                                                                                                                                                                                                                                                                                                                                                    |
| 8   | `ChannelAccountPort` is `1.0.0` (Issue #1141).                                                                                                          | `1.1.0`, additive: two terminal refusal reasons, `RISK_ACKNOWLEDGEMENT_REQUIRED` and `PROVIDER_ADAPTER_DISABLED` (asked before any secret is read). No signature changed.                                                                                                                                                                                                                                                                                                                                                                                 |

## Decision (proposed)

Accept points 1 to 8 as the conditions under which the StarSender adapter may be used, as implemented in PR #1241, with the following explicit residuals recorded rather than hidden:

- The wire contract is **unverified against the live API** (only the success body is documented); the verification checklist is `docs/awcms/starsender-adapter-runbook.md` section 6 and must be run with a test device before any production use.
- Device state is an **operator's claim**; a disconnected device is found by a failed send, not by a probe, and the worker has no write grant, so it does not mark the account `degraded` itself.
- A stored acknowledgement proves a person accepted a text version, not that they understood it; whether an acknowledgement belonging to a deactivated or erased user should still count is not decided (the record survives erasure of the person by design) and a clean rule was not found.
- Marketing consent is still keyed by tenant and recipient, not business scope (open decision M4 of Issue #1231, untouched).

## Owner questions

1. Is a **recorded, operator-attested** device state acceptable for StarSender in place of a "verified device state" (point 1), given that no verification exists? If not, the alternative is that no StarSender device can ever be `connected`.
2. Is **holding the lane and retrying** a provider-reported disconnect acceptable, instead of failing every queued message terminally (point 3)?
3. Is **not retrying a 5xx or a timeout** the right trade-off between a possible lost message and a possible duplicate (point 5)?
4. Approve (or rewrite) the **acknowledgement text** and fill its `approval` in a reviewed change (point 7). The business owner or counsel does this, not an agent.

## Alternatives rejected

- **Editing ADR-0148 in the implementation pull request.** It would have changed an Accepted owner decision without the owner. This ADR exists to prevent that.
- **Only a "verified" device state.** Impossible without a status call; the adapter could never be enabled.
- **A webhook protected by URL secrecy.** Forbidden by I9: it would let an unauthenticated caller mutate customer state.
- **Retrying 5xx like the other adapters.** A failing gateway may already have forwarded the message; with no idempotency key that can double-message a person.
- **Failing every queued message when a device disconnects.** Discards messages for a condition the tenant fixes in minutes; the lane hold bounds the cost with a retry budget.

## Consequences

- **Positive:** every point where the implementation went beyond ADR-0148 is visible, attributable and reversible by the owner; the code is safe to merge because it is off and fail closed.
- **Negative:** the adapter cannot be used until the owner decides; if the owner rejects point 1, the code that attests devices must be removed and the adapter becomes unusable.
- **Neutral:** no behaviour changes for any deployment until the flag is set, the text is approved, and an operator acknowledges and attests.
