# ADR-0131 — Admission of the generic booking module (`booking`: resources, schedules, reservations)

- **Status:** Accepted
- **Date:** 2026-10-08
- **Decision maker:** ahliweb
- **Extends:** [ADR-0011](0011-capability-ports-for-cross-module-collaboration.md) (consumers depend on a neutral port), [ADR-0034](0034-awcms-family-direct-use-templates-and-derived-pathway-removal.md) (an ERP domain module is built directly in `src/modules/`), [ADR-0063](0063-ownership-grants-run-through-the-authorization-chokepoint.md) (every handler authorizes through the chokepoint), [ADR-0094](0094-a-data-subject-is-answered-per-tenant.md) (every table answers the data-subject question), [ADR-0126](0126-generic-multi-location-stock-ledger-module-admission.md) (the pattern of an append-only, reconciled, port-fronted domain module), [ADR-0127](0127-generic-jurisdiction-neutral-tax-calculation-module.md) (the earlier trigger-plus-advisory-lock answer to non-overlap that this ADR deliberately does not repeat)
- **Related:** Issue #915 (this admission); downstream `ahliweb/awcms-one#280` (epic) and [its ADR-0040](https://github.com/ahliweb/awcms-one/blob/main/docs/adr/0040-aw-business-platform-capability-ownership-and-boundaries.md) (Accepted 8 Oct 2026, **placement only**) and [`aw-business-platform-dor.md`](https://github.com/ahliweb/awcms-one/blob/main/docs/aw-business-platform-dor.md) (owner decisions O1–O12, **still open**); Issue #916 / ADR-0132 (`hr_payroll`, which defines the workforce availability port this module consumes); [`docs/awcms/booking.md`](../awcms/booking.md) (PRD-lite, state machine, ERD, permissions/RLS matrix, threat and privacy notes, port contract, required regression test)

## Context

Hotels, villas, salons, clinics, rental shops, facilities and workshops all sell the same thing: **a claim on a limited resource for an interval of time**. Without one shared module each consumer builds its own, and each builds a different way to be wrong: a check-then-insert that two customers pass at the same instant, a "slot" table whose grid cannot express a 90-minute service with a 15-minute clean-up, a datetime stored without a zone that moves by an hour twice a year, a hold that never expires and blocks the last room until someone notices, a payment flag copied onto the reservation that disagrees with the payment ledger. The downstream template's ADR-0040 places this domain **upstream first** because a bookable resource has no dependency on a store, and a tenant with no commerce at all needs it. That ADR settles placement only; it does not admit a module. This one does.

Per `docs/awcms/21_module_admission_governance.md` §3 this is an **ERP Domain Module** (§4.3): generic across industries that rent out time, space or capacity, disableable per tenant, `type: "domain"`. Compatibility class (§6): **offline-lan-safe** — it calls no provider and works with every external integration off.

## Decision

### 1. One module, `booking`, a generic claim-on-time engine

`src/modules/booking/`, key `booking`, tables `awcms_booking_*`. It owns resources, offerings, schedules, reservations and their allocations. It owns **no money, no stock, no customer master, no staff master, no notification**: price, payment, deposits, refunds and documents belong to whatever commerce layer a tenant runs; customers to `profile_identity`; staff shifts to the workforce capability (`hr_payroll`, #916); delivery to a generic delivery capability. **It does not depend on `commerce`** — not in `dependencies`, not in `consumes`, not by import. A tenant with no store uses it unchanged; a commerce linkage is a downstream adapter that calls the port and consumes the events (§9). `profile_identity` is a soft capability (an optional customer reference) and the workforce availability port is an **optional** consumed capability (`optional: true`, §5 of doc 21): without it, staff are constrained only by the module's own double-booking rule.

### 2. Double-booking is prevented by the database, not by the handler

**Every claim on a unit of a resource is a row, and the database refuses two overlapping live rows for the same unit.** The core is one declarative constraint on `awcms_booking_resource_allocations`:

```
EXCLUDE USING gist (resource_unit_id WITH =, tstzrange(occupied_from, occupied_to, '[)') WITH &&)
  WHERE (released_at IS NULL)
```

- **Exclusive resource** (capacity 1): one unit, one row at a time.
- **Capacity N > 1** is **N unit rows, each under the same constraint** — an allocation picks a free unit in a deterministic order and inserts with `ON CONFLICT DO NOTHING … RETURNING`, trying the next unit on a conflict. "The final seat" is therefore the same problem as "the only room": at most one concurrent insert can win a unit, and the loser tries the next one or reports `SLOT_UNAVAILABLE`. No counter is read, compared and written.
- **Staff** are constrained the same way, by `EXCLUDE … (staff_ref WITH =, range WITH &&)` on staff assignments.
- **Where capacity is nonetheless computed** (a per-offering concurrency cap, a pool-wide limit, a daily maximum — anything an exclusion constraint cannot express because it is an aggregate), the rule is: the check and the write happen in one transaction that first takes `SELECT … FOR UPDATE` on the **owning pool or offering row**, locks are taken in a fixed global order (ids ascending, bytewise), and the check re-reads under the lock. READ COMMITTED with the lock is sufficient and SERIALIZABLE is not used. Counted capacity with no unit rows (very large N) is **not** admitted in v1.
- The constraint is verified by a **required regression test**: two genuinely concurrent transactions contend for the final slot and at most one commits (specified in `booking.md` §8, to be implemented with the module — the module does not ship without it).

**The `btree_gist` cost, verified.** The constraint needs the `btree_gist` extension (uuid equality inside a GiST index). `sql/171` and ADR-0127 §4 declined it as "a privileged `CREATE EXTENSION` that no migration here asks for". That statement is stale in its premise: `sql/001` (`pgcrypto`) and `sql/064` (`pg_trgm`) already run `CREATE EXTENSION IF NOT EXISTS`, and all three are **trusted extensions** in PostgreSQL 13+, creatable by a database owner with `CREATE` on the database without superuser. The deployment profile pins `postgres:18.4`. So the admission cost is: **one `CREATE EXTENSION IF NOT EXISTS btree_gist` in the booking migration, the same privilege class as the two already there**, plus an operator pre-flight line in the deploy runbook (a managed database whose migration role cannot create trusted extensions fails the migration loudly, before any table exists — it cannot half-apply). It does not contradict ADR-0127, whose non-overlap needed only a date range per profile and was served by a trigger; booking's correctness property is much more adversarial and is worth the declarative guarantee. PostgreSQL 18's `WITHOUT OVERLAPS` is syntax over the same GiST machinery and cannot take a `WHERE` predicate, so it does not fit a table whose rows are released rather than deleted.

### 3. Time is explicit

Every instant is a UTC `timestamptz`. Every interval is **half-open `[start, end)`**: inclusive start, exclusive end, so back-to-back bookings share a boundary and do not conflict. A schedule is written in **local wall-clock time with an explicit IANA timezone** (`Asia/Pontianak`, never an offset and never "server local"), and is expanded to UTC instants by one pure function. Daylight-saving gaps and folds follow RFC 5545 §3.3.5 (a nonexistent local time maps with the offset before the gap; an ambiguous one takes its first occurrence). A stored reservation is never re-derived from a schedule: **its UTC instants are facts**, so a later timezone-database update or schedule edit cannot move a confirmed booking. Setup and clean-up buffers are stored per offering and **snapshotted onto each allocation** as an `occupied` range `[start − setup, end + cleanup)` that the constraint tests; the customer-facing interval stays `[start, end)`.

### 4. Recurrence is a closed, bounded, deterministic subset of RFC 5545

Schedules and reservation series use a **structured** recurrence (frequency `DAILY` / `WEEKLY`, `INTERVAL`, `BYDAY`, `UNTIL` xor `COUNT`, `EXDATE`/`RDATE` as exceptions), validated against a closed schema, expanded by a pure function in the schedule's timezone, with hard caps (horizon, occurrences, series length). No RRULE string is parsed from clients, no `BYSETPOS`/`BYWEEKNO`/`BYYEARDAY`, no new dependency. A booked series is **materialised** into N independent reservations that share a `series_id`, created all-or-none.

### 5. A reservation is a state machine, and payment is not in it

`held → confirmed → checked_in → completed`; `held → expired`; `held | confirmed → cancelled`; `confirmed → rescheduled` (terminal, superseded by a new reservation); `confirmed → no_show`. A `BEFORE UPDATE` trigger allows exactly these transitions and only the columns each may change; terminal states are terminal. **No payment, deposit, price or balance is stored here**: a deposit is a partial payment on the linked order in the commerce layer, and confirmation is something a caller (a person, or an adapter that has observed a payment) asks for. An offering's `confirmation_mode` (`immediate`, `hold_then_confirm`) tells the module whether create returns `confirmed` or `held`.

### 6. Holds expire on the database clock, and an unswept hold never blocks a sale

A hold carries `hold_expires_at`, set from the **database clock** (`clock_timestamp()`, not the client's, and not `now()`, which is the transaction start). The exclusion constraint cannot read a clock, so expiry is two cooperating mechanisms: a job that expires holds and releases their allocations (and emits events), **and** a lazy reclaim in every writer — before inserting, the transaction releases any expired-but-unswept hold overlapping the target unit, under the reservation row lock. A confirm checks the expiry itself under `FOR UPDATE` and returns `409 HOLD_EXPIRED` even if the job has not run. A hold flood is a denial-of-service on inventory of time, so holds are capped per customer and per tenant and have a maximum lifetime (`booking.md` §9).

### 7. Reschedule is a chain, history is append-only

Rescheduling creates a **new reservation** (same `lineage_id`, `rescheduled_from_id` set) and marks the old one `rescheduled` with `superseded_by_id`, in one transaction that releases the old allocations first and then inserts the new ones, so a reschedule to an overlapping time does not conflict with itself and a refused reschedule rolls back to the untouched original. A reservation's interval is therefore immutable after creation: projections, linked orders and customer messages never see a booking silently change. Every transition appends a row to `awcms_booking_reservation_events` (no `UPDATE`, no `DELETE`, enforced by trigger and privileges). Nothing in this module is hard-deleted; a mistake is a cancellation.

### 8. Idempotent, authorized, audited, evented

Create, hold, confirm, cancel, reschedule, check-in, complete and no-show require `Idempotency-Key` (the shared OpenAPI component, ADR-0129) **and** are idempotent by state check — three layers, as in ADR-0128: the header deduplicates a retried HTTP request, the state check deduplicates the business action, and the unique constraint deduplicates the claim. A refusal inside the application is converted to a throw inside a savepoint and back to a value outside it, so a handler that returns a 4xx cannot commit half a reschedule. Every handler is a `defineTenantRoute` authorizing through `authorizeInTransaction` (ADR-0063), default-deny; every table has `tenant_id`, `ENABLE`+`FORCE` RLS with `USING` and `WITH CHECK`, and every reference is a composite `(tenant_id, id)` FK. High-risk actions (`override` — booking outside the schedule, and the policy change) are audited at `warning`/`critical` with the correlation id; no audit row, log line or event carries a customer note, name or contact. Events go through the domain-event outbox **in the same transaction** (`awcms.booking.reservation.*`, provisional names in the pack; AsyncAPI is edited when the module is built, not by this ADR).

### 9. The adapter boundary

The module exposes a `BookingPort` (`quote`, `hold`, `confirm`, `cancel`, `reschedule`) in `_shared/ports/` and emits events. A commerce adapter (downstream) maps an offering to a product, turns a hold into an order, observes payment and calls `confirm`, and cancels the order when the hold expires. **Booking never calls commerce.** Occupancy and utilization projections live on the `reporting` engine and are owned by this module.

### 10. Retention and personal data

Reservations, items, allocations, staff assignments and events are the evidence behind a customer's booking and are retained for the life of the tenant (registered with `data_lifecycle` as `delegated` with that reason, exactly as ADR-0126 §7 and ADR-0128 §7), with archive-then-purge a recorded follow-up needing its own ADR. A customer is a nullable reference, never a copied name; a free-text note is classified, length-limited, redacted from every export, audit row and event, and nulled on erasure. Where a vertical (a clinic) would put health information in a note, that is **special-category personal data** under UU PDP 27/2022 and is an owner decision (O2), not a default.

## Consequences

- A consumer holds, confirms, cancels and reschedules through one port; the database, not each consumer's handler, guarantees one claim per unit per interval.
- **Cost:** about 13 tables, ~29 permissions, new `AccessAction` members (`confirm`, `reschedule`, `check_in`, `complete`, `no_show`, and HIGH-RISK `override`), the `btree_gist` extension, a job, a port, 9 events, two projections. Availability search (a read) can be expensive; it is bounded by window, page and per-principal rate (pack §9), and is never edge-cached (it is per-tenant by nature).
- **Rollback** is forward-only like every migration here: stop calling the module, keep the tables (inert), and every downstream order stays valid. Dropping them is a restore-class decision. After a restore, reconcile reservations against allocations (pack §7).
- **Open and not decided here:** the owner decisions O1, O2, O3, O5, O8, O9 and O12 of the downstream DoR tracker (pack §11). O12 and O2 affect schema (the customer reference, note policy, first-vertical fields) and **must be answered before the migration is written**; O8 affects only projection definitions. This ADR admits the module and fixes the properties that hold regardless of those answers.
- **Update (2026-10-10): owner answers recorded.** The awcms-one owner answered O1–O12 on 2026-10-10. The answers that bind this pack are recorded in [`booking.md`](../awcms/booking.md) §11 and §7.2: O8 (occupancy excludes holds; the 90-day retention window is a customer-retention KPI; net revenue is the headline) and O12 (commerce stays the customer authority, so v1 carries only an opaque `external_customer_ref` and no `customer_profile_id`). O2 (first vertical hotel / villa / rental) conflicted with the pack's assumption that nightly stays are out of v1; it is resolved by [ADR-0135](0135-day-granularity-stays-admitted-into-booking-v1.md), which amends this ADR (Issue #931). The rest of this ADR is unchanged.
- **Not admitted in v1:** counted capacity without unit rows, resource calendars synchronised with external calendars (iCal/Google), automatic waitlists, dynamic pricing, public (anonymous) endpoints (a downstream BFF concern), multi-resource optimisation (best-fit packing), shared turnaround between consecutive bookings (buffers are conservative), and admin screens (a recorded follow-up; the module registers `experimental` until its first screen, as `inventory` and `procurement` did).

## Alternatives rejected

Scored on security, performance, maintainability, scalability, compatibility and operational complexity.

**Where it lives**

- **Inside `commerce`** (a booking is a "service" product): couples a reservation to a store, so a tenant without a store cannot use it; stores a payment flag next to a time claim; and `commerce` is the downstream template's, so a generic domain would be re-derived or drift (ADR-0040 rules 5, 7, 8). Compatibility and maintainability fail.
- **Inside `inventory`** (a resource as a stock item): the ledger counts quantity per location; a booking is an interval on a unit. Nothing about a movement, a balance or negative-stock policy applies, and forcing it in would give `inventory` a second, unrelated invariant.
- **Per-vertical modules** (hotel, clinic, salon): three copies of the hardest correctness property in the domain. Rejected on maintainability and security.
- **Generic upstream module** (chosen): one tested place for the double-booking property, no commerce edge, verticals are thin configuration and adapters.

**How double-booking is prevented**

| Option                                                                 | Verdict                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Check, then insert, in the handler (READ COMMITTED)                    | **Rejected.** The race is the bug. Both transactions see the slot free.                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `SERIALIZABLE` isolation                                               | **Rejected.** Correct but pays in predicate-lock breadth and `40001` retries on a hot slot, spreads a retry contract to every caller, and protects only transactions that opt in.                                                                                                                                                                                                                                                                                                                                                      |
| Advisory lock per resource + a checking trigger (the ADR-0127 pattern) | **Rejected for booking.** Correct only while **every** writer takes the lock — a maintenance session, a backfill or a future code path that forgets it silently double-books. The lock key is a 32-bit hash (collisions only over-serialise, but it is another invariant to test). Acceptable for tax windows edited by two humans a year; not for the property a customer pays for.                                                                                                                                                   |
| Pre-materialised slot grid with a unique key                           | **Rejected.** Fixes the granularity, cannot express variable durations or buffers, multiplies rows by resources × days, and a schedule change becomes a data migration.                                                                                                                                                                                                                                                                                                                                                                |
| A `capacity` counter row read-compared-written                         | **Rejected as the mechanism**, retained only where capacity is a computed aggregate and then **only under a pool-row `FOR UPDATE`** (§2).                                                                                                                                                                                                                                                                                                                                                                                              |
| **`EXCLUDE USING gist` on unit allocation rows (chosen)**              | Declarative: holds for every writer, including ones that do not exist yet. Security and maintainability best; performance is one GiST probe per insert and the same index serves availability reads; scalability bounded by live allocation rows (past rows are an archival follow-up). Cost: `btree_gist` (verified trusted, same class as `pg_trgm`/`pgcrypto`), `23P01` handling (`errno`, not `code`, in Bun.SQL), and a possible deadlock between multi-item writers (§ pack 8) handled by fixed lock order plus a bounded retry. |

**Other**

- **Mutate a reservation's interval in place on reschedule:** history lives only in events, projections and linked orders can see an interval change under them, and the state machine needs "confirmed → confirmed with a different time". The chain keeps every instant a fact.
- **Store payment or deposit status on the reservation:** a second source of truth beside the payment ledger (ADR-0040 rule 9); it will disagree. Booking records a state about the claim only.
- **Full RRULE strings and a recurrence library:** a large parser surface fed by clients, non-deterministic across libraries and tzdata versions, and a new runtime dependency in a repo that holds a two-dependency posture. A closed structured subset covers weekly opening hours and series.
- **Floating (zone-less) local times for schedules:** a booking would move by an hour at a DST change. Explicit IANA zone plus stored UTC instants.
- **Copying the customer's name and contact onto the reservation:** a second source of truth that `profile_identity` erasure and merge cannot reach.
- **Expiry only by job:** a stuck job would leave the last room held forever. Lazy reclaim in writers makes correctness independent of the job's health; the job is for events and tidiness.
- **A hard dependency on the workforce capability:** forces `hr_payroll` on every tenant that books a room. Optional port; without it, staff are constrained by the module's own rule only.
