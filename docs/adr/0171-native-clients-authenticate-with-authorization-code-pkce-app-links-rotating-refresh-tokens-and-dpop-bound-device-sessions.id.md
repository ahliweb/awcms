## Konteks

Aplikasi persona (pelanggan, kurir, pengemudi, mitra, petugas lapangan dan gudang) adalah klien Lynx di repo konsumen ([ADR-0146](0146-persona-apps-prefer-lynx-in-consumer-repos-astro-keeps-admin-and-public-web.id.md)). Mereka hanya memakai kontrak OpenAPI publik dan tidak boleh melonggarkan isolasi tenant, ABAC, atau idempotency. Saat ini satu-satunya kredensial manusia yang diterima repo ini adalah **bearer sesi** (`awcms_sessions`, token buram disimpan sebagai `token_hash`, `AUTH_SESSION_TTL_MIN=120`, bukan JWT, tidak diperpanjang oleh pemakaian) dari `POST /api/v1/auth/login` atau handoff BFF ([ADR-0050](0050-bff-session-handoff-code.id.md)). Itu tepat untuk browser di belakang BFF dan keliru untuk ponsel:

1. **Aplikasi native tak bisa memegang client secret**, jadi ia klien publik OAuth ([RFC 8252](https://www.rfc-editor.org/rfc/rfc8252)). Alternatif sekarang, mengumpulkan kata sandi di dalam aplikasi lalu memanggil `/login`, menaruh kredensial, faktor kedua MFA, dan ceremony passkey ke kode aplikasi, mengalahkan penegakan SSO ([ADR-0028](0028-oidc-sso-tenant-aware-account-linking-break-glass.id.md)) dan ketahanan phishing ([ADR-0168](0168-passkeys-webauthn-are-a-principal-owned-phishing-resistant-factor-that-yields-aal2-with-self-implemented-attestation-none-verification.id.md)), dan memaksa aplikasi menyalin alur (alasan yang sama ADR-0050 menolak proksi kata sandi).
2. **Bearer 120 menit berumur salah** untuk perangkat yang harus tetap masuk berminggu-minggu, dan bearer berumur panjang adalah perbaikan yang keliru: bearer yang dicuri bisa dipakai penuh.
3. **Bearer tidak terikat ke apa pun.** Siapa pun yang menyalinnya dari backup, log, atau perangkat ter-root dapat memakainya.
4. **ADR-0168 meninggalkan tiga masukan eksplisit untuk isu ini**: host asosiasi app link (K16 Q9: `APP_URL` menyajikan `/.well-known/assetlinks.json` dan `apple-app-site-association`; allow-list origin menerima `android:apk-key-hash:<b64url>` yang dikonfigurasi eksplisit, tanpa wildcard), aturan bahwa pengikatan perangkat **tidak** memakai passkey (BE/BS tak terbukti tanpa attestation), dan aturan A5 bahwa permukaan autentikasi hidup di satu host.

Fakta `origin/main` yang diandalkan desain ini (dicek pada `83f67158`):

- `awcms_sessions` ber-scope tenant di bawah FORCE RLS dan sudah memuat `assurance_level` (`sql/024`), `stepped_up_at`, `origin_auth` dengan CHECK (`sql/100`; `sql/117` sudah memperluasnya untuk akses terdelegasi, ADR-0090, bukan untuk ADR-0168, sehingga kini berisi lima nilai dan S2 menambah `native`), `client_ip_hash`, `user_agent_summary`. Step-up **merotasi** token sesi dan membawa `origin_auth` ke depan ("merotasi sesi tidak mengautentikasi ulang").
- `sql/144` memperkenalkan `credential_epoch`: penghitung tingkat principal, diperiksa pada setiap pembacaan sesi lewat satu fragmen SQL (`sessionCredentialCurrent`, `session-credential-epoch.ts`), yang mengakhiri sesi **semua** tenant saat kredensial berubah. Ia ada karena pencabutan baris sesi lintas-tenant mustahil di bawah FORCE RLS. Sesi baru dicap epoch **terkini** (`currentCredentialEpoch`), itulah sebabnya refresh tidak boleh mencetak sesi dari epoch terkini (H1).
- `sql/100` mencatat alasan tidak ada `last_seen_at`: satu UPDATE per permintaan pada baca terpanas tidak sepadan dengan kolom kosmetik. ADR ini menjaga disiplin itu.
- `requireStepUp` (`identity-access/application/mfa-session-assurance.ts`) membaca `assurance_level` dan `stepped_up_at` dari baris sesi. `MFA_ENROLLMENT_REQUIRED` dikembalikan `login.ts`, `session/switch.ts`, dan `session/tenant.ts`. `evaluateTenantEntry` mengembalikan `password_login_disabled` ([ADR-0088](0088-tenant-selection-and-switching.id.md)).
- Kode hash sekali pakai dengan namespace hash sendiri sudah ada (`ho-sha256:`, `bff-sha256:`, `mc-sha256:`), 32 byte CSPRNG, perbandingan waktu-konstan, TTL dicerminkan di CHECK (`session-handoff.ts`).
- Token webhook kanal membawa prefiks routing tak-rahasia (`wcb1.*`, `_shared/channel-webhook-token.ts`) sehingga tenant diturunkan dari token, bukan dari payload.

## Keputusan

AWCMS bertindak sebagai **authorization server OAuth 2.0 untuk klien publik native terdaftar**, memakai **alur authorization code dengan PKCE (S256)** di browser sistem, mengalihkan ke **app link** (URL `https` yang diklaim), menerbitkan **access token buram berumur pendek**, **refresh token buram berotasi dengan deteksi reuse**, dan **mengikat setiap sesi perangkat ke kunci per-instalasi yang non-exportable dengan bukti DPoP**. Pengguna mengautentikasi di browser pada satu host autentikasi, sehingga kata sandi, TOTP, passkey, SSO, Turnstile, dan pendaftaran MFA dipakai ulang, bukan diimplementasikan ulang.

Ini **bergaya OIDC, bukan OpenID Provider penuh** pada rilis pertama: tanpa dokumen discovery, tanpa `id_token`, tanpa registrasi klien dinamis (Q2). Kami tidak mengklaim kesesuaian OIDC.

Semuanya dikirim di balik `AUTH_NATIVE_ENABLED=false` (fail closed: endpoint menjawab 404 seragam saat mati).

### 1. Klien publik native terpisah dari klien web

- **Dua tabel, karena identitas aplikasi bersifat tingkat host dan pengikatan klien bersifat tingkat tenant (M1).** `awcms_native_apps` bersifat **global** (tanpa `tenant_id`, tanpa RLS; didaftarkan sebagai tabel global dengan alasan tertulis untuk `security:readiness`, seperti tabel global lain): platform (`android` atau `ios`), paket atau bundle, sidik jari SHA-256 sertifikat penandatangan yang diharapkan di `assetlinks.json`, origin `android:apk-key-hash:<b64url>` (hanya bila aplikasi memakai passkey native), `teamId.bundleId` iOS, path callback persis, status, kolom audit. Ia ditulis **hanya** di balik permission platform-scoped `identity_access.native_client.register`, dan dibaca oleh rute publik `/.well-known/*` (yang tak punya konteks tenant), allow-list origin passkey, dan generator berkas asosiasi lewat grant baca biasa, **tanpa fungsi `SECURITY DEFINER`**. `awcms_native_clients` adalah **pengikatan tenant, ber-scope tenant di bawah FORCE RLS**: `client_id` (buram, acak, bukan rahasia), `tenant_id`, `app_id` (FK ke tabel global), nama tampilan, himpunan redirect URI persis (maksimal 3, masing-masing path callback aplikasi itu), status (`active`, `disabled`), dan kolom audit. Tenant yang menonaktifkan pengikatannya mengubah **hanya pengikatan itu** dan tak pernah berkas asosiasi. **Tidak ada client secret**: klien publik tak bisa mengautentikasi dirinya, dan `client_id` tidak membuktikan apa pun. Memiliki baris klien tidak pernah memberi apa-apa dengan sendirinya; kredensial pengguna dan redirect persis yang memberi (di Android pernyataan itu butuh aturan tambahan H4).
- Klien BFF web (secret `bff-sha256:` ADR-0050, confidential) adalah objek lain dan tak pernah dapat dipakai di endpoint native, begitu pula sebaliknya.
- **Redirect URI** dicocokkan dengan **perbandingan string persis** (RFC 9700 mewajibkan pencocokan persis; tanpa prefiks, wildcard, atau pola). Aturan saat registrasi: skema `https` saja (**tanpa custom URL scheme**: tidak tahan tabrakan; RFC 8252 memilih link https yang diklaim), host persis host `APP_URL`, path di bawah `/native/callback/`, tanpa query, fragment, userinfo, atau port. Redirect loopback **tidak** diadmisi (untuk desktop; Q6 ADR ini menunda desktop).
- **Asosiasi app link adalah kepercayaan tingkat host, jadi tingkat platform.** `/.well-known/assetlinks.json` dan `/.well-known/apple-app-site-association` disajikan di host `APP_URL` dari konfigurasi yang dikendalikan operator platform, dihasilkan dari baris klien yang **aktif**, stabil per byte dan dapat di-cache. Karena RP ID dan host dipakai bersama semua tenant, **membuat atau mengubah aplikasi native (baris tabel global: sidik jari sertifikat, origin `android:apk-key-hash`, app ID iOS, path callback) adalah permission platform-scoped** (`identity_access.native_client.register`, aktivitas platform-scoped menurut [ADR-0053](0053-platform-scoped-permissions.id.md); tidak boleh di-seed ke peran tenant, aturan [ADR-0051](0051-admin-screens-consolidated-in-awcms.id.md)). Admin tenant boleh melihat dan menonaktifkan pengikatan (`awcms_native_clients`) tenantnya sendiri (ber-scope tenant, ABAC default-deny); itu tak pernah mengubah berkas asosiasi tingkat host. Registrasi mandiri oleh admin tenant tidak ada di rilis pertama (Q1) karena aplikasi nakal yang tercantum di berkas asosiasi host dapat mencegat kode dan, dengan origin passkey terdaftar, ceremony untuk **setiap** tenant yang berbagi RP.
- **Android memercayai setiap aplikasi tercantum untuk seluruh host (H4).** Digital Asset Links memberi `handle_all_urls` kepada setiap paket tercantum untuk **seluruh** host, dan path ditentukan manifest aplikasi, bukan server (iOS berbeda: berkas asosiasi membatasi tiap app ID ke path `components`). Aplikasi tenant B yang sah tetapi jahat atau terkompromi karenanya dapat memulai `/native/authorize` dengan `client_id` tenant A beserta verifier dan kuncinya sendiri, menyatakan path callback tenant A di manifestnya, menerima code, lalu menebusnya. Hanya layar persetujuan yang menghalangi (RFC 8252 "client impersonation"; nomor bagian perlu verifikasi). Normatif: **sampai attestation platform (Q7) memungkinkan token endpoint memverifikasi paket dan digest tanda tangan aplikasi penebus, paling banyak satu penerbit tanda tangan boleh tercantum untuk Android di host itu**; menambah yang kedua menuntut attestation atau **host callback per klien** yang berkas asosiasinya hanya mencantumkan klien itu. Entri asosiasi iOS mencantumkan tiap app ID dengan hanya path callback persisnya sendiri. Persetujuan ditampilkan pada **setiap** otorisasi klien native dan tak pernah diingat. **Tes merah wajib (S3):** mendaftarkan penerbit tanda tangan Android kedua di host ditolak; berkas iOS yang dihasilkan tak pernah mencantumkan path app ID lain; keduanya gagal bila penjaganya dihapus.
- Origin passkey `android:apk-key-hash:<b64url>` ([ADR-0168](0168-passkeys-webauthn-are-a-principal-owned-phishing-resistant-factor-that-yields-aal2-with-self-implemented-attestation-none-verification.id.md) K16 Q9) hanya berasal dari baris aktif `awcms_native_apps` yang didaftarkan lewat permission platform di atas, berupa string persis, dan dibaca ke allow-list origin verifier passkey. Tanpa wildcard, tanpa string environment yang dapat diperluas diam-diam oleh pemegang variabel deployment tanpa baris audit.

### 2. Authorization endpoint (browser, di satu host autentikasi)

`GET /native/authorize` adalah halaman HTML, disajikan hanya di host `APP_URL` (ADR-0168 A5: host lain mendapat 301). Ia bukan API JSON dan tidak berada di shell admin.

- Parameter wajib: `response_type=code`, `client_id`, `redirect_uri` (cocok persis dengan klien), `state` (wajib, sedikitnya 128 bit entropi diminta dari aplikasi, di-echo), `code_challenge` dan `code_challenge_method=S256`, `dpop_jkt` (thumbprint JWK kunci instalasi; RFC 9449 mengikat code ke kunci itu; nomor bagian perlu verifikasi). PKCE `plain` **ditolak**. Permintaan yang kekurangan salah satunya adalah error.
- **Urutan validasi dan permukaan error.** Klien tak dikenal, klien nonaktif, redirect yang tak cocok, atau permintaan untuk tenant selain milik klien ditampilkan sebagai **error halaman dan tidak pernah dialihkan** ke URI yang belum terverifikasi (RFC 6749 memperlakukan redirect tak valid demikian; bagian perlu verifikasi). Teks halaman identik untuk "klien tak ada", "klien nonaktif", dan "redirect salah". Hanya setelah klien dan redirect diterima, error boleh kembali ke redirect dengan `error` dan `state`.
- Permintaan disimpan di sisi server (baris berumur pendek, TTL 600 detik, gagasan sama dengan `AUTH_SSO_OAUTH_REQUEST_TTL_SEC`) dan browser hanya membawa id permintaan buram, sehingga putaran login, MFA, pendaftaran, dan SSO dapat melanjutkannya.
- Pengguna lalu mengautentikasi lewat alur yang **sudah ada**: `evaluateTenantEntry` diterapkan (`password_login_disabled`, penegakan SSO), lalu kata sandi dengan penghitung lockout global ([ADR-0086](0086-the-lockout-counter-is-global.id.md)) dan TOTP atau passkey ([ADR-0168](0168-passkeys-webauthn-are-a-principal-owned-phishing-resistant-factor-that-yields-aal2-with-self-implemented-attestation-none-verification.id.md)) sebagai faktor **kedua**, atau SSO ([ADR-0028](0028-oidc-sso-tenant-aware-account-linking-break-glass.id.md)).
- **Layar persetujuan dan identitas** selalu menampilkan: nama klien, tenant, akun, label perangkat dari aplikasi (disanitasi, tak pernah dipercaya), dan apa yang boleh dilakukan aplikasi. Ia formulir terlindung CSRF. Ia kontrol anti-phishing terhadap aplikasi bermusuhan yang membuka browser saat perhatian korban di tempat lain. Ia ditampilkan pada setiap otorisasi dan tak pernah diingat atau dilewati (H4, M8).
- **Semantik browser saat authorize (M8).** Tenant milik code **selalu tenant klien**; sesi browser yang ada di tenant lain tak pernah dipakai ulang atau dialihkan. Id permintaan tersimpan diikat ke cookie `__Host-` yang diset saat authorize dimulai, sehingga id permintaan yang ditanam penyerang (fiksasi) tak dapat dilanjutkan di browser lain. Alur ini tidak meninggalkan sesi web yang dapat dipakai ulang di luar yang sudah diterbitkan login yang ada, dan fakta itu didokumentasikan di runbook. Login tanpa kata sandi tidak ditawarkan di rilis pertama (ADR-0168 Q3): kata sandi disusul TOTP atau passkey sebagai faktor kedua, atau pengguna datang lewat SSO. **Tes merah wajib (S4):** id permintaan tanpa cookie yang cocok ditolak; sesi tenant lain tak dipakai ulang; keduanya gagal bila pengikatannya dihapus.
- **Authorization code hanya diterbitkan dari keadaan terautentikasi penuh dan tak terbatas.** Sesi enrolment-grant (keadaan di balik `MFA_ENROLLMENT_REQUIRED`) tak pernah menghasilkan code. Bila principal wajib mendaftarkan faktor (ADR-0141 dan gerbang pendaftaran), halaman mengarahkan pengguna melalui pendaftaran di browser, lalu melanjutkan permintaan tersimpan. `MFA_ENROLLMENT_REQUIRED` karenanya langkah sisi browser, tak pernah error token endpoint.
- **Authorization code** berupa 32 byte CSPRNG, base64url, disimpan sebagai hash di namespace sendiri, **sekali pakai, TTL 60 detik** (batas yang sama dengan kode handoff, dicerminkan di CHECK), terikat ke `client_id`, `redirect_uri`, `code_challenge`, `dpop_jkt`, tenant, principal, identitas, `assurance_level` yang dicapai, dan daftar metode autentikasi. Teks polosnya tak ditampilkan ke siapa pun selain redirect.
- Code membawa prefiks routing tak-rahasia (id tenant) agar token endpoint dapat masuk ke konteks tenant yang benar sebelum lookup apa pun, seperti token webhook kanal. Prefiks itu routing, bukan otoritas: baris yang ditemukan lewat hash di bawah tenant itulah otoritasnya.

### 3. Token endpoint

`POST /api/v1/auth/native/token`, `application/x-www-form-urlencoded`, grant type `authorization_code` dan `refresh_token`. Ia **endpoint tanpa sesi ber-body** dan karenanya wajib ditambahkan ke `SESSION_FREE_BODY_ENDPOINTS` dengan pola sempit dan diuji **lewat middleware** (pelajaran audit 3). Respons mengikuti RFC 6749 (`access_token`, `token_type: "DPoP"`, `expires_in`, `refresh_token`, dan JSON error RFC `{error, error_description?}`), yang merupakan **pengecualian terdokumentasi dari envelope respons AWCMS** (Q10): pustaka klien OAuth dan tumpukan Lynx mengharapkan bentuk RFC, dan dokumen OpenAPI harus menyatakannya pada operasi ini. Kode error: `invalid_request`, `invalid_grant`, `use_dpop_nonce`, `invalid_dpop_proof`, dan `unsupported_grant_type`. `invalid_client` **tidak** dipakai untuk klien tak dikenal atau salah (itu `invalid_grant`, agar kegagalan tetap tak terbedakan) karena klien publik tak punya autentikasi klien yang dapat gagal. `slow_down` **tidak** dipakai: ia milik device authorization grant (RFC 8628), bukan alur ini. `error_description` berasal dari tabel string statis, tak pernah dari data permintaan. Bukti yang gagal verifikasi adalah `invalid_dpop_proof`, dijawab sebelum lookup database apa pun, dan **tak pernah** memicu pencabutan: hanya bukti **valid** oleh kunci berbeda yang dihitung sebagai bukti reuse (L2). Token endpoint secara eksplisit **dikecualikan dari `Idempotency-Key`**: code sekali pakai dan jendela retry terbatas adalah mekanisme idempotensinya (L6). `/native/revoke` juga masuk `SESSION_FREE_BODY_ENDPOINTS`, dan `lib/auth/api-body-authentication.ts`, yang kini hanya mengurai `Bearer`, mendapat skema DPoP di S6 agar operasi native terautentikasi tidak ditolak sebelum handler (L6). `Cache-Control: no-store` pada setiap respons.

**Grant authorization_code.** Verifikasi, dalam satu transaksi di bawah tenant yang di-route: bukti DPoP (bagian 6), code lewat hash, `consumed_at IS NULL` dan belum kedaluwarsa, `client_id` dan `redirect_uri` identik dengan nilai tersimpan, `S256(code_verifier)` sama dengan challenge tersimpan (waktu-konstan), dan thumbprint kunci bukti sama dengan `dpop_jkt` tersimpan. Konsumsi dengan satu `UPDATE ... WHERE consumed_at IS NULL RETURNING` terjaga. Saat penebusan, periksa ulang bahwa principal aktif dan tenant boleh dimasuki (allow-list suspensi, `evaluateTenantEntry`) karena kebijakan mungkin berubah dalam 60 detik. Setiap kegagalan mengembalikan `invalid_grant` yang sama. **Menyajikan code yang sudah dikonsumsi mencabut family token yang dihasilkan code itu** (RFC 6749 merekomendasikan ini; bagian perlu verifikasi) dan diaudit, **tetapi hanya bila penyaji membuktikan verifier PKCE code dan kunci terikatnya** (L7): pemutaran ulang code yang dicegat tanpa itu mendapat `invalid_grant` tanpa pencabutan, sehingga pencegat tak dapat mematikan family yang sah. **Tes merah wajib (S5):** pemutaran ulang code terkonsumsi tanpa verifier valid membiarkan family hidup; dengan verifier dan kunci valid ia mencabut; keduanya gagal bila syaratnya dibuang.

**Grant refresh_token.** Bagian 5.

### 4. Bentuk token: buram, bukan JWT

| Token              | Bentuk                                                                                                     | Umur                                                                             | Disimpan                                                                                                               |
| ------------------ | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Access             | buram, 32 byte CSPRNG, base64url, prefiks penanda terlihat `awn_`, terikat DPoP                            | **60 menit** bawaan (Q3), `AUTH_NATIVE_ACCESS_TTL_SEC`, dibatasi 300 sampai 3600 | **sebagai baris `awcms_sessions`** (hanya hash), `origin_auth = 'native'`                                              |
| Refresh            | buram, 32 byte CSPRNG, base64url, prefiks penanda `awr_`, prefiks routing tenant tak-rahasia, terikat DPoP | idle 30 hari, absolut 90 hari sejak grant, keduanya dapat dikonfigurasi          | hanya hash, namespace hash sendiri, disimpan di baris family (`current_hash`, `previous_hash`) dengan indeks unik (M3) |
| Authorization code | buram, seperti bagian 2                                                                                    | 60 detik                                                                         | hanya hash, namespace sendiri                                                                                          |

**Mengapa buram dan bukan access token JWT (gaya RFC 9068).**

- **Pencabutan seketika dan memakai mesin yang sudah ada.** Deaktivasi, reset kata sandi (`sql/073`), suspensi tenant, dan pencabutan family baru semuanya bekerja dengan mengubah baris. JWT tetap sah sampai `exp` kecuali tiap permintaan resource juga membaca denylist, yang tetap pembacaan database dan sistem kedua yang harus dijaga benar.
- **Jalur panas tidak berubah.** Access token native adalah baris `awcms_sessions` yang dicari lewat hash melalui pembacaan berindeks yang sama dengan sesi lain. Setiap kontrol hilir bekerja tanpa diubah: konteks tenant, RLS, `authorizeInTransaction` (ADR-0063), `assurance_level`, `requireStepUp`, ABAC. Verifier JWT akan menjadi jalur autentikasi kedua untuk di-fuzz, dengan bahaya algorithm-confusion dan rotasi kunci yang tidak dimiliki repo ini sekarang.
- **Tanpa klaim basi.** Izin dievaluasi per permintaan dari database ([ADR-0063](0063-ownership-grants-run-through-the-authorization-chokepoint.id.md)); klaim di dalam token akan menjadi salinan basi dari bagian yang penting.
- **Pemindaian secret.** Penanda (`awn_`, `awr_`) membuat kebocoran tak sengaja dapat di-grep dan memungkinkan pemeriksaan prefiks murah untuk memilih resolver, tanpa melemahkan hash tersimpan.
- Biayanya: satu pembacaan database per permintaan, yang memang sudah dibayar setiap sesi. Kami tidak menambah tulis per permintaan (tanpa `last_seen_at`, sesuai disiplin `sql/100`).

**Mengapa hash dan hash yang mana.** Token adalah nilai CSPRNG 256 bit, sehingga hash cepat (SHA-256) benar (tanpa KDF ala kata sandi), dan tiap jenis secret punya namespace sendiri dengan CHECK pada bentuk tersimpan, seperti `ho-sha256:`, `bff-sha256:`, `mc-sha256:`. Access token native disimpan di `awcms_sessions` dalam bentuk apa pun yang sudah dituntut CHECK tabel itu; keputusan namespace untuk kolom baru diambil di S2 dengan tes bahwa hash refresh tak pernah cocok sebagai hash sesi (perlu verifikasi terhadap CHECK yang ada sebelum S2). Perbandingan hash waktu-konstan (`hashesEqual`). Token polos tak pernah dilog, diaudit, ditaruh di URL, atau disimpan setelah respons; daftar redaksi bertambah `access_token`, `refresh_token`, `code`, `code_verifier`, nilai `DPoP`, `Authorization`.

**Trade-off TTL access token.** Pencabutan tidak bergantung pada TTL pendek (baris buram). TTL hanya menentukan seberapa sering perangkat harus me-refresh, dan refresh adalah jalur tulis tersibuk yang ditambahkan ADR ini. Bawaan ini bukan angka turunan; pemilik memutuskan **60 menit** (Q3) karena pencabutan berbasis baris dan kontrol per-permintaan tetap berjalan, sedangkan 15 menit hanya melipatempatkan tulis dan churn `awcms_sessions`. Benchmark S2 masih boleh menyetelnya dalam rentang 300 sampai 3600 detik.

### 5. Rotasi refresh, family token, deteksi reuse, race

**Model.** Setiap penebusan code yang berhasil membuat **family** (`awcms_native_token_families`: tenant, principal, identitas, klien, `dpop_jkt`, **`credential_epoch` principal saat grant** (H1), `assurance_level`, metode autentikasi, `stepped_up_at` beserta metodenya saat grant, label perangkat, ringkasan user-agent kasar, hash IP berkunci, `generation`, **`current_hash`, `previous_hash`, `previous_consumed_at`** (M3), `created_at`, `idle_expires_at`, `absolute_expires_at`, `revoked_at`, `revoke_reason`). **Tidak ada tabel token per generasi** (M3): baris family menyimpan hash refresh token saat ini dan yang digantikannya, masing-masing dengan indeks unik, dan itu cukup untuk deteksi reuse; token yang cocok dengan keduanya tidak ada adalah tak dikenal. Sesi access yang diterbitkan family merujuknya (`awcms_sessions.native_family_id`, FK nullable, berindeks). **Family adalah sesi perangkat**: daftar, pencabutan, dan audit per family.

**Rotasi (M2).** Refresh token membawa prefiks routing tenant tak-rahasia. Urutan lookup: resolusi hash token di bawah tenant itu ke id family (indeks unik pada `current_hash` dan `previous_hash`), lalu `SELECT ... FROM awcms_native_token_families WHERE id = $family FOR UPDATE`, lalu **baca ulang keadaan token dan family di bawah kunci**, dalam READ COMMITTED (snapshot REPEATABLE READ akan membaca keadaan basi). Itu menyerialkan dua refresh bersamaan pada satu family dan menghapus ketergantungan pada jam; setiap perbandingan waktu-berlalu memakai `clock_timestamp()` setelah kunci dipegang, tak pernah `now()`. Lalu:

1. Resolusi token lewat hash. Tak dikenal, kedaluwarsa, family dicabut, melewati idle atau absolut, **`client_id` yang berbeda dari milik family, atau pengikatan klien yang tidak `active` (H3)**: `invalid_grant` (isi sama untuk semuanya; tanpa oracle).
2. Bukti DPoP harus terverifikasi dan thumbprint kuncinya harus sama dengan `dpop_jkt` family. **Refresh token yang disajikan dengan bukti kunci lain tak pernah dihormati**, dan itu sendiri bukti reuse (di bawah).
3. Bila token cocok dengan `current_hash`: pindahkan `current_hash` ke `previous_hash` (mengisi `previous_consumed_at`), simpan `current_hash` baru, naikkan `generation`, sisipkan sesi access baru (INSERT, bukan update di tempat pada sesi lama; access token lama cukup kedaluwarsa dalam TTL-nya, menghindari kontensi pada baris panas dan menghindari kegagalan permintaan yang sedang berjalan) **dicap `credential_epoch` family, tak pernah yang terkini (H1)**, majukan `idle_expires_at`, kembalikan pasangan baru.
4. Evaluasi ulang pada setiap rotasi: principal aktif, identitas aktif, tenant boleh dimasuki, family tidak dicabut, dan **`credential_epoch` principal saat ini tidak lebih besar daripada milik family**; bila tidak, `invalid_grant` dan family dicabut dengan `revoke_reason = 'credential_changed'` (H1). `assurance_level` **dibawa dari grant dan hanya dapat tetap atau turun, tak pernah naik**; `stepped_up_at` beserta metodenya (ADR-0168 A2) **dibawa tanpa diubah**, tak pernah disegarkan, sehingga `requireStepUp` tetap menghormati jendela kesegaran yang sama seperti di web dan gagal setelah jendela itu lewat (L3).
5. Perubahan kebijakan yang melarang kredensial lokal atau menangguhkan tenant membuat refresh berikutnya gagal seragam. Apakah ia juga mencabut family: bawaan aman adalah mencabut untuk deaktivasi dan peristiwa perubahan kredensial (bagian 9), dan menolak tanpa mencabut untuk suspensi sementara.

**Deteksi reuse.** Token yang sudah dikonsumsi lalu disajikan lagi bukan error biasa:

- **Bukti valid oleh kunci berbeda** (bukti yang gagal verifikasi adalah `invalid_dpop_proof` dan tak pernah mencabut, L2): family **dicabut** (`revoke_reason = 'reuse_detected'`), semua sesi access family yang belum kedaluwarsa dicabut dalam transaksi yang sama, baris audit `high` ditulis, dan pemanggil mendapat `invalid_grant` yang sama dengan kegagalan lain. Perangkat sah mengetahuinya pada refresh berikutnya dan pengguna diarahkan masuk lagi.
- **Kunci DPoP sama, token yang disajikan adalah `previous_hash` family, token saat ini belum dipakai, dan waktu sejak `previous_consumed_at` berada dalam jendela retry G:** ini **retry respons hilang** (ponsel tak ada sinyal saat respons tiba), bukan serangan. Diterima **sekali**: family berotasi lagi (token saat ini yang belum dipakai digantikan, diaudit sebagai `retry_superseded`), token saat ini yang baru dan sesi access baru diterbitkan. G bawaan **30 detik** (Q3), dibatasi 60 (`AUTH_NATIVE_REFRESH_RETRY_WINDOW_SEC`), diukur dengan jam **database**.
- **Kunci sama, di luar G, atau token saat ini sudah dipakai:** family dicabut seperti di atas. Token yang tidak cocok dengan `current_hash` maupun `previous_hash` adalah tak dikenal (`invalid_grant`; tak ada family yang dapat diidentifikasi, jadi tak ada yang dicabut).

**Mengapa retry terbatas, bukan tanpa retry.** Rotasi tanpa jalur retry membuat setiap paket hilang menjadi login paksa di jaringan seluler, dan akibat pertamanya penulis aplikasi memperpanjang umur refresh atau berhenti merotasi. Retry aman di sini karena token **dibatasi pengirim**: hanya pemegang kunci instalasi non-exportable yang dapat memakainya, dan RFC 9700 menerima rotasi **atau** sender-constraining untuk refresh token klien publik; desain ini punya keduanya dan memakai retry hanya di bawah batasan itu. Pencuri dengan token tanpa kunci jatuh ke cabang "kunci berbeda" dan mematikan family. Pencuri **dengan** kunci memegang perangkatnya, dan tak ada protokol token yang mengalahkan itu.

**Mengapa tidak mengembalikan respons yang sama lagi.** Itu menuntut penyimpanan penerus polos atau salinan terenkripsinya. Hash saja, selalu.

**Konkurensi lintas instance.** Kunci baris family menyerialkan per family dan satu-satunya koordinasi: tanpa dependensi keras baru (Redis sudah menjadi dependensi opsional rate limiting, ADR-0066, dan tidak diperlukan di sini), tanpa kunci terdistribusi, tanpa advisory lock berkunci masukan pengguna. "Yang lebih awal menang" diputuskan oleh `generation` di bawah kunci, bukan `now()` (pelajaran audit 4; dan `now()` adalah awal transaksi). **Setiap jalur pencabutan (pengguna, admin, kaskade, penonaktifan klien) memperbarui baris family lebih dulu dan baru kemudian mencabut sesi family**, sehingga pencabutan tak dapat kalah balapan dengan refresh yang sedang menyisipkan sesi baru. Catatan untuk konsumen: aplikasi harus menjalankan refresh single-flight. **Tes merah wajib (S5):** dua refresh bersamaan pada satu family menghasilkan tepat satu generasi baru dan tanpa pencabutan; pencabutan yang berbalapan dengan refresh tak menyisakan sesi hidup family yang dicabut; keduanya gagal bila kunci atau urutannya dihapus.

**Batas.** Paling banyak 10 family aktif per principal per klien (yang tertua digusur dan diaudit), dan satu family aktif per (principal, klien, `dpop_jkt`): login ulang dari instalasi yang sama mempensiunkan family sebelumnya. Kedaluwarsa idle dan absolut ditegakkan saat refresh dengan membandingkan jam database, dan baris kedaluwarsa dipurge oleh deskriptor data-lifecycle di migrasi yang sama. **`awcms_sessions` hari ini tidak punya deskriptor purge kedaluwarsa (hanya subject data), dan satu sesi access native per perangkat per TTL access menumpuk di tabel terpanas: deskriptor purge kedaluwarsa `awcms_sessions` berkadens di bawah satu hari dikirim sebelum flag dapat diaktifkan (M3)**, dan benchmark S2 mencatat baris per hari dan ukuran indeks.

### 6. DPoP: pengikatan perangkat dengan kunci per-instalasi non-exportable

Pengikatan **tidak** memakai passkey (butir Low ADR-0168): `backedUp` dan `backupEligible` tak terbukti tanpa attestation, dan passkey adalah kredensial pengguna, bukan identitas instalasi. Aplikasi membuat **pasangan kunci ES256 (P-256) di keystore platform** saat pertama jalan (Android Keystore, StrongBox bila ada; iOS Keychain/Secure Enclave), ditandai **non-exportable**, dan membuktikan kepemilikannya dengan **bukti DPoP** (RFC 9449) pada setiap permintaan tempat token dipakai.

- **Algoritma.** Hanya `ES256` (didukung keystore perangkat keras; `none` dan algoritma simetris ditolak seperti dituntut RFC 9449). Verifier adalah kode murni di WebCrypto, dengan disiplin sama seperti ADR-0168 A6: base64url ketat, `typ = dpop+jwt`, tepat satu `jwk` publik tertanam tanpa anggota privat, batas JSON kompak, dan verifikasi tanda tangan lewat platform dengan penanganan R dan S kanonik. Dicakup contoh RFC 9449, vektor Wycheproof ECDSA, dan **matriks merah** (tiap pemeriksaan punya tes yang gagal saat pemeriksaannya dihapus).
- **Klaim diperiksa.** `htm` dan `htu` (dibandingkan **tanpa query dan fragment**) terhadap metode dan URL permintaan kanonik sebenarnya (skema dan host dari konfigurasi, **bukan** dari header `Host`: ia dapat dipengaruhi penyerang), `iat` dalam batas selisih yang dinyatakan (60 detik diusulkan, disetel di S2), `jti` ada dan unik, `nonce` sama dengan nonce server yang berlaku, dan pada permintaan resource `ath` sama dengan SHA-256 base64url dari access token.
- **Pengikatan.** Thumbprint (`jkt`) disimpan di family dan disalin ke setiap sesi access (`awcms_sessions.dpop_jkt`). Authorization code diikat ke sana lewat parameter otorisasi `dpop_jkt` (sehingga code yang dicegat tak berguna bagi kunci lain bahkan sebelum PKCE).
- **Downgrade mustahil, dan dijangkarkan di SQL (H2).** Sesi dengan `dpop_jkt` terisi diterima **hanya** dengan `Authorization: DPoP <token>` dan bukti valid; `Authorization: Bearer` dengan token terikat adalah `401` dengan tantangan `WWW-Authenticate: DPoP`. Predikat pengikatan adalah **satu fragmen SQL yang dipancarkan sekali**, seperti `sessionCredentialCurrent`: `AND s.dpop_jkt IS NOT DISTINCT FROM ${verifiedJktOrNull}`. **Setiap pembaca sesi hidup menerima argumen pengikatan wajib**, dan gerbang baru `scripts/session-readers-check.ts` menggagalkan build untuk pembaca yang tak menyematkan fragmen itu (`resolveActiveSession` hari ini dipanggil langsung dari sedikitnya delapan tempat: `auth/me.ts`, `auth/logout.ts`, `auth/profile.ts`, `auth/preferences.ts`, `auth/mfa/status.ts`, `comments/author-resolution.ts`, `lib/auth/api-body-authentication.ts`, `mfa.ts`; dan `resolveAuthInputs` menerima Bearer **atau** cookie). Token dari cookie atau `Bearer` selalu mengikat `NULL`. **Fragmen dan gerbang mendarat di S2, di slice yang sama dengan kolom `dpop_jkt` dan sebelum slice mana pun yang dapat menyisipkan baris terikat.** Rotasi step-up sesi native **membawa** `native_family_id` dan `dpop_jkt` ke depan, seperti `origin_auth`. **Tes merah wajib (S2):** token terikat yang dikirim sebagai Bearer dan sebagai cookie ke setiap pembaca dijawab 401; tes gagal bila fragmen dihapus dari salah satu pembaca.
- **Nonce server, tanpa menyimpannya.** Nonce tanpa state: `HMAC(kunci server, slot waktu)`, slot saat ini dan sebelumnya diterima (slot 5 menit, jadi nonce hidup 5 sampai 10 menit). Kunci server adalah secret baru `AUTH_NATIVE_DPOP_NONCE_SECRET` (sedikitnya 32 byte, fail closed saat start bila native aktif dan ia hilang atau bawaan, rotasi dua kunci: `..._PREVIOUS`). Nonce hilang atau basi dijawab `use_dpop_nonce` plus header `DPoP-Nonce` **sebelum** lookup database apa pun, sehingga tak pernah menjadi oracle. `DPoP-Nonce` segar juga dikirim proaktif pada respons sukses agar aplikasi jarang membayar satu round trip untuk `use_dpop_nonce`. Nonce membatasi jendela replay bukti yang tertangkap sebesar umur nonce, sebab itu penyimpan replay hanya perlu mengingat `jti` sekitar dua slot.
- **Replay `jti`: berjenjang, agar biaya terbatas.**
  - **Token endpoint, step-up native, revoke, dan operasi native-allowed yang mendeklarasikan `x-native-high-risk`:** `jti` dicatat di database dalam tabel berumur pendek `awcms_native_dpop_jti` (**LOGGED**, M7; kunci `H(jkt || jti)`, tak pernah hash tanda tangan karena tanda tangan ECDSA dapat dimodifikasi (malleable); `expires_at`), `INSERT ... ON CONFLICT DO NOTHING RETURNING`, TTL sama dengan dua slot nonce, disapu dengan delete rentang pada `expires_at`. Sebagai gambaran skala (bukan hasil ukur), 100 000 perangkat aktif pada TTL access 15 menit (kasus pesimistis; pada 60 menit yang diputuskan sekitar seperempatnya) sekitar 110 insert refresh per detik rata-rata, **ditambah** tulis `jti` operasi `x-native-high-risk`, dan tabel hanya memuat sepuluh menit terakhir. **Tidak ada layanan baru**: Postgres cukup pada laju itu. **LOGGED karena** mitigasi yang semula tertulis di sini ("tolak bukti yang `iat`-nya mendahului awal proses") keliru: aplikasi tidak restart saat database crash, waktu start postmaster tidak berubah pada crash reinit, dan tabel UNLOGGED dikosongkan oleh crash recovery serta tidak ada di standby yang dipromosikan. Kasus terburuk replay ke tabel yang dikosongkan adalah denial of service (code yang diputar ulang atau token yang digantikan mencabut family; bukti curian tak dapat dipakai tanpa kunci karena `ath` dan sender constraint), dan WAL sekitar 110 baris per detik dapat diabaikan. Q12 mencatat keputusannya untuk pemilik. **Tes merah wajib (S2):** insert kedua `H(jkt || jti)` yang sama ditolak; tabel bukan UNLOGGED (dipin di `security:readiness`); keduanya gagal bila kunci atau logging diubah.
  - **Permintaan resource biasa (setiap panggilan API):** baris `jti` per permintaan berarti tulis per permintaan, yang repo ini tolak berdasar prinsip. Mereka dilindungi `ath` (bukti terikat ke token ini), `htm`/`htu` (ke operasi ini), jendela nonce (ke beberapa menit), dan **LRU dalam-proses** terbatas untuk nilai `jti` terbaru (per instance, TTL pendek) sebagai penyaring upaya terbaik. Replay lintas instance atas bukti identik dalam jendela nonce butuh permintaan terlindung TLS yang tertangkap, dan hanya dapat mengulang metode dan URL yang sama; mutasi high-risk non-idempoten sudah dicakup `Idempotency-Key` (aturan `awcms-idempotency`).
- **Biaya verifikasi.** Satu verifikasi ES256 per permintaan, diukur di S2 mengikuti praktik anggaran query (target ditetapkan dari benchmark, bukan diklaim di sini). Objek kunci publik yang diimpor ditahan di **LRU terbatas berkunci thumbprint kanonik**, terisi **hanya setelah** lookup sesi berhasil dan thumbprint cocok dengan milik sesi (cache tak boleh terisi dari masukan tak terautentikasi, pelajaran audit 6).
- **Yang tidak dilakukan.** Tanpa attestation platform (Play Integrity, App Attest) AWCMS tak dapat membuktikan kunci berada di perangkat keras atau klien adalah aplikasi asli; aplikasi yang dimodifikasi dapat membuat kunci perangkat lunak. Kontrol yang penting di sini adalah token yang **disalin keluar** dari perangkat (backup, log, proksi, malware tanpa akses keystore) tak dapat diputar ulang dari perangkat lain. Attestation adalah keputusan terpisah di kemudian hari (Q7).

### 7. Sesi native default-deny pada operasi yang menerimanya

[ADR-0146](0146-persona-apps-prefer-lynx-in-consumer-repos-astro-keeps-admin-and-public-web.id.md): aplikasi persona hanya memakai operasi kontrak publik dan tak pernah permukaan admin secara implisit. Sesi native karenanya diterima **hanya** oleh operasi yang ikut serta: skema keamanan OpenAPI `nativeDpop` dan ekstensi `x-native-client: true` per operasi, dicerminkan allow-list kode (`NATIVE_ALLOWED_OPERATIONS`) yang dikonsultasi middleware **sebelum** handler, dengan gerbang yang gagal bila keduanya tak sepakat (pola dua sisi yang sama dengan registri lain). Tidak diizinkan, apa pun izin principal: halaman dan API `/admin/*`, aktivitas platform-scoped, manajemen kredensial dan MFA (ganti kata sandi, pendaftaran dan reset faktor), pergantian tenant, introspeksi sesi ADR-0049 (hanya bearer, dan introspeksi bearer atas token terikat ditolak), manajemen API-key dan kredensial mesin, serta registri klien native itu sendiri. ABAC dan RBAC dievaluasi persis seperti sesi manusia pada operasi yang diizinkan; allow-list mempersempit, tak pernah melebarkan.

**Plafon izin** per klien (klien paling banyak memakai himpunan permission bernama) adalah kebutuhan nyata untuk aplikasi kurir, tetapi mengubah invarian chokepoint otorisasi ADR-0063 dan tidak diputuskan di sini (Q6). Sampai ada, allow-list operasi adalah satu-satunya penyempit.
**Siapa boleh memegang family native (M5).** Tidak ada authorization code yang diterbitkan untuk identitas terdelegasi (ADR-0090, `sql/117`; nama kolom persisnya diverifikasi di S4) atau di tenant platform, sehingga identitas terdelegasi tak dapat memperoleh family 90 hari yang melampaui grant-nya, dan owner atau pemegang permission platform tidak membawa seluruh izinnya ke aplikasi kurir. Kedaluwarsa absolut family adalah `min(terkonfigurasi, kedaluwarsa grant mana pun)`. `origin_auth = 'native'` dan `native_client_id` diekspos sebagai atribut ABAC agar tenant dapat menulis kebijakan **deny** (hanya deny; invarian ADR-0063 tak berubah). **Tes merah wajib (S4 untuk penolakan penerbitan, S5 untuk kedaluwarsa, S6 untuk atribut):** principal terdelegasi atau tenant platform tak mendapat code; family tak pernah melampaui grant-nya; kebijakan deny pada `origin_auth = 'native'` berlaku; masing-masing gagal bila kontrolnya dihapus.

### 8. MFA, step-up, AAL, dan passkey ADR-0168

- **AAL awal** adalah hasil autentikasi browser: `aal1` untuk kata sandi saja, `aal2` setelah TOTP atau passkey; family dan sesi access pertama mencatatnya. `origin_auth` untuk sesi native adalah `native`, dengan faktor pertama disimpan di daftar metode family (CHECK `origin_auth` sudah berisi lima nilai setelah `sql/117`, yang menambah akses terdelegasi untuk ADR-0090, dan bertambah `native` di S2).
- **ADR-0088 dan `MFA_ENROLLMENT_REQUIRED`.** Masuk tenant, kewajiban pendaftaran, dan saklar kebijakan dievaluasi saat authorize **dan lagi pada setiap refresh**. Pendaftaran dilakukan di browser, bukan lewat token endpoint (bagian 2). Pergantian tenant **tidak tersedia** untuk sesi native (klien terdaftar untuk satu tenant; pengguna masuk lagi untuk tenant lain); `session/switch` menolak sesi native.
- **Step-up** untuk operasi yang dijaga `requireStepUp` memakai endpoint step-up yang sudah ada, dideklarasikan native-allowed, yang sudah merotasi token sesi; untuk sesi native rotasi itu **mempertahankan family dan pengikatan DPoP**, dan `stepped_up_at` diset seperti di web. Setelah refresh `stepped_up_at` dibawa tanpa diubah (bagian 5), sehingga jendela kesegaran web berlaku dan aplikasi meminta lagi setelah jendela itu lewat. Step-up passkey dari aplikasi native dimungkinkan bila `android:apk-key-hash` atau pengenal iOS klien terdaftar (bagian 1) dan bergantung pada ADR-0168 S3 dan seterusnya; tindak lanjut `requireStepUp(..., { method: "phishing_resistant" })` yang disebut ADR-0168 A2 berlaku juga bagi sesi native.
- **Sesi native tak pernah menaikkan AAL-nya sendiri dengan refresh**, dan penurunan AAL saat faktor dihapus ditangani lewat credential epoch (bagian 5 dan 9, H1), bukan dengan mencabut baris lintas tenant, yang dibuat mustahil oleh FORCE RLS.

### 9. Logout, pencabutan, audit

- **Logout dan revoke:** `POST /api/v1/auth/native/revoke` (bentuk RFC 7009) dengan refresh token (atau access token plus bukti). Selalu mengembalikan `200` berbody kosong untuk token tak dikenal, kedaluwarsa, atau sudah dicabut, sehingga bukan oracle. Ia mencabut family dan sesi access yang belum kedaluwarsa dalam satu transaksi.
- **Daftar perangkat dan pencabutan perangkat:** pengguna dapat melihat family miliknya (label perangkat, klien, dibuat, terakhir dirotasi, UA kasar dan petunjuk IP termasker) dan mencabut salah satunya dari layar akun di bawah `/admin/account` dan dari API (baca native-allowed atas family milik pemanggil sendiri). Admin tenant dengan permission ber-scope tenant (`identity_access.native_session.revoke`, maker/checker tidak wajib tetapi diaudit) dapat mencabut family principal di tenant itu. Keduanya lewat `authorizeInTransaction`; "bukan milikmu" dan "tidak ada" tak dapat dibedakan.
- **Kaskade (H1).** Peristiwa tingkat principal (reset atau ganti kata sandi, reset MFA, penghapusan faktor, pencabutan atau reset passkey, deaktivasi principal) bekerja lewat **`credential_epoch`**, karena pencabutan baris lintas-tenant mustahil di bawah FORCE RLS (`sql/144`): penghapusan dan reset faktor menaikkan `credential_epoch` (atau `assurance_epoch` khusus yang diperiksa dengan cara sama), yang hari ini tidak mereka lakukan, dan refresh ditolak bila epoch principal melebihi milik family (bagian 5). Hanya peristiwa **satu-tenant** (deaktivasi identitas, penghapusan tenant, pencabutan admin) mencabut baris family langsung, dalam transaksi yang kini mencabut sesi. **Tes merah wajib (S5 untuk pemeriksaan refresh, S7 untuk tiap peristiwa):** reset kata sandi di tenant A membuat refresh family di tenant B gagal dengan `invalid_grant` dan mencabutnya dengan alasan `credential_changed`; satu tes per jenis peristiwa; tes gagal bila perbandingan epoch dihapus. Cek readiness membuktikan tak ada jalur yang mencabut sesi tanpa juga bertindak atas family atau epoch.
- **Klien dinonaktifkan atau terkompromi (H3).** Permintaan refresh membawa `client_id`; ia harus sama dengan milik family dan pengikatan harus `active`, bila tidak `invalid_grant`. Menonaktifkan pengikatan klien mencabut, **dalam transaksi yang sama, setiap family klien itu dan sesi access mereka yang belum kedaluwarsa** (`revoke_reason = 'client_disabled'`, diaudit `high`), baris family lebih dulu (M2). Mencabut entri berkas asosiasi tidak seketika (Google dan Apple meng-cache berkas), sehingga kaskade penonaktifan, bukan berkasnya, adalah kontrolnya. Runbook "cabut klien terkompromi" persis transaksi ini ditambah penghapusan aplikasi dari `awcms_native_apps` di sisi platform. S3 hanya membalik status (tak ada family sebelum S5); kaskade, pemeriksaan refresh, dan **tes merahnya mendarat di S5 dan flag tak dapat diaktifkan tanpanya**. **Tes merah wajib (S5):** nonaktifkan klien, lalu refresh-nya ditolak dan sesi access-nya mati; gagal bila kaskade atau pemeriksaan `client_id` dihapus.
- **Audit (dengan redaksi).** Diaudit: klien didaftarkan, diubah, dinonaktifkan (high); otorisasi diberikan (info); family dibuat (info); **reuse terdeteksi** (high); family dicabut oleh pengguna, admin, atau kaskade satu-tenant (medium); family dicabut karena `credential_changed` (high); klien dinonaktifkan (high); otorisasi ditolak setelah autentikasi (medium); supersesi jendela retry (low); perubahan origin passkey native (high). **Rotasi rutin tidak diaudit** (satu baris per perangkat per TTL access akan menjadi tabel paling bising di sistem); ia penghitung metrik. Tak ada token, code, verifier, bukti, atau IP penuh yang pernah ditulis. Hash IP berkunci tidak boleh bergantung pada kunci per-proses (pelajaran `hashClientIp`: nilai tersimpan harus tetap dapat dibandingkan).
- **Halaman callback cadangan (L8).** Halaman yang disajikan di `/native/callback/*` bila app link tidak membuka aplikasi tak pernah memantulkan `code` atau `state`, mengirim `Referrer-Policy: no-referrer` dan `Cache-Control: no-store`, tanpa analytics, melewati Varnish tanpa cache, dan query string disunting dari log proksi. **Tes merah wajib (S4):** badan respons tak pernah memuat code; gagal bila header atau pantulannya diubah.

### 10. Rate limit dan anti-enumerasi

- **Batas pra-verifikasi berkunci hanya pada apa yang diberikan jaringan** (alamat sumber tepercaya), tak pernah nilai pilihan penyerang: per IP sumber pada `/native/authorize`, token endpoint, dan revoke (M4). `client_id` dan prefiks routing tenant bersifat publik, sehingga **tak ada yang dapat dikirim pemanggil tak terautentikasi untuk menghabiskan bucket yang dibagi pengguna lain**: penghitung per-klien dan per-family hanya menghitung permintaan yang token atau code-nya **ditemukan**, dan mereka memperlambat tanpa mengunci. Melebihi batas dijawab `429` dengan `Retry-After`. Batas per-IP harus longgar, karena operator seluler Indonesia menaruh banyak pengguna sah di balik satu alamat CGNAT (L10). **Tes merah wajib (S5):** banjir token tak dikenal untuk `client_id` publik tidak memperlambat atau mengunci pengguna sah klien itu; gagal bila bucket pra-verifikasi per-klien ditambahkan.
- **Penolakan seragam.** `invalid_grant` adalah satu-satunya jawaban untuk tak dikenal, kedaluwarsa, terkonsumsi, dicabut, klien salah, redirect salah, verifier salah, kunci salah, dan principal tak aktif; isi respons seragam, yang penting untuk token acak 256 bit (kerja identik tidak diklaim); `use_dpop_nonce` diterbitkan sebelum lookup apa pun. Memutar ulang `Idempotency-Key` pada mutasi native-allowed tak boleh membuka apakah resource ada (pelajaran audit 14).
- **Tanpa enumerasi klien.** Teks error halaman otorisasi identik untuk setiap kegagalan klien; nilai `client_id` acak, bukan berurutan.
- **Lockout:** percobaan verifier dan refresh yang salah dihitung terhadap pembatas per-family yang hanya **memperlambat** (M4), tak pernah terhadap penghitung lockout kata sandi global principal (ADR-0086) dan tak pernah terhadap lockout per-`client_id`, sehingga penyerang yang memegang `client_id` publik tak dapat mengunci pengguna atau seluruh klien.

### 11. Kompatibilitas dengan bearer 120 menit

Tidak ada yang sudah ada berubah. `AUTH_SESSION_TTL_MIN=120` tetap mengatur sesi login kata sandi dan handoff; umur native punya variabel sendiri. Handoff BFF web ([ADR-0050](0050-bff-session-handoff-code.id.md)) dan introspeksi ([ADR-0049](0049-machine-credentials-and-session-introspection.id.md)) tak berubah; introspeksi menolak sesi terikat native. `awcms-astro` dan kontrak konsumen beku ([ADR-0065](0065-awcms-astro-consumer-contract-is-frozen.id.md)) tak tersentuh: endpoint native bersifat **aditif**. Kolom baru `awcms_sessions` nullable (`native_family_id`, `dpop_jkt`) dan CHECK `origin_auth` bertambah satu nilai; tak perlu backfill.

## Alternatif yang ditolak

- **Access token JWT (gaya RFC 9068).** Ditolak karena alasan di bagian 4: pencabutan, jalur autentikasi kedua, klaim basi.
- **Password grant (ROPC) atau aplikasi memanggil `/login`.** Ditolak: menaruh kredensial dan ceremony MFA, passkey, SSO di kode aplikasi, dan telah dihapus dari arah OAuth 2.1 serta RFC 9700.
- **Login WebView tertanam.** Ditolak: aplikasi melihat kredensial, dan mengalahkan SSO dan passkey (RFC 8252 mengarahkan permintaan otorisasi aplikasi native ke external user-agent karena alasan ini; kekuatan normatif persisnya perlu diverifikasi).
- **Redirect custom URL scheme.** Ditolak: aplikasi mana pun dapat mendaftarkan skema itu (tanpa verifikasi kepemilikan). App link diverifikasi terhadap host.
- **Redirect loopback.** Tidak diadmisi untuk seluler (RFC 8252 menggambarkan loopback terutama untuk aplikasi desktop, dan link https yang diklaim untuk seluler); desktop pertanyaan berikutnya.
- **Implicit flow, atau PKCE `plain`.** Ditolak di sini; RFC 9700 menjauhkan dari implicit flow dan mengutamakan PKCE S256 (kekuatan normatif persisnya perlu diverifikasi).
- **Refresh token bearer tanpa DPoP, hanya rotasi.** Ditolak: bisa jalan tetapi mengubah setiap paket hilang menjadi login paksa atau memaksa retry tak aman, dan token curian dapat dipakai penuh. Sender constraint membuat retry terbatas aman.
- **DPoP opsional per klien.** Ditolak: pengikatan opsional adalah downgrade yang dipilih penyerang. Ia wajib untuk setiap klien native.
- **Pengikatan perangkat lewat passkey.** Ditolak K16: BE/BS tak terbukti tanpa attestation, passkey kredensial pengguna.
- **Redis atau cache lain untuk `jti`.** Ditolak: dependensi keras baru untuk kira-kira satu insert per perangkat per refresh; tabel Postgres LOGGED cukup (Redis tetap dependensi opsional rate limiting saja, ADR-0066).
- **Tabel refresh token per generasi.** Ditolak (M3): ratusan juta baris pada 100 000 perangkat bila baris terkonsumsi disimpan sampai family kedaluwarsa; baris family menyimpan `current_hash` dan `previous_hash`, dan itu cukup untuk deteksi reuse.
- **Satu tabel klien ber-scope tenant.** Ditolak (M1): identitas aplikasi bersifat tingkat host dan dibaca tanpa konteks tenant oleh rute `/.well-known/*` dan daftar origin passkey, yang mengundang `SECURITY DEFINER`, dan aksi tenant akan mengubah berkas tingkat host.
- **"Grace" reuse refresh yang memutar ulang respons sebelumnya.** Ditolak: menuntut penyimpanan polos atau reversibel atas penerus.
- **`last_seen_at` pada sesi native.** Ditolak: write amplification pada baca terpanas (`sql/100`).
- **BFF di `awcms-astro` di depan aplikasi native.** Ditolak: aplikasi persona adalah klien kontrak publik (ADR-0146); BFF menyalin alur login dan menaruh penyimpanan token berumur panjang di repo yang menghadap situs.
- **OpenID Provider penuh sekarang (discovery, `id_token`, registrasi dinamis, PAR).** Ditunda (Q2): tak ada konsumen yang membutuhkannya, dan masing-masing adalah permukaan serangan.
- **Registrasi klien mandiri oleh admin tenant.** Ditunda (Q1): berkas asosiasi dan RP dipakai semua tenant.

## Keputusan atas pertanyaan terbuka (pemilik, 23 Nov 2026, K17)

Pemilik menjawab "ya lanjutkan otomatis" atas tawaran orchestrator untuk memutuskan Q1 sampai Q12 sesuai rekomendasi review keamanan; ini dibaca sebagai persetujuan dan dapat dicabut pemilik. Pertanyaan dipertahankan seperti diajukan, disusul keputusannya.

1. **Q1 — Siapa mendaftarkan klien native?** Hanya permission platform-scoped (rekomendasi, bagian 1), atau juga admin tenant untuk redirect dan sidik jari sertifikat, setelah allow-list platform atas nama paket ditambahkan? **Keputusan (pemilik, 23 Nov 2026, K17):** Hanya platform untuk identitas aplikasi (sertifikat, paket, origin); admin tenant hanya melihat dan menonaktifkan pengikatan tenantnya sendiri di rilis pertama (M1). Alasan: kepercayaan tingkat host lintas tenant (H4).
2. **Q2 — `id_token` dan discovery.** Rekomendasi: tidak ada di rilis pertama dan tanpa klaim kesesuaian OIDC. Konfirmasi, atau sebut konsumen yang membutuhkannya. **Keputusan (pemilik, 23 Nov 2026, K17):** Setuju: tanpa `id_token`, discovery, atau klaim kesesuaian OIDC. Alasan: permukaan serangan lebih kecil.
3. **Q3 — Umur.** Access 15 menit seperti diusulkan semula, refresh idle 30 hari dan absolut 90 hari, jendela retry 15 detik: konfirmasi, atau pilih dari benchmark S2. **Keputusan (pemilik, 23 Nov 2026, K17):** Access bawaan 60 menit (rentang 300 sampai 3600); idle 30 hari; absolut 90 hari; jendela retry G bawaan 30 detik. Alasan: pencabutan berbasis baris dan kontrol per-permintaan tetap berjalan; 15 menit hanya melipatempatkan tulis dan churn `awcms_sessions` (sesi web 120 menit pun tidak dievaluasi ulang).
4. **Q4 — Umur absolut family.** 90 hari memaksa login berkala dengan MFA. Dapat diterima untuk semua aplikasi persona, atau per klien? **Keputusan (pemilik, 23 Nov 2026, K17):** Umur absolut per klien, ditetapkan platform dalam 1 sampai 90 hari; tenant hanya boleh memperpendek; selalu minimum dengan kedaluwarsa grant terdelegasi mana pun. Alasan: aplikasi persona berbeda-beda.
5. **Q5 — Jendela retry refresh.** Terima retry terbatas kunci-sama (rekomendasi) atau cabut pada setiap reuse dan terima login paksa setelah paket hilang? **Keputusan (pemilik, 23 Nov 2026, K17):** Terima retry terbatas dengan aturan garis keturunan M2. Alasan: aman karena token dibatasi pengirim, dan respons hilang di jaringan seluler itu nyata.
6. **Q6 — Plafon izin per klien** (aplikasi kurir dibatasi himpunan permission) dan klien desktop: di luar lingkup di sini dan butuh ADR sendiri karena invarian ADR-0063 tersentuh. Konfirmasi. **Keputusan (pemilik, 23 Nov 2026, K17):** Di luar lingkup; sementara blokir principal terdelegasi dan platform serta ekspos atribut ABAC deny (M5). Alasan: ini hanya mempersempit.
7. **Q7 — Attestation platform** (Play Integrity, App Attest) sebagai syarat registrasi atau per-grant: ADR kemudian, atau wajib sebelum aplikasi persona produksi pertama? **Keputusan (pemilik, 23 Nov 2026, K17):** ADR terpisah, tetapi WAJIB sebelum penerbit tanda tangan Android kedua di host yang sama, kecuali tiap klien punya host callback sendiri (H4). Alasan: hanya attestation membuktikan identitas aplikasi penebus.
8. **Q8 — Secret nonce.** `AUTH_NATIVE_DPOP_NONCE_SECRET` khusus (rekomendasi) atau diturunkan dari secret yang ada? **Keputusan (pemilik, 23 Nov 2026, K17):** Secret khusus; gagal start bila hilang atau bawaan; rotasi dua kunci; dipin oleh `config:validate` dan `security:readiness`. Alasan: isolasi radius ledakan.
9. **Q9 — Satu tenant per klien, tanpa pergantian** untuk sesi native: konfirmasi. **Keputusan (pemilik, 23 Nov 2026, K17):** Setuju: satu tenant per klien dan tanpa pergantian; aplikasi SaaS multi-tenant adalah N pengikatan. Alasan: batas tenant sederhana.
10. **Q10 — Envelope respons.** Endpoint token dan revoke memakai body RFC 6749/7009, pengecualian terdokumentasi dari envelope AWCMS: konfirmasi. **Keputusan (pemilik, 23 Nov 2026, K17):** Pengecualian envelope hanya untuk token dan revoke; error resource tetap memakai envelope AWCMS plus `WWW-Authenticate: DPoP`; `error_description` dari tabel string statis; daftarkan pengecualian di gerbang envelope dan manifest konformansi keluarga. Alasan: pustaka OAuth butuh bentuk RFC.
11. **Q11 — DPoP wajib untuk semua klien** (rekomendasi) tanpa fallback bearer: konfirmasi. **Keputusan (pemilik, 23 Nov 2026, K17):** Setuju: DPoP wajib, tanpa fallback Bearer. Alasan: pengikatan opsional adalah downgrade yang dipilih penyerang.
12. **Q12 — Durabilitas penyimpan `jti`** (UNLOGGED versus logged); analisis crash-replay bagian 6 menemukan UNLOGGED tak aman untuk diandalkan. **Keputusan (pemilik, 23 Nov 2026, K17):** LOGGED. Alasan: WAL sekitar 110 baris per detik dapat diabaikan; UNLOGGED punya semantik failover dan tes crash yang sulit dijalankan di CI, dan mitigasi yang semula tertulis keliru (M7).

## Konsekuensi

- **Positif:** aplikasi native mendapat login standar yang tahan phishing; token curian tak dapat diputar ulang dari perangkat lain; pencabutan tetap satu baris; chokepoint otorisasi tetap satu; tanpa layanan baru; jalur panas tak berubah.
- **Negatif / trade-off:** permukaan baru yang besar di modul paling sensitif; registrasi tingkat platform adalah langkah manual; verifikasi DPoP per permintaan; pengecualian envelope; tanpa attestation di rilis pertama.
- **Netral:** `awcms-astro` dan BFF tak terpengaruh; kontrak konsumen mendapat operasi native aditif, dipublikasikan untuk konsumen lewat paket konformansi (ADR-0167).

## Garis besar implementasi (setelah diterima; ditulis di sini, belum dibuka sebagai isu)

Semua slice di balik `AUTH_NATIVE_ENABLED=false`. Masing-masing atomic, dengan migrasi, OpenAPI, seed permission, deskriptor lifecycle, pin `security:readiness` (ekspresi policy persis plus probe perilaku), dan bukti mutasi untuk setiap kontrol baru.

- **S0** (ADR ini): Q1 sampai Q12 diputuskan (K17), review keamanan selesai (23 Nov 2026). Sebelum Definition of Ready (`alur-pengembangan.md`): **model ancaman** (langkah 3) dan **analisis privasi** label perangkat dan hash IP, serta **matriks izin** (langkah 6), termasuk nama permission daftar dan nonaktif tenant, **di-seed untuk tenant baru dan di-backfill untuk tenant lama** (aturan ADR-0168 A11) (L9).
- **S1 (menunggu ADR-0168 S1 dan review):** hanya modul murni, tanpa endpoint, tanpa skema: verifikasi PKCE S256, verifier bukti DPoP, format token dan namespace hash, mesin keadaan family sebagai fungsi transisi murni dengan tes properti, vektor (contoh RFC 7636 dan RFC 9449, Wycheproof), matriks merah, fuzz.
- **S2:** skema (`awcms_native_apps` global, `awcms_native_clients` pengikatan, penyimpan permintaan, code, family dengan `current_hash`, `previous_hash`, dan `credential_epoch`, `jti` LOGGED, kolom di `awcms_sessions`, CHECK `origin_auth`), RLS FORCE pada tabel ber-scope tenant, `awcms_native_apps` didaftarkan sebagai global dengan alasannya, deskriptor lifecycle dan `subjectData`, **fragmen SQL pengikatan dan `scripts/session-readers-check.ts` (H2, slice yang sama dengan kolom `dpop_jkt`)**, helper `credential_epoch` untuk family (H1), **deskriptor purge kedaluwarsa `awcms_sessions` berkadens di bawah satu hari (M3, sebelum flag)**, pin readiness, tes replay `jti` (M7), benchmark dan anggaran yang mencatat baris per hari dan ukuran indeks. Tes merah: matriks pembaca H2, pin tabel global M1, kunci dan logging M7.
- **S3:** registri aplikasi (permission platform, daftar dan nonaktif pengikatan oleh tenant), publikasi berkas asosiasi di host `APP_URL` dari tabel global, **penjaga H4** (satu penerbit tanda tangan Android, `components` iOS per app ID), layar admin tercatat di `NOT_YET_SCREENED` sampai dibangun. Tes merah: H4 dan M1.
- **S4:** halaman `/native/authorize`, persetujuan pada setiap otorisasi, penyimpan permintaan dengan pengikatan cookie `__Host-` (M8), lanjut setelah pendaftaran, gerbang host, tanpa code untuk principal terdelegasi atau tenant platform (M5), halaman callback cadangan (L8). Tes merah: M8, M5, L8, dan pemeriksaan Origin pada formulir persetujuan terhadap `APP_URL` (M6).
- **S5:** token endpoint (kedua grant), revoke, entri `SESSION_FREE_BODY_ENDPOINTS` diuji lewat middleware, rate limit (M4, L10), penanganan `checkOrigin` (M6), refresh dengan pemeriksaan epoch (H1), pemeriksaan `client_id` dan klien aktif plus kaskade penonaktifan klien (H3), urutan kunci dan aturan retry (M2), aturan pemutaran ulang code (L7), kedaluwarsa family `min(terkonfigurasi, kedaluwarsa grant)` (M5). Tes merah: refresh H1, H3, M2, M4, M6, L7.
- **S6:** verifikasi sisi resource di resolver sesi, `NATIVE_ALLOWED_OPERATIONS` dan gerbang OpenAPI dua sisi, penolakan introspeksi, skema DPoP di `api-body-authentication.ts` (L6), atribut ABAC `origin_auth` dan `native_client_id` (M5). Gerbang pembaca sendiri sudah mendarat di S2 (H2); S6 hanya memperluasnya ke verifikasi sisi resource yang baru.
- **S7:** layar daftar dan pencabutan perangkat, pencabutan admin, dan kaskade perubahan kredensial: penghapusan dan reset faktor menaikkan `credential_epoch` (H1), peristiwa satu-tenant mencabut baris langsung, dengan satu tes merah per peristiwa.
- **S8:** step-up native dan origin passkey native (setelah ADR-0168 S3).
- **S9:** fixture kontrak konsumen (ADR-0167), catatan integrasi untuk konsumen, dan serah terima PoC ke repo Lynx (ADR-0146), di luar repo ini.
