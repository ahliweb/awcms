## Context

Persona applications (customer, courier, driver, partner, field and warehouse staff) are Lynx clients in consumer repositories ([ADR-0146](0146-persona-apps-prefer-lynx-in-consumer-repos-astro-keeps-admin-and-public-web.md)). They use the public OpenAPI contract only and are never allowed to widen tenant isolation, ABAC or idempotency. Today the only human credential this repo accepts is a **session bearer** (`awcms_sessions`, opaque token stored as `token_hash`, `AUTH_SESSION_TTL_MIN=120`, not a JWT, not extended by use) obtained from `POST /api/v1/auth/login` or from the BFF handoff ([ADR-0050](0050-bff-session-handoff-code.md)). That is right for a browser behind a BFF and wrong for a phone:

1. **A native app cannot hold a client secret**, so it is an OAuth public client ([RFC 8252](https://www.rfc-editor.org/rfc/rfc8252)). The current alternative, collecting the password inside the app and calling `/login`, puts the credential, the MFA second factor and the passkey ceremony into app code, defeats SSO enforcement ([ADR-0028](0028-oidc-sso-tenant-aware-account-linking-break-glass.md)) and phishing-resistance ([ADR-0168](0168-passkeys-webauthn-are-a-principal-owned-phishing-resistant-factor-that-yields-aal2-with-self-implemented-attestation-none-verification.md)), and forces the app to copy flows (the same reason ADR-0050 rejected password proxying).
2. **A 120-minute bearer is the wrong lifetime** for a device that must stay signed in for weeks, and a long-lived bearer is the wrong fix: a stolen bearer is fully usable.
3. **A bearer is not bound to anything.** Anyone who copies it from a backup, a log or a rooted device can use it.
4. **ADR-0168 left three explicit inputs for this issue**: the app-link association host (K16 Q9: `APP_URL` serves `/.well-known/assetlinks.json` and `apple-app-site-association`; the origin allow-list accepts `android:apk-key-hash:<b64url>` configured explicitly, no wildcard), the rule that device binding must **not** use passkeys (BE/BS are not provable without attestation), and the A5 rule that authentication surfaces live on one host.

Facts about `origin/main` this design relies on (checked at `83f67158`):

- `awcms_sessions` is tenant-scoped under FORCE RLS and already carries `assurance_level` (`sql/024`), `stepped_up_at`, `origin_auth` with a CHECK (`sql/100`; `sql/117` already extended it for delegated access, ADR-0090, not for ADR-0168, so it holds five values today and S2 adds `native`), `client_ip_hash`, `user_agent_summary`. A step-up **rotates** the session token and carries `origin_auth` forward ("rotating a session does not re-authenticate it").
- `sql/144` introduced `credential_epoch`: a principal-level counter, checked on every session read through one SQL fragment (`sessionCredentialCurrent`, `session-credential-epoch.ts`), that ends the sessions of **every** tenant when a credential changes. It exists because a cross-tenant revoke of session rows is impossible under FORCE RLS. New sessions are stamped with the **current** epoch (`currentCredentialEpoch`), which is exactly why a refresh must not mint sessions from the current epoch (H1).
- `sql/100` records why there is no `last_seen_at`: one UPDATE per request on the hottest read is not worth a cosmetic column. This ADR keeps that discipline.
- `requireStepUp` (`identity-access/application/mfa-session-assurance.ts`) reads `assurance_level` and `stepped_up_at` from the session row. `MFA_ENROLLMENT_REQUIRED` is returned by `login.ts`, `session/switch.ts` and `session/tenant.ts`. `evaluateTenantEntry` returns `password_login_disabled` ([ADR-0088](0088-tenant-selection-and-switching.md)).
- Single-use hashed codes with their own hash namespaces already exist (`ho-sha256:`, `bff-sha256:`, `mc-sha256:`), 32 bytes of CSPRNG, constant-time comparison, TTL mirrored in a CHECK constraint (`session-handoff.ts`).
- Channel webhook tokens carry a non-secret routing prefix (`wcb1.*`, `_shared/channel-webhook-token.ts`) so the tenant is derived from the token and never from the payload.

## Decision

AWCMS acts as an **OAuth 2.0 authorization server for registered native public clients**, using the **authorization code flow with PKCE (S256)** in the system browser, redirecting to an **app link** (claimed `https` URL), issuing a **short-lived opaque access token**, a **rotating opaque refresh token with reuse detection**, and **binding every device session to a non-exportable per-installation key with DPoP proofs**. The user authenticates in the browser on the one authentication host, so password, TOTP, passkey, SSO, Turnstile and MFA enrolment are reused and not reimplemented.

It is **OIDC-style, not a full OpenID Provider** in the first release: no discovery document, no `id_token`, no dynamic client registration (Q2). We do not claim OIDC conformance.

Everything ships behind `AUTH_NATIVE_ENABLED=false` (fail closed: the endpoints answer a uniform 404 when off).

### 1. Native public clients are separate from web clients

- **Two tables, because app identity is host-level and a client binding is tenant-level (M1).** `awcms_native_apps` is **global** (no `tenant_id`, no RLS; registered as a global table with a written reason for `security:readiness`, like the other global tables): platform (`android` or `ios`), package or bundle, the signing-certificate SHA-256 fingerprints expected in `assetlinks.json`, the `android:apk-key-hash:<b64url>` origins (only if the app uses native passkeys), the iOS `teamId.bundleId`, the exact callback paths, status, audit columns. It is written **only** behind the platform-scoped permission `identity_access.native_client.register`, and it is read by the public `/.well-known/*` routes (which have no tenant context), by the passkey origin allow-list and by the association-file generator through a plain read grant, with **no `SECURITY DEFINER` function**. `awcms_native_clients` is the **tenant binding, tenant-scoped under FORCE RLS**: `client_id` (opaque, random, not a secret), `tenant_id`, `app_id` (FK to the global table), display name, the exact redirect URI set (at most 3, each a callback path of that app), status (`active`, `disabled`), and audit columns. A tenant disabling its binding changes **only that binding** and never the association files. There is **no client secret**: a public client cannot authenticate itself, and `client_id` proves nothing. Possession of a client row never grants anything by itself; the user's credentials and the exact redirect do (on Android that statement needs the extra rule H4).
- The web BFF client (ADR-0050 `bff-sha256:` secret, confidential) is a different object and is never usable on the native endpoints, and the reverse.
- **Redirect URIs** are matched by **exact string comparison** (RFC 9700 requires exact matching; no prefix, no wildcard, no pattern). Rules at registration: scheme `https` only (**no custom URL schemes**: they are not collision-proof; RFC 8252 prefers claimed https links), host exactly the `APP_URL` host, a path under `/native/callback/`, no query, no fragment, no userinfo, no port. Loopback redirects are **not** admitted (they are for desktop; Q6 of this ADR defers desktop).
- **The app-link association is host-level and therefore platform-level trust.** `/.well-known/assetlinks.json` and `/.well-known/apple-app-site-association` are served on the `APP_URL` host from configuration controlled by the platform operator, generated from the **active** client rows, byte-stable and cacheable. Because the RP ID and the host are shared by every tenant, **creating or changing a native app (a row of the global table: certificate fingerprint, `android:apk-key-hash` origin, iOS app ID, callback paths) is a platform-scoped permission** (`identity_access.native_client.register`, a platform-scoped activity per [ADR-0053](0053-platform-scoped-permissions.md); it must not be seeded into tenant roles, [ADR-0051](0051-admin-screens-consolidated-in-awcms.md) rule). A tenant admin may list and disable the bindings (`awcms_native_clients`) of their own tenant (tenant-scoped, ABAC default-deny); that never edits the host-level association files. Self-service registration by a tenant admin is not in the first release (Q1) because a rogue app listed in the host's association file could intercept codes and, with a registered passkey origin, ceremonies for **every** tenant sharing the RP.
- **Android trusts every listed app for the whole host (H4).** Digital Asset Links grants `handle_all_urls` to every listed package for the **entire** host, and the path is decided by the app's manifest, not by the server (iOS differs: the association file restricts each app ID to `components` paths). A legitimate-but-malicious or compromised app of tenant B could therefore start `/native/authorize` with tenant A's `client_id` and its own verifier and key, declare tenant A's callback path in its manifest, receive the code and redeem it. Only the consent screen would stand in the way (RFC 8252 "client impersonation"; section number needs verification). Normative: **until platform attestation (Q7) lets the token endpoint verify the redeeming app's package and signing digest, at most one signing publisher may be listed for Android on that host**; admitting a second requires attestation or a **per-client callback host** whose association file lists only that client. iOS association entries list each app ID with only its own exact callback paths. Consent is shown on **every** authorization of a native client and is never remembered. **Red test required (S3):** registering a second Android signing publisher on the host is refused; a generated iOS file never lists a path for a different app ID; both fail when the guard is removed.
- `android:apk-key-hash:<b64url>` passkey origins ([ADR-0168](0168-passkeys-webauthn-are-a-principal-owned-phishing-resistant-factor-that-yields-aal2-with-self-implemented-attestation-none-verification.md) K16 Q9) come only from active rows of `awcms_native_apps` registered by the platform permission above, are exact strings, and are read into the passkey verifier's origin allow-list. No wildcard, no environment string that anyone with deployment-variable access can extend silently without an audit row.

### 2. Authorization endpoint (browser, on the one authentication host)

`GET /native/authorize` is an HTML page, served only on the `APP_URL` host (ADR-0168 A5: other hosts get a 301). It is not a JSON API and is not in the admin shell.

- Required parameters: `response_type=code`, `client_id`, `redirect_uri` (exact match against the client), `state` (required, at least 128 bits of entropy asked of the app, echoed), `code_challenge` and `code_challenge_method=S256`, `dpop_jkt` (the JWK thumbprint of the installation key, RFC 9449 binds the code to that key; section number needs verification). `plain` PKCE is **rejected**. A request missing any of them is an error.
- **Validation order and error surface.** An unknown client, an inactive client, a redirect that does not match, or a request for a tenant other than the client's is shown as a **page error and never redirected** to an unverified URI (RFC 6749 treats an invalid redirect that way; section needs verification). The page text is identical for "no such client", "client disabled" and "wrong redirect". Only after the client and redirect are accepted may errors return to the redirect with `error` and `state`.
- The request is stored server-side (a short-lived row, TTL 600 s, the same idea as `AUTH_SSO_OAUTH_REQUEST_TTL_SEC`) and the browser carries only an opaque request id, so the login, MFA, enrolment and SSO round trips can resume it.
- The user then authenticates through the **existing** flows: `evaluateTenantEntry` is applied (`password_login_disabled`, SSO enforcement), then password with the global lockout counter ([ADR-0086](0086-the-lockout-counter-is-global.md)) and TOTP or a passkey ([ADR-0168](0168-passkeys-webauthn-are-a-principal-owned-phishing-resistant-factor-that-yields-aal2-with-self-implemented-attestation-none-verification.md)) as the **second** factor, or SSO ([ADR-0028](0028-oidc-sso-tenant-aware-account-linking-break-glass.md)).
- A **consent and identity screen** always shows: the client name, the tenant, the account, the device label the app supplied (sanitised, never trusted), and what the app is allowed to do. It is a CSRF-protected form. It is the anti-phishing control for a hostile app that opens the browser with the victim's attention elsewhere. It is shown on every authorization and is never remembered or skipped (H4, M8).
- **Browser semantics at authorize (M8).** The code's tenant is **always the client's tenant**; an existing browser session in another tenant is never reused or switched. The stored request id is bound to a `__Host-` cookie set at authorize start, so a request id planted by an attacker (fixation) cannot be resumed in another browser. The flow does not leave a reusable web session beyond what the existing login already issues, and that fact is documented in the runbook. Passwordless sign-in is not offered in the first release (ADR-0168 Q3): password is followed by TOTP or a passkey as second factor, or the user comes through SSO. **Red test required (S4):** a request id without the matching cookie is refused; a session of another tenant is not reused; both fail when the binding is removed.
- **An authorization code is issued only from a fully authenticated, non-restricted state.** An enrolment-grant session (the state behind `MFA_ENROLLMENT_REQUIRED`) never yields a code. If the principal is required to enrol a factor (ADR-0141 and the enrolment gate), the page sends the user through enrolment in the browser, then resumes the stored request. `MFA_ENROLLMENT_REQUIRED` is therefore a browser-side step, never a token-endpoint error.
- The **authorization code** is 32 bytes of CSPRNG, base64url, stored as a hash in its own namespace, **single use, TTL 60 s** (the same bound as the handoff code, mirrored in a CHECK), bound to `client_id`, `redirect_uri`, `code_challenge`, `dpop_jkt`, tenant, principal, identity, the achieved `assurance_level` and the list of authentication methods. The plaintext is shown to nobody but the redirect.
- The code carries a non-secret routing prefix (tenant id) so the token endpoint can enter the right tenant context before any lookup, as the channel webhook token does. The prefix is routing, never authority: the row, found by hash under that tenant, is.

### 3. Token endpoint

`POST /api/v1/auth/native/token`, `application/x-www-form-urlencoded`, grant types `authorization_code` and `refresh_token`. It is a **session-free body endpoint** and therefore must be added to `SESSION_FREE_BODY_ENDPOINTS` with a narrow pattern and be tested **through the middleware** (audit lesson 3). Responses follow RFC 6749 (`access_token`, `token_type: "DPoP"`, `expires_in`, `refresh_token`, and the RFC error JSON `{error, error_description?}`), which is **a documented exception to the AWCMS response envelope** (Q10): OAuth client libraries and the Lynx stack expect the RFC shape, and the OpenAPI document must say so on these operations. The error codes used are `invalid_request`, `invalid_grant`, `use_dpop_nonce`, `invalid_dpop_proof` and `unsupported_grant_type`. `invalid_client` is **not** used for an unknown or wrong client (that is `invalid_grant`, so the failures stay indistinguishable) because a public client has no client authentication to fail. `slow_down` is **not** used: it belongs to the device authorization grant (RFC 8628), not to this flow. `error_description` comes from a static string table, never from request data. A proof that fails verification is `invalid_dpop_proof`, answered before any database lookup, and **never** triggers a revocation: only a **valid** proof by a different key counts as reuse evidence (L2). The token endpoint is explicitly **excluded from `Idempotency-Key`**: the single-use code and the bounded retry window are its idempotency mechanism (L6). `/native/revoke` also joins `SESSION_FREE_BODY_ENDPOINTS`, and `lib/auth/api-body-authentication.ts`, which parses only `Bearer` today, gains the DPoP scheme in S6 so authenticated native operations are not rejected before the handler (L6). `Cache-Control: no-store` on every response.

**authorization_code grant.** Verify, in one transaction under the routed tenant: DPoP proof (section 6), the code by hash, `consumed_at IS NULL` and not expired, `client_id` and `redirect_uri` identical to the stored values, `S256(code_verifier)` equal to the stored challenge (constant-time), and the proof key's thumbprint equal to the stored `dpop_jkt`. Consume with a single guarded `UPDATE ... WHERE consumed_at IS NULL RETURNING`. Re-check at redemption that the principal is active and the tenant is allowed to enter (suspension allow-list, `evaluateTenantEntry`) because policy may have changed in the 60 s. Any failure returns the same `invalid_grant`. **Presenting an already-consumed code revokes the token family that code produced** (RFC 6749 recommends this; section needs verification) and is audited, **but only when the presenter proves the code's PKCE verifier and the bound key** (L7): a bare replay of an intercepted code gets `invalid_grant` and no revocation, so an interceptor cannot kill the legitimate family. **Red test required (S5):** replay of a consumed code without a valid verifier leaves the family alive; with a valid verifier and key it revokes; both fail when the condition is dropped.

**refresh_token grant.** Section 5.

### 4. Token shapes: opaque, not JWT

| Token              | Shape                                                                                                  | Lifetime                                                                       | Stored                                                                                                               |
| ------------------ | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| Access             | opaque, 32 CSPRNG bytes, base64url, visible marker prefix `awn_`, DPoP-bound                           | **60 minutes** default (Q3), `AUTH_NATIVE_ACCESS_TTL_SEC`, bounded 300 to 3600 | **as an `awcms_sessions` row** (hash only), `origin_auth = 'native'`                                                 |
| Refresh            | opaque, 32 CSPRNG bytes, base64url, marker prefix `awr_`, non-secret tenant routing prefix, DPoP-bound | idle 30 days, absolute 90 days from the grant, both configurable               | hash only, its own hash namespace, held on the family row (`current_hash`, `previous_hash`) with unique indexes (M3) |
| Authorization code | opaque, as section 2                                                                                   | 60 s                                                                           | hash only, own namespace                                                                                             |

**Why opaque and not a JWT access token (RFC 9068 style).**

- **Revocation is immediate and uses the machinery that already exists.** Deactivation, password reset (`sql/073`), tenant suspension, and the new family revocation all work by changing a row. A JWT stays valid until `exp` unless every resource request also reads a denylist, which is a database read anyway and a second system to keep correct.
- **The hot path does not change.** A native access token is an `awcms_sessions` row looked up by hash through the same indexed read as every other session. Every downstream control keeps working unmodified: tenant context, RLS, `authorizeInTransaction` (ADR-0063), `assurance_level`, `requireStepUp`, ABAC. A JWT verifier would be a second authentication path to fuzz, with algorithm-confusion and key-rotation hazards that this repo does not have today.
- **No stale claims.** Permissions are evaluated per request from the database ([ADR-0063](0063-ownership-grants-run-through-the-authorization-chokepoint.md)); claims inside a token would be a stale copy of the part that matters.
- **Secret scanning.** Markers (`awn_`, `awr_`) make accidental leaks greppable and let a cheap prefix check route to the right resolver, with no weakening of the stored hash.
- The cost: a database read per request, which every session already costs. We do not add a per-request write (no `last_seen_at`, per the `sql/100` discipline).

**Why a hash and which hash.** Tokens are 256-bit CSPRNG values, so a fast hash (SHA-256) is correct (no password-style KDF), and each secret kind has its own namespace with a CHECK on the stored shape, like `ho-sha256:`, `bff-sha256:`, `mc-sha256:`. The native access token is stored in `awcms_sessions` in whatever shape that table's CHECK already requires; the namespace decision for the new columns is made in S2 with a test that a refresh hash can never match as a session hash (needs verification against the existing CHECK before S2). The comparison of hashes is constant-time (`hashesEqual`). Plaintext tokens are never logged, audited, put in a URL or kept after the response; the redaction list gains `access_token`, `refresh_token`, `code`, `code_verifier`, `DPoP`, `Authorization` values.

**Access-token TTL trade-off.** Revocation does not depend on a short TTL (it is an opaque row). The TTL only sets how often a device must refresh, and refresh is the busiest write path this ADR adds. The default is not a derived number; the owner decided **60 minutes** (Q3) because revocation is row-based and per-request controls still run, while 15 minutes only quadruples the writes and the churn of `awcms_sessions`. The S2 benchmark may still tune it inside the 300 to 3600 second range.

### 5. Refresh rotation, token families, reuse detection, races

**Model.** Every successful code redemption creates a **family** (`awcms_native_token_families`: tenant, principal, identity, client, `dpop_jkt`, the principal's **`credential_epoch` at the grant** (H1), `assurance_level`, authentication methods, `stepped_up_at` and its method at the grant, device label, coarse user-agent summary, keyed IP hash, `generation`, **`current_hash`, `previous_hash`, `previous_consumed_at`** (M3), `created_at`, `idle_expires_at`, `absolute_expires_at`, `revoked_at`, `revoke_reason`). **There is no per-generation token table** (M3): the family row holds the hash of the current refresh token and of the one it replaced, each with a unique index, which is all reuse detection needs; a token that matches neither is unknown. The access sessions the family has issued reference it (`awcms_sessions.native_family_id`, nullable FK, indexed). **A family is the device session**: listing, revoking and auditing are per family.

**Rotation (M2).** The refresh token carries a non-secret tenant routing prefix. The lookup order is: resolve the token hash under that tenant to its family id (unique indexes on `current_hash` and `previous_hash`), then `SELECT ... FROM awcms_native_token_families WHERE id = $family FOR UPDATE`, then **re-read the token and family state under the lock**, in READ COMMITTED (a REPEATABLE READ snapshot would read stale state). That serialises two simultaneous refreshes of one family and removes any dependence on the time of day; every elapsed-time comparison uses `clock_timestamp()` after the lock is held, never `now()`. Then:

1. Resolve the token by hash. Unknown, expired, or family revoked, past idle or absolute expiry, **a `client_id` that differs from the family's, or a client binding that is not `active` (H3)**: `invalid_grant` (the same body for all of them; no oracle).
2. The DPoP proof must verify and its key thumbprint must equal the family's `dpop_jkt`. **A refresh token presented with a proof for a different key is never honoured**, and is itself reuse evidence (below).
3. If the token matches `current_hash`: move `current_hash` to `previous_hash` (setting `previous_consumed_at`), store the new `current_hash`, increment `generation`, insert a new access session (INSERT, not an in-place update of an old session; the old access token simply expires within its TTL, which avoids contention on a hot row and avoids failing in-flight requests) **stamped with the family's `credential_epoch`, never the current one (H1)**, advance `idle_expires_at`, return the new pair.
4. Re-evaluate at every rotation: principal active, identity active, tenant allowed to enter, family not revoked, and **the principal's current `credential_epoch` is not greater than the family's**; otherwise `invalid_grant` and the family is revoked with `revoke_reason = 'credential_changed'` (H1). `assurance_level` is **carried from the grant and can only stay or fall, never rise**; `stepped_up_at` and its method (ADR-0168 A2) are **carried unchanged**, never refreshed, so `requireStepUp` keeps honouring the same freshness window as on the web and fails once that window has passed (L3).
5. A policy change that forbids local credentials or suspends the tenant makes the next refresh fail uniformly. Whether it also revokes the family is the safe default (revoke) for deactivation and credential change events (section 9) and is a deny-without-revoke for temporary suspension.

**Reuse detection.** A consumed token presented again is not a normal error:

- **A valid proof by a different key** (a proof that fails verification is `invalid_dpop_proof` and never revokes, L2): the family is **revoked** (`revoke_reason = 'reuse_detected'`), all unexpired access sessions of the family are revoked in the same transaction, a `high` audit row is written, and the caller gets the same `invalid_grant` as any other failure. The legitimate device finds out on its next refresh and the user is sent through sign-in again.
- **Same DPoP key, the presented token is the family's `previous_hash`, the current token has not been used yet, and the time since `previous_consumed_at` is within the retry window G:** this is a **lost-response retry** (the phone had no signal when the response arrived), not an attack. It is accepted **once**: the family rotates again (the unused current token is superseded, audited as `retry_superseded`), a fresh current token and a fresh access session are issued. G defaults to **30 seconds** (Q3), bounded at 60 (`AUTH_NATIVE_REFRESH_RETRY_WINDOW_SEC`), measured with the **database** clock.
- **Same key, outside G, or the current token was already used:** the family is revoked as above. A token that matches neither `current_hash` nor `previous_hash` is unknown (`invalid_grant`, no family can be identified, so nothing is revoked).

**Why a bounded retry and not none.** Rotation without any retry path makes every dropped packet a forced sign-in on mobile networks, and the first result is that app authors lengthen refresh lifetimes or stop rotating. The retry is safe here because the token is **sender-constrained**: only the holder of the non-exportable installation key can use it, and RFC 9700 accepts rotation **or** sender-constraining for public-client refresh tokens; this design has both and uses the retry only under the constraint. A thief with the token and without the key reaches the "different key" branch and kills the family. A thief **with** the key has the device, and nothing in a token protocol defeats that.

**Why not return the same response again.** That would require storing the plaintext successor or an encrypted copy of it. Hashes only, always.

**Concurrency across instances.** The family row lock serialises per family and is the only coordination: no new hard dependency (Redis is already an optional dependency of rate limiting, ADR-0066, and is not required here), no distributed lock, no advisory-lock keying on user input. "The earlier one wins" is decided by `generation` under the lock, not by `now()` (audit lesson 4; and `now()` is the transaction start). **Every revocation path (user, admin, cascade, client disable) updates the family row first and only then revokes the family's sessions**, so a revoke cannot lose a race against a refresh that is inserting a new session. Consumer note: the app must run refresh single-flight. **Red test required (S5):** two concurrent refreshes of one family produce exactly one new generation and no revocation; a revoke racing a refresh leaves no live session of the revoked family; both fail when the lock or the ordering is removed.

**Caps.** At most 10 active families per principal per client (oldest evicted and audited), and one active family per (principal, client, `dpop_jkt`): a re-login from the same installation retires the previous family. Idle and absolute expiry are enforced at refresh by comparing against the database clock, and expired rows are purged by a data-lifecycle descriptor in the same migration. **`awcms_sessions` has no expiry-purge descriptor today (only subject data), and one native access session per device per access TTL accumulates in the hottest table: a sub-day-cadence expiry-purge descriptor for `awcms_sessions` ships before the flag can be enabled (M3)**, and the S2 benchmark records rows per day and index size.

### 6. DPoP: device binding with a non-exportable per-installation key

Binding does **not** use passkeys (ADR-0168 Low item): `backedUp` and `backupEligible` are not provable without attestation, and a passkey is a user credential, not an installation identity. The app generates an **ES256 (P-256) key pair in the platform keystore** on first run (Android Keystore, StrongBox when available; iOS Keychain/Secure Enclave), marked **non-exportable**, and proves possession of it with **DPoP proofs** (RFC 9449) on every request the token is used on.

- **Algorithm.** `ES256` only (hardware-keystore supported; `none` and symmetric algorithms rejected as RFC 9449 requires). The verifier is pure code on WebCrypto, with the same discipline as ADR-0168 A6: strict base64url, `typ = dpop+jwt`, exactly one embedded public `jwk` with no private members, compact JSON limits, and signature verification through the platform with canonical R and S handling. It is covered by RFC 9449 examples, Wycheproof ECDSA vectors, and a **red matrix** (each check has a test that fails when the check is removed).
- **Claims checked.** `htm` and `htu` (compared **without query and fragment**) against the actual method and the canonical request URL (scheme and host from configuration, **not** from the `Host` header: it is attacker-influenced), `iat` within a stated skew bound (60 seconds proposed, tuned in S2), `jti` present and unique, `nonce` equal to a current server nonce, and on resource requests `ath` equal to the base64url SHA-256 of the access token.
- **Binding.** The thumbprint (`jkt`) is stored on the family and copied to every access session (`awcms_sessions.dpop_jkt`). The authorization code is bound to it via the `dpop_jkt` authorization parameter (so an intercepted code is useless to another key even before PKCE).
- **Downgrade is impossible, and it is anchored in SQL (H2).** A session with `dpop_jkt` set is accepted **only** with `Authorization: DPoP <token>` and a valid proof; `Authorization: Bearer` with a bound token is `401` with a `WWW-Authenticate: DPoP` challenge. The binding predicate is **one SQL fragment emitted once**, like `sessionCredentialCurrent`: `AND s.dpop_jkt IS NOT DISTINCT FROM ${verifiedJktOrNull}`. **Every live-session reader takes a mandatory binding argument**, and a new gate `scripts/session-readers-check.ts` fails the build for any reader that does not embed the fragment (`resolveActiveSession` is called directly from at least eight places today: `auth/me.ts`, `auth/logout.ts`, `auth/profile.ts`, `auth/preferences.ts`, `auth/mfa/status.ts`, `comments/author-resolution.ts`, `lib/auth/api-body-authentication.ts`, `mfa.ts`; and `resolveAuthInputs` accepts a Bearer **or** a cookie). A token from a cookie or from `Bearer` always binds `NULL`. **The fragment and the gate land in S2, in the same slice as the `dpop_jkt` column and before any slice that can insert a bound row.** A step-up rotation of a native session **carries forward** `native_family_id` and `dpop_jkt`, like `origin_auth`. **Red test required (S2):** a bound token sent as Bearer and as cookie to every reader answers 401; the test fails when the fragment is removed from any one reader.
- **Server nonce, without storing it.** Nonces are stateless: `HMAC(server key, time-slot)`, current and previous slot accepted (slot 5 minutes, so a nonce lives 5 to 10 minutes). The server key is a new secret `AUTH_NATIVE_DPOP_NONCE_SECRET` (at least 32 bytes, fail closed at start when native is enabled and it is missing or default, two-key rotation: `..._PREVIOUS`). A missing or stale nonce answers `use_dpop_nonce` plus a `DPoP-Nonce` header **before** any database lookup, so it is never an oracle. A fresh `DPoP-Nonce` is also sent proactively on successful responses so the app rarely pays a round trip for `use_dpop_nonce`. The nonce bounds the replay window of a captured proof to the nonce lifetime, which is why a replay store only has to remember `jti` for about two slots.
- **`jti` replay: tiered, to keep cost bounded.**
  - **Token endpoint, native step-up, revoke, and any native-allowed operation that declares `x-native-high-risk`:** the `jti` is recorded in the database in a short-lived table `awcms_native_dpop_jti` (**LOGGED**, M7; key `H(jkt || jti)`, never a hash of the signature because ECDSA signatures are malleable; `expires_at`), `INSERT ... ON CONFLICT DO NOTHING RETURNING`, TTL equal to two nonce slots, swept by range delete on `expires_at`. For scale of mind (not a measured result), 100 000 active devices at a 15-minute access TTL (the pessimistic case; at the decided 60 minutes it is about a quarter of that) is about 110 refresh inserts per second averaged, **plus** the `jti` writes of the `x-native-high-risk` operations, and the table holds only the last ten minutes of rows. **No new service is introduced**: Postgres is enough at that rate. **LOGGED because** the mitigation first written here ("refuse proofs whose `iat` precedes the process start") was wrong: the application does not restart when the database crashes, the postmaster start time does not change in a crash reinit, and UNLOGGED tables are emptied by crash recovery and do not exist on a promoted standby. The worst case of a replay into an emptied table is a denial of service (a replayed code or a superseded token revokes the family; a stolen proof cannot be used without the key because of `ath` and the sender constraint), and the WAL of about 110 rows per second is negligible. Q12 records the decision for the owner. **Red test required (S2):** a second insert of the same `H(jkt || jti)` is refused; the table is not UNLOGGED (pinned in `security:readiness`); both fail when the key or the logging is changed.
  - **Ordinary resource requests (every API call):** a `jti` row per request would be a write per request, which this repo refuses on principle. These are protected by `ath` (the proof is bound to this token), `htm`/`htu` (to this operation), the nonce window (to a few minutes), and a bounded **in-process LRU** of recent `jti` values (per instance, short TTL) as a best-effort filter. Cross-instance replay of an identical proof within the nonce window needs a captured TLS-protected request, and can only repeat the same method and URL; non-idempotent high-risk mutations are already covered by `Idempotency-Key` (the `awcms-idempotency` rule).
- **Verification cost.** One ES256 verification per request, to be measured in S2 against the query-budget practice (target to be set from the benchmark, not asserted here). The imported public key objects are held in a **bounded LRU keyed by the canonical thumbprint**, filled **only after** the session lookup has succeeded and the thumbprint matches the session's (the cache must never fill from unauthenticated input, audit lesson 6).
- **What this does not do.** Without platform attestation (Play Integrity, App Attest) AWCMS cannot prove the key is hardware-resident or that the client is the real app; a modified app can generate a software key. The control that matters here is that a token **copied away** from a device (backup, log, proxy, malware without keystore access) cannot be replayed from another. Attestation is a later, separate decision (Q7).

### 7. Native sessions are default-deny on which operations accept them

[ADR-0146](0146-persona-apps-prefer-lynx-in-consumer-repos-astro-keeps-admin-and-public-web.md): persona apps use public contract operations only and never the admin surface implicitly. A native session is therefore accepted **only** by operations that opt in: an OpenAPI security scheme `nativeDpop` and an extension `x-native-client: true` per operation, mirrored by a code allow-list (`NATIVE_ALLOWED_OPERATIONS`) that middleware consults **before** the handler, with a gate that fails when the two disagree (the same two-sided pattern as the other registries). Not allowed, whatever the permissions of the principal: `/admin/*` pages and APIs, platform-scoped activities, credential and MFA management (password change, factor enrolment and reset), tenant switching, session introspection of ADR-0049 (it is bearer-only and a bearer introspection of a bound token is refused), API-key and machine-credential management, and the native client registry itself. ABAC and RBAC are evaluated exactly as for a human session on the allowed operations; the allow-list narrows, it never widens.

A per-client **permission ceiling** (a client may use at most a named subset of permissions) is a real need for a courier app, but it changes the authorization chokepoint invariants of ADR-0063 and is not decided here (Q6). Until it exists the allow-list of operations is the only narrowing.
**Who may hold a native family (M5).** No authorization code is issued for a delegated identity (ADR-0090, `sql/117`; the exact column name is verified in S4) or in the platform tenant, so a delegated identity cannot obtain a 90-day family that outlives its grant, and an owner or platform-permission holder does not carry all permissions into a courier app. The family's absolute expiry is `min(configured, any grant expiry)`. `origin_auth = 'native'` and `native_client_id` are exposed as ABAC attributes so tenants can write **deny** policies (deny-only; the ADR-0063 invariants are unchanged). **Red test required (S4 for the issue refusal, S5 for the expiry, S6 for the attributes):** a delegated or platform-tenant principal gets no code; a family never outlives its grant; a deny policy on `origin_auth = 'native'` takes effect; each fails when its control is removed.

### 8. MFA, step-up, AAL, and ADR-0168 passkeys

- **Initial AAL** is what the browser authentication produced: `aal1` for a password alone, `aal2` after TOTP or passkey; the family and the first access session record it. `origin_auth` for native sessions is `native`, with the first factor kept in the family's methods list (the CHECK on `origin_auth` already holds five values after `sql/117`, which added delegated access for ADR-0090, and gains `native` in S2).
- **ADR-0088 and `MFA_ENROLLMENT_REQUIRED`.** Tenant entry, enrolment requirement and the policy switch are evaluated at authorize time **and again at every refresh**. Enrolment is done in the browser, not through the token endpoint (section 2). Tenant switching is **not** available to a native session (the client is registered for one tenant; the user signs in again to reach another tenant); `session/switch` rejects native sessions.
- **Step-up** for an operation guarded by `requireStepUp` uses the existing step-up endpoints, declared native-allowed, which already rotate the session token; for native sessions the rotation **keeps the family and the DPoP binding**, and `stepped_up_at` is set as on the web. After a refresh `stepped_up_at` is carried unchanged (section 5), so the web's freshness window applies and the app prompts again once it has passed. A passkey step-up from a native app is possible when the client's `android:apk-key-hash` or iOS identifier is registered (section 1) and depends on ADR-0168 S3 onward; the `requireStepUp(..., { method: "phishing_resistant" })` follow-up that ADR-0168 A2 names applies to native sessions too.
- **A native session never raises its own AAL by refreshing**, and an AAL downgrade on factor removal is handled through the credential epoch (sections 5 and 9, H1), not by revoking rows across tenants, which FORCE RLS makes impossible.

### 9. Logout, revocation, audit

- **Logout and revoke:** `POST /api/v1/auth/native/revoke` (RFC 7009 shape) with the refresh token (or the access token plus proof). It always returns `200` with an empty body for an unknown, expired or already revoked token, so it is not an oracle. It revokes the family and its unexpired access sessions in one transaction.
- **Device list and device revoke:** the user can list their families (device label, client, created, last rotated, coarse UA and a masked IP hint) and revoke any of them from the account screen under `/admin/account` and from the API (native-allowed read of the caller's own families). A tenant admin with a tenant-scoped permission (`identity_access.native_session.revoke`, maker/checker not required but audited) can revoke a principal's families in that tenant. Both go through `authorizeInTransaction`; "not yours" and "does not exist" are indistinguishable.
- **Cascade (H1).** Principal-level events (password reset or change, MFA reset, factor removal, passkey revocation or reset, principal deactivation) act through the **`credential_epoch`**, because a cross-tenant revoke of rows is impossible under FORCE RLS (`sql/144`): factor removal and reset bump `credential_epoch` (or a dedicated `assurance_epoch` checked the same way), which today they do not, and a refresh is refused when the principal's epoch exceeds the family's (section 5). Only **same-tenant** events (identity deactivation, tenant removal, admin revoke) revoke family rows directly, in the transaction that revokes sessions today. **Red test required (S5 for the refresh check, S7 for each event):** a password reset in tenant A makes the refresh of a family in tenant B fail with `invalid_grant` and revoke it with reason `credential_changed`; one test per event type; the test fails when the epoch comparison is removed. The readiness check proves no path revokes sessions without also acting on families or the epoch.
- **Client disabled or compromised (H3).** A refresh request carries `client_id`; it must equal the family's and the binding must be `active`, else `invalid_grant`. Disabling a client binding revokes, **in the same transaction, every family of that client and their unexpired access sessions** (`revoke_reason = 'client_disabled'`, audited `high`), family rows first (M2). Revoking an association-file entry is not immediate (Google and Apple cache the file), so the disable cascade, not the file, is the control. The runbook "revoke a compromised client" is exactly this transaction plus the platform-side removal of the app from `awcms_native_apps`. S3 only flips the status (no family exists before S5); the cascade, its refresh checks and **the red test land in S5 and the flag cannot be enabled without them**. **Red test required (S5):** disable a client, then its refresh is refused and its access sessions are dead; fails when the cascade or the `client_id` check is removed.
- **Audit (with redaction).** Audited: client registered, changed, disabled (high); authorization granted (info); family created (info); **reuse detected** (high); family revoked by user, admin, or same-tenant cascade (medium); family revoked by `credential_changed` (high); client disabled (high); authorization denied after authentication (medium); retry-window supersession (low); native passkey origin changes (high). **Routine rotations are not audited** (one row per device per access TTL would be the loudest table in the system); they are a metric counter. No token, code, verifier, proof, or full IP is ever written. The keyed IP hash must not depend on a per-process key (the `hashClientIp` lesson: persisted values must remain comparable).
- **Fallback callback page (L8).** The page served at `/native/callback/*` when the app link does not open the app never reflects the `code` or `state`, sends `Referrer-Policy: no-referrer` and `Cache-Control: no-store`, loads no analytics, passes through Varnish uncached, and the query string is redacted from proxy logs. **Red test required (S4):** the response body never contains the code; fails when the headers or the reflection are changed.

### 10. Rate limits and anti-enumeration

- **Pre-verification limits are keyed only by what the network gives us** (the trusted source address), never by an attacker-chosen value: per source IP on `/native/authorize`, the token endpoint and revoke (M4). `client_id` and the tenant routing prefix are public, so **nothing an unauthenticated caller can send may exhaust a bucket shared by other users**: per-client and per-family counters count only requests whose token or code was **found**, and they slow down without locking. Over the limit answers `429` with `Retry-After`. The per-IP limits must be generous, because Indonesian mobile carriers put many legitimate users behind one CGNAT address (L10). **Red test required (S5):** a flood of unknown tokens for a public `client_id` does not slow or lock any legitimate user of that client; fails when a per-client pre-verification bucket is added.
- **Uniform denial.** `invalid_grant` is the single answer for unknown, expired, consumed, revoked, wrong-client, wrong-redirect, wrong-verifier, wrong-key, and inactive-principal; the response body is uniform, which is what matters for a 256-bit random token (identical work is not claimed); `use_dpop_nonce` is issued before any lookup. Replaying an `Idempotency-Key` on a native-allowed mutation must not reveal whether the resource exists (audit lesson 14).
- **No client enumeration.** The authorization page error text is identical for every client failure; `client_id` values are random, not sequential.
- **Lockout:** wrong-verifier and wrong-refresh attempts count against a per-family limiter that only **slows** (M4), never against the principal's global password-lockout counter (ADR-0086) and never against a per-`client_id` lockout, so an attacker holding a public `client_id` cannot lock a user or a whole client out.

### 11. Compatibility with the 120-minute bearer

Nothing existing changes. `AUTH_SESSION_TTL_MIN=120` still governs password-login and handoff sessions; the native lifetimes have their own variables. The web BFF handoff ([ADR-0050](0050-bff-session-handoff-code.md)) and introspection ([ADR-0049](0049-machine-credentials-and-session-introspection.md)) are unchanged; introspection refuses native-bound sessions. `awcms-astro` and the frozen consumer contract ([ADR-0065](0065-awcms-astro-consumer-contract-is-frozen.md)) are untouched: the native endpoints are **additive**. The new `awcms_sessions` columns are nullable (`native_family_id`, `dpop_jkt`) and the `origin_auth` CHECK gains one value; no backfill is needed.

## Alternatives rejected

- **JWT access tokens (RFC 9068 style).** Rejected for the reasons in section 4: revocation, a second authentication path, stale claims.
- **Password grant (ROPC) or the app calling `/login`.** Rejected: puts credentials and the MFA, passkey and SSO ceremonies in app code and is removed from OAuth 2.1 direction and RFC 9700.
- **Embedded WebView sign-in.** Rejected: the app sees credentials, and defeats SSO and passkeys (RFC 8252 directs native authorization requests to an external user-agent for this reason; the exact normative wording needs verification).
- **Custom URL scheme redirects.** Rejected: any app can register the scheme (no ownership verification). App links are verified against the host.
- **Loopback redirects.** Not admitted for mobile (RFC 8252 describes loopback redirects mainly for desktop apps, and claimed https links for mobile); desktop is a later question.
- **Implicit flow, or `plain` PKCE.** Rejected here; RFC 9700 steers away from the implicit flow and prefers S256 PKCE (exact normative strength needs verification).
- **Bearer refresh token without DPoP, rotation only.** Rejected: workable but turns every packet loss into a forced sign-in or forces an unsafe retry, and a stolen token is fully usable. Sender constraint makes the bounded retry safe.
- **DPoP optional per client.** Rejected: an optional binding is a downgrade the attacker chooses. It is mandatory for every native client.
- **Device binding by passkey.** Rejected by K16: BE/BS not provable without attestation, a passkey is a user credential.
- **Redis or another cache for `jti`.** Rejected: a new hard dependency for roughly one insert per device per refresh; a LOGGED Postgres table is enough (Redis stays an optional dependency of rate limiting only, ADR-0066).
- **A per-generation refresh-token table.** Rejected (M3): hundreds of millions of rows at 100 000 devices if consumed rows are kept until the family expires; the family row holds `current_hash` and `previous_hash`, which is all reuse detection needs.
- **A single tenant-scoped client table.** Rejected (M1): app identity is host-level and is read without tenant context by the `/.well-known/*` routes and the passkey origin list, which invites `SECURITY DEFINER`, and a tenant action would change a host-level file.
- **Refresh-token reuse "grace" that replays the previous response.** Rejected: needs plaintext or reversible storage of the successor.
- **A `last_seen_at` on native sessions.** Rejected: write amplification on the hottest read (`sql/100`).
- **BFF in `awcms-astro` fronting native apps.** Rejected: persona apps are clients of the public contract (ADR-0146); a BFF would copy the login flows and put a long-lived store of tokens in a site-facing repo.
- **Full OpenID Provider now (discovery, `id_token`, dynamic registration, PAR).** Deferred (Q2): no consumer needs it, and each is an attack surface.
- **Tenant-admin self-service client registration.** Deferred (Q1): the association file and RP are shared by every tenant.

## Decisions on the open questions (owner, 23 Nov 2026, K17)

The owner answered "yes, proceed automatically" to the orchestrator's offer to decide Q1 to Q12 as the security review recommended; this is read as approval and the owner may revoke it. The questions are kept as asked, followed by the decision.

1. **Q1 — Who registers a native client?** Platform-scoped permission only (recommended, section 1), or also tenant admin for redirect and certificate fingerprints, after a platform allow-list of package names is added? **Decision (owner, 23 Nov 2026, K17):** Platform-only for app identity (certificates, package, origins); a tenant admin only lists and disables the bindings of their own tenant in the first release (M1). Reason: host-level trust across tenants (H4).
2. **Q2 — `id_token` and discovery.** Recommended: none in the first release and no OIDC conformance claim. Confirm, or name the consumer that needs them. **Decision (owner, 23 Nov 2026, K17):** Agree: no `id_token`, no discovery, no OIDC conformance claim. Reason: smaller attack surface.
3. **Q3 — Lifetimes.** Access 15 minutes as first proposed, refresh idle 30 days and absolute 90 days, retry window 15 seconds: confirm, or choose from the S2 benchmark. **Decision (owner, 23 Nov 2026, K17):** Access default 60 minutes (range 300 to 3600); idle 30 days; absolute 90 days; retry window G default 30 seconds. Reason: revocation is row-based and the per-request controls still run; 15 minutes only quadruples the writes and the churn of `awcms_sessions` (the 120-minute web session is not re-evaluated either).
4. **Q4 — Absolute family lifetime.** 90 days forces a periodic sign-in with MFA. Acceptable for all persona apps, or per client? **Decision (owner, 23 Nov 2026, K17):** Absolute lifetime per client, set by the platform within 1 to 90 days; tenants may only shorten it; always the minimum with the expiry of any delegated grant. Reason: persona apps differ.
5. **Q5 — Refresh retry window.** Accept the bounded same-key retry (recommended) or revoke on every reuse and accept forced sign-ins after packet loss? **Decision (owner, 23 Nov 2026, K17):** Accept the bounded retry with the lineage rule of M2. Reason: safe because the token is sender-constrained, and lost responses on mobile networks are real.
6. **Q6 — Permission ceiling per client** (courier app limited to a subset of permissions) and desktop clients: out of scope here and need their own ADR because ADR-0063 invariants are touched. Confirm. **Decision (owner, 23 Nov 2026, K17):** Out of scope; meanwhile block delegated and platform principals and expose the ABAC deny attributes (M5). Reason: this only narrows.
7. **Q7 — Platform attestation** (Play Integrity, App Attest) as a registration or per-grant requirement: later ADR, or required before the first production persona app? **Decision (owner, 23 Nov 2026, K17):** A separate ADR, but REQUIRED before a second Android signing publisher on the same host, unless each client has its own callback host (H4). Reason: only attestation proves the identity of the redeeming app.
8. **Q8 — Nonce secret.** A dedicated `AUTH_NATIVE_DPOP_NONCE_SECRET` (recommended) or derived from an existing secret? **Decision (owner, 23 Nov 2026, K17):** A dedicated secret; fail at start when missing or default; two-key rotation; pinned by `config:validate` and `security:readiness`. Reason: blast-radius isolation.
9. **Q9 — One tenant per client, no switching** for native sessions: confirm. **Decision (owner, 23 Nov 2026, K17):** Agree: one tenant per client and no switching; a multi-tenant SaaS app is N bindings. Reason: a simple tenant boundary.
10. **Q10 — Response envelope.** The token and revoke endpoints use RFC 6749/7009 bodies, a documented exception to the AWCMS envelope: confirm. **Decision (owner, 23 Nov 2026, K17):** The envelope exception applies to token and revoke only; resource errors keep the AWCMS envelope plus `WWW-Authenticate: DPoP`; `error_description` comes from a static string table; register the exception in the envelope gate and in the family conformance manifest. Reason: OAuth libraries need the RFC shape.
11. **Q11 — DPoP mandatory for all clients** (recommended) with no bearer fallback: confirm. **Decision (owner, 23 Nov 2026, K17):** Agree: DPoP mandatory, no Bearer fallback. Reason: an optional binding is a downgrade the attacker chooses.
12. **Q12 — `jti` store durability** (UNLOGGED versus logged); the crash-replay analysis of section 6 found UNLOGGED unsafe to rely on. **Decision (owner, 23 Nov 2026, K17):** LOGGED. Reason: about 110 rows per second of WAL is negligible; UNLOGGED has failover semantics and a crash test that is hard to run in CI, and the mitigation first written was wrong (M7).

## Consequences

- **Positive:** native apps get a standard, phishing-resistant sign-in; stolen tokens are not replayable from another device; revocation stays one row; the authorization chokepoint stays unique; no new service; hot path unchanged.
- **Negative / trade-off:** a large new surface in the most sensitive module; platform-level registration is a manual step; DPoP verification per request; the envelope exception; no attestation in the first release.
- **Neutral:** `awcms-astro` and the BFF are unaffected; the consumer contract gains additive native operations, published for consumers through the conformance pack (ADR-0167).

## Implementation outline (after acceptance; written here, not opened as issues)

All slices behind `AUTH_NATIVE_ENABLED=false`. Each is atomic, with the migration, the OpenAPI, the permissions seed, the lifecycle descriptors, the `security:readiness` pins (exact policy expressions plus behaviour probes) and a mutation proof for every new control.

- **S0** (this ADR): Q1 to Q12 decided (K17), security review done (23 Nov 2026). Before Definition of Ready (`alur-pengembangan.md`): the **threat model** (step 3) and a **privacy analysis** of the device label and the IP hash, and the **permission matrix** (step 6), including the tenant list and disable permission names, **seeded for new tenants and backfilled for existing ones** (the ADR-0168 A11 rule) (L9).
- **S1 (waits for ADR-0168 S1 and review):** pure modules only, no endpoints, no schema: PKCE S256 verify, the DPoP proof verifier, token formats and hash namespaces, the family state machine as pure transition functions with a property test, vectors (RFC 7636 and RFC 9449 examples, Wycheproof), red matrix, fuzz.
- **S2:** schema (`awcms_native_apps` global, `awcms_native_clients` binding, request store, codes, families with `current_hash`, `previous_hash` and `credential_epoch`, LOGGED `jti`, columns on `awcms_sessions`, the `origin_auth` CHECK), RLS FORCE on the tenant-scoped tables, `awcms_native_apps` registered as global with its reason, lifecycle descriptors and `subjectData`, **the binding SQL fragment and `scripts/session-readers-check.ts` (H2, same slice as the `dpop_jkt` column)**, the `credential_epoch` helper for families (H1), **the sub-day `awcms_sessions` expiry-purge descriptor (M3, before the flag)**, readiness pins, the `jti` replay test (M7), benchmark and budgets recording rows per day and index size. Red tests: H2 reader matrix, M1 global-table pin, M7 key and logging.
- **S3:** app registry (platform permission, tenant list and disable of bindings), association-file publication on the `APP_URL` host from the global table, the **H4 guards** (one Android signing publisher, iOS `components` per app ID), admin screens listed in `NOT_YET_SCREENED` until built. Red tests: H4 and M1.
- **S4:** `/native/authorize` page, consent on every authorization, request store with the `__Host-` cookie binding (M8), enrolment resume, host gate, no code for delegated or platform-tenant principals (M5), the fallback callback page (L8). Red tests: M8, M5, L8, and an Origin check on the consent form against `APP_URL` (M6).
- **S5:** token endpoint (both grants), revoke, `SESSION_FREE_BODY_ENDPOINTS` entries tested through middleware, rate limits (M4, L10), the `checkOrigin` handling (M6), refresh with the epoch check (H1), the `client_id` and active-client checks plus the client-disable cascade (H3), the lock order and retry rule (M2), the code-replay rule (L7), family expiry `min(configured, grant expiry)` (M5). Red tests: H1 refresh, H3, M2, M4, M6, L7.
- **S6:** resource-side verification in the session resolver, `NATIVE_ALLOWED_OPERATIONS` and the two-sided OpenAPI gate, introspection refusal, the DPoP scheme in `api-body-authentication.ts` (L6), the ABAC attributes `origin_auth` and `native_client_id` (M5). The reader gate itself already landed in S2 (H2); S6 only extends it to the new resource-side verification.

- **S8:** native step-up and native passkey origins (after ADR-0168 S3).
- **S9:** consumer contract fixtures (ADR-0167), a consumer-facing integration note, and the proof of concept hand-off to the Lynx repository (ADR-0146), outside this repository.
