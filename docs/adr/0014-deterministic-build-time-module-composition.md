# ADR-0014 — Deterministic build-time module composition for the base registry and derived applications

- **Status:** Accepted (the derived-application build-time composition path / `application-registry.ts` is superseded by [ADR-0034](0034-awcms-family-direct-use-templates-and-derived-pathway-removal.md); base registry composition still applies)
- **Date:** 2026-07-13
- **Decision-maker:** @ahliweb
- **Related:** Issue #740 (epic #738 `platform-evolution`, Wave 1), Issue #739/ADR-0013, ADR-0011, ADR-0012, `docs/awcms/21_module_admission_governance.md`, `docs/awcms/derived-application-guide.md`, `src/modules/module-management/domain/module-dependency-graph.ts`, `src/modules/module-management/domain/module-composition.ts`

## Context

The module registry (`src/modules/index.ts`) is one static array reviewed through a normal PR (ADR-0012 §7). Until now, the only way for a derived application (AWPOS, Smart School Portal, etc. — `derived-application-guide.md`) to add its own domain modules was to fork/vendor this base repo and then **edit directly** its own copy of `src/modules/index.ts` (ADR-0013 §5, "the pattern already in use"). That is safe while there are only a few derived repos, but it does not scale: every derived repo has to resolve merge conflicts in the same file each time it absorbs a base update, there is no single clear integration point to review, and there is no mechanism preventing a derived application's migration numbers/capability names/module keys from colliding with the base.

ADR-0013 §5 explicitly recorded this gap and deliberately **did not** design it: _"A candidate deterministic replacement mechanism ('deterministic build-time module assembly', Wave 1 of epic #738) does not exist and is not designed by this ADR — this ADR only states that once that mechanism exists, it must still obey the §1 DAG direction and must never let a derived application edit the base registry directly."_ Issue #740 is that mechanism. Before designing it, the following were read as ground truth: `docs/adr/0013-extension-layers-and-boundary-model.md` (extension layers, cross-repo DAG dependency direction, no-shared-table-write), `docs/awcms/21_module_admission_governance.md` (the five admission categories, §7's runtime-loading prohibition), `src/modules/_shared/module-contract.ts` (the `ModuleDescriptor` contract, whose shape is not changed, only additively extended), and `src/modules/module-management/domain/module-dependency-graph.ts` (the existing registry-wide DAG validator, Issue #680, reused not duplicated).

## Decision

### 1. A three-part composition API

- **`listBaseModules()`** (`src/modules/index.ts`) — returns the array of 16 base modules, unchanged in shape/order/content from before this issue.
- **A single build-time extension point, `src/modules/application-registry.ts`** — the only file a derived repo may edit. This base repo itself ships `applicationModuleRegistry: ApplicationModuleRegistry | undefined = undefined`. A derived repo replaces that value with its own `ApplicationModuleRegistry` (`{ id, modules, migrationNamespace? }`, a new type in `_shared/module-contract.ts`) — still 100% ordinary compile-time TypeScript, resolved by `bun run build`/`bun run typecheck` like any other import, **not** runtime discovery/file upload/package scanning/`eval` (this reaffirms the ADR-0013 §9/doc 21 §7 guardrail, it does not loosen it).
- **`composeModuleRegistry()`** (`src/modules/module-management/domain/module-composition.ts`) — merges base + application registry and then validates it, returning `{ valid: true, registry }` or `{ valid: false, registry, issues }`.

### 2. Two deliberately separated phases: merge (always succeeds) vs validate (can fail)

`mergeModuleRegistries(base, application)` is pure concatenation (base first, then the application registry's modules, each preserving its own order) — it **never throws**. `src/modules/index.ts` ONLY calls this function, exactly mirroring the existing architecture (`index.ts` is always pure data; `listModules()` before this issue was `return modules` without any validation — validation is always a separate explicit step invoked by a script/test, precedent `validateModuleDependencyGraph`, Issue #680). Direct consequence: because `applicationModuleRegistry` in this base repo is ALWAYS `undefined`, `mergeModuleRegistries(base, undefined)` is a pure pass-through (`[...base]`) — **the default effective build registry of the base is byte-for-byte identical to before this issue**, proven by test (`tests/unit/module-composition.test.ts`'s "listModules() is byte-identical to listBaseModules()").

`validateComposedModuleRegistry()`/`bun run modules:compose:check` (`scripts/validate-module-composition.ts`) is the actual rule engine — invoked explicitly by CI/tests, never by `index.ts` when modules are loaded.

### 3. Composition failure taxonomy (`ModuleCompositionIssue`)

Four are reused as-is from the existing registry-wide DAG validator (Issue #680), run over the merge result: `self_dependency`, `duplicate_dependency`, `missing_dependency`, `cycle`.

Nine are new in this issue (13 total — corrected from the initial draft of PR #769 which miscounted "seven"/"11"; the code (`ModuleCompositionIssue` in `module-composition.ts`) was always right, this is purely a text correction):

| Issue type                        | Validates                                                                                                      | Design note                                                                                                                                                                                                                                                                                                                                                                                                                            |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `duplicate_module_key`            | Two application registry modules share the same key, not a base key                                            | Reported ONLY when it is not a collision with the base (see the next row) — "the most specific issue wins", the same philosophy as the `self_dependency`/`duplicate_dependency` split in `module-dependency-graph.ts`                                                                                                                                                                                                                  |
| `prohibited_base_override`        | An application registry module uses the same key as ANY BASE module                                            | **Deliberately stricter** than the literal wording of doc 21 §7/ADR-0013 §9 ("Core/System modules cannot be replaced or shadowed") — widened to ALL base modules, not just Core/System, because `ModuleDescriptor.type` is inconsistently populated (9 of 16 base modules `undefined`, doc 21 §8 R1) so a Core/System-only filter cannot be relied on; this stricter superset forbids nothing a derived application legitimately needs |
| `invalid_module_type`             | An application registry module declares `type: "base"` or `type: "system"`                                     | Those two categories are reserved for the reviewed base registry; derived modules must be `"domain"`/`"integration"`/`"derived"`/unset                                                                                                                                                                                                                                                                                                 |
| `capability_provider_conflict`    | Any two modules (base or application) declare the same `capabilities.provides`                                 | The capability namespace must be unique across the whole merged registry                                                                                                                                                                                                                                                                                                                                                               |
| `capability_provider_missing`     | A REQUIRED `capabilities.consumes` (`optional` not `true`) points at a module/`capability` that does not exist | `optional: true` is never checked — matching ADR-0011's graceful-degradation semantics                                                                                                                                                                                                                                                                                                                                                 |
| `migration_namespace_overlap`     | The migration range declared by the application registry overlaps the base range                               | See §4                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `deployment_profile_incompatible` | A module claims `compatibility.deploymentProfiles` unsupported by one of its `dependencies`                    | See §5                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `navigation_path_conflict`        | Two `navigation` entries (from any module) declare an identical `path`                                         | —                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `invalid_job_descriptor`          | Reuses `validateJobDescriptor` (`job-registry.ts`, already existing) over each contributing module's jobs      | Does not duplicate the validator                                                                                                                                                                                                                                                                                                                                                                                                       |

There is no dedicated issue type for the permission catalogue (its namespace is already `${moduleKey}.${activityCode}.${action}`, cross-module collision is structurally impossible) or for health descriptors (`ModuleHealthContract` is just two optional booleans, there is no shape to validate) — both still flow into the composition inventory (§6) so they stay reflected.

### 4. Migration namespace convention

`BASE_MODULE_MIGRATION_NAMESPACE` (`module-composition.ts`) reserves `1-899` for this base repo's migrations (`sql/NNN_awcms_*.sql`) — far above today's real highest number. `ApplicationModuleRegistry.migrationNamespace` (optional) declares the range owned by the derived repo's own `sql/`; composition rejects it if it overlaps the base range. This is purely a comparison of declared data (domain functions stay filesystem-free, consistent with `module-dependency-graph.ts`) — it does **not** read the real `sql/*.sql` files; that remains the responsibility of `scripts/repo-inventory-generate.ts`. Recommendation for derived repos: start your own migration numbering at `900`.

### 5. Deployment profile compatibility metadata

`ModuleCompatibilityContract` (`_shared/module-contract.ts`) is extended ADDITIVELY with `deploymentProfiles?: readonly ModuleDeploymentProfile[]` (the same four values as `src/lib/config/registry.ts`'s `DeploymentProfile`, redeclared locally so the contract file stays dependency-free). Unset = compatible with all profiles (the same absence convention as `minAppVersion`). Composition reports `deployment_profile_incompatible` when a module claims a profile that one of its lifecycle dependencies does not support. No base module populates this field today — the extension is zero-risk to the existing base build.

### 6. Deterministic composition inventory as CI/release evidence

`buildComposedModuleInventory()` + `bun run modules:composition:inventory:generate`/`:check` (`docs/awcms/module-composition-inventory.json`) — a deterministic JSON snapshot (sorted by `key`, no wall-clock timestamp, the same freshness pattern as `repo-inventory.md`) containing every module (key/version/status/type/base-or-application source/dependencies/capability/permission-navigation-job counts/health/deploymentProfiles) plus the base and application migration namespaces. Wired into `bun run check`.

### 7. Existing registry consumers become compose-aware automatically

`listModules()` (used by `bun run modules:sync`, `bun run modules:dag:check`, `bun run repo:inventory:generate`, and every `module-management` service) now returns the result of `mergeModuleRegistries(baseModules, applicationModuleRegistry)`, not the base array directly. Because ALL existing registry consumers call `listModules()` (confirmed by a source audit before implementation — no second/duplicate module array source was found), not one of them needs a code change to become compose-aware automatically once a derived repo populates its own `application-registry.ts` — this is what the acceptance criterion "module-management sync consumes the composed registry, not an unrelated duplicate source" means.

## Consequences

- **Positive:** Derived repos no longer need to edit `src/modules/index.ts`/any base `module.ts` — a single, much smaller integration point (`application-registry.ts`) to review and re-merge each time a base update is absorbed, reducing the class of conflicts described in Context above.
- **Positive:** The migration namespace convention prevents ONE class of migration collision (numbering) via compose-time detection, before any migration file is written — not a full solution (it does not read the real `sql/`), but a real guardrail that previously did not exist at all.
- **Positive:** The default base build (effective registry) does not change at all — proven by a test against the real `listModules()`/`listBaseModules()`, not merely claimed.
- **Negative/trade-off:** Two new contract types (`ApplicationModuleRegistry`, `ModuleMigrationNamespace`) and one extended `ModuleCompatibilityContract` field — purely additive, non-breaking, but they enlarge the `_shared/module-contract.ts` contract surface a new module author must understand.
- **Negative/trade-off:** Cross-repo enforcement of "no shared-table write" (ADR-0013 §6) is **still** not automated by this mechanism — composition validates identity/dependency/capability/migration-namespace/deployment-profile at the DESCRIPTOR level, not real table access across separate processes/repos. It remains as ADR-0013 recorded: cross-repo compliance rests on manual review + the admission checklist, and is not claimed to be machine-enforced.
- **Neutral:** Does not change the `ModuleType` union, does not reclassify any module, adds no new SQL migration (composition is purely at the TypeScript descriptor level, in-memory), adds no new endpoint/event.

## Alternatives considered

- **Runtime plugin loading / dynamic import from an env-var-configurable path** — rejected explicitly: it directly contradicts the hard prohibition of doc 21 §7 and ADR-0012 §7 (no runtime code loading without a new ADR superseding ADR-0001/ADR-0002; this issue does not propose that supersede).
- **One merged array with no dedicated validation (merge only, no `validateComposedModuleRegistry`)** — rejected: it does not satisfy the acceptance criterion "duplicate key/missing dependency/cycle/missing capability/conflicting provider/prohibited Core override each fail with actionable diagnostics".
- **Restricting the `prohibited_base_override` filter to `type: "core"`/`"system"` modules (copying the guardrail's literal wording as-is)** — rejected: `type` is inconsistently populated in today's base registry (doc 21 §8 R1), so a loose rule could be bypassed by a base module that happens not to set `type`. The stricter rule (all base modules) was chosen because it is a strict superset of the requested guardrail and forbids no legitimate derived scenario.
- **Having migration namespace validation read the real `sql/*.sql` files inside the composition domain function** — rejected: it violates the "domain = pure, no I/O" convention already established by `module-dependency-graph.ts`; comparing declared data is enough to detect the most common collision class (two uncoordinated derived repos), and real filesystem reads stay the domain of `repo-inventory-generate.ts`.
- **Putting the validation engine in `_shared/` instead of `module-management/domain/`** — rejected: it would invert the dependency direction (`_shared/module-contract.ts` is deliberately import-free from the start; `module-management/domain/module-dependency-graph.ts` is already the established owner of registry-wide validation, reused not moved).
