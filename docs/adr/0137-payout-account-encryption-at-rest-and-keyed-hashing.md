# ADR-0137 — Payout-account encryption at rest, keyed hashing, and audited reveal (decided before the table exists)

- **Status:** Accepted
- **Date:** 2026-10-12
- **Decision maker:** ahliweb
- **Related:** Issue #955 (docs only; implementation is a later issue, #959); [`docs/awcms/hr-payroll.md`](../awcms/hr-payroll.md) §1 (phase 3 gate), §7.1, §9, §13; ADR-0132 (the `hr_payroll` family and its phase 3 gate); ADR-0128 (supplier identifiers: the unkeyed hash, the reveal action, and the follow-ups this ADR answers for payout accounts); ADR-0058 §E (a step-up must be conditional); ADR-0123 (backup encryption); downstream epic `ahliweb/awcms-one#280` item 25

## Context

ADR-0132 admitted `hr_payroll` but gated phase 3 on, among other things, "payout-account at-rest encryption decided". `awcms_hr_payout_accounts` will hold, per employment, the bank or wallet account an employee is paid into. It is classified `sensitive` (hr-payroll.md §9): its disclosure enables fraud against a named person, and under UU PDP 27/2022 it is personal data.

**What the repository does today, verified in code (not assumed):**

- **Reversible encryption of a recoverable secret** exists three times, each a near-identical copy: `src/lib/auth/mfa-secret-crypto.ts` (TOTP seed), `src/lib/auth/sso-credential-crypto.ts` (OIDC client secret, called from `src/modules/identity-access/application/auth-provider-directory.ts`) and `src/modules/comments/domain/subscriber-crypto.ts` (subscriber address). All are AES-256-GCM, `v1:<iv>:<tag>:<ciphertext>` (base64), a 32-byte base64 key from a **dedicated env variable per dataset** (`AUTH_MFA_SECRET_ENCRYPTION_KEY`, `AUTH_SSO_CREDENTIAL_ENCRYPTION_KEY`, `COMMENTS_SUBSCRIBER_ENCRYPTION_KEY`, declared `secret: true` in `scripts/validate-env.ts`), fail-closed key resolution (no key returns `null`, never a default), and a deliberate rationale: separate keys so one compromise exposes one dataset, and a database backup alone yields no usable secret. **Gaps for this use:** the format carries a version but **no key id** (so a key cannot be rotated without re-encrypting everything in one step), there is **no associated data** (a ciphertext copied from one row to another still decrypts), and there is a single key, not a ring.
- **Keyed hashing** exists as HMAC-SHA256 with a dedicated secret: `hashClientIp` in `src/lib/security/client-fingerprint.ts` (`AUTH_IP_HASH_SECRET`, with a placeholder-secret guard), `src/modules/visitor-analytics/domain/visitor-key.ts`, `src/modules/sync-storage/domain/sync-hmac.ts`. Their stated reason is the one that matters here: a low-entropy input hashed without a key is reversible by exhaustion.
- **The unkeyed hash that must not be repeated:** `hashIdentifierValue` (`src/modules/profile-identity/domain/identifier.ts`, plain `createHash("sha256")`), reused by procurement (`src/modules/procurement/domain/procurement-identifier.ts`). ADR-0128 recorded, in so many words, that this hash of a low-entropy identifier "can be brute-forced by anyone who can read the table", stores `normalized_value` in plaintext, and left "keyed hashing and at-rest encryption" as a follow-up that "needs a key-management decision". A bank account number is shorter and lower-entropy than a tax id. Copying the supplier-identifier pattern, as hr-payroll.md §7.1 first sketched, would knowingly ship the weakness ADR-0128 disclosed.
- **Reveal and step-up:** the procurement reveal (`suppliers.reveal`, HIGH-RISK `AccessAction`, `no-store`, audit at `warning` recording that a disclosure happened and never what) is the pattern; ADR-0128's own audit noted it is **not** step-up gated or rate limited. The step-up mechanism is `requireStepUp` in `src/modules/identity-access/application/mfa-session-assurance.ts` (denies `403 STEP_UP_REQUIRED` unless the session is `aal2` and recently stepped up, TTL `AUTH_MFA_STEPUP_TTL_SEC`). It already has a correct _conditional_ caller, `src/modules/identity-access/application/password-change.ts`, which applies it only to a person who has enrolled a factor, because an unconditional `requireStepUp` permanently locks out everyone without MFA (the ADR-0058 §E trap).
- **Backups:** ADR-0123 encrypts the backup artefact with `BACKUP_ENCRYPTION_KEY_FILE` and authenticates its manifest; that key is operational and separate from application keys.

Nothing in this ADR is implemented. There is no table, no helper, no env variable and no migration yet.

## Decision

### 1. What is encrypted, and what is only hashed

For each payout account the table stores **no plaintext of the account number**. It stores:

| Column                                        | Content                                                                                                               | Purpose                                      |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `account_ciphertext`                          | AES-256-GCM ciphertext of the normalized account number (§2)                                                          | the only recoverable copy; read by `reveal`  |
| `account_hash`, `hash_key_id`                 | keyed HMAC of the normalized value (§3)                                                                               | equality lookup and duplicate detection only |
| `account_mask`                                | display mask: last 4 characters; a value shorter than 8 characters is masked entirely, no tail (the ADR-0128 L3 rule) | the only form any list or read returns       |
| `holder_name`, `bank_code` (or wallet scheme) | **not** encrypted here; classified `confidential`, in `redactedColumns`; not part of the account number secret        | needed to render and to route payment later  |

The deliberate difference from ADR-0128: **there is no `normalized_value` column**. The plaintext exists only in memory on the request that writes it, and in memory on the request that reveals it. `account_ciphertext`, `account_hash` and `account_mask` are all in `redactedColumns` of the module descriptor and never appear in a response (except the mask in a masked read), a log line, an audit row, an event payload or an export.

### 2. Algorithm, format and key management: one shared AEAD helper with a key ring

We decided to **reuse the repository's existing mechanism (AES-256-GCM, 32-byte base64 key, fail-closed resolution, one dedicated env variable, `secret: true` in `scripts/validate-env.ts`) and fix its two gaps in one new shared helper**, `src/lib/security/field-encryption.ts` (name indicative; created by the implementing issue). It does not edit the three existing copies, whose stored `v1` rows must stay readable; migrating them to the helper is a separate decision (§Consequences).

- **Format:** `v2:<keyId>:<iv>:<tag>:<ciphertext>`, base64 segments, 12-byte random IV per encryption. The `keyId` is stored **inside the value**, so a database copy is self-describing and rotation needs no schema change. The decryptor rejects any other version rather than guessing.
- **Associated data (AAD):** the GCM authenticated data is `hr_payout_account:v1|<tenant_id>|<account_id>`. A ciphertext moved to another row or another tenant fails authentication. The row id is generated in the application before the insert so it is known at encryption time.
- **Key ring:** `HR_PAYOUT_ENCRYPTION_KEYS` = `keyId:base64key` pairs separated by commas; the **first** is the active key used to encrypt, **all** are accepted for decrypt (for example `k2:…,k1:…`). Each key is exactly 32 random bytes (`openssl rand -base64 32`), key ids are short ASCII labels. This variable is `secret: true`, has **no default**, is required whenever the `hr_payroll` module is enabled for a tenant, and is validated by `scripts/validate-env.ts` as the three existing keys are. It is separate from every other key in the repository, so a leak of one dataset's key does not expose the others (the existing rationale).
- **Rotation:** (1) generate `k2`, prepend it to the ring and deploy: new writes use `k2`, old rows still decrypt under `k1`; (2) a background re-encryption job (bounded batches, run under the tenant context, idempotent, audited as a system action with counts only) decrypts each row and re-encrypts under the active key, updating `account_ciphertext` in place; (3) when a read-only query over the `keyId` prefix of `account_ciphertext` shows no row left on `k1` **in the database and in every retained backup within the retention window**, `k1` may be dropped from the ring. A key id is **never deleted while any retained backup that matters for restore still holds rows under it**. Compromise-driven rotation is the same procedure, run immediately, and additionally rotates the hash key (§3).
- **Not in v1 of this decision:** an external KMS or envelope encryption (see Alternatives). The helper takes its keys from a small `resolveKeyRing()` seam so a KMS-backed provider can replace the env source later without changing the stored format or any caller.

### 3. Keyed hashing for lookup and duplicate detection

`account_hash = HMAC-SHA256(hashKey, tenant_id ‖ 0x00 ‖ scheme ‖ 0x00 ‖ normalized_value)`, hex, stored with `hash_key_id`. The key is a **separate** secret `HR_PAYOUT_HASH_KEYS` (same ring shape, same rules; first is active), never the encryption key and never `AUTH_IP_HASH_SECRET`. Binding `tenant_id` means the same account in two tenants produces unrelated hashes (no cross-tenant correlation). This is the primitive the ADR-0128 follow-up (3) asked for, here applied to payout accounts only.

- **Use:** a unique constraint per employment on `(tenant_id, employment_id, account_hash)`; and detection that the same account is attached to more than one employment (a recognised payroll-fraud signal, "ghost employees sharing an account"). Detection is an equality lookup on the hash, restricted to the actor who holds the update permission, and its response is **uniform** (an add returns the same acknowledgement whether or not a duplicate exists, the ADR-0128 M1 rule), so it is not a value-equality oracle. Whether a cross-employment duplicate blocks or only flags is an implementation-time rule (the issue, with an owner question if it is not obvious); this ADR fixes only that the hash cannot be reversed without the key.
- **Limits:** equality only. No prefix, suffix or fuzzy search; a search by last 4 digits uses the stored mask or is not offered.
- **Hash-key rotation** needs the plaintext, so it is done by the same re-encryption job decrypting, re-hashing under the new active hash key, and writing `account_hash` and `hash_key_id` together. During the overlap a lookup computes the hash under each key id present and matches either. `hash_key_id` makes that explicit.

### 4. Masked display, reveal, step-up

- Every list, detail and export surface shows **only** `account_mask`. A masked read needs `payout_accounts.read`.
- **Reveal** is `POST …/payout-accounts/{id}/reveal`, its own permission `payout_accounts.reveal` and a HIGH-RISK `AccessAction` (the procurement `reveal` pattern; hr-payroll.md §11), authorized through `authorizeInTransaction` (ADR-0063), granted to **no** role by the migration. The response is `Cache-Control: no-store`. The handler writes an audit row at `warning` recording **that** a disclosure happened, who, and which account id, **never** the value, its hash or its mask-derived text.
- **Step-up is conditional, not unconditional** (ADR-0058 §E; hr-payroll.md §14 left it "decided conditionally"). The gate is `requireStepUp` (`mfa-session-assurance.ts`), applied exactly as `password-change.ts` applies it: **required when the acting principal has an enrolled MFA factor** (`getMfaStatus`), not demanded of a person who has none. A reveal by an actor without MFA is therefore allowed on the permission alone and is recorded in the audit row with `stepUp: "not_enrolled"` so a reviewer sees which reveals were not second-factor protected. A tenant that wants reveal to be impossible without MFA enforces it through its existing MFA policy (`src/pages/api/v1/auth/mfa/policy.ts`), not through a rule here. The step-up is evaluated **before** the decryption, so a refusal reveals nothing.
- **Rate limit:** reveal is limited per actor and per tenant per window (a count of recent `reveal` audit rows or the repository's existing rate-limit mechanism, chosen by the implementing issue), so a holder cannot enumerate every employee's account at API speed, which ADR-0128 recorded as an open follow-up for suppliers. Exceeding it is `429`, itself audited.
- **Separation:** `payout_accounts.update` (add/remove, sees masks) and `payout_accounts.reveal` are different permissions held by different roles by default; the SoD matrix (hr-payroll.md §7.5, ADR-0132 amendment) decides whether the reveal holder may also run payroll.

### 5. Missing or wrong key: fail closed, never a plaintext fallback

- **No usable key ring at write time:** the write is refused (`503`-class error code `PAYOUT_ENCRYPTION_UNAVAILABLE`); nothing is stored and **no sentinel or plaintext is written**. This differs on purpose from `COMMENTS_SUBSCRIBER_ENCRYPTION_KEY`, where a missing key degrades a nice-to-have notification: a payout account is mandatory data and storing it unprotected is the one outcome this ADR forbids. The module's health check reports `degraded`, and `bun run security:readiness` (the existing gate that checks the other keys) gains the same check when the implementing issue lands.
- **Decryption failure** (unknown `keyId`, authentication failure, malformed value, AAD mismatch): `reveal` fails closed (a uniform error, an audit row at `warning` recording the failure class, no partial data); callers treat any throw as "cannot decrypt", never "empty". Masked reads keep working because the mask is stored.
- **Payroll runs and payslips never need the plaintext.** Calculation uses compensation, not the account number; only a later payment step does (§7), and it is out of scope here.

### 6. Backups and restore

- The **encryption keys are never in the database and never in a database backup.** They live in the deployment secret store (as the three existing keys do) and are backed up **separately** from the data, with separate access, so that neither a stolen dump nor a stolen key file alone is enough. This is the same property the existing crypto comments claim ("a database backup alone yields no usable secret").
- Column encryption **does not replace** backup encryption (ADR-0123): the backup artefact stays encrypted with its own key, because a dump also contains data that is not column-encrypted.
- **Restore into an environment without the key ring:** the database restores and works; masked reads, search by mask, lookup by hash (only if the hash ring is present) and every non-payroll function operate; **`reveal` and re-encryption fail closed**. That is the intended outcome of a stolen or misplaced dump, and it is how a restore to a scratch environment must behave.
- **Restore with an older backup:** rows may carry a `keyId` that has since been rotated out. The ring must therefore retain every key id that any restorable backup still needs (§2, the retention rule above); the restore runbook lists this as a check.
- **Restore rehearsal** (a phase 3 gate, hr-payroll.md §1) must include both cases: restore **with** the ring and prove a reveal works and an AAD-bound ciphertext still authenticates; restore **without** it and prove reveal fails closed while masked reads work.
- **Key loss** is data loss for the ciphertext: an account must be re-entered by its owner. This is stated to the operator, not hidden, and is the price of not storing a recoverable plaintext.

### 7. Explicitly out of scope

**No payment-provider call, no bank file, no disbursement and no outbound transfer of an account number is decided or enabled here.** Any such integration is a later issue and goes through the outbox, outside a database transaction (AGENTS.md; hr-payroll.md §1 "Out of scope"). When it is built, the component that needs the clear value will decrypt it in memory for that one operation under its own high-risk permission and audit, never log it, and never place it in an outbox payload in clear (the outbox payload carries the account id; the dispatcher resolves it).

### Implementation note (2026-10-12, Issue #986)

The shared helper `src/lib/security/field-encryption.ts` landed and refines the wording above without changing the decision:

- **AAD and hash input encoding.** Instead of the `|`- and NUL-joined strings written in sections 2 and 3, the helper uses a length-prefixed canonical encoding (a 4-byte big-endian length before each UTF-8 field, led by a fixed label), which is unambiguous across field boundaries. The AAD covers `purpose`, `tenant_id` and the row id; the hash input covers `purpose`, `tenant_id` and the value. The `scheme` of section 3 folds into `purpose` (for example `hr_payout_account:v1:bank`). Consumers pass a `purpose` string; the exact bytes are an implementation detail covered by the helper's tests.
- **Key rules.** Encryption and hash rings resolved through `resolveKeyRing` require exactly 32 bytes of canonical base64; the legacy parser (at least 32 bytes) remains only for the WhatsApp recipient-hash ring.
- **Encryption and hash keys must differ.** The helper cannot know a consumer's two variables, so each consumer's `scripts/validate-env.ts` entry must enforce that its encryption ring and hash ring share no key.
- **Rotation limit.** AES-GCM with random 96-bit IVs is safe for roughly 2^32 encryptions under one key; rotate a key well before that many writes (not a concern at payroll or chat-id volumes, but the bound is the reason rotation exists).

## Consequences

- **Positive:** an account number is protected by something other than RLS and discipline; a dump alone is useless; a copied ciphertext does not authenticate; rotation is possible without downtime because the key id travels with the value; the hash cannot be brute-forced from the table; the reveal path is audited, conditional-step-up and rate limited; the helper is reusable by the next sensitive field.
- **Negative / trade-off:** a **fourth** encryption helper exists beside the three `v1` copies until they migrate (they cannot be edited in place without a data migration; whether to converge them is its own issue and ADR); rotation is a job someone must run and verify; **key loss is unrecoverable data loss**; keys live in env, so a host compromise that reads the process environment reads both ciphertext access and key (a KMS would narrow this; see Alternatives); the `v2` format is not readable by the older helpers, deliberately.
- **Neutral:** this fixes the payout-account design only. It does **not** change the unkeyed `hashIdentifierValue` in `profile_identity` or procurement (ADR-0128 follow-up (3) remains open for those; the new helper is the primitive that follow-up can adopt); it adds no code, table, migration, OpenAPI path or AsyncAPI channel. Nothing is implemented by this ADR; implementation is issue #959 and must follow it.

## Alternatives considered

Security / performance / operational complexity are assessed together per option.

- **A. Copy an existing `v1` helper again with a new env key (no key id, no AAD).** _For:_ zero new design, identical to three precedents, trivially reviewed. _Against:_ cannot rotate without a flag-day re-encryption, a ciphertext is swappable between rows, and the repository would acquire a fourth copy of the same functions. _Security:_ weakest of the viable options. _Performance:_ identical (AES-GCM, microseconds). _Operations:_ simplest to start, painful the first time a key must change. **Rejected** because rotation is the property a payroll dataset most needs.
- **B. Shared `v2` helper with key id, AAD and a key ring in env (chosen).** _For:_ reuses the proven primitive, rotation and swap-resistance, no new runtime dependency (`node:crypto` as in the existing helpers; Bun-compatible), works in the offline/LAN profile with no network, fits the existing `validate-env`/readiness gates. _Against:_ keys in process memory and env; rotation job to write; one more helper. _Security:_ good; bounded by host secrecy. _Performance:_ negligible (one AEAD op per write or reveal, no extra round trip). _Operations:_ moderate, a documented procedure.
- **C. Database-side `pgcrypto` (`pgp_sym_encrypt`).** _For:_ encryption next to the data. _Against:_ the key travels inside SQL text and can land in `pg_stat_statements`, server logs and error messages; the database host becomes the key holder, which defeats "a database backup alone yields nothing"; it bypasses the Bun.SQL parameter discipline; no AAD binding to the application row. _Security:_ worse than B. _Performance:_ similar. _Operations:_ simple, but it moves the secret to the wrong tier. **Rejected.**
- **D. External KMS or envelope encryption (cloud KMS, Vault) with a per-record data key.** _For:_ strongest key custody, audited key use, native rotation, no key in app env. _Against:_ a new runtime dependency and an outbound network call on every reveal (the offline/LAN profile and ADR-0006's provider-optional posture), cost, an availability coupling of payroll to the KMS, and a provider choice the family has not made. _Security:_ best. _Performance:_ one network round trip per operation unless data keys are cached. _Operations:_ highest. **Deferred, not rejected:** the `resolveKeyRing()` seam in §2 is where it plugs in, and the stored `v2` format already carries the key id an envelope scheme needs.
- **E. No encryption; rely on RLS, role privileges and redaction (the ADR-0128 status quo).** _For:_ nothing to build. _Against:_ a database reader, a backup, a replica or a mis-granted role reads every account in clear; the repository's own audit of ADR-0128 named this a weakness. _Security:_ unacceptable for bank data. **Rejected** (this is exactly what the phase 3 gate exists to prevent).
- **Hashing, for the lookup column:** an **unkeyed SHA-256** (the ADR-0128 pattern) is reversible by exhaustion for a short numeric account and **rejected**; an HMAC under the **same** key as the encryption **rejected** (one key, two roles; a use of the key to compute oracles can be confused with decryption use, and it widens the rotation coupling); a slow password hash (argon2id) is not a deterministic lookup, so it cannot detect duplicates, **rejected**; **an HMAC under a separate, tenant-bound key (chosen)** is cheap, deterministic, and unreversible without the key.
- **Step-up, for reveal:** unconditional `requireStepUp` **rejected** (ADR-0058 §E: it locks out everyone without an enrolled factor); no step-up at all (the procurement state) **rejected** for the most sensitive reveal in the family; **conditional on an enrolled factor, with the "not enrolled" case recorded in audit and enforceable through the tenant MFA policy (chosen)**.
