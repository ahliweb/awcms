# ADR-0141 — A permission may require an enrolled MFA factor to be exercised

- **Status:** Accepted
- **Date:** 2026-10-14
- **Decision maker:** @ahliweb
- **Related:** Issue #977 (this ADR and its implementation; finding PS-13 of the phase-3 security review of [`docs/awcms/hr-payroll.md`](../awcms/hr-payroll.md) §17); [ADR-0027](0027-mfa-totp-session-assurance-step-up.md) (MFA, session assurance, the tenant MFA policy); [ADR-0087](0087-mfa-moves-to-the-principal.md) (the factor belongs to the person); [ADR-0053](0053-platform-scoped-permissions.md) (the precedent for a code-declared permission property enforced at the chokepoint); [ADR-0031](0031-segregation-of-duties-conflict-enforcement.md) (the precedent for an additive, deny-only chokepoint check); [ADR-0136](0136-configurable-payroll-segregation-of-duties-mode.md) §3 and [ADR-0137](0137-payout-account-encryption-at-rest-and-keyed-hashing.md) §4 (the two decisions whose step-up this makes load-bearing); blocks the acceptance wording of #959 and #960; refs #956

## Context

ADR-0136 §3 and ADR-0137 §4 apply step-up to the payroll-critical actions **conditionally**: required when the acting person has an enrolled factor, not demanded of a person who has none. That is the right shape, for the reason `password-change.ts` already spells out — `requireStepUp` denies any session that is not currently `aal2`, and a person with no factor can never reach `aal2`, so an unconditional step-up permanently locks out everyone without MFA.

The consequence was finding PS-13: **a holder with no enrolled factor performs reveal, relax-SoD, approve, finalise, pay and reverse with no second factor at all.** Both ADRs say a tenant "enforces it through its existing MFA policy", and that does not hold up:

- The tenant policy (`awcms_tenant_mfa_policies`, ADR-0027) is `optional` by default and is a setting for the **whole tenant**, decided by whoever administers it, not by the module whose permissions are at stake.
- `required_for_privileged` classifies "privileged" as holding **any** permission whose action is not `read`/`analyze`/`check`. It is enforced **at login** (an enrolment grant instead of a full session), so it asks every non-read holder in the tenant to enrol — a heavy lever for "the six permissions that move money" — and it says nothing at the moment of exercise.
- Nothing, anywhere, connects "this permission" to "its holder must be able to give a second factor". No issue built that, so the sentence in the ADRs described a control that did not exist.

> **A note on the citation.** The repository (ADR-0136, ADR-0137, `password-change.ts`) cited "ADR-0058 §E" for the rule _step-up must be conditional_. ADR-0058 as written is about four permissions with no enforcer, and its §E is the revocation migration; what it contributes is the **class** of trap — a requirement that nothing can satisfy denies everyone, while the call site reads as correctly guarded. The rule is correct; this ADR states it in its own words (§4) so that it no longer rests on a section that does not say it.

## Decision

### 1. A permission declares the requirement; the chokepoint enforces it at exercise

`ModulePermissionDescriptor.requiresMfaEnrolment?: boolean` (`MODULE_CONTRACT_VERSION` **4.3.0**, MINOR: purely additive, omitting it means "no requirement", which is what every existing descriptor meant). In `authorizeInTransaction`, **after** an ordinary decision has allowed, a request for a flagged permission is refused when the acting person has no **active** factor:

`403 MFA_ENROLMENT_REQUIRED`, with `details.reason` of `not_enrolled`, `enrolment_unavailable` or `machine_credential`, and a message that says what to do (see §3). It is recorded as **one** decision-log row (`deny`, `matched_policy = mfa_enrolment_required`), not an allow followed by a contradicting deny.

It is **deny-only** and runs only on a decision that already allowed: a caller who lacks the permission gets plain `ACCESS_DENIED` and learns nothing about the action or what it needs; and no grant, ownership basis or policy can make an unenrolled caller pass it. Enrolment is read fresh on every flagged decision and is never memoised in the authorization read cache — a self-service disable or an administrative reset must take effect on the very next request.

`evaluateFieldAccessInTransaction` applies the same check, so a field gated on a flagged key is not a way round the endpoint; it learns whether the request is a machine credential from the authorised context (`authorizeInTransaction` stamps `viaMachineCredential`), not from an argument a caller could omit. `POST /api/v1/access/evaluate` applies it to the caller's own enrolment so the preview agrees with the endpoint. An any-of caller (`defineTenantRoute`, `loadAdminScreen`) surfaces `MFA_ENROLMENT_REQUIRED` in preference to a sibling candidate's generic `ACCESS_DENIED`. The injected-keys test seam is **additive only** (unioned with the registry), so it can never narrow enforcement. There is **no migration**: the flag is declared in code and never read from a database column, for the reason ADR-0053 §3 gives for `scope` — a flag a row could clear is a requirement one `UPDATE` removes while every check stays green.

The early warning grant-time refusal would have given is provided instead by a **readiness report** (§5), which can list every holder — from every grant source, through the same `activeRoleGrants` fragment the chokepoint uses — without being a second enforcement point.

### 3. What the three refusals say, and why they differ

- **`not_enrolled`** — the person can fix this now: the message names `/admin/account`, which needs a session and no permission.
- **`enrolment_unavailable`** — `AUTH_MFA_ENABLED` is off, so nobody on the deployment can enrol. The message names an administrator rather than a screen that cannot help. This is **fail-closed**, deliberately unlike ADR-0027 §9 (where an unenforceable _login policy_ was left inert): an inert flag here would silently re-open the hole it exists to close on the deployments least likely to have noticed. The readiness report makes the configuration a go-live finding (§5).
- **`machine_credential`** — a credential can never hold a factor, and the account it is bound to may be a person who has one, so "enrolled" would be true of a request in which nobody presented anything. Refused outright; the message says no remedy exists for it.

### 4. Step-up stays conditional; this is not an unconditional step-up

The gate asks whether a factor **exists**. It never demands a fresh proof, never calls `requireStepUp`, and a test pins that. The rule from ADR-0136/0137 is unchanged and now has teeth:

| Person                  | Before                             | After                                                                                      |
| ----------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------ |
| No factor               | allowed, no second factor, audited | **refused with the way to enrol** (not locked out: every unflagged permission still works) |
| Enrolled, stale session | step-up required                   | step-up required                                                                           |
| Enrolled, fresh session | allowed                            | allowed                                                                                    |

The owning module keeps calling `getMfaStatus` + `requireStepUp` exactly as `password-change.ts` does; with the flag set, the condition ("has a factor") is no longer something a person can avoid by simply not enrolling.

### 5. Bootstrap, and the readiness report

**A tenant with no enrolled holder is not locked out.** Enrolment (`POST /api/v1/auth/mfa/totp/enroll/{start,verify}`) needs a session and no permission, and sits outside the chokepoint (pinned by a test), so the way to un-refuse yourself cannot itself be refused. The bootstrap is: the owner (or any holder) enrols in `/admin/account`; the very next request is served — no restart, no admin action, no policy change. Everything unflagged keeps working throughout, which is what lets the person reach the enrolment screen at all.

`bun run security:readiness` gains two checks:

- **MFA enrolment is available when a permission requires an enrolled factor** — `critical`. If any module flags a permission and `AUTH_MFA_ENABLED` is not `true`, nobody can satisfy it and every flagged action is refused for everyone.
- **Holders of permissions that require an enrolled MFA factor are enrolled** — `warning`, never `critical`. Lists the tenants with a holder who has no active factor (ids and counts only, no names), restricted to tenants where the module is actually usable (a disabled module's holders cannot exercise anything, and listing every tenant's owner for a module nobody there can reach is noise). A holder in that state is not a vulnerability — the chokepoint already refuses them — they are a person about to be asked to enrol, and a gate that blocked go-live on it would make enrolment a precondition of deploying, which is the lockout this ADR avoids.

Both pass loudly, with their reason, while no module flags anything (the state this base ships in).

### 6. What `hr_payroll` must do when it lands

Set `requiresMfaEnrolment: true` on exactly these permissions in its descriptor (spelling per the §9 catalogue of the pack at that time — the matrix spells the action `finalise`):

`payout_accounts.reveal`, `runs.approve`, `runs.finalise`, `runs.pay`, `runs.reverse`, `compensation.approve`, `sod_policy.configure`, `rules.publish`.

Not flagged, on purpose: `calculate`, `lock`, `release` and the `read`/`create` family — flagging a routine permission is a lockout the tenant did not choose. The implementing issues must (a) set the flag, (b) keep calling the conditional step-up, and (c) carry a test for each flagged permission that an unenrolled holder receives `403 MFA_ENROLMENT_REQUIRED` and an enrolled one with a stale session receives `403 STEP_UP_REQUIRED`. The acceptance wording for #959 and #960 is updated accordingly (see `hr-payroll.md` §17, PS-13).

## Consequences

- **Positive:** a control of the kind ADR-0136/0137 pointed at now exists (see the first negative bullet for how much it proves); one enforcement point covers every grant path; a new module protects its own permissions without touching `identity_access`; no migration, no new table, no tenant setting to forget; zero cost for an unflagged request (a `Set` lookup); the refusal is a way forward, not a lockout.
- **Negative / accepted trade-offs:**
  - **The gate proves a factor EXISTS on the account, not that the account's owner holds it.** A party who has an unenrolled holder's password can sign in, enrol their own authenticator, and then pass the gate (and the conditional step-up) as that holder. The requirement closes the "no second factor at all" hole of PS-13; it does not by itself defend against password theft before the legitimate holder has enrolled. Enrolment was hardened afterwards (§7, #1004): a **session alone can no longer start it**, and the owner is notified out of band, so a stolen session cannot do this and a password-holder can no longer do it silently. What remains is operational and belongs before the first payroll permission is usable: run the holders readiness report (§5) **before enabling `hr_payroll` for a tenant** and have the legitimate holders enrol first, so that the first factor on every holder's account is theirs.
  - A flagged permission can still be **granted** to an unenrolled person. They find out at first use, and the readiness report finds them earlier. This is the price of §2's rejection of grant-time refusal.
  - A flagged request costs two keyed reads (identity → principal → active factor). Only flagged requests pay.
  - With `AUTH_MFA_ENABLED` off, a flagged permission is refused for everyone. This is deliberate and surfaced as a `critical` readiness finding; a deployment that wants payroll must enable enrolment.
  - A person who disables their own factor (or whose factor an administrator resets) loses the flagged permissions on the next request. That is the point, but it is also a reason for an enrolled holder to keep their recovery codes.
  - The roles screen does not yet mark which permissions require enrolment. A follow-up.
- **Neutral:** `MODULE_CONTRACT_VERSION` 4.2.0 → 4.3.0 and the family manifest follow it. No base module sets the flag, so the in-repo blast radius is zero by construction; the first user is `hr_payroll` (#957, blocked on its DPIA).

## Alternatives considered

- **Make payroll step-up unconditional** — rejected (§4): it locks out everyone without a factor, permanently, including the tenant owner.
- **Tell tenants to set `required_for_privileged`** — rejected as the answer (§2 D): it is the status quo ADR-0136/0137 pointed at, and it is what left PS-13 open.
- **Enforce on the permission's _role_ (a role flagged "needs MFA")** — rejected: the permission is the unit that is dangerous, and a role is something a tenant edits freely; a requirement on the role disappears when someone grants the permission through another role.

## 7. Addendum (#1004, audit finding F-3 of #977): enrolment is hardened against takeover

**Problem.** `enroll/start` accepted any live session. A session is a bearer credential that outlives the moment it proved anything, so whoever held one for an unenrolled account could enrol their own authenticator and thereafter pass every conditional step-up as that account.

**Decision.**

1. **A session-authorized `enroll/start` must re-authenticate with the CURRENT password.** The caller presents `currentPassword`; a session-only attacker does not have it. It applies to **every** identity, not only holders of flagged permissions: whether an account will one day hold a flagged permission is a grant-time fact that changes, and a rule that depends on it would leave the same hole open on any account granted one later. The UX cost is one password field on a rarely used screen.
   - **One verifier, the login rule.** The check is `verifyCurrentPassword` (`current-password.ts`): the principal's credential once one has been promoted, else the identity's own hash, exactly as `login.ts` decides. Reading `awcms_identities.password_hash` directly is wrong: since ADR-0086 that is a per-tenant copy that goes stale when the password is changed from another tenant, so the old password would be accepted and the new one refused. (`password-change.ts` has the same defect and is fixed separately, #1035, reusing this verifier.)
   - **Failures count.** A wrong password increments the principal's GLOBAL lockout, like a failed login; a locked principal is refused (`429`) before any hash is verified. Trade-off accepted: someone holding only a stolen session can therefore lock the victim's sign-in for the lockout window; that is the same exposure a failed login already has, and it is bounded by the buckets below.
   - **Rate limits.** Per session (a bucket on the bearer's own hash, so rotating addresses does not help) and per source (spent only after the session is known to be valid, so junk tokens cannot burn a shared address's allowance): 10 attempts per 15 minutes each. `password/change` keeps its own source bucket; sharing one bucket across the two was considered and not done here.
2. **A fresh SSO session re-authenticates by freshness only when the person works in no other tenant.** An SSO identity has no password to present and the IdP just authenticated the person, so a session minted by the IdP within 5 minutes stands in for the password. But the factor is PRINCIPAL-global (ADR-0087) and ADR-0088 rejects one tenant's IdP vouching for a person across tenants (tenant B's IdP administrator can assert `alice@corp.com`). So the exemption holds only if `awcms_principal_has_other_tenant_identity` (`sql/261`, a narrow SECURITY DEFINER boolean: no id, no count) says the principal has no identity elsewhere. Otherwise the principal's password is required like any other session. An identity not yet linked to a principal fails closed (it is linked by address on enrolment and may already work elsewhere), and the password is verified the way login does it, by address. If password login is disabled for the identity (or no password exists) there is nothing to present: `403 REAUTHENTICATION_REQUIRED`, resolved by an administrator (reset the person's MFA / allow a password sign-in) - never by trusting the IdP. Residual: a thief of a fresh SSO session of a single-tenant person, inside the 5 minutes, can enrol; accepted, because that thief already controls the person's IdP session.
3. **An enrolment grant waives the password only when a login that just verified it minted the grant.** Each grant carries its origin (`sql/262`, `awcms_mfa_challenges.enrollment_origin`): `login` (the password sign-in, or the tenantless sign-in redeemed at `/auth/session/tenant`, whose selection token exists only after a password check) keeps the exemption; `switch` (`POST /auth/session/switch`, reached with a bearer session alone) re-authenticates exactly like a session - the current password, or `REAUTHENTICATION_REQUIRED` when none can be presented - and so does a grant with no recorded origin (minted before the column existed; it fails closed). Without this, a stolen session could switch into a required-MFA tenant, receive a grant and enrol with no password at all, and because the factor is principal-global pass step-up in every tenant.
4. **Replacing or adding a factor still requires the existing factor.** `enroll/start` refuses when an active factor exists (`409 MFA_ALREADY_ACTIVE`, before any state change); replacement is disable (which needs a fresh step-up) then enrol. A test pins that the factor is untouched.
5. **`enroll/verify` is hardened, because the pending secret is a guessable window** (`sql/260`). A pending factor is now: bound to the session (or login grant) that started it, by a derived hash, so another session of the same person cannot confirm it; time-limited to 10 minutes by the database clock, after which it cannot be confirmed and the next `start` replaces it; destroyed after 5 wrong codes (`429 MFA_ENROLLMENT_EXHAUSTED`, audited `mfa_enroll_verify_exhausted`) - the pending row is read `FOR UPDATE` and the cap is checked before a code is evaluated, so parallel guesses queue behind the committed count instead of all reading zero, and activation asserts the row was still pending; and rate limited like the login MFA challenge (per source and tenant at the MFA ceiling, and per session/grant at twice that, so a person who exhausts a secret can still start over). A pending factor that predates the binding column has a NULL binding and can never be confirmed. Without these, a thief holding a session AND the ability to see the setup screen could grind six-digit codes against one displayed secret for as long as it lived.
6. **The owner is told out of band.** On activation (and on disable), a `system.security_notice` email is enqueued through the existing auth-notification port to the account's own tenant-user mailbox (event, UTC time, coarsened IP). Enqueue-only; the dispatcher sends outside any transaction. Delivery depends on the tenant having the default template seeded (`bun run email:templates:seed-defaults`); when nothing was queued the audit event records `notified: false` and a warning is logged. **Limitation:** the notice goes to the mailbox of the account in the enrolling tenant. The factor is principal-global, but there is no principal-level verified mailbox, and reaching the person's other tenants would need the cross-tenant membership read this design avoids; a person who works in several tenants is notified in the one where the enrolment happened.
7. **Audit.** `mfa_enrolled` is `critical` (it is the event that flips the ADR-0141 gate), carrying `via` (`session` or `enrollment_grant`), `notified` and the hashed source. A refused re-authentication writes `mfa_enroll_reauth_failed` (`warning`). `mfa_disabled` records `notified`.

**What this does not close.** An attacker who **knows the password** presents it exactly as the owner would; no password prompt can tell them apart. That case is answered by the notice, the critical audit event and the operational guidance of section 5 (enrol holders before enabling a module with flagged permissions). The enrolment-grant path of a required-MFA tenant has the same exposure for the same reason. Rejected as disproportionate for this change: an emailed confirmation link that must be clicked before a first factor activates (turns a self-service step into a mail-dependent one and locks out tenants without delivery configured), and revoking the account's other sessions on enrolment (logs the owner out of their other devices; worth revisiting as a follow-up).

## 8. Addendum (#1035): password change verifies the CURRENT credential, and the principal is the single source of truth

**Problem.** `changeOwnPassword` checked `currentPassword` against `awcms_identities.password_hash`, a per-tenant copy. Since ADR-0086 login verifies against the principal's credential once promoted, and a password change or reset writes only the current tenant's copy plus the principal, so the other tenants' copies go stale. After Alice changed her password in tenant A, anyone holding a tenant-B session and her OLD password could "change" it in B, overwrite the principal credential and take the account in every tenant, while Alice's new password stopped working in B.

**Decision.**

1. **One verifier.** `changeOwnPassword` now calls `verifyCurrentPassword` (`current-password.ts`, introduced in section 7 for enrolment): the login rule (principal credential once promoted, else the identity hash, found by link or by address), the principal lockout checked first (`429`), and a wrong password counted toward that same lockout. Every current-password check in the repository now goes through it; `tests/identity-password-hash-readers.test.ts` fails the build if any other file selects `awcms_identities.password_hash`, so a new check cannot quietly reintroduce the stale read. (MFA disable, MFA reset and recovery-code regeneration use step-up with a second factor, not a password, so they have no current-password check to change.)
2. **Where a change writes: the principal credential, and nothing needs backfilling.** `setPrincipalCredential` already replaces the principal credential, clears its lockout and bumps `credential_epoch` in one statement. The current tenant's identity copy is still written, so the legacy fallback never keeps the old (possibly leaked) hash in the tenant where the change happened. The other tenants' copies are deliberately NOT chased:
   - Once a principal holds a credential, the login rule never consults an identity copy, and the change itself gives the principal one, so a stale copy is inert data, not an accepted password.
   - Writing them would need either DML on FORCE-RLS tables from a SECURITY DEFINER function (the sql/103 pattern) in every change, or a one-off backfill; the backfill has nothing correct to write (the copies legitimately differ for principals that were never promoted), and a function that writes other tenants' credentials from an ordinary request is a much larger privilege than the bug warranted.
   - Rejected: blanking or randomising the other copies. It would break the legacy fallback for an unpromoted principal and for an unlinked identity.
     So there is exactly one source of truth (the principal), one reader rule, and a test that keeps it that way. No migration.
3. **Sessions.** The epoch bump (finding A5) already ended every session of the person in every tenant. The other sessions in the current tenant are now revoked first, while the caller is still recognisable, so the audited count is real. The bump also stale-stamped the caller's own session, signing the person out of the tab they changed the password in, contrary to the documented intent; `restampOwnSessionAfterCredentialChange` now re-stamps that one session (one token hash, only while unrevoked, with the current epoch) so it survives, and the person's sessions elsewhere still end.
4. **Trade-off accepted.** Counting wrong passwords toward the global lockout lets someone holding only a stolen session lock the person out of signing in for the lockout window. That is the same exposure a failed login already has; it is bounded by the source rate limit, and the owner's recovery is the password-reset mail, which clears the lockout.

**Reset on an unlinked identity (fixed in the same change).** `setPrincipalCredentialForIdentity` used to resolve the principal only through the identity's `principal_id` link, so a reset of an identity that was never linked (ADR-0085's missed-writer case) wrote the identity copy and nothing else: login kept verifying the principal's old credential, no epoch moved, and the attacker's old password kept working everywhere. It now resolves the principal by link OR address, exactly as `login.ts` and `verifyCurrentPassword` do, replaces its credential, clears the lockout and bumps the epoch. It also LINKS the identity at that point (the same idempotent link `requirePrincipalIdForEnrollment` makes when such an identity enrols): without the link the identity's own sessions never join the epoch check, so the reset could not end them. Login itself does not link; it only promotes a credential. Residual: sessions of an unlinked identity in OTHER tenants are not ended by a change from here; they end when that identity is next linked or when they expire. Password change resolves the principal the same way but does not link.
