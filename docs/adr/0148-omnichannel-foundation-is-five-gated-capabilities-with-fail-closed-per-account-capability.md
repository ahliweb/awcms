# ADR-0148 — The omnichannel foundation is five separately gated capabilities, not one module; provider capability is fail-closed per account

- **Status:** Accepted
- **Date:** 2026-10-24
- **Decision maker:** ahliweb (owner, 2026-10-24: "implement the recommended option for each pending decision"; this is the maintainer approval Issue #1139 requires before implementation)
- **Resolves:** Issue #1139 (the architecture admission). It is the parent of the Phase B to D backlog listed in §10.
- **Amends:** [ADR-0133](0133-generic-delivery-capability-whatsapp-promotion.md) §5 rule 1 and [ADR-0074](0074-push-delivery-is-a-second-outbox.md) §5 (credentials), **only** as stated in §5 below. Every other rule of ADR-0133 (one queue per channel, purpose classes, consent independent of segments, no fallback) stands.
- **Extends:** [ADR-0006](0006-offline-first-sync-outbox.md), [ADR-0011](0011-capability-ports-for-cross-module-collaboration.md), [ADR-0055](0055-development-confined-to-awcms-and-awcms-astro.md) (upstream first), [ADR-0094](0094-a-data-subject-is-answered-per-tenant.md), [ADR-0122](0122-omes-control-center-domain-module-admission.md), [ADR-0134](0134-descriptor-declared-domain-event-consumers.md), [ADR-0137](0137-payout-account-encryption-at-rest-and-keyed-hashing.md) (the shared field-encryption helper), [ADR-0139](0139-cross-channel-notification-orchestration-not-admitted.md) (no facade, no fallback), [ADR-0140](0140-telegram-delivery-adapter-ops-staff-alerts-only.md) (staff Telegram stays unchanged)
- **Related:** Issues #1140 to #1162, #1167, #1168; downstream `ahliweb/awcms-one` ADR-0024, ADR-0040 and ADR-0047 (the per-tenant `legacy`/`upstream` mode router), and issues #458, #459, #460, #461, #466; the readiness pack [`docs/awcms/omnichannel-foundation.md`](../awcms/omnichannel-foundation.md) (data dictionary, provider capability matrix, threat model, test matrix, rollout), [`docs/awcms/omnichannel-ui-ux-screen-contracts.md`](../awcms/omnichannel-ui-ux-screen-contracts.md), [`docs/awcms/bun-delivery-realtime-runtime.md`](../awcms/bun-delivery-realtime-runtime.md)

**Docs and governance only.** This ADR and its pack add no module, table, migration, route, OpenAPI path, AsyncAPI channel, dependency or provider call, and nothing in them is evidence that any connector works. Acceptance means the **design is admitted**: each implementation issue still passes its own Definition of Ready and is built, reviewed and gated as a normal change.

## Context

Verified on `main` at 24 October 2026:

- `whatsapp_delivery` exists with **one** deployment-wide `WHATSAPP_PROVIDER` and **one** deployment credential; `WhatsappDeliveryPort.enqueue` has no sender selection. Meta Cloud API, Fonnte and `log` are the only registered providers; **StarSender is absent**. ADR-0133 forbids a second WhatsApp queue.
- `SocialPublishingPort` exists in `_shared/ports/`, but the `social_publishing` module does not, and `blog_content` uses a no-op adapter.
- `email` has one Mailketing v1 adapter and one deployment token; `telegram_delivery` is staff-ops only (ADR-0140); `push_delivery` is device push.
- Nothing in this repository represents "a tenant's connected external account". A website's social links are not connected accounts.
- Downstream `awcms-one` `commerce` already owns the CRM customer, consent, segments, campaigns and an inbox. This initiative must reuse them through sanctioned ports, not create a second customer authority, queue or agent runtime.

The product ask is a reusable, tenant-safe, **multi-account** foundation: many WhatsApp sender numbers (Meta Cloud API and an optional StarSender) and many accounts per social platform, without claiming that every provider supports inbox, publishing, broadcasting, leads or analytics. The risk is the usual one for integrations: one "universal channel" abstraction that promises the union of what providers offer, fails open on what they do not, and puts every tenant's tokens in one place.

## Decision

### 1. Five capabilities, not one module

| #   | Capability                           | Home                                                                                                                                                                                                                    | Why separate                                                                                                                                                |
| --- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C1  | Account and credential control plane | **New** system module `channel_accounts`                                                                                                                                                                                | It holds identities, grants, capability evidence, secret references and health. It sends nothing. Every channel needs it; none should own it.               |
| C2  | WhatsApp sender routing              | **Existing** `whatsapp_delivery`, additive                                                                                                                                                                              | ADR-0133 already decided the queue and the dispatcher live there. The change is a sender key on the one queue, not a new queue.                             |
| C3  | Social publishing                    | **The planned** `social_publishing` module behind the existing `SocialPublishingPort`; provider adapters are plug-ins inside it                                                                                         | Publishing (outbound, content-shaped, scheduled, approval-gated) shares nothing with messaging (conversational, consent-gated).                             |
| C4  | Inbound interaction boundary         | **No generic upstream conversation store.** Verified inbound is normalised by per-channel adapters into the domain-event envelope in §6. Whether a generic `interactions` module is warranted is Issue #1144's decision | An outbound port is not an inbox, and the conversation authority already exists downstream. Admitting a store before the boundary is decided duplicates it. |
| C5  | CRM bridge                           | **Downstream** `awcms-one` `commerce`, through ports                                                                                                                                                                    | Upstream holds no customer master, no segment, no campaign. It exposes accounts, senders, consent checks and redacted events.                               |

Email accounts (#1158 to #1162) and customer Telegram bots (#1155 to #1157) are **account kinds of C1 and consumers of C2/C3 rules**, each admitted by its own ADR that must conform to the invariants in §2. They are not separate foundations.

A single "omnichannel" mega-module is **rejected** (Options, below). The five homes also mean five independent rollbacks.

### 2. Invariants every implementation and every later ADR must keep

I1. **Tenant first.** Every row is tenant-scoped with RLS `FORCE` and default-deny RBAC/ABAC. A brand or business unit is a **business scope** (the ABAC attribute set is closed; no new attribute is added for it). An external account is unique per `(tenant, provider, external id)`; a second tenant claiming the same external account is refused, not merged.
I2. **Capability is fail-closed per account.** Absence of a capability row means denied. A capability is usable only when the provider matrix lists it for that provider, the account's verified grant carries it, the tenant policy enables it, and (where the provider requires it) approval evidence is recorded. Unsupported actions are refused, never degraded to another action or channel.
I3. **Secrets by reference.** Tokens, device keys and bot tokens live only in server-side envelope-encrypted storage (§5), are addressed by an opaque reference, and never reach the browser, an API response, a log, an audit row, an event, a job payload, the OMES host, or any AI or Hermes context. The reference is not a capability: resolving it needs the tenant context and the purpose.
I4. **One queue per channel; the sender is a key on it.** No queue per phone, per tenant, per provider or per domain (ADR-0133 §3). The sender is chosen explicitly or by a prospective policy, snapshotted on the row, and never rotated to escape a provider limit or a quality rating.
I5. **No silent fallback.** A refused, revoked, disconnected or unapproved sender or account fails closed. There is no automatic switch of sender, provider or channel (ADR-0133 §7, ADR-0139). An explicit reroute is a new, authorised, consent-checked request.
I6. **Official interfaces only.** OAuth and documented APIs. No scraping, no cookie or session reuse, no browser automation to bypass access approval. The single recorded exception is the optional **unofficial** StarSender WhatsApp gateway (§7), and only under its own gates.
I7. **No cross-platform identity merge.** A managed media account (the tenant's own Page or channel) is not a customer identity. A platform-scoped contact id (a page-scoped user id, a chat id) is never joined to another platform's id or to a CRM person without recorded, deterministic, consented evidence (§6). **LinkedIn Community Management member data is barred** from CRM lead creation, enrichment and audience matching (§8).
I8. **Consent is per channel, scope and purpose.** It is never inferred from segment membership, from a consent on another channel, or from the existence of an account. It is checked at enqueue **and again at dispatch** (ADR-0133 §4).
I9. **Verified inbound or deferred.** An inbound event is accepted only if its provenance is authenticated by a mechanism the provider supports (signature, secret header, challenge). A provider with no verifiable authentication is gated or deferred, not trusted by URL secrecy for content that mutates customer state.
I10. **Provider I/O outside transactions, under the pinned Bun runtime.** Durable queue to provider HTTPS, `ssrfSafeFetch`, bounded timeouts, per-account circuit breaker, no Node-only service (ADR-0002, ADR-0006, `bun-delivery-realtime-runtime.md`). A future SSE or WebSocket stream shows redacted status; it is not the send path and not a second queue.
I11. **AI is read-only by default.** No AI or agent context receives a token, a raw address or a raw message body beyond what the human-approval workflow explicitly releases; an AI-proposed action is executed only after a human decision recorded in AWCMS.
I12. **Retention and deletion are per platform and declared on day one.** Every table ships its `subjectData` and `data_lifecycle` descriptors in the migration that creates it, with platform-specific deletion and short-cache obligations honoured (a provider that limits how long its data may be cached sets the retention ceiling).
I13. **Additive and forward-only.** Migrations are new files; no applied migration is rewritten. Existing deployments with no account configured behave byte for byte as today.

### 3. Provider capability matrix

The matrix is a **versioned artefact**, `docs/awcms/omnichannel-foundation.md` §3 (v1, 24 October 2026) and a code mirror created by #1140 that a test holds equal to it. Each cell is one of `candidate` (the provider documents it; enabling needs a verified per-account grant, and approval where the provider requires one), `restricted` (a contract or policy limits it; denied unless separately authorised in writing), `not offered`, or `unverified` (treated as denied until Issue #1152 or the connector's own issue verifies it against the official documentation). A cell never becomes usable because a README says so: it needs an account-level capability row whose evidence reference points at the approval, scope list or contract that grants it.

### 4. Multi-sender semantics (C2)

`whatsapp_delivery` gains an immutable `sender_account_id` on each queue row (nullable: `null` is today's deployment sender and today's behaviour). The sender is `senderAccountId` on the port input or the default of a **prospective** policy per business scope (`default_sender_account_id`, with a configuration version; changing it affects only later messages). The provider adapter and the secret are resolved from the sender record of the authenticated tenant, **never** from a request-supplied token, phone number id or device id. Health, quota, throttle, retry and circuit breaker are per sender. Replies keep the thread's sender (the provider's customer-service window is per sender and recipient). A sender that is disabled, revoked, disconnected, unapproved or from another tenant makes enqueue return `refused: SENDER_UNAVAILABLE` and a claimed row terminal `failed`; it never falls to another sender or to the other provider.

**Owner decision recorded (2026-10-24):** a product built on the AWCMS-One template may select StarSender as the default sender per tenant or brand, with Meta Cloud API as the alternate, including the LPP ENTER deployment. This sets **no** global upstream default and is not a claim that StarSender is a Meta-authorised interface. The generic backend keeps the StarSender adapter **off by default** until an operator opts in and records a per-operator acknowledgement of the unofficial-provider risk; the default in a derived product is activated only after those gates, a verified device state and receiver consent. A provider's `success` response is "accepted", never "delivered".

### 5. Credentials: an explicit amendment of "per deployment, never per tenant"

ADR-0074 §5 and ADR-0133 §5 rule 1 keep provider credentials per **deployment** because a tenant-supplied token could let one tenant's administrator make the deployment speak as someone else. A multi-account foundation cannot keep that rule for **tenant-owned** accounts: a tenant's own WhatsApp number or Page is its own credential. The amendment is narrow:

- **Deployment-owned senders keep today's rule** (the platform's own system notices stay on the environment credential, unchanged).
- **A tenant-owned account's credential is allowed only** as an envelope-encrypted record in `channel_secrets` using `src/lib/security/field-encryption.ts` (AES-256-GCM, key id inside the value, associated data binding purpose, tenant and row, a key ring where the first key encrypts and all decrypt, fail-closed keys), written through an audited, high-risk, separately grantable, step-up-gated permission, and **usable only for that tenant's own accounts** (RLS plus the sender or account row's tenant).
- The risk ADR-0074 named is answered by ownership evidence instead of prohibition: OAuth with verified callback and state where the provider offers it (the token proves the tenant controls the account), a verified device pairing or business verification otherwise, and the recipient-facing identity being the tenant's own.
- The secret store is behind a `SecretStorePort` whose first adapter is the application-level key ring. A KMS or vault adapter replaces it without changing callers (the seam `resolveKeyRing()` already provides). This is the recommended option; an external vault is deferred because it adds an availability dependency that the offline/LAN profile cannot assume.
- **Accepted residual risk:** the dispatcher must decrypt, so a compromised worker process can reach more credentials than before (all tenants' sender credentials, bounded by the tenant context it sets, instead of one deployment credential). Mitigations are in the pack (§6): decrypt only inside the dispatch call, in memory, for the claimed row's tenant; a decrypt counter with an alert threshold; the key ring outside the database and its backups; rotation by prepending a key and a re-encrypt job (ciphertext, unlike a keyed hash, can be re-encrypted); and revocation that is effective on the next claim.

### 6. Inbound events and contact linkage (C4)

Until Issue #1144 decides otherwise, an inbound event is the following **envelope**, published as a domain event by a per-channel verified adapter: `tenant_id`, `channel_account_id`, `provider_event_id`, `provider_conversation_id`, sender and recipient as platform-scoped ids, `privacy_class`, `occurred_at`, authenticated provenance (how it was verified), `correlation_id`. Replay protection is a unique key on `(account, provider_event_id)`; gaps are reconciled by a bounded poll where the provider offers one; media is fetched through `ssrfSafeFetch` with a size and type cap. No unified-inbox projection is a source of truth, no reply is ever sent on a different channel than the one the message arrived on, and **linking a platform contact to a CRM person** requires a `contact_link_evidence` record (method, provenance, who and when) from a closed list of deterministic methods (the customer supplied the identifier on a first-party form; the customer replied to a message addressed to a number they gave). Probabilistic or cross-platform matching is not admitted.

### 7. WhatsApp and unofficial-provider rules

Marketing WhatsApp messages need recorded per-recipient, per-channel opt-in; the template and customer-service-window rules of the Meta policy in force apply; opt-out and suppression are immediate and win over everything queued (ADR-0133 §4). StarSender is documented as an **unofficial** WhatsApp gateway: its adapter is behind a flag, a per-operator risk acknowledgement and a verified webhook or a fail-closed status mode (§2 I9), with no claim of ban-free sending or reliable delivery status (Issue #1142).

### 8. LinkedIn (Issue #1150)

LinkedIn Community Management data about members is **not** usable for CRM lead creation, enrichment, audience matching, ad targeting or mass messaging; this is an invariant (I7), enforced by a negative test, not a configuration. Organisation-Page publishing and analytics are a **candidate** only after (a) the LinkedIn product approval is evidenced on the account, (b) a human has read the agreement for caching, retention and deletion obligations and recorded them, and (c) the publishing engine exists (#1145). LinkedIn Lead Sync and ads are a separate product and contract and are **no-build** until a separate written authorisation exists. A LinkedIn connector is **no-build** until gates (a) and (b) are signed off by the people named in the pack's checklist; this ADR cannot sign them.

### 9. What this ADR does not decide

The inbound conversation store (#1144), the additional platforms (#1152), the Telegram customer-messaging ADR (#1155), the Mailketing v2 and multi-account email ADR (#1158), and the realtime gateway ADR (#1168) are **separate decisions** that must conform to §2. Nothing here changes `telegram_delivery` (staff-ops only, one bot per deployment) or admits cross-channel orchestration.

### Compliance reading

- **UU PDP No. 27/2022.** Consent and purpose are per channel and recorded (I8); platform deletion and retention are declared per table (I12); managed accounts are kept apart from customer identity and cross-platform joining is barred (I7), which limits profiling; the data-protection impact assessment obligation for large-scale or systematic processing (Art. 34) must be answered by the **controller** per deployment before CRM-grade processing is enabled (a checklist item, not decided here); security safeguards (Art. 35) are the secret handling in I3 and §5; cross-border transfer (Art. 56) arises because the providers process abroad, and is the controller's disclosure to make; breach notification (Art. 46) needs the audit and decrypt telemetry in the pack.
- **PP 71/2019.** The operator keeps the system secure and reliable and can show access control, audit and availability evidence; per-account health, revocation and the audit trail serve that.
- **ISO/IEC 27001:2022 and 27002:2022.** Access control and rights (5.15, 5.18, 8.2), authentication information (5.17), supplier relationships (5.19 to 5.23: providers are suppliers, their terms are inputs), cryptography (8.24), logging (8.15), secure coding (8.28), information deletion (8.10), PII protection (5.34).
- **ISO/IEC 27005.** The risk register is in the pack (§8); the largest new risk is the broader credential reach of the dispatcher (§5), accepted with mitigations; the removed risks are the shared mega-module, cross-tenant sender forgery and automatic fallback.
- **ISO/IEC 27701.** The platform acts as processor or controller per deployment (owner decision O5, still open); the invariants above are the processor-side controls either way.
- **ISO/IEC 27034.** The invariants I1 to I13 are the application normative controls for this domain; each implementation issue states which it satisfies.

## Consequences

- **Positive:** a single account model that every channel conforms to; the unsafe parts (secrets, capability, fallback, identity merge) are decided before code exists; the ~30 waiting issues are unblocked in the order of §10.
- **Negative / trade-off:** a new module and an amendment of a published credential rule; the dispatcher's credential reach grows (§5); several platform rows stay `unverified` until their owners provide evidence; Phase A still has open ADRs for inbound, Telegram customers, email and realtime.
- **Neutral:** no behaviour changes for any deployment until an account is created, and every provider flag is off by default.
- **Human sign-off still needed (not performed here):** the controller or DPO for the DPIA and consent copy; counsel or the business owner for the StarSender risk acknowledgement text and for the LinkedIn agreement reading; the owner for provider developer-app approvals (Meta, TikTok, YouTube, LinkedIn); and the security review of #1140 before it merges.

## Alternatives rejected

- **A mega-module (A).** The facade ADR-0139 refused, with every credential in it.
- **A module per provider (C).** Five inconsistent account and consent models.
- **Downstream only (D).** Violates the upstream-first rule and removes the upstream security gates from the code that holds the tokens.
- **A tenant-supplied token in settings JSON.** The browser-visible, unencrypted, unaudited path I3 forbids.
- **An external vault now.** Right eventually; premature while the offline/LAN profile exists. The `SecretStorePort` keeps the door open.
- **Automatic sender or provider failover, number rotation, cross-platform contact matching, scraping.** Each is a policy or contract violation before it is an engineering choice.
