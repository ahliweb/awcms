# ADR-0132 — Admission of the `hr_payroll` module family (workforce, commission, payroll), phased

- **Status:** Accepted
- **Date:** 2026-10-08
- **Decision maker:** ahliweb
- **Extends:** [ADR-0011](0011-capability-ports-for-cross-module-collaboration.md) (consumers depend on a neutral port), [ADR-0034](0034-awcms-family-direct-use-templates-and-derived-pathway-removal.md) (an ERP domain module is built directly in `src/modules/`), [ADR-0063](0063-ownership-grants-run-through-the-authorization-chokepoint.md) (every handler authorizes through the chokepoint; ownership widens, never short-circuits), [ADR-0094](0094-a-data-subject-is-answered-per-tenant.md) (every table answers the data-subject question), [ADR-0126](0126-generic-multi-location-stock-ledger-module-admission.md) (append-only ledger, source identity), [ADR-0127](0127-generic-jurisdiction-neutral-tax-calculation-module.md) (effective-dated, jurisdiction-neutral rule versions), [ADR-0128](0128-generic-procurement-supplier-receiving-transfer-module-admission.md) (party reference by composite foreign key, classified identifiers, trigger-enforced state machine)
- **Related:** Issue #916 (this admission); downstream `ahliweb/awcms-one#280` (epic, Wave A item A3) and its ADR-0040 (placement only: the `hr_payroll` family is upstream first); the Booking admission (Issue #915, ADR-0131, written in parallel) which consumes the staff-availability port defined here; [`docs/awcms/hr-payroll.md`](../awcms/hr-payroll.md) (PRD-lite per phase, state machines, ERD, permissions/RLS matrix, acceptance scenarios, threat and privacy analysis, provisional events, open questions); [`docs/awcms/21_module_admission_governance.md`](../awcms/21_module_admission_governance.md)

## Context

Three requests arrive from the same direction and keep being built three different ways: _who works here and when_ (employment, attendance, shifts), _what a person earns on top of a wage_ (commission), and _what a person is paid and what is withheld_ (payroll). A booking or POS module needs the first (a staff member can only be booked when scheduled); a commerce module will feed the second; a finance reader will consume the third. Built per consumer, each copy invents its own way to be wrong in the places that hurt most: a name and a national id copied into an `employees` table that erasure and merge cannot reach; a "paid" flag that two clicks can set twice; a salary column readable by whoever can read the staff list; a tax rate written into code the month before it changes.

Per `docs/awcms/21_module_admission_governance.md` §3–4.3, `hr-payroll` is a named **ERP Domain Module** candidate: generic across industries that employ people, disableable per tenant, `type: "domain"`. What did not exist until now is the design that makes it safe to start: which identity it references, what it must never store, how the schedule is shared without sharing payroll, and which obligations gate the dangerous half.

This ADR admits the family and fixes its boundaries. It creates no module, table, route or migration; implementation is a sequence of later issues, each a normal change (migration, OpenAPI, AsyncAPI, tests, security review) behind the gates below.

## Decision

### 1. One family, three modules, admitted in phases with explicit gates

| Phase | Module key (`type: "domain"`) | Owns                                                                                                            | Depends on                                       | Implementation gate                                                                                                                               |
| ----- | ----------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1     | `hr_workforce`                | employment context, attendance events and corrections, shift templates and assignments, staff-availability port | `tenant_admin`, `profile_identity`               | this ADR + the usual per-issue DoD                                                                                                                |
| 2     | `hr_commission`               | commission rules (versioned) and the accrual ledger                                                             | `hr_workforce`                                   | phase 1 landed                                                                                                                                    |
| 3     | `hr_payroll`                  | compensation, payout accounts, periods, runs, lines, payslips, payroll rule versions                            | `hr_workforce`; `hr_commission` (soft, optional) | **owner decisions O4 and O7 answered, payout-account at-rest encryption decided, security review, legal review of any jurisdiction profile** (§7) |

Three modules rather than one, so that a tenant that only schedules staff (a salon, a clinic) enables phase 1 and has **no payroll table in its blast radius**: a disabled module's routes deny and its tables are inert. `workflow_approval` is a **soft** integration for corrections and compensation changes and fails closed (§4), exactly as ADR-0128 §9 did. The three are one admission because their identity, privacy, and SoD decisions are shared; payroll is "admitted, not yet buildable" until its gate holds.

### 2. Identity reference: a composite-foreign-key `profile_id` into `awcms_profiles`

**The legal and display identity of a person belongs to `profile_identity`; the HR modules own only what is true of the person _as an employee of this tenant_.** The employment row (`awcms_hr_employments`) carries a **`profile_id`** as a composite `(tenant_id, profile_id)` foreign key to `awcms_profiles (tenant_id, id)` — the same mechanism procurement already uses for its supplier (ADR-0128 §2; the `UNIQUE (tenant_id, id)` that `sql/174` added to `awcms_profiles` is reused, no new change to `profile_identity`'s table). The reference is **mandatory** (an employee is a person), validated by the database and by the handler (`PROFILE_NOT_FOUND`), and never accompanied by a copy: **no name, contact, address, birth date or national id is a column of any HR table.** Display reads go through `profile_identity`'s own surface (`display_name`, masked identifiers), so rename, merge and anonymisation reach every employment at once.

A **login link** is separate and optional: `tenant_user_id` (composite FK to `awcms_tenant_users`), nullable, because an employee need not have an account, and set only by a high-risk `assign`-class action (§6) because it is the basis of self-service (_this payslip is mine_). The link is **not** the identity: an account can be re-invited or replaced and the person stays the same.

`erp-extension-contracts.md` §4 and ADR-0020 name `_shared/ports/party-directory-port.ts` ("Issue #748, already exists"). **That file has never existed in this tree** (`src/modules/_shared/ports/` holds ten ports and no party one; `party_directory` survives only as a capability version string in `capability-contract-versions.ts` and as `profile_identity`'s `application/party-directory.ts`, which is an internal CRUD module, not a port). The contract document is corrected by this change to describe the mechanism that is real. ADR-0020 is a historical record and is not edited; this ADR is the correction.

Alternatives, judged on the seven criteria. Each of the first four keeps the person out of HR tables; the last four are the realistic contenders.

| -------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------------- | ------------------ | ------------------------------------------------------- | -------------------------------- | ------------------------------------------------------------------ |

Option B is not refused on principle: the day a **second** consumer needs a summary resolved in-process (not a join), a `PartyDirectoryPort` is justified and is built then with its own ADR; today the only consumer is this family, and it joins.

**Profile merge.** `profile_identity` can merge a profile into another (`merged_into_profile_id`). An employment keeps pointing at the id it was created with; reads resolve through the merge in `profile_identity`; HR never rewrites the reference. Merging two profiles that both carry **active employments** is a hazard (one person, two employment records, two payslips per period) and is recorded as an implementation-time guard: the merge is refused with a stated code while both employments are active (phase 1 PR).

### 3. Employment context and organisational scope

`awcms_hr_employments` is a stable header (profile, employee number, hire date); everything that changes over time — office, manager, job title, employment type, **status** (`active`, `on_leave`, `suspended`, `terminated`) — is an **effective-dated, append-only terms row** (`awcms_hr_employment_terms`), non-overlapping per employment. The current state is the row whose interval contains the instant; history is never edited. The organisational unit is the existing **office** (`awcms_offices`, a tree, `office` business-scope type with a real hierarchy adapter since ADR-0060): a composite FK, no second org tree. A free-text `department_label` is descriptive only and is **not** a scope. A manager is another employment (self composite FK); the chain is acyclic (checked by the handler and a bounded-depth trigger).

Deliberately **not** done: a bespoke HR org-unit hierarchy. It would need a new scope type and an extension of the hierarchy-port adapter for a benefit (departments inside one office) that no consumer has asked for. Recorded as a follow-up with its precondition (a consumer, and an adapter extension reviewed as a change to `identity_access`'s scope surface).

### 4. Attendance: append-only events, corrections by approval, evidence out of this admission

Attendance **events** (`clock_in`, `clock_out`, `break_start`, `break_end`) are append-only, carry a server `recorded_at` beside the claimed `occurred_at`, a `source` (`self`, `supervisor`, `kiosk`, `import`) and a client-supplied `client_event_key` unique per employment, so an offline kiosk or POS replaying its queue posts each event once (POS runs offline, outbox discipline). A **correction** never edits an event: it is a request (`awcms_hr_attendance_corrections`) that, once approved, appends a new event that `supersedes` the old; the effective record is the events not superseded. Approval is a `workflow_approval` instance, **required and fail-closed** (no published workflow → submit refused `409 APPROVAL_WORKFLOW_NOT_CONFIGURED`), because attendance feeds pay; the existing self-approval guard stops an employee approving their own correction.

**Geolocation, photo and device evidence is a separate privacy feature, OFF by default, and is not part of this admission** (owner decision O6 is open). Phase 1 creates **no evidence table and no evidence column**; the schema leaves nothing to switch on. Admitting any evidence requires its own ADR after O6 and a data-protection impact assessment, and would live in its own table with its own permission, consent record, and short retention.

### 5. Shifts, conflict detection, and the staff-availability port

Shift **templates** (local start time, duration, break, IANA zone) are patterns; shift **assignments** are concrete UTC intervals `[starts_at, ends_at)` with a zone snapshot, so editing a template never rewrites a past or published assignment. Assignments have `kind` (`work`, `time_off`; time off carries only a coarse kind — **never a medical reason**, which would be health data) and a status (`draft` → `published` → `cancelled`). **Conflict detection:** two non-cancelled assignments of one employment may not overlap as half-open intervals (`409 SHIFT_CONFLICT`, naming the conflicting assignment id only). The enforcement is a transaction that locks the employment row, checks overlap, and writes, with a **deferred constraint trigger as backstop**; a GiST exclusion constraint would be tighter but needs the `btree_gist` extension, which this repo's provisioning has never required, so it is an implementation-time decision for the phase 1 PR, not decided here.

**Booking reads the schedule through a port, never a table.** `StaffAvailabilityPort` (`src/modules/_shared/ports/staff-availability-port.ts`, created by the phase 1 PR; ADR-0011) takes opaque staff references and a UTC half-open window and returns **merged working intervals only**, with a fail-closed `unknown` for anything it cannot vouch for. Its result is an allow-list of three fields (`staffRef`, `status`, `intervals`): no name, no office, no template, no kind, and structurally no payroll data — the adapter's SQL touches only schedule tables, and a test asserts it never names a compensation or payroll table. The full contract is in `docs/awcms/hr-payroll.md` §5.2–5.3. It authorizes nothing and audits nothing (the composition root does, as for `InventoryLedgerPort`).

### 6. Authorization: the mechanisms that already exist, and the two additions that need admission

Everything is `defineTenantRoute` + `authorizeInTransaction` (ADR-0063), default-deny, with **separate permissions for separate powers** (a scheduler holds `shifts.*` and no `compensation.*`). The acceptance scenarios (epic §12) map to existing mechanisms — and no new ABAC attribute is invented:

- **Own data** (employee sees own attendance and payslip): `ownershipGrant`, computed server-side from the persisted `employment.tenant_user_id`, which **widens** the permission set and still lets tenant isolation, ABAC deny, business scope and SoD deny. Machine credentials are excluded by the chokepoint.
- **Supervisor sees their scope:** the `office` business scope with `requiredScopeRelations: ["exact","descendant"]`; a manager-line view ("my direct reports") is a server-computed `ownershipGrant` reason, not an attribute.
- **Roles that must not read payroll** (CRM marketer, receptionist) simply hold no `hr_*` permission; salary lives behind its own permission and its own tables, and the profile list shows a name, which every party in `profile_identity` already does.
- **ABAC closed allow-list.** `ABAC_ATTRIBUTES` has fourteen entries (`subject.tenantUserId`, `subject.identityId`, `subject.roles`, `subject.defaultOfficeId`, `resource.tenantId`, `resource.ownerTenantUserId`, `resource.businessScopeId`, `resource.status`, `resource.resourceType`, `resource.amount`, `action`, `env.now`, `env.dayOfWeek`, `env.ipTrusted`). Everything above fits it; **a new attribute (for example `resource.managerTenantUserId` or `resource.payrollGrade`) would need its own admission** and is not assumed.
- **Two `AccessAction` additions are required** and are an implementation-time change reviewed with phase 3: `calculate` and `pay` (both high-risk). `finalise`, `reverse`, `reveal`, `approve`, `release`, `backdate`, `assign` and `submit` already exist.

### 7. Commission: a versioned rule and an accrual ledger that compensates

A rule (`awcms_hr_commission_rules`) is **versioned and immutable once published**, effective-dated, and chooses from a closed set of calculations (`percent` of a base, `fixed` per unit) with an explicit rounding mode. An accrual (`awcms_hr_commission_accruals`) is posted by a downstream adapter through a port with a server-checked **source identity** `(tenant, source_type, source_ref, source_line, employment, operation)` under a unique key, so a paid order line or a completed reservation accrues **exactly once**; replay returns the original, a different amount for the same identity is `409 SOURCE_CONFLICT`. The rule version is chosen by the event's `occurred_at`, not by `now()`. Lifecycle `pending → approved → payable → paid`, with `voided` (before payable; no money moved) and `reversed` (after payable; a **new negative accrual** compensates, the original's monetary facts are never edited, only its status stamp advances — the same shape as a reversed procurement document). A trigger allows exactly those transitions. **This is employee commission, not affiliate commission** (ADR-0040 of the downstream: at most an implementation pattern): the beneficiary is always an employment. **Source-event consumers** (paid order line, completed reservation) are **downstream adapters** in the consumer's repository; this family never imports commerce or booking.

### 8. Payroll: effective-dated rule data, immutable runs, segregated duties

- **Rules are data, never constants.** Payroll rule versions follow ADR-0127's pattern: effective-dated, immutable once published, jurisdiction-neutral, drawn from a **closed set of calculation kinds** (fixed, percent with floor/cap, progressive bracket, lookup table). There is no expression engine and no `eval` (doc 21 §3 Q5). An **Indonesian profile** (PPh 21 under PMK 168/2023, the wage regulation PP 49/2025 as named by the issue, BPJS contributions and ceilings, overtime, THR) is **rule data**; **who owns that data is owner decision O4**, not decided here. Nothing in code names a rate, a ceiling or a tax category.
- **Period, run, line, payslip.** A period is `open → locked` (no unlock: a mistake is corrected by reversal). A run is `draft → calculated → approved → finalized → paid`, with `cancelled` before `finalized` and `reversed` after. Lines may be recomputed while `draft`/`calculated` and are frozen from `approved` by trigger; a finalized or paid run is **immutable by the database itself**, including from the table owner. **Correction is reversal**: a reversal run posts negating lines referencing the originals, the original is stamped `reversed`, a fresh run recalculates — never an edit. A payslip is derived and immutable, visible to its employee only after an explicit release.
- **Segregation of duties.** Calculate, approve, finalize, pay and reverse are separate permissions, and the **per-instance rule is in the database** (CHECK constraints: the approver differs from the calculator; the payer differs from both), independent of how a tenant configures roles. The default role-level matrix and its small-tenant consequences are in the pack §7.5 and are **owner decision O7**, proposed not decided.
- **Salary and bank data.** Compensation is its own effective-dated, append-only table behind `compensation.read`; changing it is propose-then-approve by a different person. Payout account numbers are classified `sensitive` rows (as ADR-0128 §2), masked everywhere, revealed only by an audited, separately permissioned, `no-store` endpoint — and **encryption at rest of the account value is a phase 3 gate**, because ADR-0128 recorded the plaintext `normalized_value` as a known gap and payroll multiplies its blast radius. NIK and NPWP are **not stored by HR at all**: they remain `profile_identity` identifiers, resolved when a run needs them.
- **Idempotency and audit.** Run create/calculate/approve/finalize/pay/reverse, period lock and compensation approval each need an `Idempotency-Key`, are replay-safe by state check and by unique key, and are audited with the correlation id (finalize/pay at `warning`, reverse and period lock at `critical`); no audit row, log line or event carries an amount, a name, an identifier or a reason text.
- **Out of scope:** general-ledger posting and any accounting, fiscal documents (SPT, bukti potong), bank-file generation and any payment-provider call (through the outbox, in a later issue), leave balances, loans, benefits.

### 9. Data protection and events

HR data is personal data about people who did not choose the tenant's software; UU PDP 27/2022 applies and the platform operator's role (controller, processor, or both, per deployment) is **owner decision O5**. Consequences taken now regardless: every table declares `subjectData` (ADR-0094) with retention under the employer's legal obligations rather than severance; attendance, corrections and shift history are bounded by a `data_lifecycle` descriptor; masking everywhere (salary, NIK, NPWP, bank account, per AGENTS.md); payslip notices by e-mail or push carry **no amount**. Provisional events `awcms.hr.attendance.recorded`, `awcms.hr.shift.assigned`, `awcms.hr.commission.accrued`, `awcms.hr.commission.approved`, `awcms.hr.payroll.finalized`, `awcms.hr.payroll.reversed` go through the domain-event outbox in the producing transaction, carry **opaque ids, kinds and counts and never an amount or a name**, and are defined only in the design pack until their phase's PR adds the AsyncAPI channels.

## Consequences

- A booking or POS consumer gets "who is working when" through one narrow port and cannot see, by construction, anything about pay. HR modules never copy the person, so erasure, merge and rename remain single-row operations in `profile_identity`.
- Phase 1 is buildable now; phase 3 is **admitted and gated**. The gate is deliberate: the owner decisions that change the shape of the data (O4 jurisdiction content, O7 duty separation) and the controls that cannot be retrofitted (at-rest encryption of payout accounts) are fixed before a payroll table exists, because a migration that has shipped is immutable.
- **Cost:** three modules, an estimated 19 tables over the three phases, two new `AccessAction` members, one new port file, and a conflict-detection path that locks rows. Payroll adds a per-run calculation whose cost is bounded by employees, not traffic.
- **Rollback** is forward-only like every migration here: stop calling a module, keep its tables (inert), disable it per tenant. Dropping them is a restore-class decision. After any restore run attendance and (phase 3) payroll reconciliations together.
- **Residual gaps stated now:** no step-up or rate limit on payout-account reveal until phase 3 decides it conditionally (an unconditional `requireStepUp` is the ADR-0058 §E trap); no manager-line ABAC attribute (the ownership-grant reason covers it); the merge guard and the `btree_gist` question are implementation-time decisions; leave management is a non-goal.
- **Downstream:** the DoR row for A3 in `ahliweb/awcms-one` can move to "admission accepted"; O1, O4, O5, O6 and O7 stay **open there** (§ below), and none of them is closed by this ADR.
- **Update (2026-10-10): owner answers recorded.** The awcms-one owner answered O4, O6 and O7; the pack records them ([`hr-payroll.md`](../awcms/hr-payroll.md) §7.3, §4.3, §7.5, §16). O4: the Indonesian profile is owned by each consumer (upstream ships only the engine and effective-dating). O6: attendance may use geolocation only, off by default per tenant, and still needs its own ADR. O7: separation of duties is configurable per tenant (default calculate ≠ approve ≠ pay; relaxable to prepare ≠ approve, audited). **O7 conflicts with this ADR's statement that the per-instance database rule cannot be configured away** (§7 and "Role-level SoD only" below). This ADR is not reversed by a note: the phase 3 gate now includes an amendment ADR reconciling the two, and until it is accepted the stricter text above governs.

## Alternatives rejected

- **One `hr_payroll` module for everything:** a salon that only schedules would carry payroll tables and permissions it never uses, and the largest-blast-radius half could not be disabled independently.
- **Copying person fields into HR tables (any of name, contact, national id):** see §2 option E.
- **Booking joins the shift tables, or a cache of them:** couples Booking to HR's schema and, one query later, to its salary tables. The port is the only door.
- **Attendance evidence as nullable columns "for later":** a column that exists is a column somebody fills in. Absent in phase 1 by construction.
- **Editing an attendance event, an accrual or a finalized run to correct it:** destroys the evidence of what was believed and paid. Correction is compensation or supersession.
- **Hard-coding the Indonesian tax tables in a constants file:** timeless constants for law that changes by year; wrong the first January after it is written. Rule versions with effective dates are the only form that can be wrong _and fixed_ without a deploy.
- **A rule expression language for payroll formulas:** an interpreter in the most sensitive module; the closed set of calculation kinds is reviewable and testable.
- **Unlocking a locked period:** the unlock is where retroactive pay changes hide. Reverse and recalculate instead.
- **Role-level SoD only:** a tenant with one super-role defeats it silently; the per-instance database checks cannot be configured away.
