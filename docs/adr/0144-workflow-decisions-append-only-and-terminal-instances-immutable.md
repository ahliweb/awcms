# ADR-0144 — Workflow decisions are append-only and terminal instances are immutable, in the database

- **Status:** Accepted
- **Date:** 2026-10-15
- **Decision maker:** @ahliweb
- **Amended:** 2026-10-15 by Issue #1032 (decision 6 and the revised Consequences): the engine-binding extension, `sql/301`.
- **Related:** Issues #999 (security audit finding F2 of #990), #1032; [ADR-0132](0132-hr-payroll-module-family-admission.md) (HR attendance corrections, #947, whose separation of duties reads these tables); `sql/252_awcms_workflow_approval_immutability.sql`; `src/modules/workflow-approval/README.md`.

## Context

`sql/013` called `awcms_workflow_decisions` "append-only / immutable" but issued no `REVOKE` and no trigger, so the claim was a convention. Code running as `awcms_app` inside a tenant could rewrite `decided_by_tenant_user_id` or `on_behalf_of_tenant_user_id` and turn a self-approved settle into a clean one, defeating the database-level separation of duties that HR attendance corrections and later payroll approvals rely on. The audit proved it against the real schema.

## Decision

1. **Decisions are append-only.** `awcms_app` loses `UPDATE`, `DELETE` and `TRUNCATE` on `awcms_workflow_decisions`; a `BEFORE UPDATE OR DELETE` trigger refuses both for any role that does hold the privilege.
2. **Instances are never deleted and a terminal instance is final.** `awcms_app` loses `DELETE`/`TRUNCATE` on `awcms_workflow_instances`; a trigger refuses `DELETE`, refuses every `UPDATE` of an `approved`/`rejected`/`cancelled` row, and, for a pending row, freezes the identity, requester, resource, pinned version and facts snapshot, and allows the cancel stamps only together with `status = 'cancelled'`. The only legal moves are the two the engine already performs: `pending -> approved|rejected` (the `end` node) and `pending -> cancelled` (recovery), each already guarded by `AND status = 'pending'`, which on a finished instance matches zero rows rather than raising.
3. **Tasks are final once final.** Separation of duties reaches an instance's decisions through `awcms_workflow_tasks.workflow_instance_id`, so a trigger freezes a task's instance, node and quorum columns and refuses any `UPDATE` of a `completed`/`skipped`/`cancelled` task. The legitimate task writes (decision completes, recovery cancels, escalation moves `escalation_step`/`escalated_at`/`due_at`) all happen on pending tasks.
4. **Declared, not assumed.** The narrowed verbs are registered in `scripts/security-readiness.ts` so `checkRuntimeRoleGrants` can tell "narrowed on purpose" from "broken".
5. **Maintenance bypass.** A superuser session may step outside the triggers with `SET LOCAL session_replication_role = replica` (tenant purge, test fixtures). The runtime role cannot.

6. **Additions are bound to the engine's records (amendment, Issue #1032, `sql/301`).** History could not be rewritten after #999, but `awcms_app` could still append a forged approval or finish an instance without one. Triggers now make those rows consistent with each other, with no change to the runtime role's verbs beyond the revoke below:
   - **Decision INSERT.** The task must be `pending` in the decision's tenant and so must its instance. An ordinary decision's `decided_by` must hold a `pending` assignment on the task, or `on_behalf_of` must be the holder of one and have an active, in-scope delegation to `decided_by` (the rule of `findEligibleAssignment`). `force_*` decisions, and only they, carry `is_administrative_override` and a reason; an override names no `on_behalf_of`, is made by an ACTIVE user of the same tenant, and never by the requester. A partial unique index allows one ordinary decision per seat, and the quorum counts distinct seats, so one approver cannot satisfy an `all` rule.
   - **Task.** Only INSERTed `pending`. `pending -> completed` only once the recorded decisions satisfy the quorum (the SQL twin of `evaluateQuorumOutcome`). `pending -> cancelled` only once the instance is no longer `pending` (the engine cancels the instance first, and cancels the siblings of an instance a rejection just finished). `skipped` is refused; the engine never writes it.
   - **Seats.** A seat is INSERTed `pending`, on a `pending` task of its own tenant (a composite foreign key `(workflow_task_id, tenant_id)` makes a cross-tenant seat impossible), for an ACTIVE user of that tenant who is not the instance requester. A seat is final once it leaves `pending`; its task, user and tenant never change; `pending -> decided` only when a decision for that seat exists on the task; `pending -> reassigned` only with the user it moved to, and (a deferred constraint trigger, because the engine inserts the replacement after the UPDATE) only if that user holds a PENDING seat on the same task and tenant by commit, as the engine's reassignment leaves them; `skipped` is refused. `DELETE`/`TRUNCATE` on tasks, seats and join arrivals are revoked from `awcms_app` and refused by a trigger for any role that is neither the table owner nor a superuser. Owner and superuser are exempt from the seat INSERT rules too; the escalation worker role, which is not granted `awcms_tenant_users`, skips only the active-user check.
   - **Instance verdict.** `pending -> approved|rejected` only when a simulation of the pinned graph, mirroring the engine, reaches an `end` node with that outcome: it starts at the start node, evaluates each `condition` against the instance's frozen facts (the SQL twin of `evaluateCondition`), crosses an `approval` node only through the completed task of THAT node and branch whose decisions pick the edge, fans out at `parallel`, and passes a `join` only once every awaited branch arrived. `approved` additionally needs no pending task and no reachable rejected end; `rejected` may leave sibling tasks pending, which the engine then cancels in the same transaction (a rejection on one parallel branch ends the instance at once). A `condition` that names a registered resolver cannot be re-run in SQL, so a path through one counts only once a completed approval follows it; a graph that auto-finishes through a resolver therefore cannot finish (fail closed).
   - **Definition and start.** Once a definition leaves `draft` its `graph` and `facts_schema` are frozen and its lifecycle only moves forward, because the simulation reads the pinned definition row. Every role other than the table owner and superusers (so a login created `IN ROLE awcms_app` too) can only INSERT a `draft` definition, and can only INSERT an instance against the `active`, live definition whose `version` it pins; retiring a definition later does not touch instances already started. **This does not stop a runtime caller from publishing a graph of its own** through `draft -> active` (an end-only graph, say) and starting an instance on it, which then approves with no decisions: the draft rule only makes that an explicit lifecycle step. See residual 3.
   - **Graph shape.** Publishing now refuses a `parallel` branch that can reach an `approved` end without passing its join: the instance cannot approve while a sibling branch's task is open, so such a graph could never be approved. A branch may leave the join only by rejecting.
     A SECURITY DEFINER status function was rejected: the runtime role could call it too, so it would still have to re-derive the same facts from the same tables.

## Consequences

- One application change, from decision 6: the graph engine cancels the pending sibling tasks of an instance that a rejection finishes. A grep of `src/` finds no `UPDATE`/`DELETE` of a decision, no `DELETE` of an instance, and no `DELETE` of a task, seat or join arrival.
- **Closed by decision 6 (#1032):** a verdict with no decisions behind it; a decision appended to a finished instance or a closed task; a decision whose `decided_by`/`on_behalf_of` is inconsistent with a pending seat and an active delegation; one approver counted twice; a pending task cancelled, skipped or erased to make a verdict look complete; a seat retired (status, no replacement or a replacement that already decided) to shrink an `all`/`quorum` rule; a seat created decided/skipped, on a closed task, for an unknown or inactive user, for the requester, or under another tenant's task; a published graph rewritten; an override recorded by a user who does not exist, is inactive, is in another tenant, or is the requester; and a `TEMP` table shadowing a guard's tables.
- **Residual, stated exactly.**
  1. **Decisions in SQL are consistent with seats, not authorized.** The database does not decide who may approve; it checks that the rows agree with each other. In particular the permission to force a decision (`workflow.recovery.force_decide`) is not checked in SQL: an override proves an active, non-requester user of the tenant made it, nothing more. That permission lives in the RBAC/ABAC engine the route runs (roles, access policies, delegated access, separation-of-duties rules), and re-implementing it in SQL would be a second engine that drifts from the first. The real controls are the route's RBAC/ABAC and binding consumers to engine-created instances (residual 3). This risk was accepted by the maintainer on 16 October 2026 (rated Low by the round-3 security audit of #1032: a compromised runtime role can already reach the same outcome through ordinary seats and decisions).
  2. **Identity.** The triggers bind rows to each other, not a row to a person. `decided_by` / `on_behalf_of` are consistent with a seat and a delegation; they are not proof that the named person acted. `awcms_app` can still seat any active non-requester user of the tenant on a pending task, and a reassignment to an already-seated user shrinks the `all` quorum exactly as the permitted administrative reassignment does. A consumer that needs identity still needs the session-bound actor recorded by the route's audit event.
  3. **A runtime caller can author its own workflow.** It can publish any graph through `draft -> active` (the draft rule is not a barrier), start an instance on it, seat active users and drive it to a verdict with no meaningful decisions. Nothing in SQL separates that from a legitimate definition. The only protection is that consumers bind to an instance the ENGINE created from a definition the tenant's administrators published: procurement does since #1045. A consumer that matches an instance by resource alone is exposed. The owner/fixture roles are exempt from the INSERT rules.
  4. **Resolver conditions** are not re-run (see above).
  5. **Known limits of the engine itself, mirrored by the simulation:** nested `parallel`/`join` never pass; and delegation lets one person fill two seats of a task (their own and the delegator's).
- Assignments and join arrivals are retired by status, never deleted (see decision 6 for what guards that).
- Tests that forged a decision or back-dated an instance now use the maintenance bypass; fixtures that only need a real verdict make the decision, complete the task and finish the instance, as the engine does.
