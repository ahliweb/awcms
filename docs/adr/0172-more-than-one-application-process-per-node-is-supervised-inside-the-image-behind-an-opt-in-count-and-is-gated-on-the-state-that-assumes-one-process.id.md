# ADR-0172 — Lebih dari satu proses aplikasi per node disupervisi di dalam image dengan jumlah opt-in, dan digerbangi oleh state yang mengandaikan satu proses

- **Status:** Diusulkan
- **Tinjauan:** memerlukan keputusan pemilik atas pertanyaan di "Pertanyaan terbuka". Hanya dokumen: tidak ada kode, migrasi, OpenAPI, atau dependensi yang ditulis sebelum ADR ini Diterima dan dipecah menjadi issue.
- **Tanggal:** 2026-11-23
- **Pengambil keputusan:** @ahliweb (diusulkan, belum diputuskan)
- **Terkait:** Issue [#1454](https://github.com/ahliweb/awcms/issues/1454) (ini sisa arsitekturalnya); PR [#1472](https://github.com/ahliweb/awcms/pull/1472) (pengukuran per view); [ADR-0161](0161-capacity-targets-are-measured-nfrs-and-the-scale-path-is-staged.md) (target 2.000 rps per node 2 vCPU, tahap S1 ke S2); [ADR-0066](0066-shared-rate-limiting-and-full-auth-surface-coverage.md) (rate limiting bersama); [ADR-0154](0154-realtime-progress-is-sse-first-on-the-existing-bun-process-reading-durable-state-websocket-not-admitted.md) (SSE di proses yang ada); [ADR-0083](0083-this-template-deploys-to-one-environment.md) (satu environment); [ADR-0033](0033-abac-dynamic-policy-evaluator.md) (evaluator ABAC; §Cache-nya asal invalidasi per proses). **Hanya dokumen dan tata kelola.** Tidak ada perubahan kode, skema, API, event, atau dependensi. Setiap angka di dokumen ini adalah pengukuran LOKAL dari satu workstation bersama (aplikasi dipatok 2 CPU, PostgreSQL `fsync=off`, tanpa CDN atau cache tepi, satu run per titik). Baca bentuknya, bukan digitnya. Pernyataan bertanda **needs verification** tidak dikonfirmasi ke dokumentasi atau kode Bun dan tidak boleh diandalkan.

## Konteks

ADR-0161 menetapkan NFR awal sekitar 2.000 rps lalu lintas dinamis origin per node 2 vCPU pada p95 < 500 ms. Issue #1454 mengukur sekitar 15% dari itu pada halaman publik tanpa cache, dan PR #1472 mengambil langkah termurah (cache agregat tag-link, 503 + `Retry-After` pada view yang ditolak). Yang ditinggalkan PR #1472 bersifat arsitektural.

1. **Satu proses melayani request pada satu thread.** Produksi menjalankan `bun ./dist/standalone-entry.mjs` (`Dockerfile.production`, `CMD`). `src/lib/server/standalone-entry.ts` membungkus handler yang dibangun `@astrojs/node` dan melayaninya dari `node:http` (`http.createServer`), satu proses, satu listener. Pada node 2 vCPU, satu thread paling banyak separuh mesin. "CPU 35 sampai 46% dari 2 CPU" di #1454 adalah satu thread yang hampir jenuh, bukan kapasitas sisa.
2. **Biaya per view adalah CPU di aplikasi, bukan round trip database.** PR #1472: sekitar 1,4 sampai 1,6 ms CPU untuk halaman ditambah 0,3 sampai 0,5 ms untuk redirect 307 locale; satu statement sekitar 12 us CPU aplikasi dan satu transaksi sekitar 45 us, sehingga round trip database hanya sekitar 12% CPU aplikasi. Pada seed kecil #1453 plafon satu thread sekitar 700 view/s pada host sepi. Menaikkan gate `interactive` dari 8 ke 64 memberi 0% 5xx tetapi p50 1 dtk pada 800 view/s dan 3,3 dtk pada 900: gate lebih besar mengantrekan beban, tidak menambah kapasitas.
3. **Aritmetika yang dipaksakan target.** Dua thread paling banyak punya 2 ms CPU per detik dinding per request pada 1.000 rps, yaitu 1,0 ms per request pada 2.000 rps dengan kedua thread 100%, sekitar 0,7 ms pada utilisasi wajar 70%. Pada 1,7 sampai 2,1 ms terukur per view tanpa cache (halaman plus 307), dua thread memberi plafon teoretis sekitar 950 sampai 1.400 view/s pada utilisasi 100%. **Proses saja tidak mencapai 2.000 rps tanpa cache.** Proses kira-kira menggandakan plafon satu thread; mencapai target juga butuh CPU per request yang lebih rendah, atau rasio hit tepi 99% (rumus ADR-0161: rps origin = rps tepi x (1 - rasio hit)).

## Opsi

### A. N proses per node, disupervisi di dalam image (`node:cluster`), jumlah opt-in

`standalone-entry.ts` mendapat primary yang mem-fork `APP_PROCESS_COUNT` worker (bawaan **1**: tanpa perubahan perilaku, tanpa supervisor), masing-masing menjalankan jalur kode hari ini pada port bersama. Primary tidak membuka pool database, tidak melayani apa pun, dan tidak menjalankan job; ia me-restart worker yang mati (dengan anggaran restart), meneruskan `SIGTERM` sebagai drain, dan tidak mengekspos apa pun yang baru. Satu container, satu port, satu health check; berjalan tanpa perubahan di bawah systemd, compose, Coolify, dan profil offline-LAN.

- Pro: tidak butuh fitur orkestrator; image sama di mana-mana; healthcheck dan alamat backend Varnish yang ada tetap sah; jumlah adalah satu-satunya knob baru.
- Kontra: kode supervisor baru di berkas paling sensitif keamanan pada jalur request; `node:cluster` di bawah Bun adalah permukaan kompatibilitas (teramati berfungsi, mekanisme needs verification, perilaku lintas upgrade Bun butuh tes regresi terpatok); crash loop worker harus dibatasi; pembagian tak seimbang mungkin terjadi (teramati 14/16 dan 23/17 pada 30 sampai 40 koneksi, belum diukur di bawah beban keep-alive).

### B. Satu replika container per vCPU di orkestrator

Tiap replika adalah proses tunggal hari ini; Traefik (atau Varnish dengan beberapa backend) menyeimbangkan.

- Pro: tanpa kode aplikasi baru; isolasi kegagalan per container; mekanisme yang sama adalah jalur scale-out S2 ADR-0161, jadi dibangun sekali.
- Kontra: **needs verification** bahwa Coolify dapat menjalankan beberapa replika aplikasi Dockerfile build-dari-repo pada satu host Docker (Swarm bukan yang digambarkan runbook); backend Varnish adalah satu IP hardcoded dan butuh director multi-backend; profil offline-LAN tidak punya orkestrator atau proxy, jadi tidak mendapat apa-apa; tiap replika menanggung overhead memori container penuh.

### C. Worker thread di dalam satu proses

- Pro: satu PID, satu listener.
- Kontra: pool `Bun.SQL`, setiap singleton tingkat modul, dan handler Astro tetap diinstansiasi per thread, sehingga ia punya semua masalah state bersama milik A ditambah nasib bersama (satu crash native mematikan semua thread), ditambah kecocokan yang belum diverifikasi dengan adapter Node Astro. Tidak membeli apa pun yang penting dibanding A dan mahal di model kegagalan. **Needs verification**, dan tidak direkomendasikan.

### D. `Bun.serve` + `reusePort` harfiah (kata-kata tiket untuk A)

Terverifikasi berfungsi untuk `Bun.serve`, tetapi aplikasi tidak memakai `Bun.serve`: ia memakai `node:http` lewat adapter Node Astro, tempat `reusePort` tidak dihormati. Mengadopsinya berarti mengganti jalur server (menerjemahkan `Request`/`Response` ke `IncomingMessage`/`ServerResponse` adapter, atau adapter lain), dan pembungkus header keamanan berkas statis di `standalone-entry.ts` dibangun di sekitar handler itu (Issue #464). Tidak direkomendasikan sekarang; tinjau ulang bila Astro punya adapter Bun first-party.

## Keputusan

Kami mengusulkan hal berikut.

1. **Adopsi A sebagai mekanisme bawaan dan pertahankan B sebagai jalur multi-node.** Di dalam satu image, `APP_PROCESS_COUNT` opt-in (bilangan bulat positif, bawaan 1, maksimum keras jumlah vCPU node) menjalankan sebanyak itu worker di belakang satu port. Lintas node atau host, B (replika di belakang balancer) tetap jalur S2 ADR-0161 dan bisa dikomposisikan dengan A (replika x proses). C dan D ditolak untuk sekarang.
2. **Bawaan tetap 1, dan supervisor bahkan tidak dimuat pada 1.** Tidak ada yang berubah untuk deployment yang tidak menyetel variabel itu, termasuk profil offline-LAN.
3. **Gerbang penghalang sebelum jumlah boleh melebihi 1 di mana pun.** Masing-masing issue sendiri dan masing-masing butuh tes yang gagal bila kontrolnya dihapus:
   1. **Koherensi cache policy ABAC (keamanan, penghalang keras).** Ganti "invalidasi per proses, tanpa TTL" dengan mekanisme kebasian terbatas yang bekerja lintas proses: TTL pendek, pemeriksaan versi murah per request, atau sinyal LISTEN/NOTIFY dengan TTL sebagai cadangan. Batas kebasian untuk policy yang dinonaktifkan atau diperketat harus dinyatakan, diuji lintas dua proses nyata, dan didokumentasikan sebagai latensi pencabutan. Ini juga memperbaiki cacat laten yang sama untuk replika hari ini (tidak khusus ADR ini; ADR ini yang memaparkannya).
   2. **Rate limiting.** `APP_INSTANCE_COUNT` didefinisikan ulang, atau variabel saudara ditambahkan, sehingga jumlah efektif adalah replika x `APP_PROCESS_COUNT`. Di atas 1, `config:validate` gagal tertutup tanpa Redis, persis seperti untuk replika (ADR-0066). Profil offline-LAN karena itu tetap 1 kecuali Redis lokal disediakan.
   3. **Anggaran koneksi.** `capacity-config.ts` dan `database:capacity:check` menghitung proses, bukan hanya replika: koneksi seluruh node = proses x `DATABASE_POOL_MAX` per jenis klien, slot interactive = proses x 8, `max_connections` PostgreSQL dan batas PgBouncer diperiksa terhadap hasil kalinya. Bawaan `DATABASE_POOL_MAX` per proses dipertimbangkan ulang, bukan diasumsikan (hari ini 20 per jenis klien).
   4. **Shutdown anggun dan anggaran restart.** Primary meneruskan `SIGTERM` sebagai drain (berhenti menerima, selesaikan yang berjalan, tutup pool, timeout keras), me-restart worker yang mati dengan anggaran restart dan back-off terbatas, dan keluar non-nol (agar healthcheck container dan orkestrator menyadarinya) bila anggaran habis.
   5. **Observabilitas.** Label proses (id worker) pada log dan pada gauge per proses, agregasi atau scrape per proses untuk metrik (verifikasi dulu apa yang dilakukan adapter aktif), dan respons health yang tidak menyembunyikan saudara yang mati.
4. **Klasifikasi state adalah bagian pekerjaan.** Issue implementasi mengklasifikasikan tiap ke-33 `Map` tingkat modul dan singleton lain (murni atau turunan, kebasian terbatas, atau butuh koordinasi) dalam tabel yang disimpan di samping supervisor, dan sebuah gerbang mencegah singleton mutable seluruh-proses baru mendarat tanpa klasifikasi (pola sama dengan registry dan gerbang yang ada).
5. **Job dan cron tidak disentuh.** Tetap container terpisah di bawah `flock` plus advisory lock PostgreSQL. Tidak ada job berjalan di proses aplikasi dan tidak boleh mulai.
6. **Tidak ada invarian yang dilonggarkan.** RLS tetap `FORCE`, ABAC tetap default-deny, otorisasi tetap di `authorizeInTransaction`, kunci tenant tetap pada setiap cache, idempotency dan audit tidak berubah. Gate work-class tetap per proses dan tidak dapat disetel lewat env (ukurannya tidak berubah di ADR ini).
7. **Bukan pengganti penurunan CPU per request.** Menurut Konteks 3, ADR ini kira-kira menggandakan plafon satu thread pada node 2 vCPU dan tidak dengan sendirinya memenuhi 2.000 rps tanpa cache ADR-0161. Porsi route matching, hop 307, dan dua transaksi per view tetap di backlog #1454, dan rasio hit tepi tetap tuas untuk halaman publik.

## Rencana pengukuran dan penerimaan sebelum ADR ini menjadi Diterima

Dijalankan pada harness #1283 (PR #1453) dengan pemakuan aplikasi, seed, dan bentuk tenant yang sama seperti laporan #1472, dengan restart aplikasi di antara run. Angka mirip-produksi menunggu environment #1281; sampai saat itu setiap angka adalah LOKAL dan indikatif.

1. **Baseline dan penskalaan.** N = 1, 2 (dan 3 pada pin 4-CPU) pada langkah beban yang sama. Catat titik bersih (p95 < 500 ms, 5xx <= 1%), CPU per proses, gauge pool dan work-class, dan jumlah koneksi di PostgreSQL (`pg_stat_activity`).
2. **Pembagian di bawah keep-alive.** Hitungan request per proses di bawah populasi klien keep-alive yang realistis, untuk membatasi ketidakseimbangan (14/16 dan 23/17 hanya teramati pada koneksi pendek).
3. **Tes koherensi lintas dua proses nyata.** Penonaktifan policy di A ditolak di B dalam batas yang dinyatakan; sesi yang dibuat di A sah di B; perubahan cache tag-link di A terlihat di B dalam TTL; rate limit bertahan lintas proses dengan Redis dan `config:validate` menolak kombinasi tanpanya.
4. **Tes kegagalan.** `kill -9` worker (restart, primary tidak jatuh), `SIGTERM` primary di bawah beban (drain, tanpa 5xx di luar batas in-flight), crash loop (anggaran habis, keluar non-nol).
5. **Memori.** RSS per proses dan total, dengan cache tag-link dan cache terduplikasi lain dalam keadaan hangat.
6. **Bukti mutasi.** Tiap gerbang di Keputusan 3 punya tes yang memerah saat kontrolnya dihapus (misalnya hapus sinyal policy lintas proses, atau hapus syarat Redis).

**Penerimaan (awal, direvisi setelah baseline pertama):** pada N = 2 dengan pin 2-CPU, titik bersih minimal 1,7x titik bersih N = 1 pada seed yang sama; ketiga tes koherensi dan tes kegagalan lulus; koneksi seluruh node tetap dalam anggaran yang disetujui yang dihitung `database:capacity:check`; latensi pencabutan efektif perubahan policy dinyatakan dan terpenuhi; `bun run check` penuh yang ada tetap hijau dengan jumlah bawaan 1.

## Konsekuensi

- **Positif:** kira-kira menggandakan plafon dinamis per node pada node 2 vCPU tanpa fitur orkestrator baru; satu mekanisme untuk Coolify, systemd, dan compose; menutup cacat otorisasi stale-allow yang ada hari ini untuk deployment multi-replika mana pun; mengubah "proses tunggal" dari asumsi tak tertulis menjadi daftar yang terklasifikasi dan digerbangi.
- **Negatif / trade-off:** kode supervisor di berkas masuk jalur request; batas dan koneksi efektif menjadi hasil kali yang harus dihitung operator (perkakas diperluas untuk itu); memori kali N; latensi pencabutan terbatas menggantikan invalidasi dalam proses yang eksak hari ini; Redis menjadi prasyarat untuk N > 1 di mana pun rate limit penting, yang menahan profil offline-LAN di 1.
- **Netral:** bawaan tidak berubah; ADR-0161 tidak diamendemen (targetnya tetap, kini dengan pernyataan jujur bahwa proses saja tidak mencapainya tanpa cache); pekerjaan cache tepi dan CPU per view berlanjut di #1454.

## Alternatif yang dipertimbangkan

- **Naikkan gate `interactive` dan ukuran pool.** Terukur, ditolak: mengantrekan beban (p50 1 dtk pada 800 view/s, 3,3 dtk pada 900) dan menghabiskan koneksi PostgreSQL tanpa hasil.
- **Tidak berbuat apa-apa dan bergantung pada cache tepi.** Tetap tuas utama untuk halaman publik (ADR-0161), tetapi lalu lintas admin dan API tidak bisa memakainya dan origin tetap butuh plafon satu node yang lebih tinggi.
- **Ganti server adapter Node Astro dengan `Bun.serve`.** Opsi D; ditunda, radius dampak lebih besar daripada yang dibutuhkan ADR ini.

## Pertanyaan terbuka untuk pemilik

1. **Q1, mekanisme.** A (supervisor di dalam image, direkomendasikan) sebagai bawaan, dengan B hanya lintas node, atau B saja?
2. **Q2, Coolify.** Dapatkah instalasi Coolify menjalankan beberapa replika aplikasi build-dari-repo pada satu host Docker, dan apakah pemilik menerima director Varnish multi-backend? (Menentukan seberapa menarik B sendirian.)
3. **Q3, latensi pencabutan policy.** Batas berapa yang dapat diterima agar penonaktifan atau pengetatan policy ABAC berlaku di setiap proses (misalnya 2 dtk, 5 dtk, 30 dtk), dan apakah pemeriksaan versi per request (eksak, satu query murah) lebih disukai daripada TTL?
4. **Q4, profil offline-LAN.** Konfirmasi ia tetap satu proses kecuali Redis lokal disediakan (gagal tertutup), bukan membolehkan N > 1 dengan rate limit per proses.
5. **Q5, target.** Pertahankan "2.000 rps tanpa cache per node 2 vCPU" di ADR-0161, atau nyatakan ulang sebagai rps origin pada rasio hit yang dinyatakan karena proses saja tidak mencapainya tanpa cache?
6. **Q6, Bun-only.** `node:cluster` bagian dari permukaan kompatibilitas Node milik runtime Bun dan tidak menambah dependensi atau Node.js; konfirmasi tidak ada pengecualian tertulis yang dibutuhkan (AGENTS.md aturan 11).
7. **Q7, jumlah bawaan.** Haruskah nilai produksi yang direkomendasikan adalah jumlah vCPU setelah gerbang lulus, atau tetap 1 sampai baseline mirip-produksi (#1281) ada?
