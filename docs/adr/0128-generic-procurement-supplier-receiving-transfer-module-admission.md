# ADR-0128 — Admission of the generic procurement module (`procurement`: suppliers, receiving, transfers)

- **Status:** Accepted
- **Date:** 2026-10-05
- **Decision maker:** ahliweb
- **Extends:** [ADR-0011](0011-capability-ports-for-cross-module-collaboration.md) (consumers depend on a neutral port), [ADR-0034](0034-awcms-family-direct-use-templates-and-derived-pathway-removal.md) (an ERP domain module is built directly in `src/modules/`), [ADR-0063](0063-ownership-grants-run-through-the-authorization-chokepoint.md) (every handler authorizes through the chokepoint), [ADR-0094](0094-a-data-subject-is-answered-per-tenant.md) (every table answers the data-subject question), [ADR-0126](0126-generic-multi-location-stock-ledger-module-admission.md) (the ledger this module posts through)
- **Related:** Issue #888 (this module); downstream `ahliweb/awcms-one#283`; [`docs/awcms/procurement.md`](../awcms/procurement.md) (PRD-lite, state machine, ERD, permissions/RLS matrix, ledger contract, reconciliation, rollback); `sql/174_awcms_procurement_schema.sql`; `sql/175_awcms_procurement_permissions.sql`; `src/modules/procurement/`

## Context

A domain module that buys or moves goods needs three things the inventory ledger (ADR-0126) deliberately does not have: a **counterparty** (who supplied it, with the tax and payment details that go with a vendor), a **document** a person can raise, review, approve and correct (a receipt, a return to the supplier, a requisition, a transfer between locations), and a **lifecycle** that makes the moment stock changes unambiguous. Without one shared module every consumer builds its own, and each builds a different way to make the stock number wrong: a receipt that edits a balance directly, a "finalise" button that posts twice when clicked twice, a supplier row that carries a tax number in clear text into a log.

Per `docs/awcms/21_module_admission_governance.md` §3 this is an **ERP Domain Module** (§4.3): generic across industries that buy goods, disableable per tenant, `type: "domain"`. It knows nothing about products, prices, purchase orders or accounts payable.

## Decision

### 1. One module, `procurement`, a document layer over the ledger

`src/modules/procurement/`, key `procurement`, registered after `inventory` (it depends on it). It owns suppliers and procurement documents. It owns **no stock**: there is no write to any `awcms_inventory_*` table in this module, and every stock effect goes through `InventoryLedgerPort` (ADR-0011/0126). The port gained two members for it — `postSupplierReturn` and `postTransfer` (a balanced out/in pair, ADR-0126 §6) — and its adapter delegates to the same `postMovement`/`postTransfer` the inventory HTTP surface uses, so there is still exactly one posting path.

### 2. Where supplier identity is owned

**The legal and display identity of a party belongs to `profile_identity`; this module owns only what is true of the party _as a supplier of this tenant_.** A supplier row (`awcms_procurement_suppliers`) carries the vendor code, status (`active`/`blocked`/`inactive`), a trading name for documents, categories and tags, and an **optional** `profile_id` — a composite `(tenant_id, id)` reference to `awcms_profiles`, so a tenant that never adopted the party registry still has suppliers, and renaming or anonymising the party never rewrites a supplier. The reference is validated by the database (a composite foreign key, backed by a `UNIQUE (tenant_id, id)` that `sql/174` adds to `awcms_profiles`: no data changes, no index dropped) and by the handler (`PROFILE_NOT_FOUND`), and a second supplier for the same party in one tenant is allowed because one party can supply under more than one vendor code. Copying the party's name, address or national identifiers into this table was rejected: it would be a second source of truth that `profile_identity`'s erasure and merge could not reach.

**Tax, business, payment and contact identifiers are not columns of the supplier.** They are rows of `awcms_procurement_supplier_identifiers` with a mandatory classification: `tax_id` and `business_id` are `sensitive` (a CHECK, not a convention), `payment_ref` and `contact_ref` default to `sensitive` and may be `confidential`. The row stores a normalised value, an **unkeyed SHA-256 hash** (`hashIdentifierValue`, shared with `profile_identity` and deliberately not changed here; it lets a duplicate be recognised by an equality lookup; the add is **idempotent** — a duplicate returns the same uniform `201` acknowledgement (type, label, masked value, classification; no id, no timestamp) as a fresh add, never a `409`, so a caller with `suppliers.update` but not `suppliers.reveal` cannot use it as a value-equality oracle) and a **mask** produced by the same `profile_identity` masking functions every other identifier here uses. **`normalized_value` is stored in plaintext, protected by RLS, role privileges and the redaction rules — not by encryption at rest**, and an unkeyed hash of a low-entropy identifier (a tax id) can be brute-forced by anyone who can read the table, which is why the column is in `redactedColumns` and never exported. **No response, log line, audit row or event ever carries the value, its hash or its mask-derived text except the mask itself in a read of that supplier.** Keyed hashing and at-rest encryption are recorded as follow-ups (below). The only way to read a value in clear is `POST …/identifiers/{id}/reveal`: its own permission (`suppliers.reveal`, a new HIGH-RISK `AccessAction`), `Cache-Control: no-store`, and an audit row at `warning` that records that a disclosure happened and to whom, never what. `suppliers.read` alone sees masks only. A soft-deleted supplier is visible to a list only with `includeDeleted=true` **and** `suppliers.restore` (the power that needs to see a deleted row), checked through the same chokepoint, so `suppliers.read` cannot enumerate them.

### 3. The receiving document

One table, `awcms_procurement_documents`, for four **modes**: `receive` (stock arrives from a supplier), `supplier_return` (stock leaves to a supplier), `requisition` (stock is pulled from another location) and `transfer` (stock is sent to another location). The mode decides the shape and the database checks it: the two supplier modes need a supplier and one location; the two location modes need two **different** locations and no supplier. A document carries an optional external reference (unique per supplier and mode among non-cancelled documents, by a partial unique index, `409 DUPLICATE_EXTERNAL_REFERENCE`; cancelling frees it), a document date, notes, an actor trail and up to 500 lines. The mode of a document cannot change after creation (`MODE_IMMUTABLE`).

**Line snapshots.** A line stores the item reference the ledger will use, plus the SKU, name, unit of measure and exact-decimal unit cost **as they were on the document**. A later catalogue rename or price change does not rewrite what a receipt meant. Costs are decimal strings, never floats; totals are computed by the database in exact `numeric`, and a client can never assert a state, total, snapshot or balance (a body naming one is a `400` that names the field).

### 4. The state machine is in the database

```
draft ──submit──> submitted ──finalise──> finalised ──reverse──> reversed
  │                   │
  └────cancel─────────┴───────cancel────> cancelled
```

A `BEFORE UPDATE` trigger allows exactly those transitions and, for each, only the columns that transition may change, so a finalised document is immutable **by the database itself**: not editable by a future code path, a maintenance session or a bug, and not "un-finalisable". `cancelled` and `reversed` are terminal. Lines are writable only while the parent is a draft (a trigger that checks every document a write touches, so a line cannot be moved out of a finalised document into a draft), and a submitted document's header is frozen. Nothing is deleted: `awcms_app` holds no `DELETE` and a trigger rejects it for any role. A mistake is corrected by cancelling a draft or submitted document (no stock moved) or by reversing a finalised one (compensating movements). The lifecycle events are an append-only log (§8) in which a document reaches each of `finalised`, `cancelled` and `reversed` at most once, by a unique index.

### 5. Finalising posts through the ledger, all lines or none, idempotently

`POST …/documents/{id}/finalise` locks the document `FOR UPDATE`, re-checks its state, then posts every line through the port inside **one savepoint**. A ledger refusal on line 3 (`INSUFFICIENT_STOCK`, an inactive location, `UNIT_MISMATCH`, `QUANTITY_OUT_OF_RANGE`) is _returned_ by the port, and a handler that returns a 4xx would COMMIT whatever lines 1–2 had already written; so the refusal is converted to a throw inside the savepoint (which rolls lines 1–2 back) and back to a value outside it. The response is the refusal; the document stays `submitted`; nothing was posted.

- **Source identity.** Each movement is posted under a server-owned identity `(procurement_receipt | procurement_supplier_return | procurement_requisition | procurement_transfer, document id, line no, operation)`; a client never supplies it, so it cannot squat another document's identity. A reversal has **distinct** reversal source types (`…_reversal`) so a compensation replays independently of the original.
- **Replay.** Finalising a document that is already `finalised` returns it (`replayed: true`) and posts nothing: with the same `Idempotency-Key`, a different one, or none. Underneath, the ledger itself de-duplicates on the source identity. Concurrent finalises of one document queue on the row lock and take the replay path. The `Idempotency-Key` header is **also** required (it deduplicates a retried HTTP request, the state check deduplicates the business action, the ledger identity deduplicates the movement — three independent layers), and the same key used against a different document is `409 IDEMPOTENCY_CONFLICT`, not a replay. The acting tenant user is part of the request hash, so a second user presenting the first user's key gets `409 IDEMPOTENCY_CONFLICT` rather than the first user's stored response (the idempotency record is otherwise shared across the tenant; inventory does not bind the actor yet — a follow-up for it).
- **A requisition and a transfer** are one ledger transfer per line, a balanced out/in pair that the ledger's deferred constraint trigger independently refuses to commit unless balanced (ADR-0126 §6). A transfer refused for insufficient stock posts neither leg.
- **Deadlock avoidance.** Lines post in `(item_type, item_ref, line_no)` order, compared byte-wise (never `localeCompare`), so two documents touching overlapping items reach the ledger's balance rows in the same global order: a balance row is `(location, item)`, a document's location (or transfer pair) is the same for all its lines, and the ledger itself locks a transfer's two rows in `locationId` order in either direction. Concurrent documents with the same item at different locations in opposite line order, and opposing transfers, do not deadlock (tested).
- **Links.** Each posted movement is linked to its document line in `awcms_procurement_document_movements` (append-only; a composite FK makes "a link to another tenant's movement" unrepresentable). This is what makes the document detail show its stock effect and what reconciliation compares.

### 6. Reversal is compensation

Only a `finalised` document can be reversed, once. Reversal posts compensating movements through the same port under the reversal identity (a receipt becomes a supplier return, a supplier return becomes a receipt, a transfer goes back the other way), links them, and stamps the document `reversed`. **The original movements are never touched** — the ledger is append-only. A reversal the ledger refuses (the received stock has since been sold and the policy forbids negative stock) posts nothing and leaves the document `finalised`: the honest answer is a `409`, not a forced negative balance. Reversing a draft or submitted document is refused; those are cancelled.

### 7. Retention: none, and it says so

Documents, lines, links and events are the evidence behind ledger movements and the database refuses to delete them, so nothing purges them. Each of the eight tables is registered with `data_lifecycle` as `delegated` with a stated reason (`none — retained for the life of the tenant`), exactly as ADR-0126 §7 did, rather than argued into `BOUNDED_BY_DESIGN`. Volume is bounded by documents authored by people (at most four event rows per document), not by traffic. After a restore, run the procurement **and** inventory reconciliations: documents and ledger must come back from the same point in time.

Personal data (ADR-0094): a person appears as the tenant user who created or actioned a document (`retain_under_obligation` or `severed_with_subject_row`, per table), and the trading name of a sole-proprietor supplier is retained under the purchase-record obligation **retained as is**. Nothing in this module nulls `profile_id` on anonymisation: the link remains and resolves to a profile whose identity `profile_identity` has anonymised, while the trading name on the supplier row and the document snapshots is not erased — the retention basis is the financial_tax obligation, not severance. The identifier table's `normalized_value`, `value_hash` and `masked_value` are `redactedColumns`: they never ride out in an export.

### 8. Reconciliation and reporting

`GET …/documents/reconciliation` is read-only and proves, per finalised or reversed document line, that the ledger holds exactly the movements the document says it posted: a missing link, an unlinked movement posted under a procurement identity from outside this module, a quantity or location that disagrees — each is a listed discrepancy, scoped to the tenant. It repairs nothing; the ledger's own rebuild repairs balances, and a document is never edited to match.

Two projections ride the existing `reporting` engine as **monotonic counters** over the append-only `awcms_procurement_document_events` log: `procurement.receiving` (receipts, supplier returns, requisitions and transfers finalised; documents reversed and cancelled) and `procurement.suppliers` (supplier-bound documents finalised, reversed, cancelled; a location-only document is never counted as supplier activity). `kind_mode` and `supplier_event_kind` are **generated columns**, so each metric is one `matchColumn` equality (the engine cannot express a conjunction) and cannot disagree with its inputs. Every metric is a counter because each document reaches each state at most once; there is no decrement to lose, so a rebuild reproduces the same figures. `awcms_worker` is granted `SELECT` on the events table (the worker reads the projection source as that role), and `tests/reporting-projection-worker-grants.test.ts` asks the question for every projection. The detail — which documents, which cost, per supplier — is the live, re-authorized `GET …/reports/receiving` and `…/reports/suppliers`; the projection is only the dashboard figure.

### 9. Optional approval through `workflow_approval`, soft and fail-closed

`awcms_procurement_settings.approval_threshold` (`NULL` = off, the default) names a total cost at or above which a document cannot be finalised until the `procurement.document_approval` workflow has approved it. **The threshold is cost-based and covers `receive` and `supplier_return` only** — the two modes that carry a supplier and a `unitCost` on every line (`unitCost` is therefore required on a supplier return too: a return with no cost would sum to zero and skip approval). **`requisition` and `transfer` are not cost-gated**: they carry no cost and move stock between a tenant's own locations; a tenant that needs a second pair of eyes on them has no gate today. Mode- or quantity-based gating is a recorded follow-up. Submit starts the instance; finalise is refused with `409 APPROVAL_PENDING` or `APPROVAL_REJECTED` until the verdict. The integration is **soft**: `workflow_approval` is _not_ in `dependencies` (a tenant that never approves anything need not enable it), and when a threshold is set but no workflow is published or the module is disabled, submit **fails closed** (`409 APPROVAL_WORKFLOW_NOT_CONFIGURED`) rather than letting an over-threshold document through. A rejection is final for the document (cancel it instead); cancelling withdraws a pending request. Changing the threshold is `policy.configure`, high-impact, `Idempotency-Key`, audited at `warning`: it decides which documents move stock without a second pair of eyes.

### 10. API-first; admin screens are a recorded follow-up

> **Superseded in part (Issue #905).** The "API-first / no `navigation` / `experimental`" state below was the state at admission only: `/admin/procurement` (suppliers, documents, policy, reports, reconciliation) landed in #905 together with its `navigation` entry, and the module is now `active`. Sixteen of the seventeen permissions left `NOT_YET_SCREENED`; only `documents.update` (draft edit in place) remains. The text below is kept as the record of the original decision.

Sixteen route files, no admin screen and **no `navigation` entry** (the navigation registry requires a real page and this PR adds none). The module is registered `experimental`, exactly as `inventory` (ADR-0126 §9) and `push_delivery` (ADR-0074) were for the same reason: ADR-0021 criterion 1 holds every `active` module to having a screen, and flipping the status belongs in the PR that lands the first one. The seventeen permissions are recorded in `NOT_YET_SCREENED` in `scripts/admin-screen-coverage-ledger.ts`, the ledger's own mechanism for "declared, enforced, not yet screened". **Follow-up:** admin screens for procurement — suppliers (with masked identifiers and the reveal flow), documents with line editing, finalise/reverse with the reason panel, reconciliation, the approval threshold.

### 11. Security, events and audit

- **Authorization:** every handler is a `defineTenantRoute` and authorizes through `authorizeInTransaction` (ADR-0063); default-deny. Seventeen permissions seeded by `sql/175`, granted to **no** role by the migration (existing tenants use `identity-access:permissions:backfill`). Three new `AccessAction` members: `submit` (not high-risk: it moves no stock and cancel undoes it) and the HIGH-RISK `finalise` and `reveal`; the compensating-movement action reuses `reverse`, which the tax module (ADR-0127) already added as high-risk. High-risk makes the action-time SoD check available the moment a tenant authors a maker/checker rule over them. Each high-risk guard is tested both ways: every other permission cannot do it, only that one can.
- **Tenancy:** every table has `tenant_id`, `ENABLE`+`FORCE` RLS with `USING` and `WITH CHECK`, and every reference — including those across modules (supplier, document, ledger location, ledger movement, profile) — is a composite `(tenant_id, id)` FK, so RLS is not the only wall between a document and another tenant's supplier or location.
- **Audit:** every supplier, identifier, document and policy mutation is audited with the correlation id; finalise at `warning`, reverse at `critical`, reveal at `warning`; a replay audits nothing; no audit row carries a note, a value, a hash or a name.
- **Events:** `awcms.procurement.document.finalised` and `awcms.procurement.document.reversed` go through the domain-event outbox **in the same transaction**; a refused or replayed finalise publishes nothing. Payloads are opaque ids and decimal strings. AsyncAPI channels added.
- **No provider call inside a transaction.** Nothing here calls out of the process; any later integration (a payment gateway, a supplier portal) goes through the outbox.

## Consequences

- A consumer raises a document, submits, finalises: stock changes once, through the ledger, and the document says so. Consumers stop writing receipt stock themselves; two writers is two sources of truth and reconciliation will say so.
- **Rollback** is forward-only like every migration here: stop calling the module, keep the tables (they are inert), and the ledger remains valid on its own. Dropping the tables is a restore-class decision, not a `down` migration.
- **Cost:** 8 tables, 17 permissions, 3 new `AccessAction` members, 16 routes, two new port members, and a posting path that locks rows.
- **Security-audit disposition (this PR):** the identifier add is idempotent (M1); the identifier list/reveal/remove apply the same soft-deleted-supplier rule as `getSupplier` (L1); the supplier row is read `FOR SHARE` on every document write path so a concurrent supplier delete cannot interleave (L2); `payment_ref`/`contact_ref`/`other` values shorter than 8 characters are masked entirely, no tail (L3); the database refuses `finalised`/`reversed` with an approval status other than `not_required`/`approved`, allows only `pending → approved|rejected` between submitted states, and holds `approval_instance_id` fixed after submit (M4); `finalised_by` is a NOT NULL fact beside `finalised_at`, `reversed_by` and `reverse_reason` beside `reversed_at`, and a reversed document frees its external reference so the same delivery can be received again (L7); the supplier report keeps soft-deleted suppliers with a `deleted` flag so it reconciles with the receiving report (L6).
- **Residual gaps, stated explicitly:** (M4) the database cannot verify at `draft → submitted` that an `approved` approval status came from a genuine workflow decision — it trusts the application there, and enforces only the later one-way rules; (M2) **no sibling reveal mechanism exists to mirror** — `profile_identity` exposes no clear-text reveal endpoint, and no other reveal carries step-up or a rate limit — so `suppliers.reveal` is audited and `no-store` but NOT step-up-gated or rate-limited (an unconditional `requireStepUp` is the ADR-0058 §E trap and was not invented here); (M3) **the approval threshold is cost-based**: a document whose total cost is zero or omitted, and every requisition and transfer (which carry no cost), bypasses it; (L5) there is **no location-scoped ABAC and no default maker/checker** — separating `documents.submit` from `documents.finalise` is an operator duty, expressed as a SoD rule over those two high-risk actions.
- **Follow-ups recorded by the security audit of this module (not done here):** (1) **step-up and a rate limit on reveal** — `suppliers.reveal` is audited and `no-store` but a holder can enumerate identifiers at API speed; (2) **a stricter permission for payment and contact references** than for tax/business ids, and **soft-delete of identifiers** (removal is a hard `DELETE`, audited); (3) **keyed hashing and at-rest encryption** of `normalized_value` (needs a key-management decision shared with `profile_identity`, so not changed here); (4) **mode- or quantity-based approval gating** for requisitions and transfers; (5) binding the idempotency record to the actor in `inventory` as well.
- **Deferred, not forgotten:** purchase orders and goods-receipt against an order (the document has an external reference where a consumer can store its order number); partial receipts of one document (a short delivery is a document for what arrived); costing and valuation; **a full accounts-payable ledger (a non-goal)**; supplier portals; archive-then-purge; admin screens.

## Alternatives rejected

- **Supplier identity columns on the supplier (name, address, tax number):** a second source of truth that `profile_identity`'s erasure and merge could not reach, and a plaintext sensitive value in a table every supplier query reads.
- **Identifiers as a jsonb column on the supplier:** cannot be classified, deduplicated by hash, masked per row, or constrained (`tax_id` must be `sensitive`) by the database.
- **A state machine only in the handler:** a second code path, a maintenance session or a bug could then edit a finalised document. The trigger makes immutability a property of the data.
- **Writing balances from procurement (a "fast path"):** two writers on one balance; the whole point of ADR-0126 §1 is one posting function.
- **Posting line by line and compensating a partial failure:** a handler that returns a 4xx commits what it wrote. All lines or none, in one savepoint.
- **Idempotency by header alone:** a retry with a fresh key would post twice; the state check and the ledger identity make the business action idempotent regardless of the key.
- **A hard dependency on `workflow_approval`:** forces every tenant to enable a module most will never need; soft integration that fails closed gives the same safety.
